# Data Backends in tif1

tif1 supports two DataFrame libraries: **pandas** (default) and **polars** (installed with tif1, selected with `lib="polars"`). This design balances familiarity, ecosystem compatibility, and raw performance for each use case.

The backend system is integrated into the tif1 core architecture. When tif1 loads session data, telemetry, or lap data, it constructs DataFrames with the selected backend. All subsequent operations then use that backend. A backend switch needs few code changes, but the column types differ (see [Data Contract by Backend](#data-contract-by-backend)).

## Why Multiple Backends?

The Formula 1 data analysis landscape presents unique challenges:

- **Volume**: A race session has more than 1,000 laps (1,128 for the 2025 Bahrain Grand Prix race). One lap of telemetry holds 700-800 samples of 23 columns, so the telemetry of a race holds millions of values.
- **Variety**: Different analysis tasks have different requirements. Exploratory analysis benefits from the pandas ecosystem, while large pipelines can use the polars query engine.
- **Compatibility**: Many existing tools and libraries in the Python ecosystem expect pandas DataFrames

By supporting both backends, tif1 allows optimization for specific constraints without loss of functionality.

The backend abstraction layer in tif1 handles the complexity of supporting multiple DataFrame libraries. `get_session()` loads no data. When code reads session attributes such as `.laps` or `.weather`, tif1 runs these steps internally.

1. **Fetches data** from the CDN or cache (backend-agnostic)
2. **Parses JSON** using orjson (backend-agnostic)
3. **Constructs DataFrames** using the specified backend
4. **Applies transformations** (column renaming, type casting) using backend-specific code
5. **Returns typed objects** with the appropriate DataFrame type

This architecture applies backend-specific optimizations at the lowest level and keeps the high-level API consistent.

## Pandas Backend (Default)

Pandas is the default backend in tif1 and provides maximum compatibility with the Python data science ecosystem. Pandas has been the de facto standard for tabular data in Python since 2008. Its ecosystem of tools, libraries, and community knowledge is large.

### Architecture and Design

Pandas is built on top of NumPy arrays and provides a rich, high-level API for data manipulation. Key architectural characteristics:

- **Index-based operations**: Every DataFrame has an index (row labels) that enables powerful alignment and joining
- **Single-threaded execution**: Operations run on a single CPU core, making behavior predictable but potentially slower
- **Eager evaluation**: Operations execute immediately when called
- **Object dtype flexibility**: Can store mixed types in a single column (though this impacts performance)
- **NaN for missing data**: Uses NumPy's NaN for numeric missing values, None for objects

### When to Use Pandas

Pandas is the right choice when:

- **Learning tif1**: The pandas API is more forgiving and has extensive documentation.
- **Ecosystem compatibility**: Libraries like matplotlib, seaborn, scikit-learn, and statsmodels expect pandas DataFrames.
- **tif1 charts**: The `tif1.charts` functions accept `lib="pandas"` and `lib="polars"` and draw the same figure. In both cases, the chart loads the session with the pandas backend, because matplotlib and seaborn use pandas frames. Both backends share the same payload cache. Other `lib` values raise `ValueError`.
- **Exploratory analysis**: The pandas API and Jupyter integration suit interactive work.
- **Small to medium datasets**: For datasets under 1 million rows, pandas performance is typically sufficient.
- **The complete pandas API**: Some advanced pandas features (MultiIndex, time series resampling, etc.) are not available in polars.
- **Integration with existing code**: When a codebase already uses pandas, staying consistent reduces friction.
- **Stability**: Pandas has a stable API with strong backward compatibility guarantees.

### Performance Characteristics

Pandas performance varies significantly by operation type:

- **Fast operations**: Vectorized numeric operations, boolean indexing, simple aggregations
- **Moderate operations**: String operations, groupby with multiple aggregations, merges
- **Slow operations**: Apply with Python functions, iteration, complex string parsing

Typical tif1 workloads include filtering laps, computing statistics, and grouping by driver. On the laps of one race (about 1,100 rows), each of these operations takes about 1 ms on pandas.

### Example Usage

```python
import tif1

# Pandas is the default - no need to specify
session = tif1.get_session(2025, "Monaco Grand Prix", "Race")
laps = session.laps  # Returns pandas DataFrame

# Standard pandas operations work. LapTime is timedelta64; LapTimeSeconds is float
fastest = laps.nsmallest(5, "LapTime")
by_driver = laps.groupby("Driver")["LapTime"].mean()

# Rich pandas API available
verstappen = laps[laps["Driver"] == "VER"]
verstappen_stats = verstappen["LapTime"].describe()

# Pandas indexing and selection
lap_15 = laps[laps["LapNumber"] == 15]
columns_of_interest = laps[["Driver", "LapTime", "Compound", "TyreLife"]]

# Time arithmetic: LapTime is a timedelta (LapTimeSeconds already holds float seconds)
laps["LapTime_seconds"] = laps["LapTime"].dt.total_seconds()

# Chaining operations
result = (
    laps
    .query("Compound == 'SOFT'")
    .groupby("Driver")
    .agg({"LapTime": ["mean", "std", "count"]})
    .sort_values(("LapTime", "mean"))
)
```

### Pandas-Specific Features in tif1

When using the pandas backend, tif1 provides additional functionality:

- **Categorical dtypes**: Driver names and compounds are stored as categoricals for memory efficiency
- **Timedelta columns**: Lap times are proper timedelta objects, enabling time arithmetic
- **Index**: laps keep a `RangeIndex` plus the FastF1 `index` column
- **Method chaining**: All tif1 DataFrame operations support pandas method chaining

## Polars Backend (High-Performance)

Polars is a fast DataFrame library written in Rust and designed for performance and memory efficiency. It incorporates lessons learned from pandas and uses modern hardware capabilities.

### Architecture and Design

Polars is built on Apache Arrow and uses a fundamentally different execution model:

- **Multi-threaded execution**: Automatically parallelizes operations across all CPU cores
- **Apache Arrow memory format**: Columnar, cache-friendly layout with zero-copy operations
- **Query optimization**: Analyzes and optimizes query plans before execution (in lazy mode)
- **SIMD vectorization**: Uses CPU SIMD instructions
- **Proper null handling**: Native null support without NaN confusion
- **Rust implementation**: Memory-safe, no GIL limitations, predictable performance

### When to Use Polars

Polars is the right choice when:

- **Large datasets**: Parallel execution helps most on large tables, such as the telemetry of many sessions.
- **Data pipelines**: Lazy evaluation enables query optimization.
- **Memory is constrained**: tif1 polars frames use about 25% less memory for laps and 40% less for telemetry.
- **Heavy aggregations**: Groupby operations run in parallel on all CPU cores.
- **A different API**: The polars API is more explicit but requires learning.

### Performance Characteristics

Polars gives the largest gains on large tables, in these areas:

- Groupby aggregations, joins, sorting, and filters
- String operations, window functions, and complex expressions

The tables of one session are small (about 1,100 laps, or 700-800 telemetry samples per lap). At that size, the two backends take about the same time. See [Detailed Performance Comparison](#detailed-performance-comparison) for measured values.

### Installation

Polars (`polars>=2.0.0,<3`) is installed with `tif1`. If it is missing, for example after a manual uninstall, reinstall it alongside tif1:

```bash
# A normal install already includes polars
pip install tif1

# Restore polars if it was removed from the environment
pip install "polars>=2.0.0,<3"

# Verify installation
python -c "import polars as pl; print(pl.__version__)"
```

<Note>
  `tif1` requires Python 3.11 or later (3.11 through 3.15 are tested in CI), which satisfies the Polars requirement. The library is distributed as pre-built wheels for all major platforms (Linux, macOS, Windows) and architectures (x86_64, ARM64).
</Note>

### Example Usage

```python
import tif1
import polars as pl

# Explicitly specify polars backend
session = tif1.get_session(
    2025,
    "Monaco Grand Prix",
    "Race",
    lib="polars"
)
laps = session.laps  # PolarsLaps, a polars DataFrame (LapTime is a Duration)

# Polars operations (similar but more explicit than pandas)
fastest = laps.sort("LapTime").head(5)
by_driver = laps.group_by("Driver").agg(pl.col("LapTime").mean())

# Polars expression API (powerful and composable). polars has no std() for
# a Duration, so the spread uses the float LapTimeSeconds column
verstappen = laps.filter(pl.col("Driver") == "VER")
verstappen_stats = verstappen.select([
    pl.col("LapTime").mean().alias("avg_time"),
    pl.col("LapTimeSeconds").std().alias("std_time"),
    pl.col("LapTime").min().alias("min_time"),
    pl.col("LapTime").max().alias("max_time"),
])

# Complex aggregations with expressions
result = (
    laps
    .filter(pl.col("Compound") == "SOFT")
    .group_by("Driver")
    .agg([
        pl.col("LapTime").mean().alias("mean_time"),
        pl.col("LapTimeSeconds").std().alias("std_time"),
        pl.col("LapTime").count().alias("lap_count"),
        (pl.col("LapTime") < pl.col("LapTime").quantile(0.25)).sum().alias("fast_laps")
    ])
    .sort("mean_time")
)

# Window functions (running calculations)
laps_with_rolling = laps.with_columns([
    pl.col("LapTime").rolling_mean(window_size=3).over("Driver").alias("rolling_avg"),
    pl.col("LapTime").rank().over("Driver").alias("lap_rank")
])
```

### Polars 2 notes

tif1 requires polars 2.x. tif1 returns eager `DataFrame` objects. Most polars 2.0 changes do not affect code that only reads them. The changes below matter for code that builds on the returned frames:

| Change in polars 2.0 | Effect on code that uses tif1 frames |
| :--- | :--- |
| `LazyFrame.collect()` runs on the streaming engine by default | Row order after `group_by`, joins, and `unpivot` is not guaranteed in lazy queries. Add `.sort(...)` or pass `maintain_order`. Eager frames are not affected. |
| String to `Date`, `Datetime`, and `Time` casts are removed | Use `.str.to_datetime()` on a `String` column instead of `.cast(pl.Datetime)`. tif1 returns `LapStartDate` as a `Datetime` already. |
| `pl.concat(..., how="horizontal")` requires equal heights | Use `how="horizontal_extend"` to pad a shorter frame with nulls. |
| `is_in()` no longer coerces types with loss | Cast both sides to one type first. `pl.col("LapNumber").is_in([1.0, 2.0])` raises because `LapNumber` is `Int64`; use `[1, 2]`. |
| Removed APIs: `melt`, `with_row_count`, `GroupBy.count()`, `collect(streaming=True)`, `join(how="outer")`, `pl.NUMERIC_DTYPES` | Use `unpivot`, `with_row_index`, `len()`, `collect(engine="streaming")`, `join(how="full")`, and `pl.selectors.numeric()`. The error message names the replacement. |
| `pl.Categorical(ordering=...)` is removed; categoricals always sort by string value | `TIF1_POLARS_LAP_CATEGORICAL=true` works as before. |

The complete list is in the [polars 2.0 upgrade guide](https://docs.pola.rs/releases/upgrade/2/). Telemetry frames that polars 1.x wrote to the cache load unchanged under polars 2.x. The same release changes the telemetry dtypes for `DistanceToDriverAhead` and `DriverAhead`, so tif1 rebuilds its cached telemetry frames once. It rebuilds them from the cached payloads, without a network fetch.

### Polars-Specific Features in tif1

With the polars backend, code can use these polars capabilities on the returned frames:

- **Lazy evaluation**: Call `.lazy()` on a polars frame to build an optimized query plan
- **Parallel execution**: All operations automatically use available CPU cores
- **Expression API**: Complex calculations can be expressed as optimized expressions
- **Efficient string operations**: Driver name filtering and compound matching are faster
- **Native Arrow**: Zero-copy interop with other Arrow-based tools
- **fastf1 methods**: `session.laps` is a `PolarsLaps` and telemetry is a `PolarsTelemetry`. Both are `pl.DataFrame` subclasses with the `pick_*` and telemetry methods. A `filter`, `select`, `sort`, or `with_columns` returns a plain `pl.DataFrame`. Call the methods on it through the `df.f1` namespace, for example `laps.filter(...).f1.pick_fastest()`. Refer to the [Models API](/api-reference/models).

## Detailed Performance Comparison

Performance varies by operation type, data size, and hardware. The values below were measured on one machine, with the tables that tif1 returns for one session.

### Measurement Method

- **Hardware**: Intel Core i9-13900HX (32 threads)
- **Software**: Python 3.14, pandas 3.0.6, polars 2.0.0
- **Dataset**: 2025 Bahrain Grand Prix race (1,128 laps; one lap of telemetry has 710 samples)
- **Measurement**: Median of 25 runs, with the session already in the local cache

### Measured Values

| Operation | Pandas | Polars |
| :--- | :--- | :--- |
| Load `session.laps` in a new process (SQLite frame tier) | 1.5 ms | 1.4 ms |
| Build `session.laps` from cached payloads (no frame tier) | 30 ms | 16 ms |
| Filter `Driver == "VER"` | 0.6 ms | 0.7 ms |
| Filter with 3 conditions | 0.8 ms | 0.8 ms |
| Group by `Driver`, one mean | 0.4 ms | 2.0 ms |
| Group by `Driver`, 4 aggregations | 1.1 ms | 0.3 ms |
| Sort by `LapTimeSeconds` | 0.7 ms | 0.3 ms |
| Memory of `session.laps` | 462 KB | 348 KB |
| Memory of one lap of telemetry | 148 KB | 91 KB |

Memory is `memory_usage(deep=True)` on pandas and `estimated_size()` on polars.

<Note>
  At the size of one session, both backends finish each operation in about 2 ms or less. Neither backend is faster for every operation. Measure the actual workload before a backend switch.
</Note>

## Data Contract by Backend

tif1 loads the same payloads on both backends and then applies a dtype contract per backend. The contract decides how time values, text, and missing values are represented. Read this section before writing code that runs on both backends.

### Column types by backend

The tables list the types as loaded for the 2025 Bahrain Grand Prix race. Columns not listed have the same type on both backends: `Float64` for speeds and weather readings, `String` for text.

**Laps** (`session.laps`)

| Column | pandas | polars |
| :--- | :--- | :--- |
| `LapTime`, `Sector1Time` to `Sector3Time`, `Sector1SessionTime` to `Sector3SessionTime`, `PitInTime`, `PitOutTime`, `LapStartTime`, `Time`, `WeatherTime` | `timedelta64[ns]` | `Duration("ns")` |
| `LapTimeSeconds` | `float64` | `Float64` |
| `LapNumber`, `Stint`, `TyreLife`, `Position` | `float64` | `Int64` |
| `Driver`, `Team`, `Compound`, `TrackStatus` | `category` | `String` |
| `IsPersonalBest`, `FreshTyre`, `IsAccurate`, `FastF1Generated`, `Rainfall` | `bool` | `Boolean` |
| `Deleted` | `boolean` (nullable) | `Boolean` |
| `LapStartDate` | `datetime64[ns]` | `Datetime("ns")` |
| `WindDirection` | `Int64` (nullable) | `Int64` |
| `index` | `int64`, first column (FastF1 compatibility) | not present |

Set `TIF1_POLARS_LAP_CATEGORICAL=true` to get `Categorical` for the text columns on polars. See [Environment variables](/reference/environment-variables).

**Weather** (`session.weather`)

| Column | pandas | polars |
| :--- | :--- | :--- |
| `Time` | `timedelta64[ns]` | `Duration("ns")` |
| `AirTemp`, `Humidity`, `Pressure`, `TrackTemp`, `WindSpeed` | `float64` | `Float64` |
| `WindDirection` | `Int64` (nullable) | `Int64` |
| `Rainfall` | `boolean` (nullable) | `Boolean` |

**Race control messages** (`session.race_control_messages`)

| Column | pandas | polars |
| :--- | :--- | :--- |
| `Time` | `datetime64[ns]` | `Datetime("ns")` |
| `Category`, `Message`, `Status`, `Flag`, `Scope`, `RacingNumber` | `object` (`None` when missing) | `String` (`null` when missing) |
| `Sector` | `float64` | `Float64` |
| `Lap` | `int64` (`0` when the message has no lap) | `Int64` (`null` when the message has no lap) |

**Telemetry** (`lap.telemetry`, `session.get_fastest_lap_tel()`)

| Column | pandas | polars |
| :--- | :--- | :--- |
| `Date` | `datetime64[ns]` | `Datetime("ns")` |
| `SessionTime`, `Time` | `timedelta64[ns]` | `Duration("ns")` |
| `Brake` | `bool` | `Boolean` |
| `nGear`, `DRS` (`DRS` is a `0` or `1` flag) | `Int64` (nullable) | `Int64` |
| `Source` (`"merged"`), `Status` (always `"OnTrack"`) | `object` | `Categorical` |
| `LapNumber` | `Int64` | `Int64` |
| `Speed`, `RPM`, `Throttle`, `Distance`, `RelativeDistance`, `AccelerationX` to `AccelerationZ`, `X`, `Y`, `Z` | `float64` | `Float64` |
| `DistanceToDriverAhead` | `float64` (`NaN` when nobody is ahead) | `Float64` (`null` when nobody is ahead) |
| `DriverAhead` | `str` with driver numbers, missing when nobody is ahead (`object` when every sample is missing) | `String` (`null` when nobody is ahead) |
| `Driver` | `object` | `String` |

`DriverAhead` holds driver numbers such as `"12"`, not driver codes. To find the samples with nobody ahead, use `isna()` on pandas or `is_null()` on polars. The column never holds the string `"None"`.

For code that runs on both backends, use `LapTimeSeconds` for lap times. Compare `Driver`, `Team`, and `Compound` as strings. Both work without a cast on either backend.

### Missing values and sentinels

The upstream payloads encode a missing value in two ways: JSON `null`, and the literal string `"None"`. The string form appears in 2026 lap data and in the `Lap` column of race control messages for every non-race session. It also appears in telemetry when nobody is ahead. tif1 normalizes both forms on both backends before it applies the dtype contract:

- Laps: the strings `"None"`, `"none"`, `"null"`, `"nan"`, and `""` become a missing value. The replacement runs only when a payload contains one of these tokens.
- Weather and race control messages: on polars, the same tokens become a missing value before the frame is built. A column with one sentinel then keeps its `Boolean`, `Float64`, or `Int64` type instead of becoming `String`.
- Weather on pandas: the same tokens become a missing value before the `astype` and `to_numeric` passes.
- Race control messages on pandas: the exact string `"None"` becomes `None` in the text columns and `NaN` in `Sector`. `Lap` goes through a numeric parse, so any token that is not a number becomes `0`.
- Telemetry: the same tokens become `NaN` on pandas and `null` on polars. `DistanceToDriverAhead` and the other numeric channels stay `float64` or `Float64`. `DriverAhead` stays a text column of driver numbers.
- Casts are non-strict on both backends. A value that cannot be parsed becomes a missing value; it does not raise.

The representation of a missing value follows the backend. polars uses `null` for every type. pandas uses `NaT` for time columns, `NaN` for floats, `<NA>` for nullable integers and booleans, and `None` for text columns. One difference is intentional. The race control `Lap` column is a plain `int64` on pandas (FastF1 convention). A message without a lap has `Lap == 0` on pandas and `null` on polars.

### Empty weather or race control tables

Weather and race control messages are optional tables. When a payload cannot be fetched (`NetworkError`), fails validation, or cannot be converted to the dtype contract, tif1 logs a warning. It returns an empty DataFrame for that table instead of raising. `session.load()`, `session.laps`, and telemetry are not affected. The behaviour is the same on both backends.

The warning names the table and the session, then gives the error. The event name is decoded, as in `session.event_name`:

```text
Failed to load weather for 2025/Bahrain Grand Prix/Race: <error>
```

Enable logging to see it, and test for an empty table before plotting:

```python
import logging

import tif1

tif1.setup_logging(logging.WARNING)
session = tif1.get_session(2025, "Bahrain Grand Prix", "Race")
weather = session.weather
if len(weather) == 0:
    print("no weather table for this session")
```

A session that has no weather file at all logs `No weather in session` at `INFO` level and also returns an empty DataFrame.

### Data Selection and Filtering

<CodeGroup>
```python Pandas
# Boolean indexing (most common). LapTime is a timedelta, so compare the
# float LapTimeSeconds column (or a pd.Timedelta) to a number of seconds
fast_laps = laps[laps["LapTimeSeconds"] < 100]

# Multiple conditions with & and |
verstappen_fast = laps[(laps["Driver"] == "VER") & (laps["LapTimeSeconds"] < 97)]

# Query method (string-based, convenient)
fast_laps = laps.query("LapTimeSeconds < 100")
verstappen_fast = laps.query("Driver == 'VER' and LapTimeSeconds < 97")

# isin for multiple values
soft_medium = laps[laps["Compound"].isin(["SOFT", "MEDIUM"])]

# String methods
mercedes = laps[laps["Team"].str.contains("Mercedes")]

# loc and iloc
lap_15 = laps.loc[laps["LapNumber"] == 15]
first_10 = laps.iloc[:10]
```

```python Polars
# Filter method (primary approach). LapTime is a Duration on polars;
# LapTimeSeconds works on both backends
fast_laps = laps.filter(pl.col("LapTimeSeconds") < 100)

# Multiple conditions with & and |
verstappen_fast = laps.filter(
    (pl.col("Driver") == "VER") & (pl.col("LapTimeSeconds") < 97)
)

# Chained filters (often clearer)
verstappen_fast = (
    laps
    .filter(pl.col("Driver") == "VER")
    .filter(pl.col("LapTimeSeconds") < 97)
)

# is_in for multiple values
soft_medium = laps.filter(pl.col("Compound").is_in(["SOFT", "MEDIUM"]))

# String methods
mercedes = laps.filter(pl.col("Team").str.contains("Mercedes"))

# Row slicing (no loc/iloc)
first_10 = laps.head(10)
last_10 = laps.tail(10)
rows_10_to_20 = laps.slice(10, 10)

# No boolean-mask indexing: polars reads laps[mask] as a column selector,
# so it raises (or picks columns when the lengths happen to match). Use filter.
lap_15 = laps.filter(pl.col("LapNumber") == 15)
```
</CodeGroup>

### Column Selection and Manipulation

<CodeGroup>
```python Pandas
# Select columns
subset = laps[["Driver", "LapTime", "Compound"]]

# Select by type
numeric_cols = laps.select_dtypes(include=[np.number])
```

## Converting Between Backends

A frame from one backend converts to the other with the polars functions `DataFrame.to_pandas()` and `pl.from_pandas()`. This lets different parts of a workflow use the strengths of each library.

<Note>
  Both conversions use `pyarrow`. `pip install tif1` installs it, so no extra install is necessary.
</Note>

### Basic Conversion

<CodeGroup>
```python Polars to Pandas
# Start with polars
session = tif1.get_session(2025, "Monaco", "Race", lib="polars")
laps_polars = session.laps

# Convert to pandas for compatibility
laps_pandas = laps_polars.to_pandas()

# pandas-only libraries work on the converted frame. LapTime becomes
# timedelta64[ns], so plot the float LapTimeSeconds column
import seaborn as sns
sns.violinplot(data=laps_pandas, x="Driver", y="LapTimeSeconds")
```

```python Pandas to Polars
# Start with pandas
session = tif1.get_session(2025, "Monaco", "Race", lib="pandas")
laps_pandas = session.laps

# Convert to polars for performance
import polars as pl
laps_polars = pl.from_pandas(laps_pandas)

# Polars operations on the converted frame. LapTime arrives as Duration(ns),
# as in a native tif1 polars frame. polars has no std() for a Duration, so
# aggregate the float LapTimeSeconds column and give each output a name
result = laps_polars.group_by("Driver").agg([
    pl.col("LapTimeSeconds").mean().alias("mean_time"),
    pl.col("LapTimeSeconds").std().alias("std_time")
])
```
</CodeGroup>

### Conversion Performance

Conversion between backends has a cost, so use it strategically. On the machine of the [Measurement Method](#measurement-method), the laps of one race (1,128 rows) took these times:

| Conversion | Time (1,128 laps) |
| :--- | :--- |
| Polars → Pandas (`to_pandas()`) | About 1 ms |
| Pandas → Polars (`pl.from_pandas()`) | About 2.5 ms |

<Warning>
  Frequent conversions can negate the performance benefits of using polars. Design the workflow to minimize backend switches.
</Warning>

### Zero-Copy Conversion (Arrow)

For maximum efficiency, use Apache Arrow as an intermediate format. `pyarrow` is a `tif1` dependency, so it is already installed:

```python
import pyarrow as pa
import polars as pl

# Pandas → Arrow → Polars (zero-copy when possible)
laps_pandas = tif1.get_session(2025, "Monaco", "Race").laps  # pandas DataFrame
arrow_table = pa.Table.from_pandas(laps_pandas)
laps_polars = pl.from_arrow(arrow_table)

# Polars → Arrow → Pandas (zero-copy when possible)
arrow_table = laps_polars.to_arrow()
laps_pandas = arrow_table.to_pandas()
```

<Tip>
  Zero-copy conversions avoid memory duplication and are much faster for large datasets. These conversions require compatible data types.
</Tip>

## Setting Default Backend

Configure tif1 to use a preferred backend by default. This avoids the need to specify `lib=` on every call.

### Via Configuration File

Create or edit `~/.tif1rc` (JSON format):

```json
{
  "lib": "polars",
  "enable_cache": true,
  "cache_dir": "/path/to/tif1-cache"
}
```

After this setting, all sessions use polars by default:

```python
import tif1

# Uses polars automatically
session = tif1.get_session(2025, "Monaco", "Race")
print(type(session.laps))  # <class 'tif1.models_polars.PolarsLaps'> (a polars DataFrame)
```

### Via Environment Variable

Set the `TIF1_LIB` environment variable:

<CodeGroup>
```bash Linux/macOS
export TIF1_LIB=polars
python your_script.py
```

```powershell Windows PowerShell
$env:TIF1_LIB = "polars"
python your_script.py
```

```cmd Windows CMD
set TIF1_LIB=polars
python your_script.py
```
</CodeGroup>

Environment variables take precedence over the config file.

### Programmatically

Set the backend at runtime using the config API:

```python
import tif1

# Get config instance
config = tif1.get_config()

# Set backend
config.set("lib", "polars")

# Optionally save to config file
config.save()

# All subsequent calls use polars
session = tif1.get_session(2025, "Monaco", "Race")
```

### Per-Session Override

Override the default on a per-session basis at any time:

```python
import tif1

# Set default to polars
config = tif1.get_config()
config.set("lib", "polars")

# Most sessions use polars
session1 = tif1.get_session(2024, "Spa", "Race")  # Uses polars

# But you can override for specific sessions
session2 = tif1.get_session(2024, "Monaco", "Race", lib="pandas")  # Uses pandas
```

### Configuration Precedence

When multiple configuration sources are present, tif1 uses this precedence order (highest to lowest):

1. **Explicit parameter**: `lib="polars"` in function call
2. **Runtime call**: `config.set("lib", "polars")` after import
3. **Environment variable**: `TIF1_LIB=polars`, read once when the config loads
4. **Config file**: `~/.tif1rc` setting
5. **Default**: `pandas`

```python
# Example showing precedence
import tif1

config = tif1.get_config()
print(config.get("lib"))  # TIF1_LIB, then ~/.tif1rc, then the default "pandas"

# A runtime set() replaces the value loaded from the environment or the file
config.set("lib", "polars")

# Explicit parameter overrides everything
session = tif1.get_session(2024, "Monaco", "Race", lib="pandas")
print(session.lib)  # pandas (explicit parameter wins)
```

## Lazy Evaluation Deep Dive (Polars)

Lazy evaluation is a key polars feature. It enables query optimization that can improve performance by a large factor.

### Understanding Lazy vs Eager Execution

<CodeGroup>
```python Eager (Default)
import polars as pl

# Each operation executes immediately
laps = pl.read_parquet("race_data.parquet")  # Loads entire file
filtered = laps.filter(pl.col("Driver") == "VER")  # Scans all data
selected = filtered.select(["LapNumber", "LapTime"])  # Creates new DataFrame
sorted_result = selected.sort("LapTime")  # Sorts data

# Multiple passes through data, intermediate DataFrames created
```

```python Lazy (Optimized)
import polars as pl

# Build query plan (no execution yet)
result_lazy = (
    pl.scan_parquet("race_data.parquet")  # Doesn't load yet
    .filter(pl.col("Driver") == "VER")  # Adds to plan
    .select(["LapNumber", "LapTime"])  # Adds to plan
    .sort("LapTime")  # Adds to plan
)

# Execute optimized plan (single pass, minimal memory)
result = result_lazy.collect()

# Polars optimizes: predicate pushdown, projection pushdown, etc.
```
</CodeGroup>

<Note>
In polars 2.x, `LazyFrame.collect()` runs on the streaming engine by default. The streaming engine does not keep row order after `group_by`, joins, or `unpivot`. Add `.sort(...)`, or pass `maintain_order` (for example `join(..., maintain_order="left")`), when the order matters. Call `collect(engine="in-memory")` to use the in-memory engine. Eager `DataFrame` operations, which `tif1` returns, are not affected.
</Note>

### Query Optimization Techniques

Polars applies several optimizations automatically:

#### 1. Predicate Pushdown

Filters are pushed down to the data source. The scan applies them while it reads the file:

```python
# Without optimization: Read all data, then filter
laps = pl.read_parquet("race_data.parquet")
verstappen = laps.filter(pl.col("Driver") == "VER")

# With optimization: Filter while reading (much faster)
verstappen = (
    pl.scan_parquet("race_data.parquet")
    .filter(pl.col("Driver") == "VER")
    .collect()
)
# The filter runs inside the scan (SELECTION in the query plan)
```

#### 2. Projection Pushdown

Only requested columns are read from storage:

```python
# Without optimization: Read all columns, then select
laps = pl.read_parquet("race_data.parquet")  # Reads every column
subset = laps.select(["Driver", "LapTime"])

# With optimization: Read only needed columns
subset = (
    pl.scan_parquet("race_data.parquet")
    .select(["Driver", "LapTime"])
    .collect()
)
# Reads only 2 columns from the file
```

#### 3. Filter Reordering

Cheap filters run before expensive ones:

```python
laps_lazy = pl.scan_parquet("race_data.parquet")

result = (
    laps_lazy
    .filter(pl.col("Team").str.contains("Red Bull"))  # Expensive string op
    .filter(pl.col("LapNumber") > 10)  # Cheap numeric comparison
    .collect()
)
# Polars reorders: numeric filter first, then string filter
```

Examine what polars plans to do before execution:


The plan shows predicate pushdown (`SELECTION`) and projection pushdown (`PROJECT 4/45 COLUMNS`). The scan reads only the rows and columns that the query needs.

### When to Use Lazy Evaluation

Use lazy evaluation when:

- **Reading from files**: Parquet, CSV, JSON (use `scan_*` instead of `read_*`)
- **Complex queries**: Multiple filters, joins, aggregations
- **Large datasets**: When data does not fit comfortably in memory
- **Production pipelines**: Consistent performance is critical

Do not use lazy evaluation when:

- **Interactive exploration**: Eager mode gives immediate feedback
- **Small datasets**: The optimization overhead exceeds the gain.
- **Simple operations**: Single filter or selection is already fast

### Lazy Evaluation Patterns

#### Pattern 1: ETL Pipeline

```python
def process_race_data(race_file: str, output_file: str):
    """Extract, transform, load with lazy evaluation."""
    result = (
        pl.scan_parquet(race_file)
        # Extract: Read only needed columns
        .select(["Driver", "LapNumber", "LapTime", "Compound", "TyreLife"])
        # Transform: Clean and compute
        .filter(pl.col("LapTime").is_not_null())
        .with_columns([
            (pl.col("LapTime") - pl.col("LapTime").mean().over("Driver"))
            .alias("LapTime_delta"),
            (pl.col("TyreLife") / pl.col("TyreLife").max().over(["Driver", "Compound"]))
            .alias("TyreLife_pct")
        ])
        # Load: Write optimized result
        .collect()
    )
    result.write_parquet(output_file)
```

#### Pattern 2: Multi-File Aggregation

```python
def aggregate_season(year: int):
    """Aggregate data across all races in a season."""
    race_files = [f"data/{year}/race_{i:02d}.parquet" for i in range(1, 25)]

    # Process each file lazily
    lazy_frames = [
        pl.scan_parquet(f)
        .filter(pl.col("LapTime").is_not_null())
        .group_by("Driver")
        .agg([
            pl.col("LapTime").mean().alias("avg_time"),
            pl.col("LapTime").count().alias("lap_count")
        ])
        for f in race_files
    ]

    # Concatenate and aggregate (still lazy)
    season_stats = (
        pl.concat(lazy_frames)
        .group_by("Driver")
        .agg([
            pl.col("avg_time").mean().alias("season_avg"),
            pl.col("lap_count").sum().alias("total_laps")
        ])
        .collect()
    )

    return season_stats
```

#### Pattern 3: Streaming for Huge Datasets

```python
def analyze_huge_telemetry(telemetry_file: str):

            pl.col("Speed").mean().alias("avg_speed"),

            pl.col("Throttle").mean().alias("avg_throttle")

        .collect(engine="streaming")  # Process in chunks
    )

```

### Detailed Decision Criteria

#### Choose Pandas When:

1. **Ecosystem Integration is Critical**
   - The analysis uses libraries that require pandas (seaborn, scikit-learn, statsmodels)
   - The team standardizes on pandas
   - Existing pandas code needs maintenance

2. **Dataset is Small to Medium**
   - Under 100,000 rows: Performance difference is negligible
   - Under 1,000,000 rows: Pandas is still performant enough

3. **Specific Pandas Features**
   - MultiIndex for hierarchical data
   - Advanced time series resampling
   - Flexible indexing with loc/iloc
   - Pandas-specific methods that the code depends on

4. **Learning and Exploration**
   - Data analysis in Python is new work
   - The work is interactive exploration in Jupyter
   - Stack Overflow coverage is a priority

#### Choose Polars When:

1. **Performance is Critical**
   - Data processing runs in production
   - Consistent, predictable performance is required
   - Time constraints are tight

2. **Dataset is Large**
   - Over 1,000,000 rows: Polars parallelization performs best
   - Data does not fit comfortably in RAM: Use streaming

3. **Memory is Constrained**
   - Running on limited hardware
   - Processing multiple datasets simultaneously
   - Need to minimize cloud computing costs

4. **Building Data Pipelines**
   - ETL workflows benefit from lazy evaluation
   - Query optimization reduces complexity
   - Consistent performance is more important than peak performance

5. **Heavy Aggregations or String Operations**
   - Complex groupby with multiple aggregations
   - Extensive string parsing or manipulation
   - Window functions over large groups

```python Pandas Approach
import tif1
import pandas as pd

# Process all 2024 races (the schedule is a DataFrame; loop over its EventName column)
```

### Pattern 2: Memory-Efficient Telemetry Analysis

Telemetry data can be very large. This pattern handles it efficiently:

```python
import tif1
import polars as pl

def analyze_telemetry_efficiently(year: int, event: str, driver: str):
    """Analyze telemetry without loading everything into memory."""

    # Use polars for memory efficiency
    session = tif1.get_session(year, event, "Race", lib="polars")
    driver_obj = session.get_driver(driver)

    # Get the driver's fastest-lap telemetry (about 40% less memory than pandas)
    telemetry = driver_obj.get_fastest_lap_tel()

    # Process in chunks using lazy evaluation
    corner_analysis = (
        telemetry
        .lazy()  # Convert to lazy frame
        .with_columns([
            # Identify braking zones
            (pl.col("Brake") > 0).alias("is_braking"),
            # Identify acceleration zones
            (pl.col("Throttle") > 80).alias("is_accelerating"),
            # Speed categories
            pl.when(pl.col("Speed") > 300).then(pl.lit("high_speed"))
              .when(pl.col("Speed") > 200).then(pl.lit("medium_speed"))
              .otherwise(pl.lit("low_speed"))
              .alias("speed_category")
        ])
        .group_by("speed_category")
        .agg([
            pl.col("Speed").mean().alias("avg_speed"),
            pl.col("Throttle").mean().alias("avg_throttle"),
            pl.col("Brake").mean().alias("avg_brake"),
            pl.col("Speed").count().alias("sample_count")
        ])
        .collect()  # Execute optimized query
    )

    return corner_analysis

result = analyze_telemetry_efficiently(2024, "Monaco", "VER")
```

### Pattern 3: Incremental Data Processing

Build results incrementally without loading everything at once:

```python
import tif1
import polars as pl
from pathlib import Path

def process_season_incrementally(year: int, output_dir: Path):
    """Process each race and save results incrementally."""

    output_dir.mkdir(exist_ok=True)

    for event in tif1.get_event_schedule(year, include_testing=False)["EventName"]:
        print(f"Processing {event}...")

        # Load session with polars
        session = tif1.get_session(year, event, "Race", lib="polars")

        # Process and compute statistics
        stats = (
            session.laps
            .group_by("Driver")
            .agg([
                pl.col("LapTime").mean().alias("avg_time"),
                pl.col("LapTime").min().alias("best_time"),
                pl.col("LapTimeSeconds").std().alias("consistency"),
                pl.col("LapTime").count().alias("laps_completed")
            ])
            .with_columns(pl.lit(event).alias("event"))
        )

        # Save to parquet (efficient format)
        output_file = output_dir / f"{event.replace(' ', '_')}.parquet"
        stats.write_parquet(output_file)

        # The laps frame stays in the backend lap LRU (up to 100 sessions);
        # tif1.cache.clear_lap_cache() frees those frames

    # Later: combine all results lazily
    all_stats = pl.scan_parquet(output_dir / "*.parquet").collect()
    return all_stats

# Process entire season without memory issues
season_stats = process_season_incrementally(2024, Path("./race_stats"))
```

### Pattern 5: Efficient Filtering

Apply filters efficiently to minimize data scanned:

```python
import polars as pl

# ❌ Inefficient: Multiple filters create intermediate DataFrames
result = laps.filter(pl.col("Driver") == "VER")
result = result.filter(pl.col("Compound") == "SOFT")
result = result.filter(pl.col("LapTimeSeconds") < 97)

# ✅ Efficient: Single filter with combined condition
result = laps.filter(
    (pl.col("Driver") == "VER") &
    (pl.col("Compound") == "SOFT") &
    (pl.col("LapTimeSeconds") < 97)
)

# ✅ Also efficient: Chained filters on a lazy frame. The query optimizer
# combines them into one predicate. Eager filters run one after the other
result = (
    laps
    .lazy()
    .filter(pl.col("Driver") == "VER")
    .filter(pl.col("Compound") == "SOFT")
    .filter(pl.col("LapTimeSeconds") < 97)
    .collect()
)
```

## Troubleshooting and Common Issues

### Issue 1: Polars Removed From the Environment

**Symptom**: `import polars` raises `ModuleNotFoundError: No module named 'polars'`. A session requested with `lib="polars"` logs `Polars not available, falling back to pandas` and returns pandas frames. Polars ships with `tif1`, so this means it was uninstalled or the environment is broken.

**Solution**:
```bash
# Restore the polars version tif1 declares
pip install "polars>=2.0.0,<3"

# Verify installation
python -c "import polars as pl; print(pl.__version__)"
```

### Issue 2: Type Errors After Backend Switch

**Symptom**: Code works with pandas but fails with polars (or vice versa)

**Solution**: Check for backend-specific API usage

```python
# ❌ Pandas-specific (fails with polars)
result = laps.loc[laps["Driver"] == "VER"]

# ❌ Looks portable, but polars reads the mask as a column selector:
#    it raises, or picks columns when the mask length matches the column count
result = laps[laps["Driver"] == "VER"]

# ❌ Polars-specific (fails with pandas)
result = laps.filter(pl.col("Driver") == "VER")

# ✅ Portable: the tif1 pick_* methods exist on both backends
result = laps.pick_driver("VER")

# ✅ Backend-agnostic wrapper; session.lib names the active backend
def filter_driver(laps, driver, lib="pandas"):
    if lib == "polars":
        import polars as pl
        return laps.filter(pl.col("Driver") == driver)
    return laps[laps["Driver"] == driver]

result = filter_driver(session.laps, "VER", lib=session.lib)
```

### Issue 3: Memory Issues with Pandas

**Symptom**: `MemoryError` or system slowdown with large datasets

**Solution**: Switch to polars or use chunking

```python
# Option 1: Switch to polars (tif1 polars frames use 25-40% less memory)
session = tif1.get_session(2024, "Monaco", "Race", lib="polars")

# Option 2: Process in chunks with pandas
def process_in_chunks(laps, chunk_size=10000):
    results = []
    for i in range(0, len(laps), chunk_size):
        chunk = laps.iloc[i:i+chunk_size]
        result = chunk.groupby("Driver")["LapTime"].mean()
        results.append(result)
    return pd.concat(results)
```

### Issue 4: Slow Groupby Operations

**Symptom**: Groupby on a large table takes several seconds with pandas

**Solution**: Use polars, which runs the aggregations in parallel in one pass

```python
# Before (pandas)
laps_pd = tif1.get_session(2024, "Monaco", "Race", lib="pandas").laps
stats = laps_pd.groupby("Driver").agg({
    "LapTime": ["mean", "std", "min", "max", "count"]
})

# After (polars, fast)
import polars as pl
laps_pl = tif1.get_session(2024, "Monaco", "Race", lib="polars").laps
stats = laps_pl.group_by("Driver").agg([
    pl.col("LapTime").mean().alias("mean"),
    pl.col("LapTimeSeconds").std().alias("std"),
    pl.col("LapTime").min().alias("min"),
    pl.col("LapTime").max().alias("max"),
    pl.col("LapTime").count().alias("count")
])
```

### Issue 5: Conversion Overhead

**Symptom**: Frequent conversions between backends slow down code

**Solution**: Minimize conversions, do them once

```python
# ❌ Bad: Convert back and forth
session = tif1.get_session(2024, "Monaco", "Race", lib="polars")
laps_polars = session.laps
laps_pandas = laps_polars.to_pandas()  # Conversion 1
result_pandas = laps_pandas.groupby("Driver")["LapTime"].mean()
result_polars = pl.from_pandas(result_pandas)  # Conversion 2

# ✅ Good: Stay in one backend
session = tif1.get_session(2024, "Monaco", "Race", lib="polars")
laps = session.laps
result = laps.group_by("Driver").agg(pl.col("LapTime").mean())
# Convert once at the end if needed
result_pandas = result.to_pandas()
```

### Issue 6: Lazy Evaluation Confusion

**Symptom**: A polars lazy query does not return data

**Solution**: Remember to call `.collect()`

```python
# ❌ Forgot to collect
result = (
    pl.scan_parquet("race_data.parquet")
    .filter(pl.col("Driver") == "VER")
)
print(result)  # Prints query plan, not data

# ✅ Collect to execute
result = (
    pl.scan_parquet("race_data.parquet")
    .filter(pl.col("Driver") == "VER")
    .collect()  # Execute and return DataFrame
)
print(result)  # Prints actual data
```

### Issue 7: Incompatible Library Expectations

**Symptom**: Library expects pandas DataFrame but receives polars

**Solution**: Convert before passing to library

```python
import seaborn as sns
import polars as pl

# Get data with polars
session = tif1.get_session(2024, "Monaco", "Race", lib="polars")
laps = session.laps

# Convert for seaborn (expects pandas)
laps_pd = laps.to_pandas()
sns.violinplot(data=laps_pd, x="Driver", y="LapTime")
```

### Issue 8: Column Name Conflicts

**Symptom**: Errors with column names containing spaces or special characters

**Solution**: Select such columns by string; `query()` and attribute access need valid identifiers

```python
# Both backends accept any column name through string selection
laps_pd = tif1.get_session(2024, "Monaco", "Race", lib="pandas").laps
laps_pd["Lap Time"] = laps_pd["LapTimeSeconds"]
fast = laps_pd.query("`Lap Time` < 100")   # backticks in query()
fast = laps_pd[laps_pd["Lap Time"] < 100]   # laps_pd.Lap Time is a syntax error

laps_pl = tif1.get_session(2024, "Monaco", "Race", lib="polars").laps
laps_pl = laps_pl.with_columns(pl.col("LapTimeSeconds").alias("Lap Time"))
fast = laps_pl.filter(pl.col("Lap Time") < 100)

# ✅ Prefer underscores for new columns; tif1 column names are PascalCase
```

### Issue 9: Performance Not Improving with Polars

**Symptom**: Polars is not faster than pandas for the given use case

**Possible Causes**:
1. Dataset is too small (< 10k rows)
2. Using eager mode instead of lazy
3. Bottleneck is I/O, not computation
4. Single-threaded operations (some string ops)

**Solution**: Profile and optimize

```python
import time

# Profile pandas
start = time.time()
session_pd = tif1.get_session(2024, "Monaco", "Race", lib="pandas")
result_pd = session_pd.laps.groupby("Driver")["LapTime"].mean()
pandas_time = time.time() - start

# Profile polars
start = time.time()
session_pl = tif1.get_session(2024, "Monaco", "Race", lib="polars")
result_pl = session_pl.laps.group_by("Driver").agg(pl.col("LapTime").mean())
polars_time = time.time() - start

print(f"Pandas: {pandas_time:.3f}s")
print(f"Polars: {polars_time:.3f}s")
print(f"Speedup: {pandas_time/polars_time:.2f}x")
```

### Issue 10: Type Inference Differences

**Symptom**: The same column has a different type on each backend. `LapTime` is `timedelta64[ns]` on pandas and `Duration("ns")` on polars; `Driver` is `category` on pandas and `String` on polars. See [Column types by backend](#column-types-by-backend) for the full table.

**Solution**: Use the columns that have the same type on both backends; `LapTimeSeconds` is a float on both. Alternatively, normalise once after loading:

```python
if session.lib == "polars":
    laps = laps.with_columns([
        pl.col("LapNumber").cast(pl.Int32),
        pl.col("Driver").cast(pl.Categorical),
    ])
    seconds = laps["LapTime"].dt.total_milliseconds() / 1000  # Duration → float seconds
else:  # pandas
    laps["LapNumber"] = laps["LapNumber"].astype("Int32")
    laps["Driver"] = laps["Driver"].astype("category")
    seconds = laps["LapTime"].dt.total_seconds()  # astype("float64") raises on timedelta

# Backend-neutral: LapTimeSeconds is Float64 on both backends
seconds = laps["LapTimeSeconds"]
```

## Summary and Key Takeaways

### Quick Summary

- **Pandas**: Default backend, maximum compatibility, gentle learning curve
- **Polars**: Parallel query engine, lazy evaluation, 25-40% less memory for tif1 frames
- **Choice**: Depends on dataset size, performance needs, and ecosystem requirements
- **Flexibility**: Use both in the same project, convert as needed
- **Recommendation**: Start with pandas, migrate to polars for performance-critical code

### Key Performance Insights

1. **Polars performs best with large datasets**: on one session, both backends take about 1 ms per operation
2. **Memory efficiency matters**: tif1 polars frames use 25-40% less memory
3. **Lazy evaluation helps on files**: predicate and projection pushdown read less data
4. **Conversion has cost**: Minimize backend switches
5. **Ecosystem compatibility**: Pandas still dominates for visualization and ML

### When to Use Each Backend

**Use Pandas for:**
- Learning and exploration
- Small to medium datasets (< 100k rows)
- Ecosystem integration (seaborn, scikit-learn)
- Time series analysis
- Hierarchical data (MultiIndex)

**Use Polars for:**
- Large datasets (> 100k rows)
- Production pipelines
- Memory-constrained environments
- Heavy aggregations
- String-intensive operations

### Best Practices Checklist

- Set default backend in `~/.tif1rc` for consistency
- Profile code before optimizing
- Use polars for data processing, pandas for visualization
- Minimize conversions between backends
- Use lazy evaluation for complex polars queries
- Cache expensive computations
- Test with both backends if supporting both
- Document backend choice in code comments
- Monitor memory usage for large datasets
- Use type hints for DataFrame types
