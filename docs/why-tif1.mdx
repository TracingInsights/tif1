`fastf1` is an established library for Formula 1 data in Python. The fastf1 project has done much for the F1 data community. `tif1` started as a personal project with a different philosophy in a few areas. These areas are data-fetch granularity, API rate limits, ready-made charts, CDN-based access, and extra data.

`tif1` keeps a fastf1-compatible API, so the two libraries feel familiar side by side. This fact-checked comparison helps with that decision.

## Comparison at a Glance

| Feature | fastf1 | tif1 |
| :--- | :--- | :--- |
| **Data source** | F1 live-timing API + Ergast-compatible jolpica-f1 API | TracingInsights static files on public CDNs; the Ergast tables from the TracingInsights Stats repository, jolpica-f1 only as fallback |
| **Granularity** | Session-wide `session.load()`, with flags per data type | Lazy, per file — fetch one lap of telemetry directly |
| **Rate limits** | Yes — fastf1 raises an error after **500 uncached requests/hour**, the jolpica-f1 limit | **None** for timing, telemetry and the Ergast tables served from CDNs; jolpica-f1 is asked only for what the Stats repository cannot answer, paced to its limits |
| **Access** | Some cloud runtimes get HTTP 403 from the live-timing host | Public CDN files, no key or login |
| **Built-in charts** | Plotting helpers for colors and styles; chart code in matplotlib | **22 optional one-call chart helpers** |
| **Mini-sector data** | Not in the laps data | Mini-sector color codes (`ms1`, `ms2`, `ms3`) on every lap |
| **Backends** | pandas only | pandas **and** polars |
| **Caching** | SQLite HTTP cache + pickle files of parsed data | SQLite persistent cache + in-memory LRU |
| **Network** | HTTP/1.1 (`requests`) | HTTP/2, asynchronous, multi-CDN fallback |
| **Live timing** | Supported | Archive only (timing and telemetry 2018-current, Ergast results 1950-current) |

## 1. Fetch Only the Necessary Data — No Full-Session Downloads

### The fastf1 approach

`fastf1` is session-oriented by design. `session.load()` fetches the entire session up front: the laps, telemetry, weather, and messages of all drivers.

fastf1 reads session-wide files from the F1 live-timing API. The car data and the position data each arrive as one file for all drivers. `session.load(telemetry=False)` skips them. There is no option to load one driver or one lap. That volume is reasonable for a full-session analysis. Most of it goes unused when the analysis needs only a few laps.

### The tif1 approach: lazy and fine-grained

In `tif1`, a session is a lightweight object. Data is fetched only when a property is accessed, and only the files needed for that access. The example below fetches three JSON files: the driver list, the lap table, and the telemetry of lap 19.

```python
import tif1

session = tif1.get_session(2025, "Bahrain Grand Prix", "Race")

# No session.load() needed: one telemetry file for one lap.
telemetry = session.get_driver("VER").get_lap(19).telemetry
print(telemetry[["Time", "Speed", "Throttle"]].head())
```

### Why it matters

- **Faster iteration** — the first lap of telemetry needs three small files.
- **Disk space** — the cache stores only the files actually used.
- **Bandwidth** — only the requested files travel over the network.
- **Predictable cost** — one lap of telemetry equals one file. The lap table of a session is usually one file.

## 2. No API rate limits — a verified 500 requests/hour ceiling on fastf1's data source

### The 500 requests/hour limit, verified

`fastf1` obtains its data from two upstream sources:

1. The **F1 live-timing API** (unofficial, for telemetry and timing feeds).
2. The **Ergast-compatible jolpica-f1 API** (open source, for lap times, results, and historical data). It replaces the old Ergast API.

The jolpica-f1 [Rate Limits guide](https://github.com/jolpica/jolpica-f1/blob/main/docs/rate_limits.md) documents the following for unauthenticated access:

- **Burst limit:** 4 requests per second
- **Sustained limit: 500 requests per hour**

Requests above the limits receive `HTTP 429 Too Many Requests` with the message *"Request was throttled"*. The same guide states that the unauthenticated limits decrease in the future as token access rolls out. The [Terms of Use](https://github.com/jolpica/jolpica-f1/blob/main/TERMS.md) add that abuse or excessive use may result in temporary or permanent blocking.

fastf1 applies the same ceiling on the client side. Its request session waits at least 0.25 s between requests. It raises `RateLimitExceededError` after 500 requests in one hour. One counter covers the live-timing API and jolpica-f1 together. Requests that fastf1 serves from its cache do not count.

`tif1` reads the same Ergast tables from the [TracingInsights Stats repository](https://github.com/TracingInsights-Archive/Stats), one static file per table and round, through the CDN chain. A season of race results is 24 files fetched in parallel, not a paged API walk. jolpica-f1 is asked only for what that repository cannot answer: the seasons list, driver lists, status counts, a round that is not published yet. Those requests are paced to its limits.

### When the limit matters

The 500 requests/hour ceiling is a real constraint worth planning around. Load patterns that can approach it include:

- loops over an entire season (24 weekends × several sessions),
- comparisons of a full grid across multiple races,
- backtests or model training on many sessions,
- background jobs that warm a cache.

These patterns can approach 500 requests quickly, especially with whole-session loads and an empty cache. This scenario led to the creation of `tif1` for the app at [tracinginsights.com/analysis](https://tracinginsights.com/analysis).

### Why tif1 has no rate limits

`tif1` does not depend on those APIs for distribution. It serves pre-processed static JSON files from public GitHub data repositories (`TracingInsights/{year}`). Distribution runs through **jsDelivr (primary)**, **Hugging Face buckets (fallback)**, and **StaticDelivr (backup)**. These are free, public CDNs.

The result:

- No API keys or accounts
- No request quota or request counter in `tif1`
- A configurable cap on parallel requests (for example `max_concurrent_requests`) instead of an hourly limit
- Automatic CDN failover, retries, and a circuit breaker built in
- SQLite and in-memory LRU caching, so repeat accesses do not hit the network

## 3. Charts Included — 22 Optional One-Call Chart Helpers

Many users build visualizations by hand from fastf1's raw DataFrames. For quick, repeatable plots, `tif1` additionally bundles `plot_*()` helpers that handle the loading, filtering, and styling:

### Real examples from the tif1 tutorials

```python
import tif1
import matplotlib.pyplot as plt

# Top speeds by team at the 2023 Italian Grand Prix qualifying.
# Loads the session, auto-detects the fastest trap, and plots team maxima.
fig, ax = tif1.plot_top_speeds(2023, "Italian Grand Prix", "Q")
plt.show()

# Alonso's lap times at the 2023 Azerbaijan Grand Prix, colored by tire compound.
fig, ax = tif1.plot_driver_laptimes(2023, "Azerbaijan Grand Prix", "R", drivers=["ALO"])
plt.show()

# 4-panel speed / longitudinal-g / lateral-g / driver-actions comparison.
fig, axes = tif1.plot_telemetry_comparison(2024, "Monaco Grand Prix", "Q", drivers=["VER", "LEC"])
plt.show()

# Or save straight to a file — no interactive session required.
tif1.plot_laptime_heatmap(2023, "Monaco Grand Prix", "R", save_path="monaco_heatmap.png")
```

## 4. Public CDN access

### Access to the live-timing host

fastf1 reads timing and telemetry from `livetiming.formula1.com`, which is not a public API. The host can refuse some networks. In [FastF1 discussion #949](https://github.com/theOehrly/Fast-F1/discussions/949), a Google Colab runtime got HTTP 403 from it. Another network got HTTP 200 for the same URL.

fastf1 then tries its mirror, `livetiming-mirror.fastf1.dev`. The mirror does not have every session.

### The tif1 approach: public CDNs

`tif1` serves files from **jsDelivr** (primary) and **Hugging Face buckets** (fallback), with **StaticDelivr** as a last-resort backup. These are public CDNs. `tif1` sends plain HTTPS requests:

- No API keys
- No cookies or logins
- No accounts

Any network that can reach one of these CDNs can load the data. This includes cloud runtimes and CI runners.

## 5. Extra data — mini sectors and more

### Mini-sector data

Formula 1 timing divides each of the three sectors into mini-sectors. The number of mini-sectors in a sector changes from circuit to circuit. Mini-sector colors show where a lap was a personal best or an overall best, below the sector level.

The fastf1 laps data has no mini-sector columns. The TracingInsights data pipeline behind tif1 adds them from OpenF1 when the session matches:

- **`ms1`, `ms2`, `ms3`** hold the codes for sector 1, 2, and 3, usually one digit for each mini-sector.
- Each digit is a color code, for example `1` for green, `3` for purple, and `5` for the pit lane. The [data reference](/reference/data-reference) lists all codes.

In tif1:

```python
import tif1

session = tif1.get_session(2024, "Monaco Grand Prix", "Race")

# Mini-sector color codes
laps = session.laps
print(laps[["Driver", "LapNumber", "ms1", "ms2", "ms3"]].head())
```

### A few more extras

| Capability | Details |
| :--- | :--- |
| **Per-lap weather** | `laps.get_weather_data()` picks each lap's sample from the session weather table by fastf1's rule in about 1 ms (fastf1 takes about 0.9 s for a race) |
| **Acceleration channels** | `AccelerationX`, `AccelerationY`, and `AccelerationZ` (longitudinal, lateral, and vertical, in m/s²), computed from speed and position data |
| **Polars backend** | The same data as `polars.DataFrame` objects |
| **SQLite + LRU cache** | Persistent cache survives restarts; repeat reads in one process come from memory |
| **Async fetching** | HTTP/2 parallel downloads with multi-CDN fallback and a circuit breaker |
| **Jupyter-ready** | `tif1.jupyter` adds HTML display for sessions, drivers, and laps in notebooks |
| **CLI** | `tif1` command-line tools for schedules, data inspection, and cache management |

## Honest trade-offs: when fastf1 still makes sense

Both libraries have strengths, and fastf1 remains the better choice in a few situations:

- **Live timing.** tif1 is an archive library (timing and telemetry from 2018, Ergast results from 1950). Real-time lap and telemetry data during a live session needs fastf1.
- **Freshest data.** fastf1 reads the F1 live-timing archive directly. tif1 can load a session only after the TracingInsights pipeline publishes its files.
- **Deep fastf1-internal dependencies.** A codebase that relies on fastf1 internals beyond the documented API surface (for example `fastf1.livetiming` or `fastf1._api`) needs those specific modules. tif1 does not include them; `fastf1.ergast` has its counterpart in `tif1.ergast`.

## Migration

tif1 keeps the fastf1 column names for laps and telemetry, so many scripts need only an import change. The [migration guide](/migration-from-fastf1) lists the differences, such as the 0/1 `DRS` flag and the missing `SessionTime` and `Date` telemetry columns.

```python
import tif1 as ff1  # many scripts need no other change
```
