tif1 does not replace fastf1. The timing and telemetry data in tif1 is generated with fastf1, then processed and published to the TracingInsights data repositories. tif1 differs in how that data is delivered. It keeps the fastf1 API and column names, so most fastf1 code runs after an import change.

## Comparison

| | fastf1 | tif1 |
| :--- | :--- | :--- |
| Data source | F1 live-timing API, jolpica-f1 API, MultiViewer API | Static files generated with fastf1, on public CDNs. The Ergast tables come from the TracingInsights Stats repository; jolpica-f1 is a fallback only |
| Sign-in | An F1TV Access (or higher) subscription for most features, since fastf1 3.9.0 | None |
| Rate limits | 4 requests per second and 500 uncached requests per hour across all APIs (200 of them to jolpica-f1); `RateLimitExceededError` above that | None on the CDN files. The jolpica-f1 fallback sends at most 4 requests per second and 200 per hour, and waits instead of raising |
| Download unit | The whole session through `session.load()`, with a flag per data type | One file. One lap of telemetry is one file |
| Network access | Some cloud runtimes get HTTP 403 from the live-timing host | Any network that can reach jsDelivr, Hugging Face, or StaticDelivr |
| Charts | Plotting helpers for colors and styles; chart code written by hand in matplotlib | 22 `plot_*()` functions, one call each |
| Mini sectors | Not in the laps data | `ms1`, `ms2`, `ms3` codes on each lap |
| Backends | pandas | pandas and polars |
| Caching | SQLite HTTP cache and pickle files of parsed data | SQLite cache and in-memory LRU cache |
| HTTP | HTTP/1.1 (`requests`) | HTTP/2, asynchronous, with CDN fallback |
| Live timing | Supported | Not supported. Archive only: timing and telemetry from 2018, Ergast results from 1950 |

## 1. Download only the necessary data

fastf1 loads a whole session at a time. `session.load()` downloads the laps, telemetry, weather, and messages of every driver. The car data and the position data each come as one file for all drivers. `session.load(telemetry=False)` skips them, but fastf1 has no option to load one driver or one lap.

tif1 downloads per file, when a property is read. A new session downloads no data. The example below downloads three files: the driver list, the lap table, and the telemetry of lap 19.

```python
import tif1

session = tif1.get_session(2025, "Bahrain Grand Prix", "Race")

# No session.load() needed: one telemetry file for one lap.
telemetry = session.get_driver("VER").get_lap(19).telemetry
print(telemetry[["Time", "Speed", "Throttle"]].head())
```

- The first lap of telemetry needs three small files.
- The cache stores only the files that are used.
- One lap of telemetry is one file. The lap table of a session is usually one file.

## 2. No F1TV account needed

In October 2026 Formula 1 started to require authentication on its data APIs. Since fastf1 3.9.0, most fastf1 features need an F1TV Access (or higher) subscription. fastf1 signs in to an F1 account in one of three ways: the `F1_USERNAME` and `F1_PASSWORD` environment variables, a prompt in the terminal, or a browser add-on. The login token usually expires after four days. fastf1 cannot refresh it, so a new sign-in is necessary. With the credentials in environment variables, fastf1 signs in again automatically.

tif1 does not call the F1 data APIs. It downloads files that were already generated with fastf1 and published to the CDNs. No F1 account, subscription, or sign-in is necessary, and no token expires. Servers, CI jobs, and notebooks need no stored credentials.

Source: [fastf1 F1TV Account Authentication](https://docs.fastf1.dev/api_reference/accounts_auth.html).

## 3. No rate limits on the session data

### fastf1 limits

fastf1 sends every request through its own rate limiter (`fastf1/req.py` in fastf1 3.9.0). Requests to these hosts all count toward the same limits:

- the F1 live-timing archive (`livetiming.formula1.com` and the mirror `livetiming-mirror.fastf1.dev`)
- the MultiViewer API
- jolpica-f1
- the schedule file on GitHub

| Requests | Limit | When the limit is reached |
| :--- | :--- | :--- |
| All APIs together | 4 per second (at least 0.25 s between requests) | fastf1 waits |
| All APIs together | 500 per hour | fastf1 raises `RateLimitExceededError` |
| jolpica-f1 only | 200 per hour (these also count toward the 500) | fastf1 raises `RateLimitExceededError` |

Responses from the fastf1 cache do not count ([fastf1 Rate Limits and Caching](https://docs.fastf1.dev/api_reference/cache_and_rate_limits.html)). An uncached session load sends one request for each live-timing stream, plus jolpica-f1 requests for the results. With an empty cache, these workloads reach 500 requests per hour and stop with an error:

- loops over a full season (24 weekends, several sessions each)
- full-grid comparisons across many races
- backtests or model training on many sessions
- background jobs that fill a cache

This is one reason why tif1 was built for the app at [tracinginsights.com/analysis](https://tracinginsights.com/analysis).

### jolpica-f1 limits

The jolpica-f1 [Rate Limits guide](https://github.com/jolpica/jolpica-f1/blob/main/docs/rate_limits.md) gives these limits for clients without a token:

- 4 requests per second
- 500 requests per hour

Above these limits, jolpica-f1 returns `HTTP 429 Too Many Requests` ("Request was throttled"). The guide says that the limits will go down when token access is added. The [Terms of Use](https://github.com/jolpica/jolpica-f1/blob/main/TERMS.md) say that abuse or excessive use can get a client blocked.

### tif1

tif1 reads timing and telemetry from the TracingInsights data repositories (`TracingInsights/{year}`). It reads the Ergast tables from the [TracingInsights Stats repository](https://github.com/TracingInsights-Archive/Stats), one static file for each table and round. All files go through public CDNs: jsDelivr first, then Hugging Face buckets, then StaticDelivr. A season of race results is 24 files that download in parallel, not a paged API walk.

- No API keys or accounts.
- No request quota. `max_concurrent_requests` limits the parallel requests instead.
- Retries, CDN failover, and a circuit breaker.
- SQLite and in-memory LRU caches, so a repeated read sends no request.

In normal use tif1 does not call jolpica-f1, so the jolpica-f1 limits do not apply. tif1 calls jolpica-f1 only:

- for a round that is not in the Stats repository yet. The repository is updated a few hours after jolpica-f1 has the data.
- for queries that the files do not cover: season and driver lists, status counts, `status=` filters, queries without a season, and `current`/`last`.

These calls keep to the stricter of the fastf1 and jolpica-f1 limits:

- At most 4 requests in any second and 200 in any hour, shared by all threads of the process. When a limit is reached, tif1 waits. It does not raise an error.
- On `HTTP 429`, tif1 waits for the `Retry-After` time and tries again, up to 3 times.
- Answers stay in the cache for `ergast_ttl_hours`, so a repeated query sends no request.
- `ergast_rate_limit_burst` and `ergast_rate_limit_hourly` change the limits. See [Configuration](/api-reference/config).

The MultiViewer API (circuit data) is served through the free Cloudflare CDN at no cost to MultiViewer, so tif1 does not rate-limit it. tif1 caches its answers: a circuit layout is downloaded once and kept, and the circuit index is kept for `schedule_ttl_hours`.

## 4. Built-in charts

fastf1 supplies the data and plotting helpers for colors and styles. The chart code is written by hand in matplotlib. tif1 also has 22 `plot_*()` functions. Each one loads the data, runs the analysis, and draws the chart in one call:

```python
import tif1
import matplotlib.pyplot as plt

# Top speeds by team at the 2023 Italian Grand Prix qualifying.
# Loads the session, auto-detects the fastest trap, and plots team maxima.
fig, ax = tif1.plot_top_speeds(2023, "Italian Grand Prix", "Q")
plt.show()

# Alonso's lap times at the 2023 Azerbaijan Grand Prix, colored by tire compound.
fig, ax = tif1.plot_driver_laptimes(2023, "Azerbaijan Grand Prix", "R", drivers=["ALO"])
plt.show()

# 4-panel speed / longitudinal-g / lateral-g / driver-actions comparison.
fig, axes = tif1.plot_telemetry_comparison(2024, "Monaco Grand Prix", "Q", drivers=["VER", "LEC"])
plt.show()

# Or save straight to a file — no interactive session required.
tif1.plot_laptime_heatmap(2023, "Monaco Grand Prix", "R", save_path="monaco_heatmap.png")
```

| Category | Functions |

Every chart accepts `year`, `event`, `session`, `save_path`, and `dpi`. Most charts also accept a `drivers`, `teams`, or `compounds` filter. Most charts have a tutorial in the [Tutorials](/tutorials/race-analysis) section.

## 5. No IP blocking

fastf1 reads timing and telemetry from `livetiming.formula1.com`. The host refuses some networks. In [FastF1 discussion #949](https://github.com/theOehrly/Fast-F1/discussions/949), a Google Colab runtime got HTTP 403 from it, and another network got HTTP 200 for the same URL. fastf1 then tries its mirror, `livetiming-mirror.fastf1.dev`. The mirror does not have every session.

tif1 sends plain HTTPS requests to public CDNs (jsDelivr, then Hugging Face buckets, then StaticDelivr), with no API key, cookie, or login. Any network that can reach one of these CDNs can load the data, including cloud runtimes and CI runners.

## 6. Extra data and features

### Mini sectors

Formula 1 timing divides each of the three sectors into mini-sectors. The number of mini-sectors in a sector is different at each circuit. Mini-sector colors show where a lap was a personal best or an overall best, below the sector level.

The fastf1 laps data has no mini-sector columns. The TracingInsights data pipeline adds them from OpenF1 when the session matches:

- `ms1`, `ms2`, and `ms3` hold the codes for sectors 1, 2, and 3, usually one digit for each mini-sector.
- Each digit is a color code, for example `1` for green, `3` for purple, and `5` for the pit lane. The [data reference](/reference/data-reference) lists all codes.

```python
import tif1

session = tif1.get_session(2024, "Monaco Grand Prix", "Race")

# Mini-sector color codes
laps = session.laps
print(laps[["Driver", "LapNumber", "ms1", "ms2", "ms3"]].head())
```

### Other additions

| Addition | Details |
| :--- | :--- |
| Per-lap weather | `laps.get_weather_data()` picks the weather sample of each lap from the session weather table by the fastf1 rule in about 1 ms (fastf1 takes about 0.9 s for a race) |
| Acceleration channels | `AccelerationX`, `AccelerationY`, and `AccelerationZ` (longitudinal, lateral, and vertical, in m/s²), calculated from speed and position data |
| Polars backend | The same data as `polars.DataFrame` objects |
| SQLite and LRU cache | The SQLite cache persists across restarts; repeated reads in one process come from memory |
| Async downloads | HTTP/2 parallel downloads with CDN fallback and a circuit breaker |
| Jupyter display | `tif1.jupyter` adds HTML display for sessions, drivers, and laps in notebooks |
| CLI | The `tif1` command shows schedules, inspects data, and manages the cache |

## When not to use tif1

- **Live timing.** tif1 has no live timing. It is an archive library (timing and telemetry from 2018, Ergast results from 1950), and a session is available only after it ends. For live data during a session, use fastf1 (`fastf1.livetiming`, which signs in with an F1TV account).
- **Newest data.** fastf1 reads the F1 live-timing archive directly. tif1 can load a session only after its files are published, in under a minute after fastf1 has the data.
- **fastf1 internals.** Code that uses fastf1 modules outside the documented API (for example `fastf1.livetiming` or `fastf1._api`) needs fastf1. tif1 does not include them. `fastf1.ergast` has its counterpart in `tif1.ergast`.

## Migration

tif1 keeps the fastf1 column names for laps and telemetry, so many scripts need only an import change. The [migration guide](/migration-from-fastf1) lists the differences, such as the 0/1 `DRS` flag and the missing `SessionTime` and `Date` telemetry columns.

```python
import tif1 as ff1  # many scripts need no other change
```

See the [Migration from fastf1](/migration-from-fastf1) guide for the steps, or start with the [Quickstart](/quickstart).
