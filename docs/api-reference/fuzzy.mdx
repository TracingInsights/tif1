# Fuzzy Matching in tif1

The fuzzy matching module is a performance-optimized component of `tif1`. It provides fault-tolerant string matching for resolving Formula 1 event names. The system uses the `fuzz.ratio()` scorer of RapidFuzz, a C++ string similarity library. Users can reference races with partial names, informal abbreviations, location names, circuit names, or country names. Slightly misspelled variants also work. Session names use a fixed lookup table instead. All matching takes less than one millisecond.

This guide explores the architecture, algorithms, implementation details, and practical usage patterns of the fuzzy matching system. It provides high-level conceptual understanding and low-level technical insights. The audience is developers and data scientists working with Formula 1 data.

## Introduction and Motivation

### The Problem: Cognitive Load in Data Access

When working with Formula 1 data, users face a significant cognitive burden: remembering and typing exact official event names. The burden applies to programmatic and interactive work. Consider the 2024 Belgian Grand Prix. Its official designation might be "Formula 1 Rolex Belgian Grand Prix 2024" or simply "Belgian Grand Prix". The designation depends on the data source. Users naturally conceptualize this event through multiple mental models:

- **Geographic location**: "Belgium", "Spa", "Spa-Francorchamps"
- **Informal abbreviations**: "Belgian GP", "Spa GP"
- **Circuit name**: "Circuit de Spa-Francorchamps"
- **Country name**: "Belgium"
- **Colloquial references**: "Belgium race"

The fuzzy matching system is a translation layer. It connects natural human language patterns with the precise, canonical data identifiers of the underlying data infrastructure. Users do not need to consult documentation, memorize exact naming conventions, or perform manual string matching. This reduces friction in both exploratory data analysis and production data pipelines.

### Key Benefits and Design Goals

The fuzzy matching system was architected with several critical design objectives:

#### 1. Cognitive Load Reduction
Eliminates the need to remember exact event names, session abbreviations, or naming conventions. Users can query data with the mental model that feels most natural—location, circuit, country, or official name. The system resolves their intent.

#### 2. Multi-Modal Flexibility
Accepts multiple valid representations of the same event through a feature-based matching system. Each event is described by multiple "feature strings" (location, country, official name, etc.). The matcher finds the best match across all features simultaneously.

#### 3. Graceful Error Tolerance
Handles minor typos, spelling variations, and incomplete names through Levenshtein distance-based similarity scoring. A query like "Monac" will correctly resolve to "Monaco" even though it is technically incorrect.

#### 4. Performance Optimization
Achieves sub-millisecond matching times through a hybrid algorithm. The algorithm prioritizes fast exact substring matching before falling back to more expensive fuzzy ratio calculations. A full event name lookup takes about 0.1-0.3ms on a current workstation.

#### 5. Deterministic Consistency
Provides reproducible results with clear exact/fuzzy match indicators. The same query against the same reference data will always produce identical results, enabling reliable automated systems and testing.

#### 6. Cross-Season Compatibility
Works across the Formula 1 seasons that ship with `tif1` (2018-2026) despite evolving naming conventions, event formats (conventional vs. sprint weekends), and schedule changes. The system adapts to each season's unique characteristics.

#### 7. Transparency and Debuggability
Returns both the matched result and a boolean flag. The flag indicates whether the match was exact or fuzzy. This enables applications to provide user feedback, logging, and validation workflows.

### Real-World Impact

In practice, this system transforms the user experience from:

```python
import tif1

# Without fuzzy matching - requires exact knowledge
session = tif1.get_session(2024, "Belgian Grand Prix", "Qualifying")
```

To a much more natural interaction pattern:

```python
import tif1

# With fuzzy matching - works with natural language
session = tif1.get_session(2024, "Belgium", "Q")
session = tif1.get_session(2024, "Spa", "qualifying")
session = tif1.get_session(2024, "belgian", "Qualifying")
# All three resolve correctly
```

Session names do not use fuzzy matching: `"quali"` raises `ValueError`. The [Session Name Resolution](#session-name-resolution) section lists the accepted forms.

This flexibility is particularly valuable in:
- **Interactive Jupyter notebooks** where users are exploring data
- **Command-line interfaces** where typing speed matters
- **Educational contexts** where users are learning F1 geography
- **International audiences** who may use different naming conventions

## Architecture Overview

The `tif1` fuzzy matching system uses a **hybrid multi-stage matching strategy**. The strategy combines multiple algorithmic techniques. This balances accuracy, performance, and user experience. The architecture is fundamentally different for event names versus session names, reflecting their distinct usage patterns and requirements.

### Event Name Matching: Multi-Stage Fuzzy Algorithm

Two direct lookups run before the fuzzy pipeline (see `_find_event_by_name` in `tif1/events.py`):

1. **Exact name**: A case-insensitive match against the `EventName` values of that season returns at once.
2. **Alias table**: `EVENT_NAME_ALIASES` in `tif1/core_utils/constants.py` maps circuit, city, and country names ("Spa", "Silverstone", "Monza", "Interlagos", "COTA", "USA") to events. The lookup folds accents and case, turns punctuation into spaces, and drops "Grand Prix", "GP", "Formula 1", and "F1". An alias resolves against the calendar of the requested season. An alias of an event that is not on that calendar raises `EventNotInSeasonError` (a `ValueError`) from `get_event_by_name()` and `get_session()`.

Only names that miss both lookups reach `fuzzy_matcher`. The fuzzy step sent several circuit names to the wrong race. For a name that resolves wrongly, add an alias; do not change the scorer.

Names that reach `fuzzy_matcher` go through a four-stage pipeline powered by RapidFuzz:

#### Stage 1: String Normalization
All query and reference strings undergo normalization to maximize match success rates while preserving distinguishing characteristics:

```python
# Normalization process
original = "Monaco Grand Prix"
normalized = original.casefold().replace(" ", "")
# Result: "monacograndprix"

# Special characters preserved for disambiguation
original = "Spa-Francorchamps"
normalized = original.casefold().replace(" ", "")
# Result: "spa-francorchamps" (hyphen retained)
```

**Normalization rules:**
- Convert to lowercase using `casefold()` (Unicode-aware, handles international characters)
- Remove space characters (`replace(" ", "")`); tabs and newlines stay
- Keep all other characters (hyphens, apostrophes, accents) as they are
- No stemming or lemmatization (preserves exact character sequences)

#### Stage 2: Exact Substring Matching (Fast Path)
The system first tries exact substring matching. This fast path scans all feature strings before any fuzzy algorithm runs:

```python
query = "monaco"
reference = [
    ["monacograndprix", "monaco", "montecarlo"],
    ["britishgrandprix", "silverstone"],
]

# Indices of the elements with a feature that contains the query
matches = [i for i, feature_list in enumerate(reference)
           if any(query in feature for feature in feature_list)]
print(matches)  # [0]

# Exactly ONE element contains the substring: fuzzy_matcher() returns (0, True)
# at once, with no fuzzy scoring
```

**Performance characteristics:**
- O(n×m) substring checks, where n=number of events, m=features per event
- Typical execution: about 0.01-0.03ms for 24 events
- A unique substring hit skips the fuzzy scoring

#### Stage 3: Fuzzy Ratio Matching (Fallback Path)
When substring matching fails, the system falls back to edit-distance scoring. Failure means zero matches or multiple matches:

```python
from rapidfuzz import fuzz

query = "monac"  # Missing letter
feature = "monaco"

# Calculate similarity ratio (0-100 scale)
ratio = fuzz.ratio(query, feature)
# Result: 90.9 (very high similarity despite the missing letter)
```

**Algorithm details:**
- Uses RapidFuzz's `fuzz.ratio()` (normalized Indel similarity, a Levenshtein variant without substitutions)
- Scores range from 0 (completely different) to 100 (identical)
- The scores go into a float array and keep their fractional part (90.9 stays 90.9)
- Computed for all features of the candidate events: the events with a substring hit, or all events if none has one
- Returns event with highest-scoring feature
- Typical execution: about 0.07-0.09ms for 24 events

**Score floor:** Event resolution (`_find_event_by_name` in `tif1/events.py`) rejects a best score below 70. Then `get_event_by_name()` and `get_session()` raise `EventNotFoundError` with the message `No event matching '<name>' in <year>`. The floor is not part of `fuzzy_matcher`, which always returns the best index. Typos of real events score 75-97 ("Sao Paolo" 75, "Monacco" 92). Names that resemble no event score 67 or less ("Moon GP", "Paris", "Invalid GP").

#### Stage 4: Disambiguation (Tie-Breaking)
When multiple events achieve the same maximum similarity score, the system uses a disambiguation strategy:

```python
# Example: the query "practice" is a substring of all three elements
reference = [
    ["practice1", "fp1", "practice"],
    ["practice2", "fp2", "practice"],
    ["practice3", "fp3", "practice"],
]

# Each element scores 100 on its "practice" feature: a three-way tie.
# All three tied elements share "practice", so that feature is not compared.
# The features that only one tied element has ("practice1", "fp1", ...) decide.
# Here they tie again (94.1 each), so element 0 wins.
```

**Disambiguation rules:**
1. Find the elements that hold the top score (the tied elements). An element outside the tie never wins.
2. Count how many tied elements have each feature string.
3. Score each tied element on the features that no other tied element has. Use the Stage 3 scores.
4. Return the tied element with the highest such score.
5. If still tied, return the tied element with the lowest index (deterministic ordering).

This tie-break fixes typos such as "Bahrein". In 2025, the query ties the Bahrain Grand Prix and the pre-season testing event, which share the location and country. The official event names then decide, and "Bahrein" resolves to the Bahrain Grand Prix.

### Session Name Matching: Dictionary-Based Lookup

Session names use a fundamentally different approach—**deterministic dictionary lookup** rather than fuzzy matching. This design choice reflects the fact that session names are:
- Limited in number (8 canonical types)
- Well-defined with standard abbreviations
- Used frequently in tight loops (performance-critical)
- Less prone to user variation than event names

#### Dictionary Structure

`tif1/events.py` defines these tables for `Event.get_session_name()`. `get_session()` uses the same mappings from `tif1/core.py` (`SESSION_MAPPING` and `_CANONICAL_SESSION_NAMES`).

```python
# Canonical session types
_SESSION_TYPES = (
    "Practice 1", "Practice 2", "Practice 3",
    "Qualifying", "Sprint", "Sprint Shootout",
    "Sprint Qualifying", "Race"
)

# Abbreviation mappings (looked up with the input in uppercase)
_SESSION_TYPE_ABBREVIATIONS = {
    "FP1": "Practice 1",
    "FP2": "Practice 2",
    "FP3": "Practice 3",
    "Q": "Qualifying",
    "S": "Sprint",
    "SS": "Sprint Shootout",
    "SQ": "Sprint Qualifying",
    "R": "Race",
}

# Case-insensitive full name lookup ({"practice 1": "Practice 1", ...})
_SESSION_TYPES_BY_CASEFOLD = {session.casefold(): session for session in _SESSION_TYPES}
```

#### Lookup Algorithm

```python
def resolve_session_name(identifier: str, available_sessions: list[str]) -> str:
    """Simplified from get_session() in tif1/core.py."""
    key = identifier.strip()

    # Step 1: Try abbreviation match (case-insensitive: the input is upper-cased)
    canonical = _SESSION_TYPE_ABBREVIATIONS.get(key.upper())

    # Step 2: Try full name match (case-insensitive, extra spaces ignored)
    if canonical is None:
        canonical = _SESSION_TYPES_BY_CASEFOLD.get(" ".join(key.casefold().split()), identifier)

    # Step 3: The event must have the session - raise error
    if canonical not in available_sessions:
        raise ValueError(f"Session '{canonical}' does not exist for this event")
    return canonical
```

`Event.get_session_name()` tries the full name first and the abbreviation second. For an unknown name, its error message is `Invalid session type '...'`.

**Performance characteristics:**
- O(1) dictionary lookup (hash table)
- Typical execution: about 0.001ms
- No fuzzy matches: an unknown name raises `ValueError`
- Deterministic and predictable

### Architectural Rationale

The hybrid approach (fuzzy for events, dictionary for sessions) follows from these differences:

| Aspect | Event Names | Session Names |
|--------|-------------|---------------|
| **Variability** | High (about 20-24 per year, changing names) | Low (8 fixed types) |
| **User Input** | Diverse (location, circuit, country) | Standardized (FP1, Q, R) |
| **Typo Tolerance** | Critical (long names, international) | Less critical (short abbreviations) |
| **Performance** | About 0.1-0.3ms | About 0.001ms |
| **Ambiguity** | Common (multiple "Grand Prix") | Rare (distinct abbreviations) |

This architecture serves both use cases and keeps the user experience simple.

## Core API: `fuzzy_matcher`

The `fuzzy_matcher` function is the low-level primitive that powers all event name resolution in `tif1`. Most users interact with higher-level APIs like `get_session()` and `get_event_by_name()`. Understanding this function provides insight into the matching algorithm's behavior and performance characteristics.

### Function Signature

```python
def fuzzy_matcher(
    query: str,
    reference: list[list[str]]
) -> tuple[int, bool]
```

### Parameters

#### `query: str`
The search string to match against the reference data. This represents the user's input—what they typed or provided programmatically.

**Examples:**
- `"Monaco"` - Location name
- `"Spa-Francorchamps"` - Circuit name
- `"british grand prix"` - Full event name
- `"Monac"` - Typo/partial name

**Preprocessing:** The query undergoes normalization (casefold + space removal) before matching, so case and spaces are irrelevant.

#### `reference: list[list[str]]`
A list of lists where each inner list represents one matchable element (for example, one event). Each inner list contains multiple "feature strings" that describe that element.

**Structure:**
```python
reference = [
    # Element 0: Monaco Grand Prix
    ["Monaco Grand Prix", "Monaco", "Monte Carlo", "Monaco"],

    # Element 1: British Grand Prix
    ["British Grand Prix", "Silverstone", "Britain", "United Kingdom"],

    # Element 2: Italian Grand Prix
    ["Italian Grand Prix", "Monza", "Italy", "Autodromo Nazionale di Monza"]
]
```

**Design rationale:** The multi-feature approach allows each event to be described through multiple lenses. `tif1` uses the location, country, event name, and official name of each event. This increases match success rates. Users do not need to know which descriptor to use.

### Return Value

Returns a tuple `(index, exact)` containing:

#### `index: int`
The zero-based index of the best matching element in the reference list.

**Example:**
```python
from tif1.fuzzy import fuzzy_matcher

reference = [
    ["Monaco Grand Prix", "Monaco"],
    ["British Grand Prix", "Silverstone"],
    ["Italian Grand Prix", "Monza"]
]

index, exact = fuzzy_matcher("Silverstone", reference)
# index = 1 (British Grand Prix is at index 1)
```

<Note>
  `fuzzy_matcher()` changes `reference` in place: it normalizes every feature string and pads short feature lists with `""`. Keep a copy of the display names before the call, or pass `copy.deepcopy(reference)`.
</Note>

#### `exact: bool`
A boolean flag indicating the match quality:

- `True`: The query was a substring of at least one feature string in exactly one element. This indicates high confidence—the user's input unambiguously identifies a single event. A partial name such as `"monac"` is a substring of `"monaco"`, so it also gives `True`.

- `False`: Fuzzy ratio matching was used because either:
  - Zero substring matches were found (typo or very partial name)
  - Multiple substring matches were found (ambiguous query)

**Usage:** Applications can use this flag to provide user feedback, logging, or validation:

```python
import logging

from tif1.fuzzy import fuzzy_matcher

logger = logging.getLogger(__name__)

reference = [
    ["Monaco Grand Prix", "Monaco"],
    ["British Grand Prix", "Silverstone"],
]
names = [features[0] for features in reference]  # before the in-place normalization

query = "Monaoc"  # Transposed letters: not a substring of any feature
index, exact = fuzzy_matcher(query, reference)
if not exact:
    resolved_name = names[index]
    logger.warning(f"Fuzzy match: '{query}' → '{resolved_name}'")
    # Optionally prompt user for confirmation
```

### Matching Algorithm (Detailed)

The function implements a four-stage pipeline. The blocks in this section run the steps one by one on this input:

```python
query = "Monaoc"
reference = [
    ["Monaco Grand Prix", "Monaco"],
    ["British Grand Prix", "Silverstone"],
]
```

#### Stage 1: Normalization

```python
# Normalize query
query = query.casefold().replace(" ", "")

# Normalize all reference features in-place
for i in range(len(reference)):
    for j in range(len(reference[i])):
        reference[i][j] = reference[i][j].casefold().replace(" ", "")

# Pad shorter feature lists with "" (scores 0, never a substring hit)
# (an empty reference makes fuzzy_matcher() return (0, False) here)
width = max((len(features) for features in reference), default=0)
for features in reference:
    features.extend([""] * (width - len(features)))
```

**Why casefold?** Unlike `lower()`, `casefold()` applies the full Unicode case folding, for example German ß becomes "ss":
```python
"STRASBOURG".lower() == "strasbourg"  # True
"Straße".lower() == "STRASSE".lower()  # False: "straße" != "strasse"
"Straße".casefold() == "STRASSE".casefold()  # True: both give "strasse"
```

#### Stage 2: Exact Substring Matching

```python
full_partial_match_indices = []
for i, feature_strings in enumerate(reference):
    if any(val and query in val for val in feature_strings):
        full_partial_match_indices.append(i)

# If exactly one element contains the query as substring,
# fuzzy_matcher() returns (full_partial_match_indices[0], True) here
print(full_partial_match_indices)  # []: "monaoc" is not a substring, so go to Stage 3
```

**Examples:**

```python
# Example 1: Unique substring match
query = "monaco"
reference = [
    ["monacograndprix", "monaco", "montecarlo"],
    ["britishgrandprix", "silverstone"]
]
# "monaco" is substring of features in element 0 only
# Returns: (0, True)

# Example 2: Multiple substring matches (ambiguous)
query = "grand"
reference = [
    ["monacograndprix", "monaco"],
    ["britishgrandprix", "silverstone"]
]
# "grand" appears in both elements
# Falls through to fuzzy matching
# Returns: (0, False) - "monacograndprix" scores 50, "britishgrandprix" 47

# Example 3: No substring matches (typo)
query = "monaoc"
reference = [
    ["monacograndprix", "monaco"],
    ["britishgrandprix", "silverstone"]
]
# "monaoc" is not a substring of any feature
# Falls through to fuzzy matching
# Returns: (0, False) - closest match by fuzz.ratio()
```

#### Stage 3: Fuzzy Ratio Matching

```python
import numpy as np
from rapidfuzz import fuzz

# Determine which elements to score
if full_partial_match_indices:
    # If we had multiple substring matches, only score those
    candidate_indices = full_partial_match_indices
else:
    # If we had zero substring matches, score all elements
    candidate_indices = range(len(reference))

# Compute fuzz.ratio() for each feature of each candidate
# (a float array: 47.6 stays 47.6; padding "" scores 0)
ratios = np.zeros((len(reference), width), dtype=float)
for i in candidate_indices:
    ratios[i] = [fuzz.ratio(val, query) if val else 0.0 for val in reference[i]]

print(np.round(ratios, 1).tolist())  # [[47.6, 83.3], [9.1, 23.5]]
```

**Levenshtein Distance Explained:**

The Levenshtein distance measures the minimum number of single-character edits (insertions, deletions, substitutions) required to transform one string into another. RapidFuzz's `fuzz.ratio()` uses a close relative, the Indel distance, and scales it to 0-100:

```python
from rapidfuzz import fuzz

fuzz.ratio("monaco", "monaco")    # 100 (identical)
fuzz.ratio("monaco", "monac")     # 90.9 (1 deletion)
fuzz.ratio("monaco", "monaca")    # 83.3 (1 substitution = 1 deletion + 1 insertion)
fuzz.ratio("monaco", "silverstone")  # 23.5 (very different)
```

**Formula:** `fuzz.ratio()` is the normalized Indel similarity. The Indel distance counts insertions and deletions only, so a substitution counts as 2:
```python
from rapidfuzz.distance import Indel

s1, s2 = "monaco", "silverstone"
indel_distance = Indel.distance(s1, s2)  # 13
ratio = 100 * (1 - indel_distance / (len(s1) + len(s2)))
print(round(ratio, 1), round(fuzz.ratio(s1, s2), 1))  # 23.5 23.5
```

#### Stage 4: Disambiguation

```python
max_ratio = float(ratios.max())
tied = np.flatnonzero(ratios.max(axis=1) == max_ratio)

if len(tied) == 1:
    result = int(tied[0])
else:
    # Several elements share the best score. Count how many tied
    # elements have each feature: a shared feature cannot tell them apart.
    rows_with_feature = {}
    for i in tied:
        for val in set(reference[i]):
            if val:
                rows_with_feature[val] = rows_with_feature.get(val, 0) + 1

    # Score each tied element on the features only it has
    tie_scores = [
        max(
            (ratio for val, ratio in zip(reference[i], ratios[i])
             if val and rows_with_feature[val] == 1),
            default=0.0,
        )
        for i in tied
    ]
    # argmax returns the first (lowest-index) element on a further tie
    result = int(tied[int(np.argmax(tie_scores))])

# fuzzy_matcher() returns (result, False)
print(result, False)  # 0 False: "monaco" scores 83.3
```

**Disambiguation Example:**

```python
query = "grandprix"
reference = [
    ["monacograndprix", "monaco"],
    ["britishgrandprix", "silverstone"]
]

# "grandprix" is a substring of both elements, so both are scored
# Ratios (rounded):
# Element 0: [75.0, 13.3]  (max=75.0 for "monacograndprix")
# Element 1: [72.0, 20.0]  (max=72.0 for "britishgrandprix")

# No tie: element 0 wins (75 > 72) and the disambiguation step does not run.
# With a tie, the two elements share no feature, so each would be scored
# on all its features, and the higher one would win.
```

**Substring hits in several elements:**

```python
query = "grand"
reference = [
    ["monaco grand prix", "monaco"],
    ["british grand prix", "silverstone"]
]

# After normalization:
reference = [
    ["monacograndprix", "monaco"],
    ["britishgrandprix", "silverstone"]
]

# Substring matching finds "grand" in both "monacograndprix" and "britishgrandprix"
# Falls to fuzzy matching

# Fuzzy ratios (rounded):
# Element 0: [fuzz.ratio("monacograndprix", "grand"), fuzz.ratio("monaco", "grand")]
#          = [50.0, 18.2]
# Element 1: [fuzz.ratio("britishgrandprix", "grand"), fuzz.ratio("silverstone", "grand")]
#          = [47.6, 25.0]

# Element 0 wins with score 50
# Returns: (0, False)
```

### Performance Characteristics

#### Time Complexity

- **Best case (exact substring, single match):** O(n×m) substring checks where n=elements, m=features per element
  - Measured: about 0.01-0.03ms for 24 events with 4 features each

- **Worst case (fuzzy matching all elements):** O(n×m) `fuzz.ratio()` calls
  - Measured: about 0.07-0.09ms for 24 events with 4 features each
  - RapidFuzz is about 70 times faster than the pure Python Levenshtein function in "Performance Comparison with Alternatives"

#### Space Complexity

- O(n×m) for the reference array and ratios matrix
- The string array stores every feature at the length of the longest one. For the 2024 schedule (25 events, 4 features, up to 54 characters), that is about 22KB

### Integration with tif1

`events.py` resolves event names with `_fuzzy_match`, a private variant of `fuzzy_matcher` that also returns the best score (0-100):

```python
# Simplified from tif1/events.py
def _find_event_by_name(year, event_names, name, exact_match=False):
    if exact_match:
        # No aliases, no fuzzy matching: case-insensitive comparison only
        for event_name in event_names:
            if event_name.lower() == name.lower():
                return create_event(year, event_name)
        return None  # get_event_by_name() raises EventNotFoundError

    # 1. Exact EventName (case-insensitive)
    for event_name in event_names:
        if event_name.casefold() == name.casefold():
            return create_event(year, event_name)

    # 2. Alias table (EVENT_NAME_ALIASES): "Spa", "Monza", "Interlagos", "USA"
    targets = EVENT_NAME_ALIASES.get(alias_key(name), ())
    if targets:
        for target in targets:
            if target in event_names:
                return create_event(year, target)
        return None  # get_event_by_name() raises EventNotInSeasonError

    # 3. Fuzzy matching on Location, Country, EventName, and OfficialEventName
    reference = [
        [
            metadata["Location"].casefold(),
            metadata["Country"].casefold(),
            remove_common_words(event_name),
            remove_common_words(metadata["OfficialEventName"]),
        ]
        for event_name, metadata in schedule_metadata(year, event_names)
    ]
    index, exact, score = _fuzzy_match(remove_common_words(name), reference)
    matched_event_name = event_names[index]

    if score < 70:
        return None  # get_event_by_name() raises EventNotFoundError

    if not exact:
        logger.warning(f"Correcting user input '{name}' to '{matched_event_name}'")

    return create_event(year, matched_event_name)
```

`remove_common_words()` drops "formula 1", the year, "grand prix", and "gp" from a name. The score floor of 70 lives here, in event resolution. `fuzzy_matcher()` applies no floor and always returns the best index.

## Detailed Algorithm Walkthrough

This section provides an in-depth, step-by-step walkthrough of the fuzzy matching algorithm with concrete examples, edge cases, and performance analysis.

### Step 1: String Normalization

Normalization is the critical first step that enables flexible matching while maintaining reasonable accuracy. The process transforms all strings into a canonical form that ignores irrelevant differences.

#### Normalization Process

```python
def normalize(s: str) -> str:
    return s.casefold().replace(" ", "")
```

#### Why Casefold Instead of Lower?

The `casefold()` method is more aggressive than `lower()` and handles Unicode edge cases:

```python
# ASCII characters - identical behavior
"MONACO".lower()     # "monaco"
"MONACO".casefold()  # "monaco"

# German sharp S - different behavior
"STRAẞE".lower()     # "straße" (ß → ß)
"STRAẞE".casefold()  # "strasse" (ß → ss)

# Greek sigma - different behavior
"ΣΊΣΥΦΟΣ".lower()    # "σίσυφος"
"ΣΊΣΥΦΟΣ".casefold() # "σίσυφοσ" (final ς folds to σ)

# Turkish dotted I - same behavior: both keep the combining dot
"İSTANBUL".lower()   # "i̇stanbul"
"İSTANBUL".casefold() # "i̇stanbul"
```

For the accented names in F1 data (Nürburgring, São Paulo, Montréal), `casefold()` and `lower()` give the same result. Neither removes accents, so the fuzzy step treats "montreal" and "montréal" as different strings. The alias lookup folds accents before the fuzzy step, so "Montréal" still resolves to the Canadian Grand Prix.

#### Why Remove Spaces?

Space removal maximizes match success by ignoring formatting variations:

```text
# All of these normalize to the same string
"Monaco Grand Prix"  → "monacograndprix"
"MonacoGrandPrix"    → "monacograndprix"
"Monaco  Grand  Prix" → "monacograndprix"
"monaco grand prix"  → "monacograndprix"
```

This allows users to type:
- `"MonacoGP"` (no spaces)
- `"Monaco GP"` (one space)
- `"Monaco Grand Prix"` (full spaces)

All match successfully.

#### Why Preserve Special Characters?

Normalization removes only spaces. Hyphens, apostrophes, and accents stay:

```text
"Spa-Francorchamps"  → "spa-francorchamps"
"Spa Francorchamps"  → "spafrancorchamps"
```

So "spafrancorchamps" is not a substring of "spa-francorchamps". The fuzzy score of the two forms is still high (96.97). The alias table maps both forms to the Belgian Grand Prix before the fuzzy step runs.

#### Normalization Examples

```text
# Event names
"Formula 1 Rolex Belgian Grand Prix 2024" → "formula1rolexbelgiangrandprix2024"
"Monaco Grand Prix"                       → "monacograndprix"
"British Grand Prix"                      → "britishgrandprix"

# Location names
"Spa-Francorchamps"                       → "spa-francorchamps"
"Monte Carlo"                             → "montecarlo"
"Silverstone"                             → "silverstone"

# Session names
"Practice 1"                              → "practice1"
"Qualifying"                              → "qualifying"
"Sprint Shootout"                         → "sprintshootout"

# User queries (with typos)
"monac"                                   → "monac"
"belgian gp"                              → "belgiangp"
"Spa Francorchamps"                       → "spafrancorchamps"
```

### Step 2: Exact Substring Matching

After normalization, the algorithm tries to find exact substring matches. This is the "fast path" that handles the majority of queries without expensive fuzzy calculations.

#### Algorithm

The code is the Stage 2 block in "Matching Algorithm (Detailed)". It collects the indices of the elements with a substring hit. If there is exactly one, it returns `(index, True)`.

#### Success Criteria

An exact match is returned if and only if:
1. The query is a substring of at least one feature in exactly one element
2. No other elements contain the query as a substring

#### Example 1: Unique Substring Match (Success)

```python
query = "monaco"
reference = [
    ["monacograndprix", "monaco", "montecarlo"],  # Element 0
    ["britishgrandprix", "silverstone", "britain"],  # Element 1
    ["italiangrandprix", "monza", "italy"]  # Element 2
]

# Check each element:
# Element 0: "monaco" in "monacograndprix"? YES
#            "monaco" in "monaco"? YES
#            "monaco" in "montecarlo"? NO
#            → Element 0 matches

# Element 1: "monaco" in any feature? NO

# Element 2: "monaco" in any feature? NO

# Result: Exactly one element (0) matches
# Returns: (0, True)
```

#### Example 2: Multiple Substring Matches (Ambiguous)

```python
query = "grand"
reference = [
    ["monacograndprix", "monaco"],  # Element 0
    ["britishgrandprix", "silverstone"]  # Element 1
]

# Check each element:
# Element 0: "grand" in "monacograndprix"? YES → Element 0 matches
# Element 1: "grand" in "britishgrandprix"? YES → Element 1 matches

# Result: Two elements match (ambiguous)
# Falls through to fuzzy matching
# Returns: (0, False) - "monacograndprix" scores 50, "britishgrandprix" 47
```

#### Example 3: No Substring Matches (Typo)

```python
query = "monaoc"  # Transposed letters
reference = [
    ["monacograndprix", "monaco", "montecarlo"],
    ["britishgrandprix", "silverstone", "britain"]
]

# Check each element:
# Element 0: "monaoc" in "monacograndprix"? NO
#            "monaoc" in "monaco"? NO (substring must be exact)
#            "monaoc" in "montecarlo"? NO

# Element 1: "monaoc" in any feature? NO

# Result: Zero elements match
# Falls through to fuzzy matching
# Returns: (0, False) - "monaoc" is closest to "monaco"
# Note: "monac" (missing 'o') IS a substring of "monaco" and returns (0, True)
```

#### Performance Analysis

**Time Complexity:** O(n×m×k) where:
- n = number of elements (events)
- m = features per element
- k = average feature length

**Typical Performance:**
- 24 events × 4 features = 96 substring checks over about 1,920 characters
- Measured: about 0.01-0.03ms

### Step 3: Fuzzy Ratio Matching

When exact substring matching fails, the algorithm falls back to edit-distance similarity scoring with RapidFuzz.

#### Levenshtein Distance Fundamentals

The Levenshtein distance measures the minimum number of single-character edits needed to transform one string into another. Three operations are allowed:

1. **Insertion**: Add a character
2. **Deletion**: Remove a character
3. **Substitution**: Replace a character

#### Examples

```text
# Distance = 1 (one deletion)
"monaco" → "monac"
# Delete 'o' at end

# Distance = 1 (one insertion)
"monac" → "monaco"
# Insert 'o' at end

# Distance = 1 (one substitution)
"monaco" → "monaca"
# Substitute 'o' → 'a' at end

# Distance = 3 (three operations)
"monaco" → "monza"
# Substitute 'a' → 'z', substitute 'c' → 'a', delete the final 'o'

# Distance = 10 (many operations)
"monaco" → "silverstone"
# Completely different strings
```

#### RapidFuzz Ratio Calculation

RapidFuzz's `fuzz.ratio()` scales the Indel distance (a Levenshtein distance without substitutions) to a 0-100 scale:

```python
from rapidfuzz import fuzz

# Formula (normalized Indel similarity):
# ratio = 100 * (1 - indel_distance / (len(s1) + len(s2)))
# The Indel distance allows insertions and deletions only (a substitution costs 2)

# Identical strings
fuzz.ratio("monaco", "monaco")  # 100

# One character difference
fuzz.ratio("monaco", "monac")   # 90.9
# indel_distance=1, total_len=11, ratio=100*(1-1/11)=90.9

# Three edits
fuzz.ratio("monaco", "monza")   # 72.7
# indel_distance=3, total_len=11, ratio=100*(1-3/11)=72.7

# Completely different
fuzz.ratio("monaco", "silverstone")  # 23.5
# indel_distance=13, total_len=17, ratio=100*(1-13/17)=23.5
```

Note: `fuzz.ratio()` returns a float. The Levenshtein distances above (1, 3, 10) differ from the Indel distances that the ratio uses (1, 3, 13).

#### Algorithm Implementation

The code is the Stage 3 block in "Matching Algorithm (Detailed)". The element with the highest score wins. A tie between elements goes to Stage 4.

#### Detailed Example

```python
from rapidfuzz import fuzz

query = "monaoc"  # Typo (transposed letters)
reference = [
    ["monacograndprix", "monaco", "montecarlo"],  # Element 0
    ["britishgrandprix", "silverstone", "britain"],  # Element 1
    ["italiangrandprix", "monza", "italy"]  # Element 2
]

# No substring matches, so score all elements
# (comments show the integer part of each float score)

# Element 0 scores:
fuzz.ratio("monaoc", "monacograndprix")  # 47
fuzz.ratio("monaoc", "monaco")           # 83
fuzz.ratio("monaoc", "montecarlo")       # 62
# Max score for element 0: 83

# Element 1 scores:
fuzz.ratio("monaoc", "britishgrandprix")  # 9
fuzz.ratio("monaoc", "silverstone")       # 23
fuzz.ratio("monaoc", "britain")           # 15
# Max score for element 1: 23

# Element 2 scores:
fuzz.ratio("monaoc", "italiangrandprix")  # 18
fuzz.ratio("monaoc", "monza")             # 72
fuzz.ratio("monaoc", "italy")             # 18
# Max score for element 2: 72

# Overall max: 83 (element 0, feature "monaco")
# Returns: (0, False)
```

#### Why Score All Features?

Each element has multiple features because events can be described in multiple ways:

```python
# Belgian Grand Prix can be matched via:
reference = [
    [
        "belgiangrandprix",    # Official name
        "belgium",              # Country
        "spa-francorchamps",   # Circuit name
        "spa"                   # Circuit nickname
    ]
]

# All of these queries should match:
"belgium"           # Matches feature 1 (exact)
"spa"               # Matches feature 3 (exact)
"belgian"           # Matches feature 0 (substring)
"francorchamps"     # Matches feature 2 (substring)
"belgum"            # Matches feature 1 (fuzzy, typo)
"spaa"              # Matches feature 3 (fuzzy, typo)
```

By scoring all features and taking the maximum, the algorithm finds the best match. This works regardless of which descriptor the user chose.

### Step 4: Disambiguation

When multiple elements achieve the same maximum similarity score, the algorithm uses a disambiguation strategy. The strategy compares only the tied elements, on the features that they do not share.

#### The Disambiguation Problem

Consider this scenario:

```python
query = "grandprix"
reference = [
    ["monacograndprix", "monaco"],
    ["britishgrandprix", "silverstone"]
]

# Fuzzy scores (integer part):
# Element 0: fuzz.ratio("grandprix", "monacograndprix") = 75
#            fuzz.ratio("grandprix", "monaco") = 13
#            Max: 75

# Element 1: fuzz.ratio("grandprix", "britishgrandprix") = 72
#            fuzz.ratio("grandprix", "silverstone") = 20
#            Max: 72

# Element 0 wins (75 > 72), but what if they were tied?
```

If both elements had the same max score, the algorithm needs a tie-breaker.

#### Disambiguation Algorithm

The code is the Stage 4 block in "Matching Algorithm (Detailed)". Only the elements that share the top score stay in the comparison. Each of them is scored on the features that no other tied element has. The highest of these scores decides. An element outside the tie never wins.

#### Disambiguation Example

```python
query = "grand"
reference = [
    ["monaco grand prix", "monaco"],
    ["british grand prix", "silverstone"]
]

# After normalization:
reference = [
    ["monacograndprix", "monaco"],
    ["britishgrandprix", "silverstone"]
]

# Substring matching finds "grand" in both elements
# Falls to fuzzy matching with candidate_indices = [0, 1]

# Fuzzy scores (integer part):
# Element 0:
fuzz.ratio("grand", "monacograndprix")  # 50
fuzz.ratio("grand", "monaco")           # 18
# Max: 50

# Element 1:
fuzz.ratio("grand", "britishgrandprix")  # 47
fuzz.ratio("grand", "silverstone")       # 25
# Max: 47

# Element 0 wins (50 > 47)
# Returns: (0, False)

# But what if both had score 50?
# Disambiguation would:
# 1. Count how many tied elements have each feature:
#    "monacograndprix": 1, "monaco": 1
#    "britishgrandprix": 1, "silverstone": 1
# 2. No feature is shared, so each element keeps its best score (50 each)
# 3. Still tied: return the first tied element (element 0)
```

#### Real Disambiguation Scenario

```python
query = "practice"
reference = [
    ["practice 1", "fp1", "practice"],
    ["practice 2", "fp2", "practice"],
    ["practice 3", "fp3", "practice"]
]

# After normalization:
reference = [
    ["practice1", "fp1", "practice"],
    ["practice2", "fp2", "practice"],
    ["practice3", "fp3", "practice"]
]

# Substring matching finds "practice" in all three elements
# Falls to fuzzy matching with candidate_indices = [0, 1, 2]

# Fuzzy scores:
# Element 0:
fuzz.ratio("practice", "practice1")  # 94
fuzz.ratio("practice", "fp1")        # 18
fuzz.ratio("practice", "practice")   # 100 ← Max
# Max: 100

# Element 1:
fuzz.ratio("practice", "practice2")  # 94
fuzz.ratio("practice", "fp2")        # 18
fuzz.ratio("practice", "practice")   # 100 ← Max
# Max: 100

# Element 2:
fuzz.ratio("practice", "practice3")  # 94
fuzz.ratio("practice", "fp3")        # 18
fuzz.ratio("practice", "practice")   # 100 ← Max
# Max: 100

# All three have max_ratio=100 (tie!)

# Disambiguation:
# 1. Count how many tied elements have each feature:
#    "practice1": 1, "fp1": 1, "practice": 3 ← Appears in all three!
#    "practice2": 1, "fp2": 1, "practice": 3
#    "practice3": 1, "fp3": 1, "practice": 3

# 2. Score each tied element on its unshared features only:
#    Element 0: "practice1" 94, "fp1" 18  Max: 94
#    Element 1: "practice2" 94, "fp2" 18  Max: 94
#    Element 2: "practice3" 94, "fp3" 18  Max: 94

# 3. Still tied! Return first match (element 0)
# Returns: (0, False)
```

This disambiguation strategy stops a feature that several tied elements share (here "practice") from deciding the match. The features that only one tied element has then decide.

#### Edge Case: All Top Features Common

If every top-scoring feature is shared, disambiguation leaves all of them out. The next-best features then decide:

```python
query = "gp"
reference = [
    ["monaco gp", "gp"],
    ["british gp", "gp"]
]

# After normalization: [["monacogp", "gp"], ["britishgp", "gp"]]
# "gp" scores 100 in both elements (tie), and both tied elements have it, so it is left out
# Remaining scores: "monacogp" 40, "britishgp" 36
# Returns: (0, False)
```

If no tied element has an unshared feature with a score above 0, `argmax` returns the first tied element.

### Performance Optimization Techniques

#### 1. Early Exit on Exact Match

The algorithm checks for exact substring matches before fuzzy matching, providing a 2-5x speedup for common queries:

```python
# Fast path (exact substring)
query = "monaco"
# Execution: about 0.01-0.02ms

# Slow path (fuzzy matching)
query = "monaoc"
# Execution: about 0.07-0.09ms
```

#### 2. Candidate Filtering

When multiple substring matches are found, only those candidates are scored in fuzzy matching:

```python
# Without filtering: Score all 24 events
# With filtering: Score only the events that matched the substring
```

#### 3. NumPy Vectorization

Using NumPy arrays enables vectorized operations that are faster than Python loops:

```python
import numpy as np

ratios = np.zeros((24, 4), dtype=float)  # 24 events, 4 features

# Python loop (slow)
max_scores = []
for row in ratios:
    max_scores.append(max(row))

# NumPy vectorization (fast)
max_scores = np.max(ratios, axis=1)
# Speedup: about 8x for a 24×4 array
```

#### 4. RapidFuzz C++ Implementation

RapidFuzz computes the scores in C++. It is much faster than a pure Python Levenshtein function:

```python
# Pure Python Levenshtein: about 0.007ms per call
# RapidFuzz fuzz.ratio(): about 0.0001ms per call
# Speedup: about 70x (see "Performance Comparison with Alternatives")
```

## Usage in tif1: High-Level APIs

While `fuzzy_matcher` is the low-level primitive, most users interact with higher-level APIs. These APIs integrate fuzzy matching directly into the data loading workflow. This section explores how fuzzy matching is exposed through `tif1`'s public API.

### Event Name Resolution

Event names are resolved through several high-level functions. All of them use the same order: exact name, alias table, then fuzzy matching.

#### `get_session()` - Primary Entry Point

The most common way to load F1 data, `get_session()` accepts fuzzy event names:

```python
import tif1

# All of these work and resolve to the same event:
session = tif1.get_session(2024, "Belgium", "Race")
session = tif1.get_session(2024, "belgian grand prix", "Race")
session = tif1.get_session(2024, "Spa", "Race")
session = tif1.get_session(2024, "spa-francorchamps", "Race")
session = tif1.get_session(2024, "belgian", "Race")
session = tif1.get_session(2024, "belgum", "Race")  # Typo handled

# All resolve to: Belgian Grand Prix - Race
```

**How it works:**
1. `get_session()` calls `get_event_by_name(year, event_name)`
2. An exact `EventName` match (case-insensitive) returns at once
3. The alias table resolves circuit, city, and country names ("Spa", "Monza", "Interlagos")
4. Other names go to `fuzzy_matcher()` with these features per event:
   - Location (for example, "Spa-Francorchamps")
   - Country (for example, "Belgium")
   - Event name without the common words (for example, "belgian")
   - Official name without the common words (for example, "rolex belgian" from "FORMULA 1 ROLEX BELGIAN GRAND PRIX 2024")
5. Returns a `Session` object for the matched event

The common words are "formula 1", the year, "grand prix", and "gp". They are also removed from the query. `get_session()` does not load session data. `session.event_name` holds the resolved name.

#### `get_event()` - Event Object Retrieval

Get an `Event` object (without loading session data) using fuzzy matching:

```python
import tif1

# Get event by name (fuzzy)
event = tif1.get_event(2024, "Monaco")
print(event.EventName)  # "Monaco Grand Prix"
print(event.Location)   # "Monaco"
print(event.Country)    # "Monaco"

# Get event by round number (exact)
event = tif1.get_event(2024, 1)  # First race of the season
print(event.EventName)  # "Bahrain Grand Prix"

# Fuzzy matching with typos
event = tif1.get_event(2024, "Monac")  # Missing 'o'
print(event.EventName)  # "Monaco Grand Prix"

# Multiple valid descriptors
event = tif1.get_event(2024, "Spa")
event = tif1.get_event(2024, "Belgium")
event = tif1.get_event(2024, "Belgian")
# All return the same event
```

For cases that need explicit name-based lookup (not round number):

### Session Name Resolution

Session names use **dictionary-based lookup** (not fuzzy matching), but still provide flexibility through predefined abbreviations and case-insensitive matching.

#### Supported Session Name Formats

```python
import tif1

# Full names (case-insensitive)
session = tif1.get_session(2024, "Monaco", "Practice 1")
session = tif1.get_session(2024, "Monaco", "practice 1")
session = tif1.get_session(2024, "Monaco", "PRACTICE 1")
```

## Exact Matching Mode

While fuzzy matching provides excellent user experience for interactive use, some applications require strict validation and exact name matching. The `tif1` API provides an `exact_match` parameter for these scenarios.

### When to Use Exact Matching

Exact matching is appropriate for:

1. **Validation workflows**: Ensuring user input matches official names exactly
2. **Automated systems**: Preventing unexpected fuzzy matches in production pipelines
3. **Data integrity**: Guaranteeing that only canonical names are accepted
4. **Testing**: Verifying that test data uses correct official names
5. **API endpoints**: Enforcing strict input validation for web services

### Enabling Exact Matching

```python
from tif1.events import get_event_by_name

# Fuzzy matching (default behavior)
event = get_event_by_name(2024, "Monaco")  # Works
event = get_event_by_name(2024, "monte carlo")  # Works
event = get_event_by_name(2024, "monac")  # Works (typo)

# Exact matching (strict mode)
event = get_event_by_name(2024, "Monaco Grand Prix", exact_match=True)  # Works
event = get_event_by_name(2024, "monaco grand prix", exact_match=True)  # Works (case-insensitive)
event = get_event_by_name(2024, "MONACO GRAND PRIX", exact_match=True)  # Works (case-insensitive)

# Each of these raises ValueError in exact mode:
# get_event_by_name(2024, "Monaco", exact_match=True)  # Not an exact EventName
# get_event_by_name(2024, "monte carlo", exact_match=True)  # Aliases are not used
# get_event_by_name(2024, "monac", exact_match=True)  # Typo
```

### Exact Matching Algorithm

Exact matching uses simple case-insensitive string comparison:

```python
def exact_match_algorithm(query: str, event_names: list[str]) -> str | None:
    """Find exact match (case-insensitive) in event names."""
    query_lower = query.lower()
    for event_name in event_names:
        if event_name.lower() == query_lower:
            return event_name
    return None  # No match found
```

**Key characteristics:**
- Case-insensitive: `"Monaco"` == `"monaco"` == `"MONACO"`
- Whitespace-sensitive: `"Monaco Grand Prix"` != `"MonacoGrandPrix"`
- No partial matching: `"Monaco"` != `"Monaco Grand Prix"`
- No typo tolerance: `"Monac"` != `"Monaco"`
- O(n) time complexity where n = number of events

## Performance Analysis

The fuzzy matching system is designed for high performance, with careful attention to algorithmic complexity, caching strategies, and optimization techniques. This section provides detailed performance analysis and benchmarking results.

### Time Complexity Analysis

#### Exact Substring Matching (Fast Path)

**Complexity:** O(n × m × k)
- n = number of events (typically 24 for a full F1 season)
- m = features per event (typically 4: location, country, event name, official name)
- k = average feature string length (typically 15-30 characters)

**Typical execution:**
- 24 events × 4 features × 20 chars = 1,920 character comparisons
- Measured: about 0.01-0.03ms

#### Fuzzy Ratio Matching (Slow Path)

**Complexity:** O(n × m) `fuzz.ratio()` calls
- One call for each feature of each candidate event
- Each call compares two short strings in C++

**Typical execution:**
- 24 events × 4 features = 96 calls
- Measured: about 0.07-0.09ms in total

**Optimization:** RapidFuzz is about 70 times faster than the pure Python Levenshtein function in "Performance Comparison with Alternatives".

#### Session Name Lookup

**Complexity:** O(1)
- Dictionary hash table lookup
- Constant time regardless of number of sessions

**Typical execution:** about 0.001ms

### Benchmark Results

#### Test Environment

The numbers on this page come from one run on a Linux workstation with Python 3.14 and RapidFuzz 3.14. Timings change with the machine and its load, so treat them as orders of magnitude.

#### Event Name Matching Benchmarks

```python
import time
from tif1.fuzzy import fuzzy_matcher

# Setup: 24 events, 4 features each (realistic F1 season)
reference = [
    [f"Event {i} Grand Prix", f"Location {i}", f"Country {i}", f"Circuit {i}"]
    for i in range(24)
]

def benchmark(query, iterations=1000):
    start = time.perf_counter()
    for _ in range(iterations):
        fuzzy_matcher(query, reference)
    elapsed = (time.perf_counter() - start) / iterations
    return elapsed * 1000  # Convert to milliseconds

# Benchmark 1: Exact substring match (fast path)
time_exact = benchmark("Location 5")
print(f"Exact substring: {time_exact:.3f}ms")
# Output: Exact substring: 0.032ms

# Benchmark 2: Fuzzy match with typo (slow path)
time_fuzzy = benchmark("Locaton 5")  # Typo: missing 'i'
print(f"Fuzzy matching: {time_fuzzy:.3f}ms")
# Output: Fuzzy matching: 0.084ms

# Benchmark 3: Ambiguous query (multiple substring matches)
time_ambiguous = benchmark("Grand")
print(f"Ambiguous query: {time_ambiguous:.3f}ms")
# Output: Ambiguous query: 0.117ms

# Benchmark 4: Very short query
time_short = benchmark("E")
print(f"Short query: {time_short:.3f}ms")
# Output: Short query: 0.176ms

# Benchmark 5: Very long query
```

### Caching Strategy

#### Event Schedule Caching

Event schedules are memoized per season to avoid repeated file I/O, JSON parsing, and network requests:

```python
def _get_events_cached(year: int) -> tuple[str, ...]:
    """Events as an immutable tuple, memoized per season."""
    return _get_year_schedule(year).events
```

**Benefits:**
- First call: about 3ms for a past season (reads and converts all vendored schedule files once); a live season adds one fetch per `schedule_ttl_hours` window
- Subsequent calls: ~0.001ms (memo hit)
- A live season's memo expires with the TTL, so a long-running process picks up calendar changes

#### Session List Caching

Session lists are also cached per (year, event) combination:

```python
def _get_sessions_cached(year: int, event: str) -> tuple[str, ...]:
    """Resolved session list, memoized per season and queried name."""
    record = _get_year_schedule(year)
    sessions = record.sessions.get(event)
    if sessions is None:
        sessions = tuple(_build_sessions_for_event(year, event))
        record.sessions[event] = sessions
    return sessions
```

**Benefits:**
- First call: about 0.01ms for an exact event name; other names are resolved like `get_event_by_name()` (about 0.5-1ms)
- Subsequent calls: ~0.002ms (memo hit for the same queried name)
- The memo lives on the season record, so a refreshed live schedule drops it with the old events

#### Why Fuzzy Match Results Are NOT Cached

`fuzzy_matcher()` keeps no cache, and `get_event_by_name()` does not cache its result. The reasons:

1. **Matching is already very fast** (about 0.01-0.1ms)
2. **Memory usage would grow** (unlimited query variations)
3. **Cache hit rate would be low** (users rarely repeat exact queries)

**Benchmark comparison:**

```python

```

### Optimization Techniques

#### 1. Early Exit on Exact Match

The algorithm checks for exact substring matches before fuzzy matching:

A unique substring hit returns `(index, True)` before any fuzzy scoring (Stage 2). Only the other queries reach the `fuzz.ratio()` calls (Stage 3).

**Impact:** The fast path took about 0.014ms and the slow path about 0.07-0.09ms in the benchmarks above.

#### 2. Candidate Filtering

When multiple substring matches are found, only those candidates are scored (see the `candidate_indices` lines in Stage 3).

**Impact:** The rows of the other events stay at 0 and are not scored.

#### 3. NumPy Vectorization

`np.max(ratios, axis=1)` replaces a Python loop over the rows (see "Performance Optimization Techniques" in "Detailed Algorithm Walkthrough").

**Impact:** About 8x faster than the loop for a 24×4 array.

#### 4. RapidFuzz C++ Implementation

RapidFuzz computes `fuzz.ratio()` in C++:

```python
# Pure Python Levenshtein: about 0.007ms per call
# RapidFuzz fuzz.ratio(): about 0.0001ms per call
# Speedup: about 70x
```

#### 5. String Normalization In-Place

Normalization writes the normalized strings back into the lists of the caller:

```python
reference = [["Monaco Grand Prix", "Monaco"], ["British Grand Prix", "Silverstone"]]

# In-place modification (current)
for i in range(len(reference)):
    for j in range(len(reference[i])):
        reference[i][j] = reference[i][j].casefold().replace(" ", "")

print(reference)  # [['monacograndprix', 'monaco'], ['britishgrandprix', 'silverstone']]
```

**Impact:** The reference of the caller changes after the call. Pass a copy if the original strings are still needed.

### Performance Best Practices

#### 1. Reuse Reference Data

`fuzzy_matcher()` normalizes the whole reference on every call, also a reference that is already normalized. A pre-normalized reference therefore saves no time. For 24 events, the normalization is a small part of the 0.01-0.1ms per call.

#### 2. Pass the Exact Name When Known

An exact `EventName` resolves before any fuzzy matching, with or without `exact_match=True`:

```python
from tif1.events import get_event_by_name

# Same speed: an exact EventName skips the fuzzy step in both modes

event = get_event_by_name(2024, "Monaco Grand Prix", exact_match=True)   # ~0.08ms

# Slower: a typo goes through the fuzzy step
event = get_event_by_name(2024, "Belgum")  # ~0.3ms
```

#### 3. Cache Session Objects

If loading the same session multiple times, cache the Session object:

Module-level `get_event_by_name()` reads the cached raw schedule and does not build a DataFrame. Use it for lookups by name. `get_event_schedule()` builds the full schedule (a few milliseconds), so call it once when a loop needs the DataFrame:

### Performance Comparison with Alternatives

#### vs. Pure Python Levenshtein

```python
# Pure Python implementation
def levenshtein_python(s1, s2):
    if len(s1) < len(s2):
        return levenshtein_python(s2, s1)
    if len(s2) == 0:
        return len(s1)
    previous_row = range(len(s2) + 1)
    for i, c1 in enumerate(s1):
        current_row = [i + 1]
        for j, c2 in enumerate(s2):
            insertions = previous_row[j + 1] + 1
            deletions = current_row[j] + 1
            substitutions = previous_row[j] + (c1 != c2)
            current_row.append(min(insertions, deletions, substitutions))
        previous_row = current_row
    return previous_row[-1]

# Benchmark
import time

s1, s2 = "monaco grand prix", "monac"

# Pure Python
start = time.perf_counter()
for _ in range(1000):
    levenshtein_python(s1, s2)
time_python = (time.perf_counter() - start) / 1000 * 1000
print(f"Pure Python: {time_python:.3f}ms")
# Output: Pure Python: 0.007ms per call

# RapidFuzz
from rapidfuzz import fuzz
start = time.perf_counter()
for _ in range(1000):
    fuzz.ratio(s1, s2)
time_rapidfuzz = (time.perf_counter() - start) / 1000 * 1000
print(f"RapidFuzz: {time_rapidfuzz:.3f}ms")
# Output: RapidFuzz: 0.000ms per call (about 0.0001ms)

print(f"Speedup: {time_python / time_rapidfuzz:.1f}x")
# Output: Speedup: 71.9x
```

### Summary

The `tif1` fuzzy matching system achieves excellent performance through:

1. **Hybrid algorithm**: Fast exact matching (about 0.01-0.03ms) with fuzzy fallback (about 0.07-0.09ms)
2. **Optimized libraries**: RapidFuzz is about 70x faster than a pure Python Levenshtein function
3. **Caching**: Event schedules and session lists are memoized; fuzzy results are not cached
4. **Algorithmic optimizations**: Early exit, candidate filtering, NumPy vectorization
5. **Scalability**: Linear scaling with events/features, handles 100+ events under 1ms

For typical F1 data access patterns (24 events, 4 features), fuzzy matching adds only about 0.1ms overhead. This is small next to a session load, which reads its data from the network or the cache.

```python
    """
    Load multiple sessions with fuzzy matching and error handling.

    Args:
        year: Championship year
        event_session_pairs: List of (event_name, session_name) tuples

    Returns:
        Dictionary mapping (event, session) to Session object or error
    """
    results = {}

    for event_name, session_name in event_session_pairs:
```

## Error Handling and Debugging

Understanding how to handle errors and debug fuzzy matching issues is important for building reliable applications.

### Common Error Scenarios

#### 1. Event Not Found

A typo resolves to the closest event, with a warning in the log. A name that resembles no event (best fuzzy score below 70) raises `EventNotFoundError`, a `ValueError`. An alias of an event that is not on that calendar raises `EventNotInSeasonError`, a subclass of `EventNotFoundError`:

```python
import tif1

# A typo resolves to the closest event: compare the resolved name with the input
session = tif1.get_session(2024, "Belgum", "Race")
print(f"Resolved to: {session.event_name}")  # Belgian Grand Prix, with a warning in the log

# A name that resembles no event raises
try:
    session = tif1.get_session(2024, "InvalidEventName", "Race")
except tif1.EventNotFoundError as e:
    print(f"Error: {e}")
    # Error: No event matching 'InvalidEventName' in 2024

# An alias of an event that was not held that year raises
try:
    session = tif1.get_session(2021, "Suzuka", "Race")
except tif1.EventNotInSeasonError as e:
    print(f"Error: {e}")
    # Error: 'Suzuka' refers to the Japanese Grand Prix, which is not on the 2021 calendar

    # Show available events for the year
    events = tif1.get_event_schedule(2021, include_testing=False)
    print(f"\nAvailable events for 2021:")
    for event in events["EventName"]:
        print(f"  - {event}")
```

**Common causes:**
- The name resembles no event of that year (`EventNotFoundError`)
- The alias names an event that is not on the calendar of that year (`EventNotInSeasonError`)
- A typo close to another event name, so fuzzy matching picks a different event (check `session.event_name`)
- Year is outside the schedule data (2018-2026 ship with `tif1`), and the name is an alias

## Implementation Details

This section provides deep technical insights into the fuzzy matching implementation. Developers can use it to understand or extend the system.

### RapidFuzz Integration

`tif1` uses RapidFuzz for high-performance fuzzy string matching. RapidFuzz is a C++ implementation of various string matching algorithms with Python bindings.

#### Why RapidFuzz?

1. **Performance**: about 70x faster than the pure Python Levenshtein function on this page
2. **Standard metrics**: Levenshtein and Indel distances (`fuzz.ratio()` uses the Indel distance)
3. **Reliability**: Well-tested, widely used library
4. **Compatibility**: Pure Python fallback available

#### Levenshtein Distance Algorithm

The classic way to compute the Levenshtein distance is the Wagner-Fischer dynamic program below. RapidFuzz uses faster algorithms in C++ that give the same results:

```python
def levenshtein_distance(s1: str, s2: str) -> int:
    """
    Compute Levenshtein distance using dynamic programming.

    Time complexity: O(m×n) where m, n are string lengths
    Space complexity: O(m×n) for full matrix, O(min(m,n)) optimized
    """
    m, n = len(s1), len(s2)

    # Create distance matrix
    dp = [[0] * (n + 1) for _ in range(m + 1)]

    # Initialize base cases
    for i in range(m + 1):
        dp[i][0] = i  # Deletions
    for j in range(n + 1):
        dp[0][j] = j  # Insertions

    # Fill matrix
    for i in range(1, m + 1):
        for j in range(1, n + 1):
            if s1[i-1] == s2[j-1]:
                dp[i][j] = dp[i-1][j-1]  # No operation needed
            else:
                dp[i][j] = 1 + min(
                    dp[i-1][j],      # Deletion
                    dp[i][j-1],      # Insertion
                    dp[i-1][j-1]     # Substitution
                )

    return dp[m][n]

# Example
distance = levenshtein_distance("monaco", "monac")
# Returns: 1 (one deletion)
```

#### RapidFuzz Optimizations

RapidFuzz runs compiled C++ code, which is much faster than Python. `fuzz.ratio()` also accepts a `score_cutoff` that stops the computation early. `tif1` does not pass one, so every score is computed in full.

### Caching Strategy Details

#### Schedule Memo Implementation

The season memo is a plain dictionary keyed by year. A lock guards the writes. `_load_schedule_payload()` reads the vendored schedule files once and keeps them with `@lru_cache(maxsize=1)`:

```python
def _get_events_cached(year: int) -> tuple[str, ...]:
    """
    Memo structure:
    - Hash table: {year: _YearSchedule(payload, events, expires_at, sessions)}
    - expires_at: math.inf for a vendored past season; fetch time plus
      schedule_ttl_hours for a live season
    - No eviction: a handful of seasons per process
    """
    return _get_year_schedule(year).events
```

#### Why Not Cache Fuzzy Match Results?

Caching fuzzy match results would require:

```python
from functools import lru_cache

from tif1.fuzzy import fuzzy_matcher

@lru_cache(maxsize=1000)
def fuzzy_matcher_cached(query: str, reference_tuple: tuple) -> tuple[int, bool]:
    # Convert tuple back to list
    reference = [list(features) for features in reference_tuple]
    return fuzzy_matcher(query, reference)
```

**Problems:**

1. **Reference must be hashable**: Requires converting list to tuple on every call
2. **Low hit rate**: Users rarely repeat exact queries
3. **Memory usage**: Unlimited query variations could fill memory
4. **Marginal benefit**: Matching is already fast (about 0.01-0.1ms)

**Benchmark:**

```python

```

### NumPy Integration

The fuzzy matcher uses NumPy for vectorized operations:

### Thread Safety

The fuzzy matching system is thread-safe with caveats:

#### Thread-Safe Components

1. **Schedule memo**: A lock (`_year_schedules_lock`) guards the writes; reads are plain dictionary lookups
2. **RapidFuzz functions**: Thread-safe (no shared state)
3. **NumPy operations**: Thread-safe (operates on local arrays)
4. **`get_event_by_name()` and `get_session()`**: Each call builds a new reference list, so threads do not share one

#### Non-Thread-Safe Components

1. **In-place normalization**: Modifies reference list in-place. This matters only when threads pass the same list to `fuzzy_matcher()`

```python
# This modifies the reference list
for i in range(len(reference)):
    for j in range(len(reference[i])):
        reference[i][j] = reference[i][j].casefold().replace(" ", "")
```

**Solution for multi-threaded use:**

```python
import copy

from tif1.fuzzy import fuzzy_matcher

def fuzzy_matcher_threadsafe(query: str, reference: list[list[str]]) -> tuple[int, bool]:
    """Thread-safe version that copies reference."""
    reference_copy = copy.deepcopy(reference)
    return fuzzy_matcher(query, reference_copy)
```

### Extension Points

`fuzzy_matcher()` has no parameters for a different scorer or a different normalization. These are the options for custom use cases:

#### Custom Similarity Metrics

`fuzzy_matcher()` always uses `fuzz.ratio()`. For another scorer, call RapidFuzz directly:

```python

```

#### Custom Normalization

`fuzzy_matcher()` normalizes with `casefold()` and space removal. Normalize the query and the reference before the call to apply stricter rules:

```python
from tif1.fuzzy import fuzzy_matcher

def aggressive_normalize(s: str) -> str:

    return ''.join(c for c in s.casefold() if c.isalnum())

reference = [["Spa-Francorchamps", "Belgium"], ["Monza", "Italy"]]
```

## Summary and Key Takeaways

The `tif1` fuzzy matching system is a high-performance solution for resolving Formula 1 event and session names. Here are the key points:

### Core Concepts

1. **Hybrid Algorithm**: Combines fast exact substring matching (about 0.01-0.03ms) with fuzzy ratio matching (about 0.07-0.09ms)
2. **Multi-Feature Matching**: Each event described by multiple features (location, country, event name, official name) for maximum flexibility
3. **Dictionary-Based Sessions**: Session names use O(1) dictionary lookup (&lt;0.01ms) rather than fuzzy matching
4. **Transparent Results**: Returns both match result and exact/fuzzy flag for validation and logging

### Performance Characteristics

- **Event matching**: 0.1-0.3ms per name lookup, well under 1ms
- **Session matching**: about 0.001ms (dictionary lookup)
- **Scalability**: Linear O(n) with number of events, handles 100+ events under 1ms
- **Caching**: Event schedules and session lists memoized, fuzzy results not cached
- **Optimization**: RapidFuzz is about 70x faster than a pure Python Levenshtein function

### Usage Guidelines

1. **Use fuzzy matching for user input**: Provides best UX, handles typos and variations
2. **Use exact matching for validation**: Ensures data integrity in production systems
3. **Log fuzzy matches**: Track what users are typing for analytics and debugging
4. **Provide helpful errors**: Show available options when matching fails
5. **Cache Session objects**: Reuse loaded sessions to avoid repeated data fetching

### Best Practices

- **Interactive use**: Fuzzy matching (Monaco, Spa, Q, FP1)
- **Production code**: Exact matching with validation
- **Configuration files**: Use exact official names
- **API endpoints**: Exact matching, or fuzzy matching with the resolved name in the response
- **Testing**: Exact matching to catch errors early

### Common Pitfalls

1. **Using P1/P2/P3 instead of FP1/FP2/FP3**: Not supported, use FP abbreviations
2. **Assuming all events have all sessions**: Sprint weekends have different formats
3. **Not handling fuzzy match warnings**: Check logs for unexpected matches
4. **Caching fuzzy results**: Matching takes well under 1ms, so a cache gains little
5. **Thread safety**: Do not share one reference list between threads: `fuzzy_matcher()` changes it in place

### When to Use What

| Scenario | Fuzzy Match | Exact Match | Rationale |
|----------|-------------|-------------|-----------|
| Jupyter notebook | ✅ | ❌ | User convenience |
| CLI tool | ✅ | ❌ | Typing speed |
| Web API | ❌ | ✅ | Explicit contracts |
| Config files | ❌ | ✅ | Clarity |
| Unit tests | ❌ | ✅ | Catch errors |
| Production pipeline | ❌ | ✅ | Predictability |
