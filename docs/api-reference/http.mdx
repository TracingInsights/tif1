## Overview

The HTTP and networking layer is the foundation of `tif1`'s data fetching infrastructure. It is engineered for performance, reliability, and resilience. It loads Formula 1 telemetry and session data from remote CDN sources. Cold starts can require fetching 100+ telemetry files in parallel.

The networking layer is optimized for the patterns of F1 data access. These patterns include high-concurrency parallel fetching, connection reuse, retry strategies, and graceful degradation under failure conditions. A full session (20 drivers × 50+ laps) yields 1000+ telemetry files.

### Architecture Philosophy

The networking layer is built on four core principles that guide every design decision:

1. **Performance First**: Every design decision prioritizes speed and throughput. Connection pooling removes the TCP and TLS handshakes from reused connections. HTTP/2 multiplexing allows multiple requests over a single connection. JSON parsing uses `orjson`, which is faster than the standard library parser.

2. **Resilience by Design**: Network failures are expected, not exceptional. The circuit breaker pattern prevents cascading failures by blocking requests during sustained outages. Exponential backoff with jitter reduces load on failing services while allowing recovery. Multi-CDN fallback ensures graceful degradation when primary sources fail. The system can tolerate complete CDN failures. It recovers automatically when services come back online.

3. **Resource Efficiency**: The thread pool is sized from the concurrency settings, open connections are reused, and the cache avoids repeat downloads. The connection pool (at least 256 connections) is larger than the default concurrency caps.

4. **Observability**: Metrics for connection reuse, circuit breaker state, and CDN health support monitoring and debugging. Periodic logging of the connection counters needs no manual instrumentation.

### Key Components

The networking stack provides a complete set of features:

#### 1. High-Performance HTTP Session Management

The session layer uses `niquests` (a modern fork of `requests` with HTTP/2 and HTTP/3 support) with aggressive connection pooling and reuse strategies:

- **Dynamic Connection Pooling**: Pool size automatically scales based on configured concurrency. The minimum is 256 connections, up to 512+ for burst handling
- **Keep-Alive Headers**: Every request sends `Keep-Alive` values from `keepalive_timeout` (default: 120s) and `keepalive_max_requests` (default: 10000)
- **HTTP/2 and HTTP/3 Support**: HTTP/2 with multiplexing by default; HTTP/3 only when `http_disable_http3` is `False`
- **DNS-over-HTTPS (DoH) Resolvers**: The `http_resolvers` list can name Cloudflare and Google DoH resolvers. tif1 moves to the next entry only when building the session with an entry fails
- **Thread-Safe Creation**: Session creation and closing run under a lock
- **Connection Reuse Metrics**: Request counters with a reuse rate

#### 2. Async Parallel Fetching

Built on Python's `asyncio` with thread pool executors for maximum concurrency:

- **Concurrent Request Handling**: Fetch 20-128+ files simultaneously (configurable based on workload)
- **Thread Pool Optimization**: Shared executor with worker count matching concurrency requirements
- **Process Pool JSON Parsing**: Optional multi-process JSON parsing for non-telemetry payloads (off by default; `json_parse_workers`)
- **Semaphore-Based Rate Limiting**: Automatic concurrency control to prevent CDN throttling
- **Graceful Error Handling**: Failed requests return `None` instead of crashing, enabling partial data loading

#### 3. Retry Logic

The retry mechanism uses exponential backoff, jitter, and multi-CDN fallback:

- **Configurable Retry Count**: Default 3 tries per request, the first one included. Zero-retry mode (one try) gives the fastest cold starts
- **Exponential Backoff**: Delay increases exponentially (2^attempt seconds) with configurable factor
- **Jitter Support**: On the async path, random jitter of up to `retry_jitter_max` seconds prevents thundering herd problems (the default `0.0` adds no jitter). The sync retry path scales each delay by a random factor from 0.5 to 1.5 when `retry_jitter` is on
- **Max Delay Cap**: Configurable maximum delay (default: 60s) prevents excessive wait times
- **CDN Fallback**: Automatically tries all configured CDN sources before failing
- **Smart Error Classification**: Distinguishes between retryable errors (5xx, timeouts) and fatal errors (404, validation failures)
- **Pool Exhaustion Handling**: Automatic backoff when connection pool is exhausted (0.01-0.5s with jitter by default)

#### 4. Circuit Breaker Pattern

Prevents cascading failures and protects against sustained network issues:

- **Failure Threshold**: Opens after 5 consecutive failures (configurable)
- **Timeout Period**: Blocks requests for 60 seconds when open (configurable)
- **Half-Open State**: After the timeout, requests go through again; a success closes the breaker and a failure opens it again
- **Thread-Safe State Transitions**: Atomic state changes using reentrant locks
- **Monotonic Time Tracking**: Uses `time.monotonic()` for accurate timeout tracking
- **Protected Paths**: Async fetches and the sync retry path check the breaker. The sync zero-retry path and `PayloadLoader.get_url()` do not

#### 5. Multi-CDN Fallback System

Reliable CDN management with automatic failover, health tracking, and optional minification:

- **Multiple CDN Support**: Configure multiple CDN sources with priority ordering via `cdns` config array
- **Automatic Failover**: Switches to backup CDNs on failure without user intervention
- **Health Tracking**: Tracks failure counts per CDN, automatically disables after 3 consecutive failures
- **jsDelivr Primary**: jsDelivr is the primary CDN. Hugging Face buckets are the fallback, and StaticDelivr is the last-resort backup
- **URL Formatting**: Automatic URL construction for TracingInsights data repositories (StaticDelivr: `{cdn_base}/{year}/main/{gp}/{session}/{path}`, jsDelivr: `{cdn_base}/{year}@main/{gp}/{session}/{path}`, Hugging Face: `{cdn_base}/{year}/resolve/{gp}/{session}/{path}`)
- **Dynamic Enable/Disable**: CDNs can be dynamically disabled based on error patterns (for example, HTTP/2 multiplexing incompatibility after redirects)
- **Minification for custom mirrors**: `cdn_use_minification` requests `file.min.json` from custom mirrors that serve minified copies. The default CDNs ignore it, because none of them serves `.min.json` files
- **Failure Recovery**: A successful request resets the failure count of that CDN. A CDN with 3 failures is no longer tried, so only `reset()` or `reload()` brings it back
- **Priority Ordering**: CDNs are tried in priority order (lower priority number = higher precedence)

**CDN Configuration:**

The default CDN configuration uses jsDelivr as the primary source. Hugging Face buckets are the fallback, and StaticDelivr is a last-resort backup:

```json
{
  "cdns": [
    "https://cdn.jsdelivr.net/gh/TracingInsights",
    "https://huggingface.co/buckets/tracinginsights",
    "https://cdn.staticdelivr.com/gh/TracingInsights"
  ],
  "cdn_use_minification": false
}
```

Configure multiple CDNs for redundancy:

```json
{
  "cdns": [
    "https://cdn.jsdelivr.net/gh/TracingInsights",
    "https://your-custom-cdn.com/TracingInsights"
  ],
  "cdn_use_minification": true
}
```

**Minification Benefits:**

`cdn_use_minification` only affects custom mirrors listed in `cdns`. For such a mirror, JSON files are requested in minified form:
- Original: `https://mirror.example.com/tif1/2024@main/Bahrain%20Grand%20Prix/Race/VER/laptimes.json`
- Minified: `https://mirror.example.com/tif1/2024@main/Bahrain%20Grand%20Prix/Race/VER/laptimes.min.json`

jsDelivr minifies only JavaScript and CSS, and Hugging Face and StaticDelivr mirror the repository as it is. A `.min.json` request answers 404 on all three, so tif1 never sends one there. The option is off by default.

**CDN Health Management:**

The CDN manager tracks failures per source and automatically disables CDNs that fail repeatedly:

```python
from tif1.cdn import get_cdn_manager

cdn_manager = get_cdn_manager()

# Check available CDNs
sources = cdn_manager.get_sources()
for source in sources:
    print(f"{source.name}: enabled={source.enabled}, priority={source.priority}")

# Reset failure counts (useful after network recovery)
cdn_manager.reset()
```

**Unsupported CDNs:**

The following CDN sources are explicitly blocked due to rate limiting or compatibility issues:
- `raw.githubusercontent.com` - GitHub's raw content CDN has aggressive rate limiting (60 requests/hour for unauthenticated users). The one request tif1 makes there on purpose is the live season's `schedule_{year}.json` in `tif1.events`, outside the CDN chain and cached for `schedule_ttl_hours`

Always use a proper CDN like jsDelivr that is designed for high-volume content delivery.

#### 6. Rate Limiting and Concurrency Control

Prevents CDN throttling and manages resource consumption:

- **Configurable Concurrency**: Default 22 concurrent requests, and 32 for telemetry prefetch (configurable to 128+)
- **Semaphore-Based Control**: Async semaphores limit concurrent operations
- **Per-Operation Limits**: Different limits for different workloads (lap data vs telemetry)
- **Backoff on Exhaustion**: Automatic short backoff when the connection pool reports exhaustion

#### 7. Performance Monitoring

Real-time metrics for optimization and debugging:

- **Connection Reuse Tracking**: Monitor connection pool efficiency (reuse rate, total requests, pools created)
- **Periodic Logging**: Automatic statistics logging at configurable intervals (default: 60s)
- **Circuit Breaker State**: Inspect current state (closed, open, half-open) and failure counts
- **CDN Health Metrics**: Track per-CDN failure counts and enabled status

### Use Cases and Optimizations

The networking layer is specifically optimized for F1 data loading scenarios:

#### Cold Start Optimization (100+ Telemetry Files)

When loading a session for the first time, `tif1` may need to fetch 100+ telemetry files in parallel:

- **High Concurrency**: 32 concurrent requests during telemetry prefetch by default (configurable to 128+)
- **Connection Reuse**: Persistent connections skip the TCP and TLS handshakes
- **HTTP/2 Multiplexing**: Multiple requests over single connection reduce latency
- **Zero-Retry Mode**: Tries each CDN once without delays. `ultra_cold_skip_retries` (default: `True`) turns it on for the cold-start path
- **Process Pool Parsing**: Optional multi-process JSON parsing for non-telemetry payloads. Telemetry always parses in threads because of IPC overhead

#### Large JSON Payloads (Lap Data, Telemetry Arrays)

Lap and telemetry data can contain thousands of data points:

- **Fast JSON Parsing**: Uses `orjson` on the raw response bytes
- **Raw Cache Writes**: An unchanged payload is stored as the original bytes, without a new serialization
- **Validation Pipeline**: Optional payload validation (disabled by default for performance)
- **Cache Integration**: Parsed data automatically cached to avoid re-fetching

#### Network Failure Scenarios

Graceful degradation when CDN sources fail or network is unstable:

- **Multi-CDN Fallback**: Automatically tries backup CDNs (jsDelivr → Hugging Face buckets → StaticDelivr)
- **Circuit Breaker Protection**: Prevents cascading failures by blocking requests during sustained outages
- **Exponential Backoff**: Reduces load on failing services while allowing recovery
- **Partial Data Loading**: Failed requests return `None`, allowing successful data to be used

#### Resource-Constrained Environments

Optimizations for limited bandwidth or CPU:

- **Configurable Concurrency**: Reduce concurrent requests (5-10) for slow connections
- **Connection Pool Sizing**: Adjust pool size based on available resources
- **Timeout Configuration**: Increase timeouts (60s+) for slow networks
- **Minification for custom mirrors**: `cdn_use_minification` applies only to mirrors that serve `.min.json` copies

### Thread Safety and Resource Management

All networking components are designed for safe concurrent use:

- **Thread-Safe Sessions**: HTTP session creation and closing run under a lock
- **Reentrant Locks**: Circuit breaker uses reentrant locks for nested call support
- **Atomic State Transitions**: Circuit breaker state changes run under its lock. CDN failure counters use no lock (see the [CDN API](/api-reference/cdn))
- **Automatic Cleanup**: Resources automatically released via `atexit` handlers
- **Graceful Shutdown**: Executors and sessions properly closed on program exit

### Configuration

The networking layer is configurable via environment variables or `.tif1rc` file. All networking-related settings can be tuned for each specific use case, from ultra-fast cold starts to resource-constrained environments.

**Configuration File Location:**

The `.tif1rc` file is a JSON configuration file that can be placed in:
1. Path specified by `TIF1_CONFIG_FILE` environment variable (highest priority)
2. Current working directory (if `TIF1_TRUST_CWD_CONFIG=true`)
3. Home directory (`~/.tif1rc`) (default location)

tif1 reads the first of these files that exists. Environment variables override the file values.

**Configuration Options Explained:**

**Basic HTTP Settings:**
- `timeout` (int, default: 30): Request timeout in seconds. Increase for slow connections or large files.
- `max_retries` (int, default: 3): Total tries for each request, including the first. Each try walks every CDN. Set to 1 (or 0) for zero-retry mode (one try).
- `max_workers` (int, default: 20): Thread pool size for async operations. The executor is sized as the max of `max_workers` and the concurrency caps (`max_concurrent_requests`, telemetry prefetch).

**Retry Strategy:**
- `retry_backoff_factor` (float, default: 2.0): Exponential backoff multiplier. Delay = factor^attempt seconds.
- `retry_jitter` (bool, default: true): Add random jitter to backoff delays to prevent thundering herd.
- `retry_jitter_max` (float, default: 0.0): Maximum jitter in seconds on the async path (random value between 0 and this). The default adds no jitter there.
- `max_retry_delay` (float, default: 60.0): Maximum backoff delay in seconds (caps exponential growth).

**Circuit Breaker:**
- `circuit_breaker_threshold` (int, default: 5): Number of consecutive failures before opening circuit.
- `circuit_breaker_timeout` (int, default: 60): Seconds to wait before testing recovery (half-open state).

**Connection Pooling:**
- `pool_connections` (int, default: not set): Number of connection pools to maintain. If not set, tif1 uses the largest concurrency setting, with a minimum of 256.
- `pool_maxsize` (int, default: not set): Maximum connections per pool. If not set, tif1 uses 4x `pool_connections` (1024 with the defaults). The minimum is 512.
- `keepalive_timeout` (int, default: 120): Timeout in seconds sent in the `Keep-Alive` request header.
- `keepalive_max_requests` (int, default: 10000): Request limit sent in the `Keep-Alive` request header.

**Concurrency Control:**
- `max_concurrent_requests` (int, default: 22): Maximum concurrent HTTP requests for general operations.
- `telemetry_prefetch_max_concurrent_requests` (int, default: 32): Maximum concurrent requests for telemetry prefetch.

**Protocol Configuration:**
- `http_multiplexed` (bool, default: true): Enable HTTP/2 multiplexing for reduced latency.
- `http_disable_http3` (bool, default: true): HTTP/2 over TCP is the default. Set it to `false` to negotiate HTTP/3.
- `http_resolvers` (array, default: ["standard", "doh+cloudflare://", "doh+google://"]): Resolvers to try in order when tif1 builds the session.

**CDN Configuration:**
- `cdns` (array, default: jsDelivr, Hugging Face buckets, StaticDelivr): CDN sources in priority order.
- `cdn_use_minification` (bool, default: false): Request `.min.json` files from custom mirrors. The default CDNs ignore it.

**Pool Exhaustion Handling:**
- `pool_exhaustion_backoff_base` (float, default: 0.01): Base backoff delay in seconds when pool is exhausted.
- `pool_exhaustion_backoff_max` (float, default: 0.5): Maximum backoff delay in seconds for pool exhaustion.
- `pool_exhaustion_backoff_jitter` (float, default: 0.01): Maximum random jitter in seconds for pool exhaustion backoff.

**Advanced Performance:**
- `json_parse_workers` (int, default: 0): Number of worker processes for JSON parsing. 0 = disabled (recommended for telemetry).
- `connection_stats_log_interval` (float, default: 60.0): Seconds between automatic connection stats logging.

## HTTP Session Management

The HTTP session layer provides a shared `niquests.Session` instance with optimized configuration for F1 data fetching. The session is lazily initialized on first use and automatically cleaned up on program exit.

### `get_session`

Get or create the global HTTP session instance with connection pooling and a configurable resolver list.

```python
def get_session() -> niquests.Session
```

This function implements a thread-safe singleton pattern, ensuring only one session instance exists across the entire application. The session is configured with:

**Connection Pooling:**
- Dynamic pool sizing based on configured concurrency levels
- Minimum 256 connections for optimal performance
- Maximum pool size of 512+ for burst handling
- Non-blocking pool behavior (pool_block=False) to prevent deadlocks

**Keep-Alive Headers:**
- `Connection: keep-alive` and `Keep-Alive: timeout=120, max=10000` on every request
- Configurable via `keepalive_timeout` and `keepalive_max_requests`
- The server decides how long it keeps a connection open

**DNS Resolution:**
- Default list: system DNS (`standard`), then Cloudflare DoH (`doh+cloudflare://`), then Google DoH (`doh+google://`)
- Configurable via `http_resolvers` config option (array of resolver strings)
- tif1 builds the session with the first entry. It moves to the next entry only when building the session with an entry raises an error
- A failed DNS lookup during a request does not switch the resolver. With the default list, tif1 uses system DNS
- tif1 hands the chosen resolver to the `HTTPAdapter` that it mounts on `https://`, so HTTPS requests use it

**Configuring DNS Resolvers:**

Customize the DNS resolver order in the `.tif1rc` file:

```json
{
  "http_resolvers": ["standard", "doh+cloudflare://", "doh+google://"]
}
```

Or via environment variable:

```bash
export TIF1_HTTP_RESOLVERS="standard,doh+cloudflare://,doh+google://"
```

Valid resolver values:
- `"standard"`, `"default"`, `"none"`, or `""` - Use system DNS
- `"doh+cloudflare://"` - Cloudflare DNS-over-HTTPS (1.1.1.1)
- `"doh+google://"` - Google DNS-over-HTTPS (8.8.8.8)

tif1 tries each resolver in order until a session builds. If building fails with every resolver, a `NetworkError` is raised. The older spelling `doh://cloudflare` is translated to `doh+cloudflare://`.

**Protocol Support:**
- **HTTP/2 with multiplexing** (configurable via `http_multiplexed`, default: `true`)
  - Multiple requests over a single TCP connection
  - Reduces latency by eliminating TCP handshake overhead
  - Header compression reduces bandwidth usage
  - Automatic protocol negotiation via ALPN
- **HTTP/3 support** (off by default; set `http_disable_http3` to `false` to negotiate it)
  - QUIC-based protocol (UDP)
  - Automatic fallback to HTTP/2 if HTTP/3 is unavailable
- **Automatic protocol negotiation**
  - Client and server negotiate the best available protocol
  - Transparent fallback from HTTP/3 → HTTP/2 → HTTP/1.1

**HTTP/2 Multiplexing Benefits:**

HTTP/2 multiplexing improves F1 data loading in several ways:
- **Fewer Connections**: Many requests to a CDN share one TCP connection
- **No Head-of-Line Blocking at the HTTP level**: Slow responses do not block fast ones
- **Reduced Latency**: Fewer TCP and TLS handshakes
- **Lower Resource Usage**: Fewer file descriptors and socket buffers

**Multiplexing Compatibility:**

Some CDNs have issues with HTTP/2 multiplexing after redirects. On the async fetch path, an error like `"non-multiplexed response after a redirect"` disables the CDN automatically. Multiplexing can also be disabled manually:

```json
{
  "http_multiplexed": false
}
```

Or via environment variable:

```bash
export TIF1_HTTP_MULTIPLEXED=false
```

**HTTP/3 Considerations:**

HTTP/3 (QUIC) is off by default. In interleaved live A/Bs of the bulk telemetry fetch, HTTP/2 over TCP was at parity or faster, and every stalled fetch observed ran over HTTP/3. To negotiate HTTP/3 again:

```json
{
  "http_disable_http3": false
}
```

Or via environment variable:

```bash
export TIF1_HTTP_DISABLE_HTTP3=false
```

**Performance Optimizations:**
- `trust_env=False` to skip environment lookups on every request. The session therefore ignores proxy variables (such as `HTTPS_PROXY`) and `.netrc` files
- `Connection: keep-alive` and `Keep-Alive` headers on every request
- Connection reuse tracking for monitoring

**Returns:**
- Shared `niquests.Session` instance (lazily initialized)

**Raises:**
- `NetworkError`: If session creation fails with all configured DNS resolvers

**Thread Safety:**
- Uses double-checked locking pattern for safe concurrent initialization
- Multiple threads can safely call `get_session()` simultaneously
- tif1 sends requests on the shared session from its worker threads

**Example:**
```python
from tif1.http_session import get_session

# Get shared session (thread-safe)
session = get_session()

# Make requests (connection automatically reused)
response1 = session.get("https://cdn.jsdelivr.net/gh/TracingInsights/2024@main/Bahrain%20Grand%20Prix/Race/drivers.json")
response2 = session.get("https://cdn.jsdelivr.net/gh/TracingInsights/2024@main/Bahrain%20Grand%20Prix/Race/VER/laptimes.json")

# Connections are automatically reused between requests
data1 = response1.json()
data2 = response2.json()
```

<Note>
  The HTTP session is automatically managed. Direct interaction is rarely needed. The async fetch layer handles all session management internally.
</Note>

<Warning>
  Do not close the session manually while other code still uses it. The session is shared across the entire application and automatically cleaned up on program exit.
</Warning>

### `close_session`

Close the global HTTP session and release all connections.

```python
def close_session() -> None
```

This function performs a graceful shutdown of the HTTP session, closing all active connections and releasing resources. It is automatically registered with `atexit` for cleanup on program exit, so manual calls are rarely necessary.

**Behavior:**
- Closes all connections in the connection pool
- Releases socket file descriptors
- Clears internal session state
- Thread-safe with lock protection
- Idempotent (safe to call multiple times)

**When to Use:**
- Testing scenarios that need a reset of session state
- Long-running applications that need to free resources
- Before forking processes (to avoid sharing file descriptors)

**Example:**
```python
from tif1.http_session import close_session
import atexit

# Automatic cleanup on program exit (already registered by default)
atexit.register(close_session)

# Manual cleanup (rarely needed)
close_session()
```

<Note>
  Session cleanup is automatically registered with `atexit`, so manual cleanup is usually unnecessary. The session closes properly when the program exits.
</Note>

### `get_connection_stats`

Get current connection pool statistics for monitoring, debugging, and optimization.

```python
def get_connection_stats() -> dict[str, Any]
```

This function provides metrics about connection pool usage. The metrics show how effectively connections are reused. A low rate after many requests can point to a pool or concurrency problem.

**Returns:**

Dictionary with the following metrics:

- `total_requests` (int): Number of payload requests that tif1 sent through the shared session since process start (or the last reset)
- `connections_reused` (int): Number of those requests that used an open pooled connection
- `connections_created` (int): Number of shared sessions created (typically 1)
- `reuse_rate` (float): Percentage of requests that reused connections (0-100)

**Reuse Rate Interpretation:**
- **90-100%**: Excellent - optimal connection reuse
- **70-90%**: Good - most connections are reused
- **50-70%**: Fair - some optimization possible
- **&lt;50%**: Poor - check pool configuration or request patterns

<Note>
  tif1 counts a request as reused when niquests reports no connection or TLS handshake time for it (`response.conn_info`). `connections_created` counts session creations, not TCP connections. Requests sent directly with `get_session().get()` are not counted.
</Note>

**Example:**


## Async Parallel Fetching

The async fetch module provides high-performance parallel data loading. It uses Python's `asyncio` with thread pool executors and optional process pool JSON parsing. This layer is optimized for F1 data loading patterns. Cold starts may require fetching 100+ telemetry files at once.

### Architecture

The async fetch system uses a multi-layered architecture:

1. **Async Coordination Layer**: `asyncio` manages concurrent operations and task scheduling
2. **Thread Pool Executor**: Handles blocking I/O operations (HTTP requests, file I/O, JSON parsing)
3. **Process Pool Executor**: Optional multi-process JSON parsing for large payloads (configurable via `json_parse_workers`)
4. **HTTP Session Layer**: Shared `niquests.Session` with connection pooling and reuse
5. **Cache Integration**: Automatic cache reads/writes with memory and SQLite tiers

### `fetch_json_async`

Asynchronously fetch and parse JSON data with caching, retry logic, CDN fallback, and validation.

```python
async def fetch_json_async(
    year: int,
    gp: str,
    session: str,
    path: str,
    max_retries: int | None = None,
    timeout: int | None = None,
    *,
    use_cache: bool = True,
    write_cache: bool = True,
    validate_payload: bool = True
) -> dict[str, Any]
```

This is the core async fetching function behind the parallel data loading in `tif1`. Single session tables also load through the sync `PayloadLoader` path. It implements a multi-stage pipeline optimized for performance and reliability.

**Pipeline Stages:**

1. **Cache Lookup**: Checks the in-memory cache first, then the SQLite cache. A recent "missing on every CDN" verdict raises `DataNotFoundError` here
2. **Network Fetch**: Tries primary CDN (jsDelivr), falls back to Hugging Face buckets, then StaticDelivr on failure
3. **JSON Parsing**: Uses `orjson` for fast parsing, optional process pool for non-telemetry payloads
4. **Validation**: Optional payload validation (non-strict mode allows partial data), off unless a `validate_*` config flag is on
5. **Cache Write**: Persists the payload to the SQLite cache for fast subsequent access

**Zero-Retry Mode**: When `max_retries` is 1 (or 0), the function tries each CDN once without delays. This mode suits fast startup when occasional transient failures are acceptable.

**Pool Exhaustion Handling**: On pool exhaustion, tif1 waits a short backoff (0.01-0.5s with jitter by default). The fetch then moves on to the next CDN. This prevents cascading failures.

**Parameters:**

- `year` (int): Season year (for example, 2024)
- `gp` (str): Grand Prix name (for example, "Bahrain Grand Prix")
- `session` (str): Exact session name (for example, "Race", "Qualifying", "Practice 1", "Sprint")
- `path` (str): Path to JSON file relative to session directory
  - Driver list: `"drivers.json"`
  - Lap data: `"session_laptimes.json"` (all drivers), `"VER/laptimes.json"`, `"HAM/laptimes.json"`, etc.
  - Telemetry: `"VER/1_tel.json"` (`{driver}/{lap}_tel.json` format)
  - Weather: `"weather.json"`
  - Race control: `"rcm.json"`
- `max_retries` (int | None): Total tries for each request, including the first
  - Default: Uses `max_retries` config value (typically 3)
  - Set to 1 for zero-retry mode (ultra-fast cold start, tries each CDN once); 0 behaves the same here
  - Set to 5+ for unreliable networks
  - The wait between tries uses exponential backoff, plus optional jitter
- `timeout` (int | None): Request timeout in seconds
  - Default: Uses `timeout` config value (typically 30)
  - Increase to 60+ for slow connections or large files
  - Applies per-request, not total operation time
  - Timeout triggers retry with next CDN
- `use_cache` (bool): If True, read from cache before network fetch
  - Default: True
  - Set to False to force fresh fetch (bypasses cache read entirely)
  - Automatically False in CI mode (`ci_mode=True`)
  - Cache lookup checks memory first, then SQLite
- `write_cache` (bool): If True, persist successful network responses to cache
  - Default: True
  - Set to False for ephemeral data (testing, one-time queries)
  - Automatically False in CI mode (`ci_mode=True`)
  - Writes to the SQLite cache (persistent across processes)
- `validate_payload` (bool): If True, run payload validation before returning data
  - Default: True
  - Validation runs only when the `validate_data`, `validate_lap_times`, or `validate_telemetry` config flag for that payload is `True`; all three default to `False`
  - Validation is non-strict (allows missing optional fields)
  - Validates race control, weather, lap times, and telemetry based on file path (`drivers.json` is not validated)
  - Sanitizes telemetry payloads (removes validator-only defaults that break DataFrame construction)

**Returns:**
- Parsed JSON data as dictionary (never None, raises on error)
- Dictionary structure depends on file type:
  - `drivers.json`: `{"drivers": [{"driver": "VER", "dn": "1", "fn": "Max", "ln": "Verstappen", "team": "Red Bull Racing", ...}, ...]}`
  - `*/laptimes.json`, `session_laptimes.json`: `{"lap": [...], "time": [...], "s1": [...], "compound": [...], ...}`
  - `*_tel.json`: `{"tel": {"time": [...], "speed": [...], "rpm": [...], "distance": [...], ...}}`
  - `weather.json`: `{"wT": [...], "wAT": [...], "wTT": [...], ...}`
  - `rcm.json`: `{"time": [...], "cat": [...], "msg": [...], "flag": [...], ...}`

  Payload keys are short CDN names. `Session` renames them to the DataFrame columns (`LapNumber`, `AirTemp`, ...).

**Raises:**

- `NetworkError`: If network request fails after all retries and CDN fallbacks
  - Includes URL and status code (if available) for debugging
  - Raised when all CDNs fail or circuit breaker is open
  - Check circuit breaker state and CDN health if this occurs frequently
- `DataNotFoundError`: If data does not exist (every CDN refused it with a 4xx status other than 408 or 429, such as 404)
  - Includes year, event, and session for context
  - Not retried (404 is a fatal error indicating missing data)
  - Common for sessions that have not been run yet or invalid driver codes
  - With `use_cache=True`, tif1 remembers the verdict for `missing_payloads_ttl_days` (default: 7) and raises again without a network request
- `InvalidDataError`: If JSON parsing or validation fails
  - Includes a reason for debugging
  - Not retried (data corruption is a fatal error)
  - May indicate CDN issues or incompatible data format

### `fetch_multiple_async`

Fetch multiple JSON files in parallel with optimized batch size, graceful error handling, and automatic rate limiting.

```python
async def fetch_multiple_async(
    requests: list[tuple[int, str, str, str]],
    *,
    use_cache: bool = True,
    write_cache: bool = True,
    validate_payload: bool = True,
    max_retries: int | None = None,
    timeout: int | None = None,
    max_concurrent_requests: int | None = None,
    defer_telemetry_writes: bool = False
) -> list[dict[str, Any] | None]
```

This function is the core of parallel data loading, enabling efficient fetching of 100+ files simultaneously. It is optimized for telemetry prefetch scenarios. Use it to load lap data and telemetry for all drivers in a session.

**Concurrency Management:**

The function uses two strategies based on request count and concurrency limit:

1. **Small Batches** (requests ≤ max_concurrent_requests):
   - Uses `asyncio.gather()` for maximum parallelism
   - All requests execute simultaneously without queuing

2. **Large Batches** (requests > max_concurrent_requests):
   - Uses semaphore-based rate limiting to prevent CDN throttling
   - Limits concurrent requests (cache reads included), queues excess until slots become available

**Error Handling Philosophy:**

Unlike `fetch_json_async` which raises exceptions, this function implements graceful degradation for partial data loading:

- Failed requests return `None` instead of raising exceptions
- Successful requests return parsed data dictionaries
- `DataNotFoundError` (404) is silently converted to `None` (common for missing telemetry files)
- Other exceptions are logged with warning level and converted to `None`
- Allows partial data loading (some files succeed, others fail)
- Check result list for `None` values to identify failed requests

**Parameters:**

- `requests` (list[tuple[int, str, str, str]]): List of (year, gp, session, path) tuples
  - Each tuple represents one file to fetch
  - Example: `[(2024, "Bahrain Grand Prix", "Race", "VER/laptimes.json"), (2024, "Bahrain Grand Prix", "Race", "HAM/laptimes.json")]`
  - Can contain 100+ tuples for telemetry prefetch (all drivers × all laps)
  - Order is preserved in results (result[i] corresponds to requests[i])
- `use_cache` (bool): If True, read from cache before network fetch
  - Default: True
  - Applies to all requests in the batch
- `write_cache` (bool): If True, persist successful network responses to cache
  - Default: True
  - Applies to all requests in the batch
  - Failed requests are not cached (an all-CDN 4xx verdict is remembered, see `fetch_json_async`)
- `validate_payload` (bool): If True, run payload validation before returning data
  - Default: True
  - Applies to all requests in the batch
  - Validation runs only when the `validate_*` config flag for that payload is `True`
- `max_retries` (int | None): Total tries for each request, including the first
  - Default: Uses `max_retries` config value (typically 3)
  - Applies independently to each request
  - Failed requests after all retries return `None`
- `timeout` (int | None): Request timeout in seconds
  - Default: Uses `timeout` config value (typically 30)
  - Applies per-request, not total batch time
  - Increase for slow connections or large files
- `max_concurrent_requests` (int | None): Maximum concurrent requests
  - Default: Uses `max_concurrent_requests` config value (typically 22)
  - Increase to 50-128 for fast connections and telemetry prefetch
  - Decrease to 5-10 for slow connections or rate-limited CDNs
  - Higher values = faster but more resource intensive
- `defer_telemetry_writes` (bool): If True, collect telemetry payloads and write them to the cache in one serial flush after the batch
  - Default: False
  - The cache writes then do not occupy concurrency slots

**Returns:**

- List of fetched data dictionaries (same length as `requests`)
- Each element is either:
  - `dict[str, Any]`: Successfully fetched and parsed data
  - `None`: Request failed (logged but not raised)
- Order matches input `requests` list (result[i] corresponds to requests[i])
- Filter out `None` values to get only successful results

**Example - Load Multiple Drivers:**
```python

    """Load lap data for multiple drivers in parallel."""

            lap_count = len(data['lap'])

        else:
            print(f"{driver}: Failed to load")
```

## Rate Limiting

The async fetch module includes automatic rate limiting to prevent CDN throttling:

- Maximum 22 concurrent requests by default (configurable via `max_concurrent_requests` config)
- Configurable via `max_concurrent_requests` parameter in `fetch_multiple_async`

The HTTP session uses aggressive connection pooling for maximum performance:

- Dynamic pool sizing based on concurrency (at least 256 connections and a pool size of at least 512)
- Reuses TCP connections across requests
- `Keep-Alive` request headers with configurable values (default: 120s, 10000 max requests)

- Reduced network overhead

## Retry Logic

Payload requests include automatic retry with exponential backoff and CDN fallback:

- Default: 3 tries, the first one included (configurable via `max_retries` config)
- Backoff: 2^attempt seconds, plus optional jitter (configurable)
- Max delay: 60 seconds (configurable via `max_retry_delay`)
- Retries on: Connection errors, timeouts, 5xx errors, pool exhaustion
- No retry on: 404 (data not found), 4xx client errors
- CDN fallback: Tries all configured CDN sources before failing
- Zero-retry mode (`max_retries=1`): Ultra-fast cold start optimization (tries all CDNs once, no delays)

**Example retry behavior:**
```text
Attempt 1: Immediate (CDN 1, then CDN 2, CDN 3)
Attempt 2: Wait ~1 second, retry all CDNs
Attempt 3: Wait ~2 seconds, retry all CDNs
All 3 attempts failed: raise NetworkError
```

**Pool exhaustion handling:**
When connection pool is exhausted, automatic backoff is applied:
- Base backoff: 0.01 seconds, doubled on each try (configurable via `pool_exhaustion_backoff_base`)
- Max backoff: 0.5 seconds (configurable via `pool_exhaustion_backoff_max`)
- Jitter: up to 0.01 seconds (configurable via `pool_exhaustion_backoff_jitter`)

## Circuit Breaker Integration

HTTP requests are protected by a circuit breaker to prevent cascading failures:

- Opens after 5 consecutive failures (configurable via `circuit_breaker_threshold`)
- Blocks requests for 60 seconds when open (configurable via `circuit_breaker_timeout`)
- After the timeout, lets requests through again (half-open state)
- Closes on successful request
- Thread-safe with atomic state transitions
- Uses monotonic time for accurate timeout tracking

**States:**
- `closed`: Normal operation, requests allowed
- `open`: Too many failures, requests blocked
- `half-open`: Testing recovery; requests are allowed, and the next result closes or reopens the breaker

See [Retry & Reliability](/api-reference/retry) for details.

## Advanced Topics

### Connection Pool Optimization

The connection pool is central to `tif1`'s networking performance. Tune it to match the workload. Correct tuning has a direct effect on performance.

**How Connection Pooling Works:**

For each HTTP request, the session checks if an existing connection to that host is available in the pool:
1. **Pool Hit**: Reuse existing connection (no TCP handshake and no TLS negotiation)
2. **Pool Miss**: Create new connection (full TCP + TLS overhead)

With HTTP/2 multiplexing enabled, multiple requests can share a single connection. This improves pool efficiency.

**Pool Sizing Guidelines:**

The pool size should match the concurrency requirements:

```python
from tif1 import get_config

config = get_config()

# The sizing tif1 applies when pool_connections and pool_maxsize are not set
max_concurrent = max(
    config.get("max_workers"),
    config.get("max_concurrent_requests"),
    config.get("telemetry_prefetch_max_concurrent_requests"),
)
pool_connections = max(256, max_concurrent)  # At least 256, or match concurrency
pool_maxsize = max(512, pool_connections * 4)  # 4x for burst handling
print(pool_connections, pool_maxsize)
```

**Monitoring Pool Health:**

```python
from tif1.http_session import get_connection_stats
import time

def monitor_pool_health(duration_seconds=60):
    """Monitor connection pool health over time."""
    start_time = time.time()

    while time.time() - start_time < duration_seconds:
        stats = get_connection_stats()

        print(f"Time: {time.time() - start_time:.1f}s")
        print(f"  Total requests: {stats['total_requests']}")
        print(f"  Reuse rate: {stats['reuse_rate']:.1f}%")
        print(f"  Pools created: {stats['connections_created']}")

        # Alert on low reuse rate
        if stats['total_requests'] > 50 and stats['reuse_rate'] < 70:
            print("  ⚠️  WARNING: Low connection reuse rate!")
            print("     Consider increasing pool_connections or reducing concurrency")

        time.sleep(10)

# Sample the counters for twenty seconds
monitor_pool_health(20)
```

**Pool Exhaustion Detection:**

Pool exhaustion occurs when all connections are in use and new requests must wait. This manifests as:
- Increased latency (requests queued waiting for connections)
- "Pool timeout" or "Max retries" errors
- Automatic backoff delays (0.01-0.5s with jitter by default)
- A `Connection pool exhaustion detected` warning in the log

### Zero-Retry Mode (Ultra-Fast Cold Start)

Zero-retry mode is an advanced optimization that trades reliability for speed. Instead of retrying failed requests with exponential backoff, it tries each CDN once and moves on. The time saved is the backoff delay of each retry, which only failed requests pay.

**Enabling Zero-Retry Mode:**

```python
from tif1 import get_config

config = get_config()
config.set("max_retries", 1)  # one try per request (0 also makes one try)
```

Or via environment variable:

```bash
export TIF1_MAX_RETRIES=1
```

**How It Works:**

```python
# Normal mode (max_retries=3):
# Try 1: CDN 1 → fail → CDN 2 → fail → CDN 3 → fail → wait ~1s
# Try 2: CDN 1 → fail → CDN 2 → fail → CDN 3 → fail → wait ~2s
# Try 3: CDN 1 → fail → CDN 2 → fail → CDN 3 → fail → raise NetworkError
# Total: ~3 seconds of delays (plus jitter, if retry_jitter_max is above 0)

# Zero-retry mode (max_retries=1):
# Try CDN 1 → fail → immediately try CDN 2 → fail → immediately try CDN 3
# Total: ~0 seconds of delays
```

**When to Use:**

- ✅ Fast, reliable networks (fiber, datacenter)
- ✅ Development/testing environments
- ✅ When speed is critical and occasional failures are acceptable
- ❌ Slow or unreliable networks
- ❌ Production systems requiring high reliability

**Handling Failures in Zero-Retry Mode:**

```python
import asyncio
from tif1.async_fetch import fetch_multiple_async

async def robust_zero_retry_fetch():
    """Fetch with zero-retry mode and handle failures gracefully."""
    requests = [
        (2024, "Bahrain Grand Prix", "Race", f"{driver}/laptimes.json")
        for driver in ["VER", "HAM", "LEC", "SAI", "NOR"]
    ]

    # First attempt with one try per request
    results = await fetch_multiple_async(requests, max_retries=1)

    # Identify failures
    failed_indices = [i for i, r in enumerate(results) if r is None]

    if failed_indices:
        print(f"First attempt: {len(results) - len(failed_indices)}/{len(results)} succeeded")

        # Retry failures with up to 3 tries each
        failed_requests = [requests[i] for i in failed_indices]
        retry_results = await fetch_multiple_async(failed_requests, max_retries=3)

        # Merge results
        for i, result in zip(failed_indices, retry_results):
            results[i] = result

        print(f"After retry: {sum(1 for r in results if r)}/{len(results)} succeeded")

    return results

asyncio.run(robust_zero_retry_fetch())
```

### HTTP/2 Multiplexing Deep Dive

HTTP/2 multiplexing lets `tif1` send many requests over few connections. Learn how it works to gain the full benefit.

**What is Multiplexing?**

HTTP/2 allows multiple requests to share a single TCP connection:

```text
HTTP/1.1 (6 connections):
Connection 1: [Request 1] → [Response 1]
Connection 2: [Request 2] → [Response 2]
Connection 3: [Request 3] → [Response 3]
Connection 4: [Request 4] → [Response 4]
Connection 5: [Request 5] → [Response 5]
Connection 6: [Request 6] → [Response 6]

HTTP/2 (1 connection):
Connection 1: [Req 1][Req 2][Req 3][Req 4][Req 5][Req 6]
              [Res 1][Res 2][Res 3][Res 4][Res 5][Res 6]
```

**Benefits:**

1. **Reduced Latency**: No new TCP and TLS handshakes for requests on an open connection
2. **Lower Resource Usage**: Fewer file descriptors, socket buffers, and kernel resources
3. **Better Throughput**: No head-of-line blocking (slow requests do not block fast ones)
4. **Header Compression**: HPACK compression reduces bandwidth usage

**Measuring Multiplexing Efficiency:**

```python
from tif1.http_session import get_connection_stats

from tif1.async_fetch import fetch_multiple_async

    """Measure HTTP/2 multiplexing efficiency."""

    requests = [
        (2024, "Bahrain Grand Prix", "Race", f"VER/{lap}_tel.json")
        for lap in range(1, 58)
    ]

    await fetch_multiple_async(
        requests, max_concurrent_requests=50, use_cache=False, write_cache=False
    )

    # Check connection stats
    stats = get_connection_stats()

    print(f"Total requests: {stats['total_requests']}")
    print(f"Sessions created: {stats['connections_created']}")
    print(f"Requests per session: {stats['total_requests'] / max(1, stats['connections_created']):.1f}")

    # connections_created counts shared HTTP sessions (usually 1), not TCP
    # connections: all requests go through one pooled, multiplexed session

asyncio.run(measure_multiplexing())
```


### Circuit Breaker Patterns

The circuit breaker prevents cascading failures by blocking requests during sustained outages. Learn its state machine to use it effectively.

**State Machine:**

```text
CLOSED (normal operation)
  ↓ (5 consecutive failures)
OPEN (blocking requests)
  ↓ (60 seconds timeout)
HALF-OPEN (testing recovery)
  ↓ (success)        ↓ (failure)
CLOSED            OPEN
```

**Monitoring Circuit Breaker:**

```python
from datetime import datetime
from tif1.retry import get_circuit_breaker
import time

def monitor_circuit_breaker(duration_seconds=60):
    """Monitor circuit breaker state over time."""
    cb = get_circuit_breaker()
    start_time = time.time()

    while time.time() - start_time < duration_seconds:
        print(f"Time: {time.time() - start_time:.1f}s")
        print(f"  State: {cb.state}")
        print(f"  Failures: {cb.failures}")

        if cb.state == "open":
            print("  ⚠️  Circuit breaker is OPEN - requests are blocked!")
            if cb.last_failure_time:
                elapsed = (datetime.now() - cb.last_failure_time).total_seconds()
                remaining = cb.timeout - elapsed
                print(f"  Time until half-open: {remaining:.1f}s")

        time.sleep(5)

monitor_circuit_breaker(10)
```

**Solutions:**

```python
import asyncio
from tif1.async_fetch import fetch_multiple_async
from tif1 import get_config

config = get_config()

# Solution 1: Reduce concurrent requests
config.set("max_concurrent_requests", 5)
config.set("telemetry_prefetch_max_concurrent_requests", 10)

# Solution 2: Add delays between batches
async def fetch_with_delays(requests):
    """Fetch (year, gp, session, path) tuples in batches of 10."""
    batch_size = 10
    all_results = []

    for i in range(0, len(requests), batch_size):
        batch = requests[i:i+batch_size]
        all_results.extend(await fetch_multiple_async(batch, max_concurrent_requests=5))

        # Add delay between batches
        if i + batch_size < len(requests):
            await asyncio.sleep(2)  # 2 second delay

    return all_results

# Solution 3: Increase retry backoff to give CDN time to recover
config.set("retry_backoff_factor", 3.0)
config.set("max_retry_delay", 120.0)
```

### Pool Exhaustion

**Symptoms:**
- "Pool timeout" or "Max retries" errors
- Automatic backoff delays (0.01-0.5s by default)
- A `Connection pool exhaustion detected` warning in the log

**Diagnosis:**

```python
from tif1 import get_config
from tif1.http_session import get_connection_stats

# Check pool configuration
config = get_config()
print(f"Pool connections: {config.get('pool_connections')}")

# Check connection stats
stats = get_connection_stats()
print(f"Total requests: {stats['total_requests']}")
print(f"Reuse rate: {stats['reuse_rate']:.1f}%")
print(f"Pools created: {stats['connections_created']}")

# Calculate if pool is undersized
max_concurrent = max(
    config.get("max_concurrent_requests"),
    config.get("telemetry_prefetch_max_concurrent_requests")
)
print(f"Max concurrent: {max_concurrent}")
print(f"Pool connections: {config.get('pool_connections', 256)}")

    print("⚠️  WARNING: Pool is undersized for your concurrency!")
```

**Solutions:**

```python
from tif1 import get_config

config = get_config()

# Solution 1: Increase pool size to match concurrency
max_concurrent = max(
    config.get("max_concurrent_requests"),
    config.get("telemetry_prefetch_max_concurrent_requests")
)
config.set("pool_connections", max(512, max_concurrent))
config.set("pool_maxsize", max(2048, max_concurrent * 4))

# Solution 2: Reduce concurrency to match pool size
config.set("max_concurrent_requests", 10)
config.set("telemetry_prefetch_max_concurrent_requests", 50)

# Solution 3: Increase pool exhaustion backoff tolerance
config.set("pool_exhaustion_backoff_max", 10.0)

# Solution 4: Enable HTTP/2 multiplexing for better connection reuse
config.set("http_multiplexed", True)
```

```python
import asyncio
from tif1.async_fetch import fetch_json_async
from tif1.exceptions import NetworkError, DataNotFoundError, InvalidDataError

async def test_connectivity():
    """Test network connectivity and CDN health."""
    test_cases = [
        (2024, "Bahrain Grand Prix", "Race", "drivers.json", "Driver list"),
        (2024, "Bahrain Grand Prix", "Race", "VER/laptimes.json", "Verstappen laps"),
        (2024, "Bahrain Grand Prix", "Race", "VER/1_tel.json", "Verstappen lap 1 telemetry"),
    ]

    for year, gp, session, path, description in test_cases:
        try:
            data = await fetch_json_async(year, gp, session, path)
            print(f"✓ {description}: OK ({len(data)} keys)")
        except DataNotFoundError:
            print(f"✗ {description}: Data not found (404)")
        except NetworkError as e:
            print(f"✗ {description}: Network error ({e})")
        except InvalidDataError as e:
            print(f"✗ {description}: Invalid data ({e})")
        except Exception as e:
            print(f"✗ {description}: Unexpected error ({type(e).__name__}: {e})")

asyncio.run(test_connectivity())
```
