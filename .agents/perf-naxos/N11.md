# N11: the cold lazy path (`load_telemetry_lazy=True`): result

Branch `perf/naxos-N11`, control d28ce70 (`/tmp/naxos/control`). Both arms of every
A/B ran with `TIF1_LOAD_TELEMETRY_LAZY=true`, so `load()` is lazy in both.
Verdict: **PARTIAL (SHIP the lone-lap rule; the deferred payload flush is rejected).**
`git commit` was denied in this sandbox. Everything is staged, and the intended commit
message is in `.agents/perf-naxos/N11_COMMITS.md`.

## 1. Hypothesis

When lazy telemetry becomes the default, a cold script pays for each driver's
first-access wave. Some of that time is not link time. The section asked me to
instrument the cold lazy timeline on both backends, find the parts that are not
bytes on the wire, and cut them. Candidate causes were a first foreground wave
that waits for niquests, waves that do not overlap the previous driver's frame
build, the lookahead rule for out-of-order reads, the per-driver ramp-up, and the
frame-tier writes at exit.

## 2. What the timeline showed

I used `tools/perf/naxos_n11_cold_bench.py --trace` and `naxos_n11_timeline.py`. A
patched-seam tracer records each wave, each stream request, the niquests and stdlib
GETs, the niquests warm-up and the writer threads.

- **A lone-lap read pays for a whole driver.**
  - `get_driver(d).get_fastest_lap().get_telemetry()`, `lap.telemetry`,
    `pick_fastest().get_car_data()` and `get_fastest_lap_tel()` each start the
    driver's full wave: 57 files, ~0.4-0.6 s of link time.
  - Then 57 frames are built: 100-400 ms under load.
  - Then the exit joins the writers for 57 payload-tier rows and 57 frame-tier
    rows. On polars that includes the pyarrow import for the IPC writer. The exit
    tail is 430-490 ms in control.
  - The script needed one file, ~60 KB, roughly one round trip.
  - This is workload (b), and the most common fastf1 notebook pattern. E1 noted it
    as a follow-up.
- **The niquests warm-up is not on the critical path.**
  - It starts during `load()` (first-wave bridge) and finishes within 100-350 ms,
    before or early in the first wave.
  - The first wave's requests ride the stdlib bridge (`stdlib=57` in the traces).
  - Request medians are 110-130 ms on a quiet link, the same as later niquests
    waves.
- **The frame build is slowed by the payload-tier flush, which starts exactly when
  the build starts.**
  - The flush is `_flush_telemetry_writes`, run by `_stream_telemetry_payloads` and
    by the stream's on-idle hook as the wave completes. It does orjson dumps (~50 ms
    of GIL per driver), zstd and SQLite, 300-500 ms per 57-lap wave in background.
  - Offline, one driver's 57 frames build in 35-50 ms (pandas) and 50-100 ms
    (polars).
  - Inside the cold wave the build takes 120-400 ms.
  - I tried deferring the flush until after the build. It did not pay (section 3).
- **In a sequential loop over every lap, the build is the bottleneck, not the
  link.**
  - With the lookahead the wave wait is ~0. Per-driver builds take 0.6-1.2 s
    instead of ~50 ms, because the build shares the GIL with 22 background requests,
    the stream loop and the writers.
  - This is E10's design working as intended (link and CPU overlap). Removing that
    contention means less Python per request or a faster build, which is outside
    this round's time box. See section 6.

## 3. What changed

`src/tif1/core.py`:
- `Session._ensure_lazy_telemetry` asks `_lazy_lone_lap(refs)` first.
- The lone path applies only when all of these hold:
  - the call asks for exactly one lap;
  - its driver is still pending and this is the driver's first touch;
  - the driver is not `_lazy_lookahead_next`, the next driver of a laps-row-order
    read, which keeps E10's pipelining;
  - the stream does not already hold that lap (a new `PriorityFetchStream.holds`);
    otherwise the request joins the background wave;
  - the session is not served from the cache (`_lazy_telemetry_from_cache()`).
- When it applies, `_fetch_lazy_lone_lap` does the following:
  - fetches that one file through `PayloadLoader.get` with the wave's ultra-cold
    and validation choices, without cache reads or writes. That is the sync
    transport over the first wave's stdlib connections, so niquests is never
    imported for it.
  - memoizes the payload;
  - hands the row to the background payload-tier writer
    (`schedule_telemetry_writes`, the tier a wave writes, so batch readers find it);
  - builds and memoizes the frame with the wave's `_frames_from_payloads`.
- The frame is not written to the frame tier, as for any lap fetched on its own. A
  warm session builds a driver's first lone lap from its payload anyway.
- The driver stays pending. Its next touch fetches the rest in one wave, and the
  wave filters out the memoized lap.
- A failed lone fetch leaves the lap to the per-lap path that follows. That path
  fetches it again and records the failure, as before.

`src/tif1/core_utils/telemetry_stream.py`:
- `PriorityFetchStream.holds(key)`.

Tests:
- `tests/unit/test_lazy_telemetry_load.py` and `test_lazy_telemetry_stream.py`
  asserted the old rule ("the first lone lap brings the driver's wave"). I adjusted
  them to keep their intent:
  - The wave and lookahead tests now start their wave with the merged
    `pick_drivers(d).telemetry`.
  - The lone-touch tests assert one file, then the rest in one wave.
  - The cached-session batching test pre-marks the drivers as touched.
- New `TestLoneFirstTouch` (both backends) covers:
  - one lap, then the rest in one wave;
  - frames equal to the eager load (per-lap, `get_car_data`, merged after a lone
    touch);
  - the predicted driver takes the wave;
  - a lap the stream holds joins it;
  - which touches are lone;
  - a failed lone fetch leaves the driver to its wave.
- New test: a lone payload goes to the telemetry-tier writer.

Tools (all in `tools/perf/`):
- `naxos_n11_cold_bench.py` is E10's cold bench with both arms lazy and these
  workloads: `nb4`, `fastest1`, `fetch_all`, `iterlaps`, `fastest4`, `driver_loop`.
  It also reports p90 and has `--trace`.
- `naxos_n11_timeline.py` summarizes the traces.
- `naxos_n11_build_probe.py` times one driver's frame build offline.

**Measured and rejected (not in the tree): deferring the stream's payload flush
until after the wave's frames are built.**
- The change: a `building` event; the on-idle hook skips the flush while it is set;
  the wave flushes after `_schedule_frame_materialization`.
- Cold `nb4`, 6 pairs:
  - pandas 4891 → 4798 ms (3/6). `merged_NOR`/`merged_PIA` improved 918/970 →
    629/689, `merged_VER`/`merged_LEC` got worse.
  - polars 4313 → 5312 ms (1/6), every wave slower.
- Moving the flush off the build puts it beside the next wave's requests instead.
  The GIL is shared either way. This is the same family as Sestos L8 (overlapping
  the flush with assembly).

## 4. Measurements

box load average was 15-68 on 32 cores, with other agents' cold benches on the same
link. Absolute numbers drift a lot (`load` 0.13-2.7 s, one 57-file wave 0.4-1.6 s),
so read the pairs. Medians are whole-process wall in ms (p90 in brackets); "pairs"
counts the pairs the candidate won. 2025 Bahrain race.

`fastest1` and `fastest4` win on every pair on both backends:
- each fastest-lap read is one file (~80-220 ms) instead of a 57-file wave plus 57
  frames;
- the exit tail no longer waits for 57 payload and frame-tier rows (on polars that
  also drops the pyarrow import for the IPC writer).

`driver_loop` is the cost:
- a loop over one driver's laps now pays the lone lap's round trip and then a
  56-file wave, instead of one 57-file wave;
- the two runs measured +6-9% on pandas (2/8, 4/8) and +21-49% on polars (2/8,
  3/8);
- the expected cost is one round trip (~100-200 ms). The polars medians exceed that
  because of the very noisy link in those runs: the same tree's 56-file wave
  waited 573 to 1578 ms in four traced runs.

`nb4` (merged telemetry first) and `fetch_all` do not take the lone path. The
control/candidate code path is identical for them. The `nb4` rows in section 3 are
from the rejected flush variant.

## 5. Verdict

**PARTIAL: SHIP the lone-lap rule.**
- A cold lazy session's single-lap reads drop 64-73% on both backends, 8/8 pairs
  each. That is the fastest lap of one driver, the fastest laps of four drivers, and
  `get_fastest_lap_tel()`.
- Frames, `fetch_all` maps and cache read-backs are identical to the eager load.
- The cost is a loop over all the laps of one driver: +6-21% (one extra round trip,
  noisier on polars). A loop over every lap of the session is neutral.
- With the lazy default, single-lap reads are far more common than single-driver
  lap loops. Still, the integrator should weigh it; a fix is sketched in section 6.

**REJECT: deferring the stream's payload flush past the build.** No consistent
win (pandas 3/6, polars 1/6).

## 6. CHANGELOG

- A cold `load(telemetry="lazy")` session (the lazy default) no longer fetches a
  driver's whole lap set when the script asks for one of its laps first.
  `pick_fastest().get_telemetry()`, `get_car_data()`, `lap.telemetry` and
  `get_fastest_lap_tel()` fetch that one lap file, and the driver's next touch
  brings the rest in one wave.
  - On the 2025 Bahrain race, one driver's fastest-lap telemetry drops from
    2.9 s to 1.05 s (pandas) and from 2.8 s to 0.92 s (polars).
  - The fastest laps of four drivers drop from 4.2 s to 1.1 s (pandas) and from
    4.4 s to 1.5 s (polars).
  - The exit no longer writes 57 frames per driver for one lap.
  - A loop over every lap of one driver pays one extra round trip (~0.1-0.2 s).

## 7. Notes for the integrator

- **The one-driver loop regression, and a fix to try.**
  - `Laps.iterlaps()` (pandas and polars) could mark the drivers of the frame it
    iterates as "touched" before it yields: `session._lazy_lone_drivers.update(...)`.
    A loop would then start with the wave, as before, while a lone read outside a
    loop keeps the single fetch.
  - I did not have the time to measure it. It also changes the unit tests' `_lap()`
    helper, which finds laps through `iterlaps`. It needs a cold A/B on
    `driver_loop` and `fastest4`.
  - Do not "fix" it by prefetching the driver's other laps in the background after
    the lone lap. That is E10's +24% pattern (background traffic sharing the link
    with the next foreground request), and exit would wait for GETs in flight.
- **Cache layout.**
  - A lone lap's payload goes to the telemetry tier, through the background writer
    as a wave's does. Its frame is not written to the frame tier.
  - A later warm session builds that lap from the payload tier (`_cached_payload_
    telemetry_df`, or the payload batch of a lazy or eager warm load), so it needs
    neither the network nor the async pipeline.
  - Warm read-back parity is 1133/1133 on both backends.
- **Failure semantics.**
  - A failed lone fetch is retried once by the per-lap path, which raises or records
    the failure exactly as before. On a 404, that is one extra request.
  - The driver stays pending, so its next touch is a normal wave.
- **Where the remaining cold time goes** (pandas `nb4` on a quiet link, per driver):
  - ~400 ms of link per 57-file wave;
  - 120-200 ms of frame build;
  - the background payload flush (300-500 ms) and frame write (100-250 ms);
  - ~200-300 ms of exit tail for the last driver's writes.
  - In `iterlaps` the builds run at 600-1200 ms per driver beside the lookahead's
    requests (GIL), versus ~50 ms alone.
  - The levers left are less Python per request in the stream path, which today
    makes one `fetch_multiple_async` call per lap with two executor cache lookups
    that the wave already did. The other is faster per-frame builds: polars
    ~0.9-1.8 ms per frame, mostly `pl.Series` construction plus one query plan per
    frame in `_polars_strings_from_codes`, whose eager `Series[Series]` alternative
    measured slower (131 vs 81 µs).
  - Scheduling the flush differently did not pay.
- **The network was heavily shared during every run.** Several `load` phases took
  2.4-2.7 s, and one control wave took 5.5 s. The fastest-lap wins are far outside
  that noise (8/8 on both backends); the `driver_loop` and `nb4` numbers are not.
