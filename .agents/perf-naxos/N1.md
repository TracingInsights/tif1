# N1: numpy's import without OpenBLAS's thread-pool start on the critical path

Branch `perf/naxos-N1`, 4 commits on d28ce70. Box: i9-13900HX (8 P-cores with HT = CPUs 0-15,
16 E-cores = CPUs 16-31, one NUMA node, `intel_pstate`/powersave), Python 3.13, numpy 2.5.4
(scipy-openblas 0.3.34, `MAX_THREADS=64`, `NO_AFFINITY`), tif1-native 0.2.1. Load average
8-70 during the session (other agents); every number below is interleaved.

## 1. Hypothesis

`import numpy` costs ~60 ms more in a fresh process because OpenBLAS starts its thread pool
in its library constructor. If tif1 imports numpy with one thread and gives OpenBLAS its default
count back off the critical path, every pandas session (and a polars session's first telemetry
arithmetic) gets that time back. The pool must end the same as an untouched process's: same
`openblas_get_num_threads()`, matrix products on the same number of threads, no environment
leak, nothing done when the user chose a count or imported numpy first.

**What the cost really is.** Starting the threads is cheap (31 `pthread_create`, ~7 ms). The
cost is that each new worker busy-waits for `2**28` TSC ticks (~120 ms at this box's 2.2 GHz
TSC) before it sleeps. In `driver/others/blas_server.c`, `blas_thread_server` loops on
`YIELDING`, which on x86-64 is a `nop` loop (`common.h`), not `sched_yield`. Evidence, fresh
`import numpy`, 12-15 interleaved runs:

| setting | median | min |
|---|---|---|
| default (32 threads) | 81-131 ms | 77-82 |
| `OPENBLAS_NUM_THREADS=1` | 61 | 60 |
| `OPENBLAS_NUM_THREADS=2/8/16` | 61-62 | 61 |
| `OPENBLAS_NUM_THREADS=24` / `32` | 98 / 128 | 73 / 77 |
| `OPENBLAS_THREAD_TIMEOUT=4` (default count; workers sleep at once) | 62 | 62 |

The harm is nonlinear: up to 16 spinners are free and 24+ are expensive. 31 spinning cores
take the importing thread's HT sibling and the package's power/turbo budget. So the effect is
largest on a lightly loaded machine (a user's laptop) and vanishes when other processes already
saturate the box. With load 30+ even the `OPENBLAS_NUM_THREADS=1` upper bound fell inside the
noise of whole-process walls; at load 9-17 it won 11-12/12. `strace`/`perf` were not available
in the sandbox. The mechanism comes from the OpenBLAS sources (v0.3.30 `blas_server.c`,
`memory.c`, `openblas_env.c`, `common.h`, `common_x86_64.h`) and the experiments above.

Consequences for the design, all measured:

* Restoring the pool later from a daemon thread (`openblas_set_num_threads` creates the new
  workers spinning) only moves the spin: an 8-pair A/B was noisy-neutral.
* No public API creates the workers lazily. The library exports no `blas_thread_shutdown` and
  no data symbols. `openblas_set_threads_callback_function` replaces the server and cannot
  defer it.
* Workers grown by `openblas_set_num_threads` allocate their thread buffer on their first job.
  The constructor allocates all of them up front (`adjust_thread_buffers`). After a pandas
  import this put ~40 ms on the user's first threaded BLAS call (2000x2000 `@`: untouched 116,
  grown 158, grown + one warm-up dgemm 126 ms; 12 rounds).
* Pinning the spinning workers to ONE CPU gives the tif1 gain. But on this hybrid part the
  user's first threaded BLAS call after that was ~50-70 ms slower (the workers barely ran while
  pinned); it converged by the 3rd call. Pinning to 4 of 32 CPUs gave the same tif1 gain and no
  BLAS penalty, and so did 8 of 32. Pinning to 16 (half) lost the tif1 gain. Spreading the
  workers' last CPU before unpinning did not help. On `taskset -c 0-7` (four P-cores with HT,
  homogeneous) the one-CPU pin had no BLAS penalty.

## 2. What changed

* `src/tif1/core_utils/blas_threads.py` (new; imports only `os`/`sys`). `install()`, called
  from `tif1/__init__.py`, puts a one-shot meta-path finder first in `sys.meta_path`. It does so
  only on Linux, when numpy is not imported, when none of `OPENBLAS_NUM_THREADS`,
  `GOTO_NUM_THREADS`, `OMP_NUM_THREADS`, `OPENBLAS_DEFAULT_NUM_THREADS` is set, and unless
  `TIF1_BLAS_DEFER` is `0/false/no/off`.
  * The finder never returns a spec; it only watches the import order. On the lookup of
    `numpy._core._multiarray_umath` it checks that the wheel bundles exactly one
    `numpy.libs/libscipy_openblas*` (otherwise it removes itself and does nothing), re-checks
    the environment, and sets `OPENBLAS_NUM_THREADS=1`. The extension's dlopen runs OpenBLAS's
    constructor with one thread. At the next import (numpy's C init imports submodules right
    away) it pops the variable, removes itself, and calls `_restore_pool`.
  * `_restore_pool` runs in the importing thread, still inside numpy's import (~15 ms on 32
    CPUs). It reads `openblas_get_num_procs()`, which counts the caller's affinity mask, i.e.
    the constructor's default without the variable, and calls `openblas_set_num_threads(count)`.
    No BLAS call can ever see a one-thread pool, so no result can change through a different
    split of a threaded reduction. It then runs one `cblas_dgemm` of zeros
    (M = 128 × threads, N = K = 64, so OpenBLAS splits M over every thread) so each new worker
    allocates its buffer as the constructor would. Finally it pins the workers with
    `openblas_setaffinity(i, ...)` (exact worker indices, no thread-id guessing) to the
    highest-numbered CPUs other than the main thread's, one per eight in the mask (4 of 32;
    E-cores on Intel hybrid parts).
  * The daemon thread `tif1-blas-pool` (`_unpin_when_asleep`) gives every worker the
    importing thread's affinity mask back with `os.sched_setaffinity(tid, mask)`, by kernel
    thread id, so a `fork` that made OpenBLAS join its workers only yields `ESRCH`. It does so
    when the first of these happens:
    * all pinned workers sleep (it polls `/proc/self/task/<tid>/stat` of workers 0-2 every 2 ms,
      then all workers every 10 ms once those sleep);
    * 30 ms after the first one slept;
    * a pinned worker takes a minor page fault (a user BLAS job; a spinning worker touches no
      memory);
    * 0.3 s pass.

    The final state matches an untouched process: thread count, worker threads, buffers,
    affinity masks, `os.environ` (checked by the tests below).
* `src/tif1/__init__.py`: imports the module and calls `install()` (+0.4 ms on `import tif1`,
  0/20 pairs; no configuration read).
* Tests:
  * `tests/unit/test_blas_threads.py` (13): the finder's env/uninstall logic on a fake wheel
    layout; other BLAS builds and chosen thread counts left alone; `install()` no-ops. Fresh
    interpreters check that the pool equals an untouched process's right after
    `import numpy` and after the unpin thread: thread count, task count, every task's affinity,
    no env leak, finder gone. Also that a user `OPENBLAS_NUM_THREADS=3` and `TIF1_BLAS_DEFER=off`
    are respected, and that a `fork` inside the pin window, with BLAS in both processes, leaves
    the parent's pool at the default count with every task on the full mask.
  * `tests/unit/test_private_seams.py`: new seam `numpy-bundled-openblas` (numpy 2.5.4) with
    `test_numpy_bundled_openblas` (wheel layout, extension name, exported symbols).
  * `tests/unit/test_pergamon_contracts.py`: the "`import tif1` loads only `tif1.exceptions`"
    contract now names `tif1.core_utils` and `tif1.core_utils.blas_threads` too. Its point (no
    configuration read before the user sets it) still holds.
* `AGENTS.md`: one architecture bullet.
* Harness (my copies in `tools/perf/`):
  * `naxos_n1_ab.py` (`delphi_warm_ab.py` + `--control-env/--candidate-env/--taskset`);
  * `naxos_n1_warm_bench.py` (+ `blas_after`: pandas `laps`, then two 2000x2000 `@`, OpenBLAS
    thread count, env check);
  * `naxos_n1_multi_ab.py` (N arms of tree+env, interleaved, one cache);

## 4. Verdict: SHIP (with the caveats in §6)

The gain is real when the machine has idle CPUs, the normal case for a user's laptop:
* pandas `import_get_session` -9.7% (10/10), `laps` -5.5% (9/10, and 9-12/12 in three 3-arm
  runs), `all_tel` -1.7 to -6.4% (8-10 of 10-12);
* polars `notebook` -6.6% (9/10), its analysis phase -50 ms;
* `taskset 0-7`: `laps` -5.0% (10/12), `blas_after` -5.7% (9/12);
* cold `laps` -4.4% (8/10).

The low-load confirmation run on the committed code also gives `laps` -9.7% (9/10) and
`all_tel` -8.8% (9/10). The pandas `notebook` wall did not clear the bar (5/10 and 7/12). Its get_session phase is
40 ms faster, but the rest of the notebook is long and noisy. The candidate keeps 50-60% of
the `OPENBLAS_NUM_THREADS=1` upper bound. The remainder is the 15 ms restore inside numpy's
import (mostly the 31 buffer allocations the constructor would also have made) plus the workers
spinning on 4 CPUs. The cost is +0.4 ms on `import tif1`, and the first one or two large threaded BLAS
calls after a session are 0-25 ms slower each on this hybrid part (equal on `taskset 0-7`),
which a BLAS-heavy script about pays back from the faster session start. No value changes,
and the pool ends identical to an untouched one.

## 5. CHANGELOG paragraph

- **numpy's import no longer waits on OpenBLAS's thread pool.** numpy's Linux wheels start
  one OpenBLAS worker per CPU while numpy imports, and each worker busy-waits about 120 ms
  before it sleeps. On a 32-CPU laptop part those 31 spinning workers made `import numpy` take
  110-185 ms instead of 60-110 ms and slowed the rest of the session start. When tif1 is
  imported first and no BLAS thread count is set, numpy now loads OpenBLAS with one thread.
  tif1 then restores OpenBLAS's default count, and the workers' buffers, inside numpy's import,
  and keeps the new workers' busy-wait on one CPU in eight until they sleep. The pool ends as
  before: the same thread count, workers and affinity, and nothing left in the environment.
  Warm pandas `get_session` 372 -> 333 ms; `laps` script 429 -> 405 ms; polars notebook
  594 -> 555 ms (the first telemetry arithmetic imports numpy). Linux scipy-openblas wheels only;
  `OPENBLAS_NUM_THREADS`/`OMP_NUM_THREADS`/`GOTO_NUM_THREADS` set by the user, or numpy imported
  before tif1, leave OpenBLAS alone; `TIF1_BLAS_DEFER=0` turns it off.

## 6. Notes for the integrator

* **Hybrid CPUs and the first BLAS call.** Pinning all workers to one CPU made the next
  threaded BLAS call on the 13900HX 50-70 ms slower in most runs. The kernel reports
  `cpu_capacity` 1024 on every CPU, and spreading the workers' last CPU before unpinning did not
  help. My best guess is the workers' PELT utilization history, but that is not proven.
  `_CPUS_PER_PIN = 8` (4 of 32) measured equal to the untouched pool, and so did 8 of 32. If an
  integrator sees a BLAS regression on another hybrid part, raise the pin width (`// 4`) before
  anything else; 16 of 32 lost the tif1 gain.
* **Measurement climate.** The box's load swung from 8 to 70. With load above ~30 even the
  `OPENBLAS_NUM_THREADS=1` upper bound vanished in whole-process walls (a 20-round run at load
  30 showed nothing for any arm). Trust the low-load and `taskset` runs, and the import-level
  probe, which held its ~60-75 ms gap at every load.
* **Platforms.** Linux only (`sys.platform == "linux"`). macOS arm64 wheels use Accelerate, so
  nothing to do there. macOS x86-64 and Windows wheels bundle scipy-openblas with the same
  spin, but `openblas_setaffinity` is Linux-only. `blas_server_win32.c` differs and I could not
  measure either platform; a follow-up could enable the count restore without pinning there
  after measuring. MKL and system OpenBLAS builds are left alone (only a single
  `numpy.libs/libscipy_openblas*` arms it). numpy 1.x wheels (`libopenblas64_p-*`) are no-ops.
  Pyodide is no-op (platform). Free-threaded builds should work but were not tested.
* **Fork.** OpenBLAS's `pthread_atfork` handler shuts the pool down before `fork` and rebuilds it
  lazily with `blas_num_threads` threads in both processes. Those new threads inherit the forking
  thread's mask, not a pin. The unpin thread therefore addresses workers by kernel thread id and
  ignores `ESRCH`; an earlier version went through OpenBLAS's `pthread_t` table, which a fork
  would have left pointing at joined threads. `test_fork_inside_the_pin_window` covers it. The
  pinning itself (31 `openblas_setaffinity` calls, microseconds, inside numpy's import) still
  uses that table: a `fork` from another thread in exactly that window is the one remaining
  theoretical race.
* **Environment.** `OPENBLAS_NUM_THREADS=1` is in `os.environ` from the lookup of numpy's
  extension module to the next import: microseconds, but process-wide. A subprocess spawned by
  another thread in exactly that window would inherit it. glibc `setenv` races with concurrent
  `getenv` in other threads (the same caveat as any `os.environ` write).
* **A failed restore** (missing symbol after a scipy-openblas rename) logs a warning and leaves
  OpenBLAS at one thread for the process. The `numpy-bundled-openblas` seam test and the weekly
  canary check the symbols, so a numpy bump that renames them fails CI first.
* **Perf gate baseline.** I did not rewrite `tests/fixtures/perf/baseline.json`. The change
  moves every pandas `get_session` down (0.91-1.00 here) and polars' notebook analysis (0.61).
  Rewrite it at merge if the gate's headroom should follow, then review the digest diff (the
  digests do not change: parity 0/133, 0/131).
* **Docs.** `TIF1_BLAS_DEFER` is env-only, read at `import tif1` like `TIF1_PRELOAD_IMPORTS`, and
  is not in `config.py`. A line in the configuration docs page (`docs/`, not in this sparse
  checkout) is left to the integrator.
* The polars `laps` workload pays +0.4 ms on `import tif1` for the module and the armed finder.
  A process that never imports numpy keeps the finder (one frozenset lookup per import) for its
  lifetime.
