# N6. Pandas per-lap telemetry: `lap.telemetry` / `get_car_data()` per-lap overhead

Tree `/tmp/naxos/N6`, branch `perf/naxos-N6`, against the frozen control
`/tmp/naxos/control` (d28ce70). All A/Bs ran both arms on `/tmp/naxos/warm-N6`.
The box was heavily shared: load average 25-38 on 32 cores during every
timing run. `get_session` swung by 50-150 ms between arms, and the swapped
run's notebook wall reached 2.2 s. Read the pairs and minima, not the
medians. `git commit` was denied in this session: everything is staged, and
the intended message is in `N6_COMMITS.md`.

## 1. Hypothesis

The pandas notebook's `iterlaps` telemetry loop (every lap of the race: 1128
`lap.telemetry` calls, ~140-150 ms in-process) and `car_data_loop` (VER's 57
laps, `get_car_data()`, ~25-28 ms) carry per-lap constant costs: Python call
depth, per-lap pandas constructions, `iterlaps`' per-row Series, index
building. Cutting them should shrink both loops without changing a single
value, dtype, index, class or `_metadata`. Each lap's frame must stay
independent of the others and of the memo.

## 2. What changed

### Profile first (probes in `tools/perf/naxos_n6_*.py`)

Where the loop goes, warm cache, fresh process, in-process timers
(`naxos_n6_breakdown.py`, `naxos_n6_gc.py`, `naxos_n6_micro.py`):

| piece | cost | per lap | changed? |
|---|---|---|---|
| 19-row batch read at the 2nd driver (D5) | 40-60 ms | | no: E5 / DO_NOT_RETRY |
| first driver's lone row read | 6-10 ms | | no (D5 minimax policy, see notes) |
| row decodes (`DriverFrameSource`), 20 rows | ~1 ms each steady, 1.3-2.5 after the batch, 2-7 inside it (overlapped with the wait); the first pays the 5 ms block probe | | no: near its floor (0.3 ms of it is pyarrow's dictionary `take`) |
| lap frame build (`_LapBuilder.build`) | 16 us steady, ~24 in the loop | 16-24 us | no: 9 blocks, already the Q18 direct route |
| `_LapBuilder` init | 0.21 ms per group in the loop (27 us steady) | | no: page faults on the fresh group-level `Int64` constant arrays; per-lap arrays touch the same bytes |
| `Laps.to_numpy(dtype=object)` | 9-14 ms | 8-12 us | GC only: boxing 13.5k `Timedelta` + 1.1k `Timestamp` is inherent |
| `_lap_from_row` | ~10-12 ms | ~10 us | **yes** |
| `Lap.telemetry`: two `Series.get` | ~3 ms | 2.9 us | **yes** |
| other wrapper layers (memo, adopt, `_session_telemetry`, ultra-cold check) | ~5 ms | ~4.5 us | no: ~1 us each |
| cyclic GC | ~11.5 ms (31 gen-0 + 3 gen-1 passes) | | partly |

GC is inherent to the object count. A lap frame creates 53 GC-tracked
objects: each of its 9 blocks carries a `BlockValuesRefs`, a list and a
weakref for pandas' copy-on-write tracking. A `Lap` creates 13. The boxed
`Timedelta`/`Timestamp` scalars are tracked too. `car_data_loop`'s per-lap
part is only ~2.5 ms of its ~25. The rest is one-time costs: the first lap
from the payload tier (7.5 ms, including the 5 ms direct-block probe whose
pyarrow imports the path needs anyway), the lone row read (8.4 ms) and one
gen-1 GC pass (3.3 ms).

### The change: `src/tif1/models.py` only (plus tests)

- **`iterlaps` rows without inference, over one shared placement.**
  `_lap_from_row` gained an optional `placement`. With it, the row block is
  built directly (`NumpyBlock(values, placement, 1)` +
  `SingleBlockManager(block, index)`), skipping `maybe_convert_objects` (3.3
  us) and `SingleBlockManager.from_array` (a fresh `BlockPlacement` per row).
  `_object_row_placement(frame)` gives the placement only when the frame has
  a non-nullable numpy `int`/`uint`/`bool` column (the laps table has
  `LapNumber`-like int64 and five bool columns). Every row then holds a
  Python int or bool, and pandas' inference with `convert_numeric=False`
  returns such a row unchanged. That is why `pd.Series(np.array([1, "a"],
  dtype=object))` stays object.

  The rule is checked once per process by `_probe_object_rows`: eight mixed
  rows (bool/int/NaN/None/NaT/Timedelta/Timestamp/str) must come back as the
  same array, and the direct block must match `from_array`'s (block class,
  ndim, placement, values identity, index). If any check fails, `iterlaps`
  infers every row as before. The probe uses an object `Index`: a `str`
  Index would import pyarrow's pandas shim (the first version cost 5 ms;
  now 0.3-0.5 ms once). Sharing a placement between blocks is what pandas
  itself does (`make_block_same_class`).
- **The frame's object interleave runs under `_suspend_gc()`.**
  `to_numpy(dtype=object)` boxes ~14.6k GC-tracked scalars in one call.
  Deferring cyclic GC to its end saves ~4 gen-0 passes (31 -> 27). It is a
  bounded burst inside one call; GC is never held across the generator's
  yields.
- **`Lap.telemetry` reads `Driver`/`LapNumber` directly.**
  `_driver_and_lap_number(lap)` caches the two labels' positions for the
  last column Index it saw (every `Lap` of one `iterlaps` shares its frame's
  Index, and an Index is immutable) and reads `lap._values[pos]`. That is
  what `Series.get` -> `_get_value` returns for a label held once. A missing
  or duplicated label, or a `get_loc` that is not an int, falls back to
  `lap.get`.

Tests:
- `tests/unit/test_naxos_n6_lap_rows.py` (16, offline):
  - the probe holds on the installed pandas;
  - which frames get the placement (parametrized);
  - `iterlaps` rows equal the public constructor's (types, dtype, name,
    session, `vars`, block class, placement, CoW refs) with zero inference
    calls and one shared placement;
  - rows stay independent (value and dtype-changing writes stay local; the
    frame is untouched);
  - frames that may convert (all-timedelta) still infer every row;
  - a failing probe infers every row;
  - a converting inference fails the probe;
  - the interleave runs with GC off and GC is back on afterwards;
  - `_driver_and_lap_number` equals `get` (cache per index, live values,
    another column order, missing/duplicated/integer labels);
  - `Lap.telemetry` asks the session for `(driver, int(lap))`.
- `tests/unit/test_private_seams.py`: the `pandas-lap-rows` seam now lists
  `SingleBlockManager(block, index)`, `NumpyBlock(values, placement, 1)` and
  the `maybe_convert_objects` rule, and its test fails if
  `_probe_object_rows()` or `_object_row_placement` falls back.

No cache format, schema, frame-tier or polars change.

## 4. Verdict: SHIP (small), the hypothesis's larger target REJECTED with numbers

What to keep: the whole change (one file, probe-gated, parity exact).

- The named in-process phase, the notebook's `iterlaps` telemetry loop,
  wins in every run: 6/8, 6/8, 6/8 in the harness, 11/16 and 7/8 in the
  probe, and 5/8 swapped at load average 38. Expected size is ~7-10 ms of
  ~140 (5-7%).
- The notebook wall is not worse: 5/8, 6/8, 6/8 faster. The 3% wall bar
  cannot be claimed on this box.
- `car_data_loop` is neutral (4/8, 9/16). Its 57 laps carry ~2.5 ms of
  per-lap cost against ~22 ms of one-time costs, and the probe's one-time
  0.3-0.5 ms cancels its ~0.3 ms row saving.
- `driver_tel` runs unchanged code.

The larger target, cutting the loop's per-lap overhead substantially, does
not hold: ~110 of the ~140 ms are not per-lap Python overhead.
- The batch row read and decodes are ~60-80 ms (E5 and DO_NOT_RETRY: reading
  ahead beside the loop loses).
- The lap builds are already on the Q18 direct block route (16 us, 9 blocks).
- The `Timedelta` boxing is ~10 ms and is the scalar objects themselves.
- GC is ~11 ms, driven by pandas' per-block CoW bookkeeping (53 tracked
  objects per frame).

## 5. CHANGELOG paragraph

- `Laps.iterlaps()` builds each `Lap` row directly over one shared block
  placement. It skips the Series constructor's object inference when the
  frame has a non-nullable int or bool column (the laps table always does),
  since such a row always stays object dtype. The rule is checked against
  pandas once per process, and any drift restores the inference. The
  frame's object interleave runs with cyclic GC paused. `Lap.telemetry`
  reads `Driver`/`LapNumber` by position instead of two `Series.get` calls.
  Building the 1128 rows of a race takes 10-12 -> ~4 ms. A loop over every
  lap's `telemetry` after `load()` is ~7-10 ms faster in-process (~140 ->
  ~132 ms on a quiet box; 6/8 pairs in three A/Bs). Values, dtypes, index,
  names and classes are unchanged.

## 6. Notes for the integrator

- **Where the rest of the loop goes.** The table in section 2 is the map for
  the next round. The candidates I measured and left alone:
  - An `iterlaps` hint so the first touched driver batches every lazy row
    instead of reading its own row alone. It saves the 6-10 ms lone read in
    a full loop, but a script that iterates every lap and touches one
    driver's telemetry would read 20 rows instead of one (+35-50 ms). That
    breaks D5's minimax rule (no shape worse than control by more than one
    lone read).
  - Per-lap instead of group-level `Int64`-constant arrays: same bytes, so
    same page faults.
  - A per-lap `DriverAhead` decode: ~12 us per lap against 0.3 ms per
    driver row, worse.
  - A `DatetimeArray._simple_new` bypass in the build: 0.4 us per lap.
  - Fewer wrapper layers between `Lap.telemetry` and the memo: ~1 us each.
  - The direct-block probe (5 ms on the first frame of a process) is mostly
    the `pyarrow.pandas_compat` import, which the per-lap path pays anyway.
- **Private API.** The `pandas-lap-rows` seam entry now also covers
  `SingleBlockManager(block, index)`, `NumpyBlock(values, placement, 1)` and
  the `maybe_convert_objects` rule. A pandas that converts numeric object
  rows, or changes the single-block manager, turns `_probe_object_rows`
  False, `iterlaps` falls back to inferring every row, and the seam test
  fails.
- **`_LAP_KEY_LOCS`** is a single-slot module cache holding a strong
  reference to the last column Index read (a few hundred bytes). Index
  immutability makes a hit always valid. Two threads racing on it can only
  overwrite each other's valid entry.
- **Harness oddity.** `delphi_warm_ab.py` shows a net-zero shift of a few
  ms from `picks_x8` into `load` for this tree. It follows the tree when the
  roles are swapped, but I could not reproduce it with the same steps
  outside the harness: same imports, same GC placement, neutral 10- and
  12-pair runs. Worth a look if another N-agent sees `load` move without
  touching it.
- **Probes kept** in `tools/perf/naxos_n6_*.py`:
  - `breakdown`, `gc`, `gc_phases`: stage timers and GC placement;
  - `micro`, `rows`, `decode`, `first_decode`, `probe_cost`, `car_loop`,
    `load_imports`: the per-piece costs;
  - `loop_ab`: an interleaved in-process A/B of the loops, `load` and the
    picks;
  - `profile`: cProfile of the loop.

  Run them from the tree root with `PYTHONPATH` pointing at the tree (not
  `python -I`, which drops `PYTHONPATH`).
