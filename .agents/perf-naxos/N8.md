# N8. Cold one-driver telemetry: the wave's tail

Control: `/tmp/naxos/control` (d28ce70). Candidate: `/tmp/naxos/N8`, branch
`perf/naxos-N8`. `git commit` is denied in this sandbox: everything is staged,
and the intended commits are in `N8_COMMITS.md`.

## 1. Hypothesis

A cold `laps.pick_driver("VER").telemetry` (57 lap files, ~3.5 MB gzipped)
took 1.6-3.9 s on pandas and ~1.0 s on polars, while the same process's
`laps` took 590/355 ms. That is far slower than the link's bandwidth would
explain, and the variance suggested tail latency: jsDelivr edge misses, slow
connections, the hedge/backoff policy, or the E9 bridge -> niquests handover.
The section asked to trace the wave per request, find what the slow runs have
in common, and fix what the timeline shows.

## 2. What the timeline shows, and what changed

### Instrumentation (tools only, nothing in `src/`)

`tools/perf/naxos_n8_trace.py` runs fresh-process cold workloads (empty
cache, live CDN) with hooks installed from outside the library. It records
every stdlib request (connect, TTFB, body end, bytes, new or kept-alive
connection, jsDelivr `x-cache`/`age`), every niquests request (start,
resolved, body, reuse, HTTP version), each `fetch_json_async`, hedges and CDN
failures (log records), the first-wave start, the niquests session build and
warm-up, the modules imported during the step, and (optionally) a 1 ms
main-thread stack sampler or cProfile. `naxos_n8_analyze.py` breaks each run
into pre-wave / wave / post-wave and new- versus reused-connection requests.
`naxos_n8_arms.py` interleaves arms (a tree plus env per arm).

### Findings (24 traced cold control runs, 12 per backend, plus 48 in the experiments)

- **The whole wave runs on the stdlib bridge.** In 23 of 24 control runs all
  57 telemetry GETs went over `http.client` (E9's bridge). niquests'
  warm-up (`warm_connections_done`) completed at 850-1330 ms process time,
  after the wave had ended. In one run it took the last 10 requests.
- **Connections.** Each wave opens exactly 20 new HTTP/1.1 connections (22
  slots; 2 are kept alive from the first wave). Requests on a new connection
  take 170-520 ms (median per run; connect 45-180 ms, TTFB 100-300 ms), and on
  a reused one 60-170 ms. In good runs the last request starts at 340-390 ms
  and the wave ends at 470-500 ms. The last requests to finish are usually
  first-batch requests on new connections that ran for the whole wave
  (TCP slow start with 20 flows starting together).
- **No hedges, no CDN failures, no edge-miss outliers.** The edge answered
  `HIT` at the second layer for every file; 1-5 files per wave were `MISS` at
  the first layer, with no latency signature. The slow runs (1.3-2.0 s) are
  slow everywhere at once: connect times 100-180 ms instead of 45-70 ms. That
  was the shared link: up to ten agents ran cold benches beside this one, and
  N9 was downloading 69 MB per run (load average 32 on 32 cores during the
  final runs).
- **The link, not tif1, sets the wave's pace.** `curl --parallel` of the same
  57 files took 670-1310 ms over 22 HTTP/1.1 connections, 1120-1840 ms over
  57 connections and 440-1950 ms over one HTTP/2 connection. tif1's wave took
  430-520 ms in the same hour, so it is already at or above curl.
- **What the process does beside the wave.** During `driver_tel`, about 250
  modules are imported in the niquests warm-up thread (niquests 130, urllib3
  85, jh2 24, h11, charset_normalizer, qh3, ...). That is ~120-145 ms of CPU
  holding the GIL, while 22 executor threads re-acquire the GIL after every
  SSL read (1431 `SSLSocket.read` calls per wave). niquests then serves
  none of the wave's requests.
  Experiment (warm-up disabled by a monkeypatch in the tracer, pandas, 8
  interleaved pairs): `driver_tel` phase 620 -> 529 ms, wave 515 -> 453 ms,
  process wall 1231 -> 1168 ms (6/8). E9 measured the same direction:
  "stdlib-only" was ~50 ms faster on `driver_tel`, but was not shipped
  because it dropped HTTP/2, hedging and OCSP for every cold request.
- **After the wave.** Pandas spends ~70 ms and polars ~120-140 ms building
  the 57 lap frames. The main-thread sampler puts ~25% of the polars build in
  `helpers._polars_strings_from_codes`. Its `Series.gather` runs as a polars
  query plan (`engine.py:collect` under it). That is ~0.2 ms per lap and
  18-30 ms for the first call in a process (fresh-process probe).
- The concurrency cap was tried as well (22 vs 12 vs 8 connections, 8
  pairs): no clear winner on the shared link (12: median +88 ms, p90 -540 ms;
  8: worse). Not changed.

### Change 1: start the niquests warm-up only past one driver's wave (`first_wave.py`)

`first_wave.bridge_open()` counts the requests it routes over the bridge.
It starts `warm_niquests()` only for the request after `BRIDGE_WARM_AFTER`
(80). A race has at most ~78 laps (Monaco), so one driver's wave in any
session is below the bound. A one-driver wave then runs on the stdlib
connections without the import convoying with it, and a cold one-driver
script never imports niquests (24/24 -> 1/24 runs; the one exception is a
request the bridge refused, which goes to niquests as before). A second
driver's wave, `fetch_all` and an eager `load()` cross the bound and hand
over to niquests as before (HTTP/2, hedging, OCSP), ~80 requests later than
in control. Everything else is unchanged: the bridge answers only a `200`
with a JSON object (anything else goes to niquests at once), bridged requests
are bounded by `cdn_hedge_max_delay`, the sync transport, the
`cdn_first_wave=False` switch and the proxy / no-`wassima` path.

How this differs from DO_NOT_RETRY: it is neither E9's rejected handover
trigger (that started niquests *earlier*) nor E9's "stdlib-only" (that never
imported niquests on a cold load). The bridge-then-niquests design stays; only
the point where the warm-up starts moves to where it can pay off.

Docstrings: `first_wave` (module, `BRIDGE_WARM_AFTER`, `warm_niquests`,
`bridge_open`), `async_fetch._stdlib_served`,
`payload_loader.NiquestsTransport.get_bytes`; `AGENTS.md` (the bridge
paragraph).
Tests (`tests/unit/test_first_wave.py`):
`test_telemetry_wave_starts_on_the_stdlib_while_niquests_warms` now checks
that no warm-up happens up to the bound and one happens past it, on the
wave's URLs. New `test_one_driver_wave_never_warms_niquests` sends 80 lap
requests through `fetch_multiple_async` over the fake CDN with niquests
forbidden, expects no warm-up, and expects the 81st request to start one.
The binary-request test sets the bound to 1.

### Change 2: `DriverAhead` codes to strings without a query plan (`core_utils/helpers.py`)

`_polars_strings_from_codes` (the only caller is `_polars_typed_channel`, the
per-lap polars build from a native-decoded payload) now looks the codes up in
Python for arrays of up to `_STRINGS_LOOKUP_MAX` (4096) samples (a lap has
~1k). Longer arrays index the Series with the codes (`Series[ndarray]`, an
eager kernel, faster than `gather` at every size measured: 0.05/0.23/7.0 ms
vs 0.12/0.35/7.9 ms at 800/45k/900k codes). A code of -1 still lands on the
appended null. The result is the same Series: values, `String` dtype, flags,
one chunk. 228 laps of 4 drivers built both ways are identical (values,
schema, per-column flags and chunks). A new test,
`test_long_code_arrays_index_the_series`, checks that both branches give the
same Series. Warm polars paths never call this function (0 calls in a warm
`driver_tel` + `fetch_all`: they read the frame tier).

## 4. Verdict

**SHIP both changes.**

- The hypothesis as stated (tail latency from edge misses, hedging or
  backoff) is **not what the timelines show**. There were no hedges, no
  failures and no edge-miss signature. The slow runs were the shared link
  being slow for every request at once, and tif1's 57-file wave was already at
  or above curl on the same link. The wave's real overhead was CPU beside
  it: the niquests warm-up's import, started by the bridge, which never
  served the wave. Behind it sat a query plan per lap in the polars frame
  build.
- Change 1 clears the bar on pandas: cold `driver_tel` wall **1926 -> 1582
  ms (-18%), 18/24 pairs**, p90 3563 -> 2397, phase 1018 -> 698. On polars,
  with both changes, the median falls 13% (2150 -> 1871) and the p90 falls,
  but only **15/24 pairs**, below the 6-of-8 bar. Polars measured in the
  most congested hour, and its wave also carries the numpy import.
  `driver_tel_x2` (a second wave that crosses the bound) is not worse: pandas
  second wave 574 -> 513 (5/8), polars 803 -> 650 (8/8). `laps` and
  `fastest_lap_tel` run unchanged code (deltas are drift). `all_tel` shows
  no cost from the later handover.
- Change 2 is an in-process win measured without the network: the cold
  polars build of one driver's laps is **82 -> 63 ms** (10 fresh processes),
  with identical frames. It follows AGENTS.md's rule against query plans on
  polars hot paths.
- Parity: 0/133 and 0/131 warm surfaces, 0/4 and 0/4 cold frames, and 228
  of 228 laps identical in the changed builder. Unit suite, ruff and ty are
  clean. The perf gate passes.

## 5. CHANGELOG paragraph

- A cold script's first telemetry wave of one driver no longer imports the
  HTTP library. Since the bridge (Elis E9), a cold
  `laps.pick_driver("VER").telemetry` ran all 57 lap requests on the
  standard-library connections the first wave opened, but its first request
  also started the niquests import and connection warm-up in a background
  thread: ~250 modules and 120-145 ms of CPU under the GIL that never
  finished before the wave did and slowed the wave's receive threads. The
  warm-up now starts after 80 bridged requests, more than one driver's laps
  of any session, so a one-driver wave runs on the standard library alone and
  a longer wave (another driver, `fetch_all_laps_telemetry()`, an eager
  `load()`) moves to niquests as before. Cold
  `laps.pick_driver("VER").telemetry`, 2025 Bahrain race, pandas, 24
  interleaved pairs on a shared link: 1926 -> 1582 ms median (p90 3563 ->
  2397), the telemetry step 1018 -> 698 ms. Polars: 2150 -> 1871 ms (24
  pairs, 15 faster; the telemetry step 1312 -> 1075 ms), and a second
  driver's wave 803 -> 650 ms (8/8). Polars also turns a lap's `DriverAhead` codes into strings with a
  list lookup instead of `Series.gather`, which polars 2 runs as a query plan
  (~20 ms for the first of a process): building one driver's 57 lap frames
  from payloads takes 63 ms instead of 82 ms.

## 6. Notes for the integrator

- **Security scope (OCSP).** Requests on the stdlib bridge verify the chain
  and host name but skip niquests' soft-fail OCSP check (E9, documented). For
  a one-driver wave nothing changes: in control the whole 57-file wave was
  already bridged. Longer cold waves are bridged for ~80 requests more than
  before (the warm-up starts at request 81 instead of 1, then takes
  ~0.3-0.5 s). Two-driver scripts bridge the first wave and ~25-60 requests of
  the second. `cdn_first_wave=False` still sends everything through
  niquests. The docs sentence in
  `docs/reference/environment-variables.mdx` (`TIF1_CDN_FIRST_WAVE`) and
  `COMPATIBILITY.md` ("the first telemetry requests ... until niquests has an
  open connection") remain true. A precise addition for the env-var page,
  not made here because `docs/` is outside this sparse checkout: "niquests
  loads after 80 such requests, more than one driver's laps."
- **The bound is a module constant** (`first_wave.BRIDGE_WARM_AFTER = 80`),
  not a config knob, like `WAIT_LIMIT`. A session with more than 80 laps per
  driver (no F1 session since 2018 has that many) would start the warm-up in
  that driver's wave, which is control's behaviour, only later.
- **Not hedged on the bridge.** A stalled bridged request is bounded by
  `cdn_hedge_max_delay` (4 s) and then goes to niquests (E9). The traces
  showed no stall, and this did not change.
- **Not done, and why:** tail duplication of first-batch stragglers (the
  queue drains at ~350 ms and the last request ends ~100 ms later, so at
  most ~20-60 ms is available, below this link's noise); a lower
  concurrency cap (inconclusive); pre-opening the 20 telemetry connections
  during `get_session` (it saves the ~50-130 ms handshakes but not slow
  start, opens 20 TLS connections for laps-only scripts, and would need its
  own A/B); building lap frames during the wave (DO_NOT_RETRY:
  streamed/overlapped assembly, and GIL work beside the wave is exactly what
  change 1 removed).
- **Polars still imports numpy inside the wave** (the native decoder's
  arrays, 87 modules) and pyarrow after it (the background frame-tier
  writer: `pyarrow.lib`, `pyarrow.ipc`). Both are GIL work beside the wave or
  at exit, and a follow-up candidate for cold polars `driver_tel`.
- Raw data: `.agents/perf-naxos/trace_ctl_{pandas,polars}.json` (control
  timelines), `exp_*.json` (experiments), `N8_cold_*.json` (A/Bs; pooled by
  `tools/perf/naxos_n8_pool.py`), `N8_ab_warm_polars.json`, `sample_*.json`,
  `mods_*.json`. The `src/` change touches no tool; every harness I ran is a
  copy or a new file in `tools/perf/naxos_n8_*.py`.
