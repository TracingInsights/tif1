# N10. Warm pandas `fetch_all_laps_telemetry()` and the merged-telemetry build

Branch `perf/naxos-N10`, tree `/tmp/naxos/N10`, measured on 2026-11-06
against the frozen control `/tmp/naxos/control` (d28ce70). Both arms read
one cache copy, `/tmp/naxos/warm-N10`. `git commit` is denied in this
sandbox, so everything is staged. The two intended commits and their file
split are in `N10_COMMITS.md`.

## 1. Hypothesis

N10 asked where the warm `fetch_all` time goes once the row reads (D9) and
the lz4 decode (G1/G6) were off the critical path: per-lap frame
construction, the TF1 decode, the widen, or the dict build. It asked to cut
the largest stage.

Profiling found a stage none of the earlier rounds measured: **cyclic GC
passes that free nothing**.

- **Inside `fetch_all`.** The frame-tier read builds the race's 1128 lap
  frames under `_suspend_gc()` (Rhodes R3). That leaves ~55 000 GC-tracked
  containers in generation 0. The first young collection after GC is back on
  traverses all of them, as a 9-10 ms gen-1 pass, and collects 0 objects.
- **Inside `get_session()`.** The same thing happens on a larger scale.
  `import pandas` (and polars) creates ~150 000 long-lived module objects
  with GC on. That costs ~50 young collections, all of which free nothing:
  26-33 ms of GC inside the pandas `get_session()` and 11 ms on polars. It
  also leaves those objects in the young generations, so the collections of
  the work after the import traverse them again (`car_data_loop`'s one
  gen-1 pass, 3-4 ms; the notebook loop's gen-1 passes).

The hypothesis I tested: moving the survivors of such a burst straight into
the oldest generation removes those passes without changing any value or
any garbage the collector frees. A full collection still visits these
objects. The young collections, which never find garbage among them, no
longer do.

## 2. What changed

**The mechanism: `src/tif1/core_utils/gc_control.py` (new, stdlib only).**

- `suspend_gc(*, promote=False)` is the Rhodes R3 context manager, moved
  here. `cache._suspend_gc` is the same function object, so every existing
  import works.
- With `promote=True`, a normal exit calls `promote_young_objects()`, which
  runs `gc.freeze(); gc.unfreeze()`.
  - `gc.freeze` splices every generation's list into the permanent
    generation. `gc.unfreeze` splices the permanent generation back into the
    oldest one.
  - On the generational collector of CPython 3.11-3.13 that is two list
    merges, O(1). Measured: 0.00-0.02 ms with a 1 M-object heap
    (`tools/perf/naxos_n10_gc_promote_micro.py`).
  - Docs: https://docs.python.org/3/library/gc.html#gc.freeze and
    `gc.unfreeze` ("put them back into the oldest generation").
- Guards: `promote_young_objects()` does nothing when any of these holds.
  - The young generation is below its collection threshold (nothing to
    save).
  - `gc.get_freeze_count() != 0`. The application froze objects itself, for
    example a pre-fork server, and `unfreeze` would release them.
  - The interpreter is not a GIL build of CPython < 3.14
    (`gc_promote_ok()`, resolved once). The free-threaded collector walks
    the heap in `freeze`. The incremental collector of 3.14 re-marks the
    lists it moves. I could not run 3.14/3.15 in this sandbox, so they keep
    today's behaviour (see section 6).
  - The burst raised, or the caller had GC off already.
- `sysconfig` (for `Py_GIL_DISABLED`) is read only after the first promoted
  burst, which is the pandas or polars import. Both import `sysconfig`, so
  its 3 ms cold import never lands on tif1.

**Commit 1: frame bursts.**

- `cache.py`: `promote=True` on the read-side bursts whose results the
  session memoizes:
  - `_get_driver_frames` (the pandas `fetch_all` / batch path);
  - `get_telemetry_frames_batch`'s legacy per-frame rows;
  - `get_telemetry_frame_sources`;
  - `LazyDriverFrameSource` hydration;
  - `SessionMemo.materialize_telemetry`.
- `core.py`: `promote=True` on the two cold frame builds from payloads
  (`fetch_all_laps_telemetry_async`, `_frames_from_payloads`).
- Unchanged: the write-side bursts (serialization garbage, background
  writer thread), the laps-frame unpickle and the merged-batch assembly
  (few survivors).

**Commit 2: imports.**

- `lazy_import.import_promoted(name)`: a module already in `sys.modules` is
  returned untouched. Otherwise the module is imported under
  `suspend_gc(promote=True)`.
  - `LazyModule._lazy_load` loads through it. That covers pandas, numpy and
    `tif1.models` for pandas sessions, and numpy for polars sessions.
- `runtime.import_supported_polars` wraps its `import polars` the same way.
  The statement stays, so tests that put `None` or a fake into
  `sys.modules["polars"]` behave as before.
- `tif1.__getattr__` resolves its lazy exports (`tif1.get_session` ->
  `tif1.core`) through `import_promoted`. That removed the last gen-1 pass
  in `get_session` (during `tif1.core`'s own stdlib imports: `inspect`,
  `ast`, `orjson`).
- `AGENTS.md`: `gc_control.py` added to the `core_utils` list.

## 3. Measurements

**Box load.** Other Naxos agents kept the load average at 25-68 on 32 cores
for the whole session: control `get_session` measured 422-925 ms against
the 392 ms baseline. Wall medians therefore swing by up to 2x between
pairs. The GC time itself (from `gc.callbacks`) is deterministic, and the
main thread's CPU time is much less load-sensitive than its wall, so both
are reported next to the walls.

### Where the warm pandas `fetch_all` went (control, fresh process)

`naxos_n10_stages.py` and `naxos_n10_steps.py`, ~95 ms phase:

| stage | ms |
|---|---|
| index query + submit | 3-4 |
| waiting on worker rows | 4-9 |
| `DriverFrameSource.__init__` × 20 | 41-48 |
| ... of which `str` column decode | 9.5 uncontended, ~19 with the workers running |
| ... of which the constant object block (`Source`/`Status`/`Driver`, 1 MB of fresh memory per driver) | 9.6 uncontended |
| ... of which the direct-blocks probe (once per process) | 5-9 |
| per-lap frame builds (1128 × ~24 us) | 25-30 |
| **the gen-1 GC pass after the burst** | **8.6-10.7** |

The other stages were tried and left alone:

- **`str` decode.** Building the large_string buffers with numpy was 4x
  slower; the dictionary cast was no faster. The Arrow `take` (~0.4 ms per
  43 k rows) is the floor.
- **Object block.** A broadcast assignment saves ~12%. The rest is page
  faults on fresh memory.
- **Per-lap builds.** Already hand-assembled (Pergamon Q18).
- **Collecting every row before decoding** (no GIL contention with the
  workers). The decode drops 44 -> 34 ms, but the total grows: 82 -> 88 ms.

## 5. CHANGELOG paragraph

- Warm sessions no longer pay for cyclic-GC passes that free nothing.
  - **Lap frames.** A pandas `fetch_all_laps_telemetry()` builds a race's
    1128 lap frames with GC paused. The first young collection afterwards
    used to traverse all ~55 000 of their containers (a 9-10 ms pass) and
    find no garbage.
  - **Imports.** `import pandas` ran ~50 such collections (26-33 ms of a
    warm pandas `get_session()`, 11 ms with polars) and left its ~150 000
    module objects for the collections after it to traverse again.
  - **The fix.** These bursts (the read-side frame builds, and the first
    import of pandas, numpy, polars and `tif1.core`) now run with GC paused
    and end with `gc.freeze(); gc.unfreeze()`, which moves their survivors
    straight into the oldest generation in O(1). Full collections still
    visit them.
  - **Numbers** (fresh process, 2025 Bahrain race, a loaded box, 12
    interleaved pairs):
    - GC inside `get_session()`: 26-33 -> 0 ms;
    - pandas `fetch_all_laps_telemetry()`: 161 -> 133 ms;
    - its whole script: 866 -> 759 ms (10/12);
    - `get_session()` main-thread CPU: -13 to -66 ms;
    - polars `laps` / `all_tel` / notebook scripts: -5 to -10% (9/12).
  - **Where it applies.** GIL builds of CPython 3.11-3.13. Skipped on
    free-threaded builds, on 3.14+ (incremental collector), and in a process
    that froze objects itself.

## 6. Notes for the integrator

- **Semantics.** Promotion changes when, not whether, cyclic garbage is
  freed.
  - Young cyclic garbage that exists at the moment of a promotion (the
    user's or the import's) moves to the oldest generation. It is freed at
    the next full collection instead of the next young one, so its
    `__del__` / weakref callbacks run later.
  - A test pins that a cycle built inside a promoted burst is still freed
    by `gc.collect()`.
  - Promoted objects are not added to CPython's `long_lived_pending`, so
    full collections become rarer, not more frequent.
- **Applications that use `gc.freeze()` themselves** (gunicorn/uWSGI
  pre-fork, Instagram-style) are left alone: any non-zero
  `gc.get_freeze_count()` skips the promotion, because `unfreeze` would
  release their frozen objects.
- **Delphi D1's exit freeze** is unaffected: it runs at exit, after every
  promotion. `test_exit_gc_freeze.py` needed its spy to ignore the runtime
  `freeze`/`unfreeze` pairs; its assertions are unchanged.
- **CPython 3.14/3.15 are not covered.** The sandbox denied running the
  installed 3.14/3.15 interpreters, so `gc_promote_ok()` keeps them on
  today's behaviour.
  - 3.14 reintroduced the incremental collector. Its `_PyGC_Freeze` walks
    the moved lists to set their space bits: O(n), though cheap per object.
    The young/old structure also differs, so the saving may be smaller or
    larger.
  - Follow-up: run `tools/perf/naxos_n10_gc_promote_micro.py` and
    `naxos_n10_import_gc.py` on 3.14 (CI tests 3.11-3.15). If promotion
    pays there, widen the gate.
  - Free-threaded builds stay off: the free-threaded `freeze` walks the
    whole heap.
- **The `sysconfig` read in the gate** is deferred to the first promotion,
  which follows the pandas/polars import. Both import `sysconfig`. A cold
  `sysconfig` costs 3 ms, and `import tif1` alone never pays it.
- **The interactive preload** (`tif1._preload_third_party`, a REPL-only
  daemon thread) still imports pandas with GC on. Running it under
  `suspend_gc` would pause GC process-wide while the user's cell runs. I
  left it alone; the main thread's `import_promoted` finds pandas loaded and
  does nothing.
- **Overlap with N4** (deferring pandas/polars submodules) and **N1**
  (numpy's OpenBLAS start). These are orthogonal and stack: fewer modules
  imported means fewer objects to promote, but whatever is imported still
  runs without young collections. When merging N4's `LazyLoader` deferrals,
  the deferred submodules execute later, outside `import_promoted`. Wrap the
  ones tif1 triggers on a hot path the same way if they show up in
  `naxos_n10_gc_phases.py`.
- **Perf gate baseline.** The gate passes; I did not rewrite
  `tests/perf_gate/baseline.json`. The change is meant to move
  `get_session` (both backends) and the pandas `all_tel` phase down, so the
  integrator should rewrite it on a quiet box after merging (not on this
  one, at load 25-68).
- **The probes were run from this tree.** `naxos_n10_cpu_ab.py` is my copy
  of the `delphi_warm_bench` workloads: same session, offline, fresh
  process, alternating arm order. It adds main-thread `thread_time()` per
  phase, because the walls were unreadable at this load.
- **Remaining `fetch_all` stages**, for whoever comes next:
  - ~20 ms of the 20 `DriverFrameSource` inits are the `DriverAhead` `str`
    decode plus the constant object block. Both are page-fault/allocation
    bound; storing `Source`/`Status`/`Driver` as one object array shared
    across drivers would break frame independence.
  - ~25 ms is the 1128 per-lap builds (9 blocks each, ~24 us).
  - The direct-blocks probe (5-9 ms once per process) imports
    `pyarrow.pandas_compat`. Cheapening it is a possible small follow-up
    (any warm pandas telemetry workload pays it).
