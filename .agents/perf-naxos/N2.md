# N2. A warm polars `load()` keeps the driver rows lazy (Delphi D5 for polars)

Branch `perf/naxos-N2`, tree `/tmp/naxos/N2`. Measured against the frozen
control `/tmp/naxos/control` (d28ce70) on 2026-11-06, both arms on
`/tmp/naxos/warm-N2`. The box was shared with the other Naxos agents
throughout: the load average was 20-70 on 32 cores, and `get_session`,
which runs before any changed code, moved by up to ±120 ms between pairs.
Read the in-process phases and pairs won; the walls carry that noise.
`git commit` was denied in this session. Everything is staged, and the
intended message is in `N2_COMMITS.md`.

## 1. Hypothesis

A warm polars `session.load()` (telemetry on, the default) read every
driver's Arrow IPC frame-tier row (`_get_polars_ipc_frames`, ~115 ms of a
race's ~125-150 ms `load`) to memoise all 1128 lap frames. Pandas stopped
doing this in Delphi D5. The hypothesis: if `load()` learns from the rows'
`laps` column (the `[lap, rows]` spans, read without the blobs) that the
tier holds every lap, and reads a row only when one of its driver's laps
is first touched, then `load()` costs ~10 ms. `load()` then one driver's
telemetry should read one row. D5's minimax rule applies: a loop over every
lap after `load()` must not get materially slower. Frames must be exactly
the ones the eager load gives.

Result: holds. `load()` 125-157 → 9-14 ms. The `load_only` wall drops 34%,
`load()` + one driver 32%, `load()` + two drivers 14-17%. A loop over every
lap is unchanged because a new `iterlaps()` walk hint makes it read all rows
at once. The cost: scripts that touch three or more drivers outside an
`iterlaps()` walk (a `for d in session.drivers` loop, a list of 4-6
drivers) pay up to two lone row reads more than the eager load (+26 to
+54 ms in-process under this box's load; section 3.3).

## 2. What changed

`src/tif1/cache.py`
- `Cache.get_telemetry_frame_laps(..., lib="pandas" | "polars")`: the D5 lap-list
  query now also reads the polars IPC table's `laps` column (the `[lap, rows]`
  spans; the lap numbers come back). It costs one SQL query and no blob
  reads. An unreadable span list leaves its driver absent.

`src/tif1/core.py`
- `Session._telemetry_load_pending` → `_polars_telemetry_load_pending` (polars,
  cache on, not ultra-cold):
  - A session the cache does not hold, or laps the tier lacks, keep the eager
    batch exactly as before. Laps the tier lacks may be tolerated only when
    the negative-result cache knows they are missing, which the eager batch
    also skips.
  - Otherwise the pending laps are registered as `load(telemetry="lazy")`
    registers them (`_set_lazy_telemetry_refs`, factored out of
    `_register_lazy_telemetry`), and `load()` reads nothing.
  - Cold loads: `_session_cache_available()` is false, so the path is
    unchanged.
- `_ensure_lazy_telemetry` (the existing lazy-wave dispatcher): on a cached
  session the first `_LAZY_CACHED_LONE_WAVES = 2` waves read their drivers
  alone, and the third reads every driver still pending in one pooled batch.
  Before, the second wave batched (D5's rule). Section 3.3 has the
  measurement behind the cap. Cold lazy waves (CDN, stream) are unchanged.
- `_ensure_lazy_telemetry_walk(walk_refs, driver)`: on a cached session,
  while `driver` is still pending, one wave brings every driver of the
  `iterlaps()` walk the lap came from. A loop over the session's laps reads
  all rows in one pooled batch, the eager load's read, instead of lone reads
  followed by a batch.
- `_memoized_telemetry`: when memoised frames and tier frames mix (a lazy
  `load()`, a touched driver, then `fetch_all_laps_telemetry()`), the map is
  put in laps-row order (`_in_lap_order`). This order is already promised
  by `_in_lap_order`'s docstring. Without it, the touched drivers came
  first, unlike the eager load, a difference the delphi digest cannot see
  because it sorts the keys.

`src/tif1/models_polars.py`
- `_LapWalk`: shared by the laps of one `PolarsLaps.iterlaps()` call; it builds
  the walk's `(driver, lap)` refs on first use from the rows `iterlaps`
  already materialises. `PolarsLap._walk` (class default `None`).
  `PolarsLap.telemetry` (and therefore `get_car_data`, `get_pos_data` and
  `get_telemetry`) calls the session's `_ensure_lazy_telemetry_walk` first.
  Per lap this costs one attribute read and one call that returns at once
  after the batch.

Tests
- New `tests/unit/test_naxos_n2_polars_lazy_load.py` (17 tests, real SQLite
  cache in `tmp_path`, offline). They cover:
  - a warm `load()` reads no row;
  - two lone reads, then one batch;

  - a driver batch and `fetch_all` after a lazy load (laps-row order);

- `tests/unit/test_lazy_telemetry_load.py`: the D5 second-wave test now

Tools (`tools/perf/`, run from the repo root)

### 3.2 The notebook is neutral: the same read in a different place

The instrumented probe (`naxos_n2_notebook_probe.py`, 8 reps, load
average ~24) runs the notebook's `load()`, eight picks and `iterlaps`
telemetry loop. It times the frame-tier reads inside them:

| arm | load | of which tier read | picks | loop | of which tier read | total |
|---|---|---|---|---|---|---|
| control | 129.6 | 115.1 (1 read) | 3.2 | 40.8 | 0 | 173.6 |
| candidate | 8.8 | 0 | 3.2 | 166.4 | 118.9 (1 read) | 178.4 |

The walk turns the loop's first lap into the one pooled 20-row read that
control's `load()` did. The ~6 ms of frame adoption moves with it. Without
the walk (first A/B, `N2_ab_polars_v1.json`, D5's lone read then batch),
the loop paid a lone read plus a 19-row batch: notebook 696 → 739 (3/8).

### 3.3 The lone-wave cap: why two (`N2_lone_cap_probe_v2.txt`, 8 rotations, load ~20-28)

`load()` + access, in-process ms (medians; walls in the file). The cap
is the number of lazy waves read alone before one batch:

| shape | control (eager) | cap 1 (D5) | **cap 2 (shipped)** | cap 4 |
|---|---|---|---|---|
| 2 drivers (VER, LEC) | 129 | 130 | **45** | 44 |
| top 2 (PIA, RUS) | 158 | 156 | **43** | 54 |
| 4 drivers | 139 | 199 | 165 | 130 |
| 6 drivers, shuffled | 159 | 163 | 175 | 198 |
| `session.drivers` loop | 179 | 190 | 176 | 225 |

A polars row read alone costs 10-25 ms (more under load). The pooled
batch costs ~115 ms for 20 rows on a quieter box, and its cost hardly
shrinks with fewer rows under contention: 16 rows 190 ms against 20 rows
191 ms at load ~30 (`naxos_n2_notebook_probe.py` with
`N2_PROBE_DRIVERS`).

- Cap 1 makes every shape with two or more drivers ~one lone read worse
  than the eager load, including the 2-driver comparison.
- Cap 2 wins the 2-driver shapes by 80-115 ms, and its worst case is two
  lone reads above the eager load: +16..+26 ms here, +26..+54 ms in the
  final A/Bs under heavier load.
- Cap 4 also wins 3-4 drivers, but costs ~4 lone reads (+40..+46 ms) on
  the drivers loop and on 5+ drivers.

An earlier version of this branch batched on the second wave when it
continued the previous one in laps-row order (E5's `_walks_lazy_order`).
I removed it: with cap 2 it saves at most one lone read on a drivers
loop, and it turned the top-2 comparison (P1 and P2 are adjacent) back
into a batch.

## 4. Verdict: SHIP

- `load()` on a warm polars race: 125-157 → 9-14 ms.
- `load_only` wall -34% (7/8). `load()` + one driver's fastest-lap car data
  -32% (8/8). `load()` + two drivers -14% / -17% (7/8, 8/8).
- A loop over every lap after `load()` costs what it did: the notebook was
  8/12, 5/8 and 4/8 across three runs, and the instrumented probe puts the
  same 115-119 ms read in the loop instead of in `load()`.
- Frames, dtypes, chunks, classes and `fetch_all` order are identical
  (0/131, 0/133, 0/3562 ×2).

What it costs: scripts that touch three or more drivers outside an
`iterlaps()` walk pay two lone row reads on top of the read the eager
load did. That is +16..+26 ms in-process at load ~20-28 and +26..+54 ms
in the final A/Bs at load ~30 (`load_then_drivers_loop` 1/8 and 5/12 on
the wall, `load_then_6_shuffled` 1/8 and 5/12, `load_then_4_drivers` 4/8
and 6/12). The cap is one constant (`core._LAZY_CACHED_LONE_WAVES`).
Setting it to 1 gives D5's strict minimax (every multi-driver shape +1
lone read, the 2-driver win lost); section 3.3 has the table for choosing.

## 5. CHANGELOG paragraph

- A warm polars `Session.load()` no longer reads every driver's
  telemetry frame-tier row. Those reads were ~115 ms of the ~130 ms
  `load()` for a 2025 race. `load()` now reads the rows' lap spans and
  leaves the rows to the first access of each driver's laps, as pandas has
  done since Delphi. `load()` then `laps`/`results` costs 11 ms instead of
  134 (444 -> 292 ms per process). `load()` then one driver's fastest-lap
  car data reads one row (373 -> 254 ms), and two drivers read two rows
  (385 -> 330 ms). The third driver touched reads every remaining row in
  one batch. A loop over `laps.iterlaps()` reads all rows at its first
  telemetry access, which is the read `load()` used to do, so the notebook
  workload is unchanged. Scripts that touch three or more drivers outside
  such a loop pay two single-row reads on top of that batch (+20-50 ms).
  Laps the frame tier does not hold, and cold sessions, keep the eager
  load.
- `fetch_all_laps_telemetry()` returns its frames in laps-row order when
  some drivers were already read before the call. Before, a lazily loaded
  driver that had been touched came first.

## 6. Notes for the integrator

- **Policy constant.** `_LAZY_CACHED_LONE_WAVES = 2` applies to every
  cached lazy session: the new default polars `load()` and an explicit
  `load(telemetry="lazy")` on a warm polars session. Cold lazy waves keep
  the per-driver waves and stream lookahead. D5's rule (second wave
  batches) was the previous behaviour of the cached `telemetry="lazy"` path.
- **The walk hint is iterlaps-only.** `for d in session.drivers:` cannot
  carry a hint (a plain list). An E5-style background read-ahead for
  polars would take the 3+-driver shapes from "two lone reads + batch" to
  roughly "two lone reads". E5's lifecycle work (exit hook, close, fork)
  would apply. That is a separate hypothesis. Polars' pooled reader
  (`pl.read_ipc`) releases the GIL, while the lone stream reader holds it.
- **Contention sensitivity.** The pooled 8-thread IPC read is very sensitive
  to box load: 115 ms at load ~20, 190 ms at ~30, 500-900 ms at ~60-70
  (`naxos_n2_batch_probe.py`). Every arm here was interleaved, but absolute
  numbers from this session overstate all reads. On a quiet machine both
  the lone reads and the batch are cheaper, so the worst case shrinks too.
- **Tier coverage rule.** The lazy path needs the IPC spans to cover every
  pending lap, apart from laps the negative-result cache knows are missing.
  The perf gate's 4-driver fixture therefore stays eager, and so does a
  cache that holds only some drivers' rows. Rows in the legacy per-frame
  `telemetry_frames_pl` table count as not covered.
- **Errors move with the reads.** With a lazy load, a corrupt IPC row
  surfaces at the first access of that driver: the wave falls through to the
  payload tier, then the per-lap path, exactly as `telemetry="lazy"` does.
  An eager load hit it inside `load()`. Frames and fallbacks are the same.
- **Memory.** Untouched drivers are never decoded. A loop or `fetch_all`
  holds what the eager load held.
- `delphi_parity.py` does not call `load()`; `naxos_n2_load_parity.py` is
  worth folding into the round tooling for any change to the lazy paths.
