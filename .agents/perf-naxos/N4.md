# N4. Defer heavy modules that pandas/polars import but tif1's paths never use

Verdict: **REJECT**. Module-level deferral cannot reach the expensive parts
of `import pandas` or `import polars`. Every heavy subtree is pulled in
either by a `from x import name` (the import system must run the module to
bind the name) or by a module-level attribute read in another module. Example:
`pandas.core.arrays.arrow.array` builds `ARROW_CMP_FUNCS = {"eq": pc.equal, ...}`
at import time, which forces `pyarrow.compute`. The modules that can be deferred
and that tif1's eleven warm workloads never touch add up to ~16 ms of
importtime. ~12 ms of that is stdlib modules, and deferring stdlib modules is
unsafe: orjson segfaulted, and polars' own lazy numpy proxy raised. The safe,
package-private remainder is ~4 ms. The best safe variant is that remainder plus
a memo for `pyarrow.compute`'s docstring scrape. It does not move any measured
wall: pandas `laps` 478 -> 489 ms (3/8 pairs), `all_tel` 774 -> 771 (6/8),
`notebook` 942 -> 924 (4/8); 16 pairs: `laps` 638 -> 622 (10/16),
`import_get_session` 604 -> 568 (7/16). Parity: 0/133 pandas, 0/131 polars.
The branch holds that variant, tested, lint/type-clean and parity-clean, for
reference only. Nothing on it should be merged except, optionally, the
measurement tools.

## 1. Hypothesis

A warm pandas script is ~470 ms, of which ~340 ms is `import pandas`.
`-X importtime` shows large subtrees that tif1 never seems to need:
`pyarrow.compute` 40 ms, `pandas.core.groupby` 55, `pandas.io`,
`pandas.plotting`, `numpy._core._add_newdocs` 25, and on polars `polars.io`
40 and `polars.functions` 47. The idea: install a deferral
(`importlib.util.LazyLoader` or something narrower) just before tif1 imports
pandas/polars, so these modules are created but executed only on first use.
Users who import the modules themselves must still get complete, working
modules. Nothing may change for a process that imported pandas before tif1.

## 2. What changed (and what was tried)

### 2.2 Why the stdlib `LazyLoader` cannot be used

Measured with a ten-line script: after `LazyLoader` creates
`pyarrow.compute`, a *second* `import pyarrow.compute as pc` statement loads
it. CPython's `import_ensure_initialized` (Python/import.c)
reads `mod.__spec__` to check `_initializing` on every import of a module
already in `sys.modules`, and `_LazyModule.__getattribute__` loads on any
attribute, `__spec__` included. pandas imports `pyarrow.compute` from several
modules, so a stdlib lazy module would load at the second import statement.
The PEP 810 text also records the documented limits of `LazyLoader` (no
`from ... import`, spec resolution cost), and scientific-python's
`lazy_loader` discourages `load()` of subpackages because the parent loads
eagerly.

### 2.3 The deferral mechanism (kept on the branch)

`src/tif1/core_utils/deferred_imports.py`:

- `DeferredModule`: a `ModuleType` subclass whose body runs on the first
  attribute read, set or delete *other than `__spec__`*, so later import
  statements bind the same object without loading it. It follows
  `LazyLoader`'s threading semantics. Another thread waits on the module's
  `RLock` while the body runs. A read from inside the body sees the partial
  module. A failing body removes the module from `sys.modules` and re-raises,
  as an eager import would. Only `SourceFileLoader`/`SourcelessFileLoader`
  modules are deferred: an extension module runs its init in `create_module`,
  so there is nothing to defer.
- `deferring(names)`: a context manager that puts a meta-path finder first on
  `sys.meta_path` for the duration of the block. It wraps the listed modules'
  loaders. Duck-typed: `importlib.abc` would import `importlib.resources`,
  which Delphi D2 removed from tif1's startup.
- `import_pandas()`: the first `import pandas` of the process, with
  `PANDAS_DEFERRED` deferred and the `pyarrow.compute` scrape memo active (see
  below). `core._load_pandas_models()` calls it when pandas is not imported
  yet. The polars path is untouched: no polars candidate is safe (2.5).
- `_pyarrow_compute_scrape_memo()`: while `pyarrow.compute` imports, its
  `_make_global_functions()` re-parses each options class's numpydoc
  docstring once per wrapper: 109 parses of 57 docstrings with pyarrow 26.
  The memo swaps `pyarrow.vendored.docscrape.NumpyDocString` for a
  per-docstring cache and restores it afterwards. Every wrapper's `__doc__`
  and `__signature__` are identical (digest-checked by the seam test).

### 2.4 The audit

`tools/perf/naxos_n4_defer_probe.py` defers each pure-Python module that
`import pandas`/`import polars` executes, one at a time (`--scan`). It
records whether the module stays deferred through the import, and if not,
which attribute read loaded it and from where. It then defers the survivors
together until nothing loads (`--fixpoint`), runs all eleven
`delphi_warm_bench` workloads with that set (`--workloads`), and times
interleaved pairs (`--time`, wall and main-thread CPU).

- pandas: 441 pure-Python modules, 45 stay deferred alone (plus `pandas`
  itself), and 41 remain after excluding side effects (below). All survive
  together. `N4_scan_pandas.json`, `N4_fix_pandas.json`.
- Touched by the workloads (`N4_wl_pandas.json`): `numpy.ma`, `pandas.api` (and
  with it all seven `pandas.api.*`), `pyarrow.types` (`is_string`/`is_time` on
  the first string column), `numpy._core._methods`/`_dtype`, `ctypes` (tif1's
  own huge-page buffer in `cache.py`), `pandas.compat.numpy.function`,
  `dateutil.relativedelta`, `pandas.core.methods.selectn` (`nsmallest` in the
  notebook's fastest laps).
- Never touched, stdlib (importtime ms in the `laps` workload): `tarfile`
  4.1, `pydoc` 2.5 (with `pkgutil` 0.4), `socket` 2.1, `zipfile` 1.7, `gzip`
  0.5, `pprint` 0.4, `base64` 0.4, `hashlib` 0.4. Total ~12.1.
- Never touched, package-private: `numpy.random._pickle` 3.5 cumulative but
  0.2 self (`numpy.random` imports its children on the next lines anyway),
  `pandas.testing` 2.2 (with `pandas._testing`), `pandas.core.groupby.base`
  1.5, `numpy.lib.format` 1.0, and ten modules of 0.1-0.4 each. ~4-5 ms real.
- Excluded for import-time side effects: `pandas._config.dates` (registers
  the `display.date_dayfirst`/`date_yearfirst` options, so `pd.get_option`
  would raise), `numpy._core._add_newdocs`/`_add_newdocs_scalars` (the
  docstrings), `numpy._distributor_init` (the Windows wheels' DLL setup), and
  `numpy.lib.scimath` (its `array_function_dispatch` decorators register in
  `numpy._core.overrides.ARRAY_FUNCTIONS`, which `numpy.testing.overrides`
  reads). The final 15 (`PANDAS_DEFERRED`) were AST-checked: their bodies and
  those of their children (`pandas._testing.*`) define names only.
- polars: 265 pure-Python modules, 7 stay deferred alone, all of them stdlib
  except `polars.plugins`: `tokenize`, `hashlib`, `email`, `zipfile`,
  `importlib.metadata` (6.3 cumulative), `uuid`. The eleven polars workloads
  never touch them (`N4_wl_polars.json`), but see 2.5.

### 2.5 Why stdlib modules must not be deferred

- `uuid` deferred: **orjson's extension segfaults at init**. Its Rust code
  does `PyImport_ImportModule("uuid")` and reads the module's dict through
  the C API (`PyObject_GenericGetDict` + `PyMapping_GetItemString`). No
  `__getattribute__` runs on that path, so it gets NULL for the type and
  dereferences it. In tif1's own order orjson is initialised first, but any
  C extension imported later that reads a deferred module's dict directly
  crashes the same way. tif1 cannot audit every extension a user may load.
- `tokenize` deferred: the polars `notebook` workload raises
  `TypeError: 'module' object does not support item assignment` inside
  polars' own lazy numpy proxy (`polars._dependencies._LazyModule._import`).
  The proxy keeps its globals dict as `self._globals` and runs
  `self.__dict__.update(numpy.__dict__)`. Under the changed import order,
  numpy's namespace already held its `_globals` submodule at that point, so
  the next `np.ma` read failed. With nothing deferred, or with any of the
  other five deferred, the workload passes, and a minimal reproduction without
  tif1 does not fail. This is an import-order hazard, not a standing polars
  bug.

Both failures come from code outside tif1 that depends on what a stdlib
module looks like at a given moment. A deferral that a library installs on
behalf of its users cannot rule that out. Only pandas/numpy-private modules,
which only pandas/numpy code reaches and always through attribute reads, are
listed. `test_pandas_deferred_names_are_not_stdlib` pins that rule.

### 2.6 `pyarrow.compute`

It is imported by every pandas session (2.1). Its 27.5 ms self time is
`_make_global_functions()`: ~290 wrappers, each running `inspect.signature`
of its options class, a numpydoc scrape of that class's docstring, and four
`dedent`s. `tools/perf/naxos_n4_pc_memo.py` times `import pyarrow.compute`
alone (fresh process, pyarrow already imported), 20 interleaved pairs:

| variant | wall (ms, control -> memo) | paired median | pairs | main-thread CPU paired median |
|---|---|---|---|---|
| scrape memo (kept) | 72.2 -> 62.4 | -11.5 | 16/20 | -9.6 (15/20) |
| + `dedent` and `inspect.signature` memos (not kept) | 61.9 -> 45.4 | -14.7 | 15/20 | -14.8 (15/20) |

Wrapper digests are identical in both. The extended variant would have to
patch `textwrap.dedent` and `inspect.signature` process-wide during the
import, and `pyarrow.compute` binds `dedent` at its top, so the patched
function would stay bound there. Not kept.

## 4. Verdict

REJECT. The premise holds only for a small set of modules. pandas and polars
bind almost everything heavy by name at import time, so a module-level
deferral never sees it. The only large deferrable items either carry
user-visible side effects (numpy's docstrings) or are read on every tif1 path
anyway (`pandas.api` via pyarrow's pandas shim, `numpy.ma` via every Index).
What is left is ~16 ms of importtime, three quarters of it stdlib modules,
and deferring stdlib modules crashed or broke third-party code in two of seven
polars candidates. The safe remainder plus the `pyarrow.compute` memo is
~5-10 ms in theory. It is not measurable in a whole process on this box (4 of
5 A/B rows within noise in both directions; 0 of 5 meet the bar).

## 5. CHANGELOG paragraph

None: nothing ships. If an integrator kept the variant anyway, the entry
would read:

- A pandas session's first `import pandas` no longer executes fifteen
  pandas/numpy helper modules that tif1 never uses (`pandas.testing`, the
  masked/datetimelike accumulation kernels, `numpy.lib.format`, ...): each
  runs on its first attribute read instead. `pyarrow.compute` parses each
  options-class docstring once instead of once per compute function.
  Together this removes ~5-10 ms of CPU from the import. That is below the
  run-to-run noise of a whole warm script (no measurable change in `laps`,
  `all_tel` or `notebook` wall time). No value, docstring or signature
  changes.

## 6. Notes for the integrator

- `git commit` was denied in this sandbox: everything is staged on
  `perf/naxos-N4` and the two intended commit messages are in
  `N4_COMMITS.md`.
- Do not merge `src/` or `tests/` from this branch: they hold the rejected
  variant for reference, like Delphi D4. The probe tools
  (`tools/perf/naxos_n4_importtime.py`, `naxos_n4_defer_probe.py`,
  `naxos_n4_pc_memo.py`) are reusable for any later import-time work. The
  importtime tables and audit JSONs are next to this file.
- The real fix for `pyarrow.compute` is upstream. Caching
  `_scrape_options_class_doc` and `inspect.signature(options_class)` per
  options class in `pyarrow/compute.py` (e.g. `functools.cache`), plus the
  constant `dedent` blocks, would take ~15 ms off every `import pyarrow.compute`,
  and therefore off every `import pandas` with pyarrow installed. That is worth
  an Apache Arrow issue/PR. No existing issue was found (searched the pandas
  and Arrow trackers; closest: pandas#42863, ARROW-4637).
- The real fix for pandas' heavy subtrees is also upstream. PEP 810 (explicit
  lazy imports, accepted for Python 3.15, with the `__lazy_modules__`
  compatibility list for older Pythons) lets pandas/polars mark `pandas.io.*`,
  `pandas.plotting`, `polars.io.iceberg`, etc. lazy at their own `from`
  imports. That is exactly where a library outside the package cannot reach.
  Re-measure when pandas or polars adopt it; tif1 needs no change for that.
- Two hazards for anyone retrying a deferral from outside a package: (1) C
  extensions that read a module's dict through the C API (orjson does it for
  `uuid`, and also for `dataclasses`, `enum`, `zoneinfo` and, when serializing
  numpy, `numpy`) see a deferred module as empty and can segfault; (2) code
  that depends on import order (polars' `_LazyModule`) can break when a
  deferral shifts it. Also, stdlib `LazyLoader` modules load on the second
  `import` statement (`__spec__` read), which makes it a no-op for any module
  imported twice.
- A surprise for N1: `time.process_time()` during `import pandas` is ~3 s on
  this 32-core box (OpenBLAS's spinning pool threads), versus ~330 ms of
  main-thread CPU.
