# Naxos N3: polars telemetry arithmetic without numpy and without query plans

## 1. Hypothesis

In the warm polars notebook the four-lap telemetry analysis (`add_distance`,
`add_differential_distance`, `resample_channels("0.1s")`, `fill_missing`,
`slice_by_time`, `merge_channels`) cost 158 ms against 20 ms on pandas. The
cost was the numpy import inside `integrate_distance` (the first numpy use of
a polars process) and the query plans of `_resample_by_rule`. Rewriting these
methods on eager polars Series kernels and Python lists, with the same
values, should remove both costs. Profiling found one more: the first
`pl.Series(ndarray)` of a process imports `numpy.ma`, another ~22 ms. Before
the change each `resample_channels` call ran 13 query plans. The first one in
a process cost ~68 ms (polars starts its thread pool there), later ones ~9 ms.

## 2. What changed

`src/tif1/models_polars.py` is the only library file changed.

- **Distances.** `_differential_distance_values` now uses Series arithmetic.
  The divisors (3.6 and 1e9) are full-length Series because polars turns a
  division by a scalar into a multiplication by its reciprocal, 1 ulp off
  numpy. `max(diff, 0)` is a `zip_with` over `seconds - _shift_down(seconds)`.
  `integrate_distance` sums with `itertools.accumulate`, which matches numpy
  because `np.cumsum` adds sequentially (`_cumulative_sum`).
  `add_relative_distance` no longer calls `np.full`.
- **Fills.** `fill_missing` computes interpolation for Float64 columns of up
  to 20k rows with `_interpolated` (built on `_linear_fill_plan` and
  `_linear_fill`). This reproduces polars' `interpolate()`, which computes
  `low + step * ((high - low) / steps)`, followed by forward and backward
  fill. I verified the formula bit for bit, long gaps included. `_held`
  builds its fill positions from a list; the `Source` gap mask is a Series.
- **Resampling.** `_resample_eager` handles frames of up to 20k rows whose
  clocks are nanosecond and whose axis is sorted with no nulls, which covers
  every telemetry frame tif1 builds. Anything else returns None and goes to
  the old plan path, unchanged.
  - Bins come from a single pass over the axis list.
  - Continuous channels: a one-row bin keeps its value; a larger bin takes
    a Kahan sum in row order divided by its count (`_bin_mean`,
    `_kahan_means`). Empty bins go through `_linear_fill`. Clean channels
    share one fill plan, and their one-row bins are a single gather.
  - Held channels take the last row at or before each bin start (`bisect`,
    last of equal timestamps, as `join_asof` backward does), forward-filled
    then backward-filled across the bins.
  - Clocks are built from integer lists.
- **Slices and merges.**
  - `slice_by_mask` and `slice_by_time` use Boolean Series masks, with
    padding added as a constant-mask window.
  - `_slice_with_edges` and `_edge_samples` use `bisect` on lists.
  - `merge_channels` calls `_nearest_rows`, which does the same
    nearest-row rule with `bisect`.
  - Also numpy-free now: `_lap_number_mask` (Series `is_in`),
    `_get_lap_numbers`, `get_first_non_zero_time_index`, and `_take_rows`
    when given a list (`_index_series` builds the index in polars' index
    dtype, which `Series.__getitem__` uses without converting).
- **Size switch.** The list kernels (cumulative sum, `_nearest_rows`,
  `_held`) hand over to numpy above `_LIST_KERNEL_MAX_ROWS = 200_000` rows,
  or above 4096 rows when `numpy.ma` is already loaded, because numpy is
  free to call then (`_numpy_kernels`). Both paths give identical values.
- **Still on numpy:** `add_track_status`, unsorted or null clocks
  (`_stable_order`) and multi-driver joins. They are rare and outside this
  hypothesis.

Tests and tools:

- `tests/unit/test_naxos_n3_polars_arithmetic.py` (44 tests, new). Each
  kernel is checked against what it replaced, comparing the `repr` of every
  float: distances against the old numpy arithmetic (copied into the test);
  `_linear_fill` against polars' `interpolate().forward_fill().backward_fill()`;
  `fill_missing` against the expression path; the resampler against the plan

### Parity

- **`delphi_parity.py --lib polars`: 0 differing surfaces out of 131.** The
  pandas backend was not touched (a pandas session never imports
  `models_polars`), and the perf gate's pandas parity digests pass.
- **Wider digest (`naxos_n3_arith_digest.py`, 7632 surfaces).**
  - The candidate is deterministic: two runs are identical.
  - Results are identical with numpy (and `numpy.ma`) preloaded, so the
    numpy branch of every list kernel matches the list branch, including on
    the 40k-row whole-race frame.
  - Against control, 110 surfaces differ, all in `resample_*` or
    `merge_10hz` (which resamples). Nothing else differs: no distance, fill,
    slice or merge.
- **Why those 110 differ.** Control differs from itself on 111 surfaces
  between two runs. The query plan's grouped `mean` is not deterministic at
  the ulp level:
  - With one thread, on lap-sized frames, it adds a bin's rows plainly in
    row order.
  - With several threads it adds them in an order that depends on the
    threads. I reproduced this on synthetic data: 1000-row frames give
    different digests from run to run with 32 threads, but are stable with
    `POLARS_MAX_THREADS=1`.
  - On some other frame sizes it computes a deterministic Kahan sum. Which
    path runs depends on rows and groups in a way I could not pin down
    (500, 2000 and 5000 rows gave Kahan; 1000, 1500 and 2500 gave a plain
    sum).
- **The bin mean I chose.** The eager resampler always uses the Kahan mean.
  This matches control most often: 110 differing surfaces, against 1562 for
  a plain row-order sum. On bins of at most two rows the order cannot matter
  and the unit tests require exact equality there.
- **Size of the differences** (`naxos_n3_resample_ulps.py`, 892 resampled
  laps, 7.68M floats):
  - eager vs plan: 8711 values differ, 7711 of them by 1 ulp and 835 by 2
    ulps.
  - plan vs plan, the same frames resampled twice back to back: 5167 values
    differ, with the same shape (4423 by 1 ulp, 629 by 2).
  - The rare large ulp counts in both histograms are means near zero
    produced by cancellation (Z, acceleration channels at ~1e-17).
  - So the candidate is as close to the plan as the plan is to itself.
- **The other 7 surfaces.** Seven surfaces agreed across both control runs
  but differ from the candidate. All are race lap 35, which has a pit gap:
  there the plan took its deterministic plain-sum path on a multi-row bin,
  and the 1-ulp difference passes into the interpolated neighbours of that
  bin.

## 4. Verdict

**SHIP.**

- The polars notebook wall is 17% faster (716 → 596 ms, 13/16 pairs) and its
  analysis phase ~9x faster (162 → 18 ms).
- The four-driver `add_distance` script and the analysis-only workload win
  8/10 and 9/10 pairs.
- The process never imports numpy on these paths, which also removes the
  `numpy.ma` import (~22 ms) that the first ndarray-to-Series conversion
  triggered.
- Official parity is 0/131. The only value differences are at the 1-ulp
  level in multi-row resample bins, where control itself is not
  reproducible.
- The eager resampler is also deterministic, which the plan was not.

## 5. CHANGELOG

**Performance:** the polars `PolarsTelemetry` arithmetic no longer imports
numpy or runs query plans on a lap. `add_distance`,
`add_differential_distance` and `add_relative_distance` use Series
arithmetic, with full-length divisors so values match numpy bit for bit, and
an `itertools.accumulate` cumulative sum. `fill_missing`, `slice_by_time`,
`slice_by_lap`, `slice_by_mask` and `merge_channels` use Boolean masks,
`bisect` and list kernels. `resample_channels(rule=)` bins, averages,
interpolates and holds values on Series and lists for frames up to 20k
rows; larger or unusual frames keep the query plan. A fresh polars process
no longer pays numpy's import (~100 ms) plus `numpy.ma` (~22 ms) at its
first `add_distance`, and a 0.1 s resample of a lap takes ~3 ms instead of
~9 ms (~56 ms for the first one of a process). The warm polars notebook's
four-lap analysis drops from 162 to 18 ms and the whole notebook from 716 to
596 ms. Resampled values are now deterministic. On bins of three or more
samples they can differ by an ulp from the previous query plan, whose
grouped mean varied from run to run by the same amount.

## 6. Notes for the integrator

- **Resample ulps.** This is the one judgement call. Any future digest that
  hashes polars `resample_channels` output on multi-row bins was already
  flaky on control at the ulp level (111 of 7632 surfaces between two control
  runs). After this change it is stable. If another branch's digests were
  written from control, a resample surface can differ by the same ulp.
  `delphi_parity.py`'s four analysis laps happen not to.
- **Perf gate baseline.** I did not rewrite `tests/perf_gate/baseline.json`.
  The change moves the polars `notebook / telemetry_analysis_3` phase from
  157.7 to ~12 ms, and the gate passes as it is, because it only fails on
  slowdowns. Rewrite the baseline once after merging the round, on a quiet
  machine, so the gate guards the new level. Rewriting it here at load 30
  would have re-baselined every phase noisily and conflicted with the other
  branches.
- **Upstream canary.** The eager resampler reproduces three upstream
  behaviours: polars' `interpolate` formula, `join_asof` taking the last of
  equal keys, and the grouped mean (Kahan, with a one-row group returning
  its value as-is). The first two are pinned by tests against polars itself
  (`test_linear_fill_matches_polars_interpolate`,
  `test_resample_held_columns_take_the_last_of_equal_timestamps`,
  `test_resample_matches_the_query_plan`), so the canary will flag a polars
  change. These are public APIs, so there are no new `test_private_seams.py`
  entries. `pl.get_index_type()` is public.
- **Thresholds.** `_EAGER_RESAMPLE_MAX_ROWS = 20_000` keeps a driver's
  whole-race frame (~40k rows) on the plan. There the Python Kahan loop over
  ~40k rows times ~12 channels would cost more than the plan's fixed cost,
  which the plan amortises. `_LIST_KERNEL_MAX_ROWS = 200_000` is where a
  list kernel would cost about as much as numpy's import. Both are guesses
  from this box and could be tuned.
- **Still on numpy:** `add_track_status`, unsorted or null clocks in
  `merge_channels` / `slice_by_time(interpolate_edges=True)`, and
  `_resample_onto_dates` (`new_date_ref`, which uses query plans). They are
  rare, not in the notebook, and left alone.
- **Not checked:** the cold workloads (the change is CPU-side on warm
  frames) and `taskset` core-count variation.
- **Surprises:**
  - Python 3.12+'s `sum()` of floats is itself compensated, so a test
    expecting a plain sum needs an explicit loop.
  - A plan-free `Series[Series]` gather is fastest with an index Series in
    polars' index dtype (UInt32): a list or an Int64 index is converted and
    range-checked first.
