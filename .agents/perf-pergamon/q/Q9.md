# Q9: season-scale workloads (many cached sessions in one process)

## Verdict

- **Per-session time overhead: REJECTED (probe).** After the first session, the
  non-decode work per session is about 1.7 ms, against 30-170 ms of telemetry
  decode. No gen-2 collection runs during the loads, so there is nothing to
  freeze, memoize or probe more cheaply that would rise above the noise.
- **Retention across sessions: KEPT (memory and GC fix, time-neutral).** The
  process-global pandas lap cache pinned every loaded `Session` together with
  its whole telemetry memo. A notebook that loads a season keeps every race's
  frames alive for up to `MAX_CACHE_SIZE` = 100 sessions, even after it drops
  the sessions. The fix stores a session-free shallow copy. It changes no
  frame (parity 0/19 740) and adds about 0.2 ms per session.

## Workload and protocol

- Corpus: the user's cache (`~/.cache/tif1/cache.sqlite`, 1.2 GB), copied to
  `/tmp/tif1-q-Q9/a` and never written at the source. It holds 11 sessions
  from 2018 to 2025 (9859 frames). One candidate run over the copy upgraded
  the legacy per-lap rows to driver rows (P3): 0 legacy rows left, 11 × 20
  driver rows. That upgraded copy served **both** arms. The cache format does
  not change, so the arms share the same copy.
- `season_bench.py` (scratch, `/tmp/tif1-q-Q9/scripts/`) runs one fresh
  process per run. It does `get_session` → `.laps` →
  `fetch_all_laps_telemetry()` for all 11 sessions and drops each session
  before the next (`del`). It records per-session phases, `gc.get_stats()`
  deltas, minor faults and RSS. It also reports peak RSS, and after the loop
  the cost of a first and second `gc.collect()` and the count of tracked
  objects. `ab.py` interleaves control (`/tmp/tif1-pergamon-control/src`) and
  candidate runs, alternating ABAB/BABA.
- The box was busy throughout (load average around 11, other agents
  benchmarking). Whole-loop wall times varied by ±30 % between runs of the
  same arm.

## Probe: where the per-session time goes (2nd..11th session)

The steady-state loop takes 0.96-1.4 s for 11 sessions: 0.32-0.36 s for the
first (import chain) and 0.6-1.1 s for the other ten.

| step (per session, after the first) | real cost | notes |
|---|---:|---|
| `get_session` (event resolution, `Session.__init__`, probes) | 0.23 ms | schedule is `lru_cache`d; `_resolve_gp_name` runs twice per call at 0.08 ms each; `_session_cache_available` 5 calls, negligible |
| `.laps` (laps frame tier unpickle) | 0.45 ms | |
| `_telemetry_lap_refs` | 1.0 ms | `laps[[Driver, LapNumber]]` take + `astype`; direct column access would be ~0.1 ms. That saves ~9 ms per 10 sessions, below the noise, so it was not done |
| SQL read of the driver rows | 6-27 ms | 26-74 MB of lz4 per session (these seasons compress 1.5×); proportional to data, about 3 GB/s |
| decode (`decode_driver_frames`) | the rest | under cProfile, 0.19 s of 1.07 s across 10 sessions goes to per-frame `ArrowStringArray.__getitem__` slicing of `str` columns (`_group_parts`/`_decode_str`, ~8000 calls). This is decode work, so it is outside Q9 and noted for the decode owners |

GC during the loop: 1 gen-0 collection per session and **0 gen-1/gen-2**,
because R3's `_suspend_gc` covers the decode. `gc.freeze()` would therefore
save nothing during the loads. It would also be unsafe: a session is a nest
of reference cycles (`Session._laps` ↔ `Laps.session`, memo ↔
`Telemetry.session`, `PayloadLoader` ↔ bound methods), and frozen cycles are
never collected. **Rejected without implementation.**

## Finding: the lap cache pins every session

`Session.laps` stored the session-bound `Laps` itself in
`get_backend_lap_cache("pandas")`. A `gc.get_referrers` probe showed this
chain: `_global_lap_cache` → `Laps` → `Laps.session` → `Session` →
`SessionMemo` → all `Telemetry` frames. Measured in the control:

- RSS grows by 100-170 MB per race and never comes back. It reaches 1.44 GB
  after 11 sessions even though each session is deleted. A 24-race season
  would hold about 3 GB, and the LRU allows 100 sessions.
- About 500k gc-tracked objects stay alive, so every later full collection in
  the user's process scans them: ~100 ms per gen-2 pass, growing with each
  session.
- Side bug: a second `get_session` for the same event got laps bound to the
  **first** session (`s2.laps.session is s1`). That routes
  `s2.laps.pick_driver(...).telemetry` through the old session's memo and
  options.

Clearing the lap cache alone does not free memory right away. The session
cycles above mean a dropped session is reclaimed by the next gen-2
collection, not by refcounting. Both arms use the same memory until a gen-2
runs; after that, the candidate's memory is reusable.

## Change

`src/tif1/core.py`, `Session.laps` plus two new helpers:

- `Session._unbound_laps(laps)` (staticmethod): the global cache now stores
  `laps.copy(deep=False)` with `session=None`. This is a copy-on-write
  shallow copy, so no data is copied. The session keeps its own bound object.
- `Session._bind_cached_laps(cached)`: a cache hit returns a fresh shallow
  copy bound to the requesting session. Non-`Laps` or already-bound entries
  (e.g. planted by tests) are returned unchanged, so the existing identity
  test still holds.
- Polars is unaffected: its laps are plain frames with no back-reference.

Test: `tests/unit/test_q9_lap_cache_retention.py` (new file, kept out of the
shared contracts file to avoid merge conflicts). It asserts three things:

- The cached entry is a session-free `Laps` equal to the session's laps.
- A dropped session (with a memoized telemetry frame) is collected after
  `gc.collect()`.
- A cache hit binds to the new session, and mutating one session's laps
  leaves the other session and the cache entry unchanged.

All 3 tests fail on the control tree and pass on the candidate.

## Numbers

Parity (`digest.py`): laps plus every telemetry frame of all 11 sessions,
each loaded twice so the second load exercises the lap-cache hit. Digests
cover columns, dtypes, block count, block classes and
`hash_pandas_object` values. Control vs candidate: **0 mismatches of 19 740**
(22 laps frames + 19 718 telemetry frames). The candidate binds laps to the
requesting session in 22/22 loads; the control does so in 11/22.

Wall time is noise-dominated: the second batch overlapped `uv sync` and
pytest runs. The mechanism bounds the difference directly:

- `_unbound_laps` costs 0.22 ms per session load.
- `_bind_cached_laps` costs 0.29 ms per lap-cache hit, which is still below
  the 0.45 ms laps-tier read it replaces.

Both were measured best-of-200 on the loaded box (17 blocks, 1237×46). That
is at most ~2 ms per 10-session loop, with no other code path changed.

Same loop with a gen-2 collection after each session, which stands in for a
notebook whose own allocations trigger GC (3 pairs, `Q9_ab_collect.json`):

| metric | control | candidate | candidate lower |
|---|---:|---:|---:|
| **peak RSS** | **1440 MB** | **395 MB** | 3/3 |
| end RSS | 1419 MB | 366 MB | 3/3 |
| total wall incl. the collects | 2.171 s | 1.972 s | 3/3 |

In the control, each collect scans the growing pinned heap and frees nothing.

## Risks

- Identity: `s2.laps is s1.laps` no longer holds for a second session of the
  same event. They are equal frames bound to their own sessions. No test or
  code relied on cross-session identity; the existing
  `test_laps_property_uses_backend_specific_cache_when_enabled` (plain
  DataFrame planted in the cache) still gets the identical object back.
- Copy-on-write: the session's laps now shares blocks with the cached copy.
  An in-place value write to `session.laps` copies the touched block once
  (laps frames are ~1-2 MB). Before this change, such a write also leaked
  into every later session that hit the cache.
- Per-instance memos on `Laps` (`_merged_telemetry_cache`) are not carried
  into the cached copy, which is intended: they hold session-bound frames.
- Memory is only released at the next gen-2 collection (session cycles), not
  at `del`. Breaking those cycles is out of scope.
