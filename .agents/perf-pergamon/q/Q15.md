# Q15: the payload-tier warm load uses all cores

**Verdict: KEPT.** Native decoder: telemetry 1.068 s to 0.654 s (−39 %), candidate faster in 8 of 8 pairs.
orjson only: 2.316 s to 2.237 s (−3 %), faster in 5 of 6 pairs, no regression. polars: 2.239 s to 1.867 s (−17 %), faster in 4 of 4 pairs.
Frame parity 1452/1452 for pandas and for polars, with and without `tif1_native`.

## Hypothesis

A warm cache with empty frame tiers falls back to the payload tier. This happens with pre-frame-tier caches,
interrupted background frame writes, invalidated frame tables and `_FRAME_TIER_SCHEMA_VERSION` bumps.
In that case the payload tier decodes 1452 zstd JSON rows serially. Both zstd and the native parser release the GIL,
so decoding on worker threads should help on a multi-core box. K2 rejected this on a 1-core sandbox.

## Scenario and protocol

- `/tmp/tif1-q-Q15/noframes.sqlite` is a copy of the snapshot with every row of `telemetry_frames_drv`,
  `telemetry_frames`, `telemetry_frames_pl` and `telemetry_frames_pl_ipc` deleted, then vacuumed.
  It keeps 1452 payload rows, which are 19.8 MB of zstd and 78.9 MB of JSON.
- `tools/q15_payload_tier_ab.py` gives every run its own fresh copy of that file, because each run re-materializes the frames.
- It times a fresh-process `get_session` + `laps` + `fetch_all_laps_telemetry()`.
- Control and candidate alternate in interleaved pairs (ABAB...).
- `--no-native` simulates a missing `tif1_native` by making its import fail (`sys.modules["tif1_native"] = None`).
- The box has 32 cores. Load average was 8-15 from other agents during the runs.

## Profile of the control (in process, 1452 frames)

| stage | ms |
|---|---:|
| `get_telemetry_batch` total | 634 |
| SQL `fetchall` | 19-34 |
| zstd (`zstandard`, serial) | 130 |
| native parse (serial) | 370 |
| orjson parse instead of native (serial) | 440 |
| LRU sets / loop | ~40 |
| `_create_telemetry_df` × 1452 (assembly, GIL-bound) | 450-470 |

The frame write itself runs on the background writer after `fetch_all` returns, so it is outside the timed phase.

## Mechanism probes

zstd decompression of all 1452 rows, best of 5:

| binding | serial | 2 threads | 4 threads | 8 threads |
|---|---:|---:|---:|---:|
| `zstandard`, one decompressor per thread | 130 | 72 | 40 | 30 |
| pyarrow `Codec("zstd")` + `to_pybytes` | 138 | 79 | 48 | 48 |
| stdlib `compression.zstd`, 3.14 | 142 | 114 | 78 | 62 |
| stdlib `compression.zstd`, 3.15 | 151 | 132 | 88 | 75 |

All of them release the GIL. A single `zstandard.ZstdDecompressor` must not be shared between threads, so workers
use a thread-local instance. The stdlib module-level `decompress` is safe as is.

Native parse (`tif1_native.decode_telemetry`), all 1452 payloads already decompressed:

| threads | time |
|---|---:|
| serial | 370 ms |
| 2 | 208 ms |
| 4 | 196-205 ms |
| 6, static chunks | 111 ms |
| 8 | 150-197 ms |
| 16 | 160-212 ms |

It stops scaling past 6 threads. After the GIL-released scan, `to_py` runs with the GIL held. It builds the
`DriverAhead` channel as a Python list of `str`: 525 strings per payload, about 614k objects for the session.
This GIL-held part, not the parse, is the floor. TH4's 35 ms on 8 threads does not reproduce at this load.

`Cache.get_telemetry_batch` in process (fresh `Cache` each time), 6 rounds:

| decode workers | native: median / min | orjson: median / min |
|---:|---:|---:|
| 1 | 536 / 486 ms | 548 / 475 ms |
| 2 | 386 / 299 ms | 478 / 444 ms |
| 4 | 201-239 / 178-203 ms | 501 / 437 ms |
| 6 | 203-222 / 177-185 ms | 454 / 424 ms |
| 8 | 254-315 / 234-256 ms | 508 / 465 ms |

- Chunks per worker (1, 2, 4 or 8) make no measurable difference.
- I chose 6 workers, capped by the CPU affinity count, and 4 chunks per worker.
- orjson holds the GIL, so with orjson only the zstd step overlaps.

Streaming the decoded rows into the frame assembly (rejected). I wrote a generator that assembled frames while the
workers were still decoding. Fresh processes, median of `fetch_all` over 6 rounds:

| variant | median |
|---|---:|
| control | 1152 ms |
| decode everything, then assemble (sync path) | 766 ms |
| streaming | 896 ms |
| decode everything, then assemble (old async path) | 810 ms |

Streaming loses because of the GIL. The main thread holds it while assembling, so each worker waits up to the 5 ms
switch interval to get it back for `to_py`. Lowering `sys.setswitchinterval` to 0.05 ms brought streaming to about
700 ms, but that setting is process-global. Decoding everything first and then assembling is as good without it.
Streaming is not shipped. As before (F10), assembly stays serial.

## What changed

`src/tif1/cache.py`:

- `_zstd_decompress_mt` (new): a thread-safe zstd decompress, with a thread-local `ZstdDecompressor` for
  `zstandard` and the module function for stdlib zstd.
- `_decompress_frame_blob` and `_decode_sqlite_value` now use it. This also fixes a latent bug: P2's
  parallel frame decompression calls `_decompress_frame_blob` from worker threads. On legacy zstd frame rows,
  those threads shared one `ZstdDecompressor`.
- `_usable_cpu_count()` (new) uses `sched_getaffinity`.
- `_decode_payload_rows(rows, workers, min_parallel)` (new) yields `(driver, lap, raw, parsed)` chunks in
  completion order. Workers decompress, and also parse when `tif1_native` is present; otherwise the consumer parses
  with orjson as chunks complete. It is serial below 64 rows or with fewer than 2 usable CPUs, which covers K2's
  1-core case.
- Constants: `_PARALLEL_PAYLOAD_MIN_ROWS = 64`, `_PARALLEL_PAYLOAD_MAX_WORKERS = 6`,
  `_PARALLEL_PAYLOAD_CHUNKS_PER_WORKER = 4`.
- `Cache.iter_telemetry_batch` (new) is the body of the old `get_telemetry_batch` as a generator: memory hits first,
  then SQLite rows through `_decode_payload_rows`. `get_telemetry_batch` builds its dict from it under `_suspend_gc`.

`src/tif1/core.py`:

- `Session.fetch_all_laps_telemetry` (sync): when refs remain after the memo and frame tiers, it serves the payload
  tier synchronously through the existing `_fetch_telemetry_batch_from_refs`. Only refs still missing start
  `asyncio.run(...)`, and the async path then finds these frames in the memo. A payload-tier warm load therefore no
  longer imports asyncio or starts an event loop.
- Two helpers were extracted from `fetch_all_laps_telemetry_async` and are shared by both paths:
  `Session._frames_from_payloads` (the build loop) and `Session._schedule_frame_materialization`
  (the background writer).
- `_FRAME_MATERIALIZATION_LOCK` (new) serializes the background frame writes. A load served partly from the payload
  tier and partly from the network now schedules two writes. Per-driver rows are read, merged and written back, so
  two overlapping writers for the same driver would drop each other's laps.

`tests/unit/test_pergamon_contracts.py`, new Q15 section with 6 tests:

- parallel decode equals serial, with and without native;
- a corrupt row surfaces as `ValueError`;
- thread-safe zstd from 8 threads;
- the batch read uses the parallel decoder and fills the memory tiers;
- a payload-tier warm load is asyncio-free, its frames equal `_create_telemetry_df` of the stored payload, it keeps
  refs order, and the frame tier is materialized afterwards.

`tools/q15_payload_tier_ab.py` (new) is the A/B harness, with `--child`, `--no-native`, `--lib` and `--dump` for parity.

## Risks and notes

- **Threads per call:** a payload-tier batch of 64 or more rows starts up to 6 short-lived threads per call.
  Boxes with 1 usable CPU stay serial.
- **Corrupt rows:** in the batch path, a corrupt row now stops the batch after any chunks that already completed
  (logged, partial result). The old serial loop also stopped at the first corrupt row; which rows survive now
  depends on completion order.
- **Mixed loads:** in a load that is partly payload tier and partly network, the async path's result map lists the
  memoized payload-tier frames first, in laps order. The frame tier is written in two serialized writes instead of one.
- **Follow-up levers, not done here:**
  - Interning `DriverAhead` strings (or returning them as a numpy array) in `tif1_native`'s `to_py` would shrink the
    GIL-held part that limits decode scaling.
  - The polars payload-tier assembly takes about 1.8 s, against 0.45 s for pandas. It is a much bigger target than
    the decode.
