# Q10 — fastest-lap convenience paths on a warm cache

**Verdict: KEPT.** Every fastest-lap entry point is 2.2-3.8x faster as the first
telemetry call on a warm session. None of them imports `asyncio` any more.
Results are identical to the control: `equals`, dtypes, index, block layout,
subclass and `.driver`, for pandas and polars.

## Hypothesis

`Session.get_fastest_lap_tel`, `get_fastest_laps_tels(...)`,
`Driver.get_fastest_lap_tel` / `get_fastest_lap` were built for cold starts.
On a warm cache they still read the raw laptime payloads and do not use the
warm tiers.

## Probe (control, fresh process, first call after `get_session`, 2026 Monaco Race)

`tools/q10_fastest_probe.py` wraps every `Cache` method with a counter.

| entry | wall | tiers touched | asyncio |
|---|---:|---|---|
| `s.get_fastest_lap_tel()` | 38 ms | drivers.json + session_laptimes (json tier through `asyncio.run(fetch_multiple_async)`), one driver row of the frame tier | imported |
| `s.get_fastest_laps_tels()` | 54 ms | json tier (async), 21 telemetry payloads (`get_telemetry_batch`) + merged assembly | imported |
| `s.get_fastest_laps_tels(drivers=[3])` | 35 ms | same, 3 payloads | imported |
| `s.get_fastest_laps_tels(by_driver=False)` | 37 ms | same as `get_fastest_lap_tel` | imported |
| `s.get_driver(d).get_fastest_lap_tel()` | 29 ms | `get_driver` prefetch through `asyncio.run`, one driver row | imported |
| `s.get_driver(d).get_fastest_lap()` | 80 ms | `get_driver` prefetch (async), then `Driver.laps` built from the payload | imported |
| `s.laps.pick_fastest().get_telemetry()` | 17 ms | laps frame tier + one driver row | no |

Where the time went:
- `import asyncio` (~17 ms) plus `asyncio.run` for reads that are already cache hits.
- `_derive_driver_laptime_payloads_from_session`: about 5 ms. It gathered every
  cell separately and called `len()` again for every cell (62k calls).
- Splitting and scanning the session laptime payload when the laps frame tier
  already holds the answer.

## Mechanism (what changed, `src/tif1/core.py` only)

1. **`Session._cached_payloads_sync(paths)`** (new): a synchronous version of
   `fetch_multiple_async(use_cache=True)` that only handles cache hits. It does
   the same `Cache.get` (memory, then SQLite) and returns the same objects. It
   returns None if the session is cold, the cache is disabled, `ci_mode` is
   set, or any path misses. In those cases the caller keeps the async fetch
   unchanged. Used in:
   - `_fetch_laptime_payloads`, for the session-laptimes read and the pending
     per-driver reads;
   - `_prefetch_driver_lookup_and_laps`, so `get_driver` no longer imports
     asyncio on a warm session.
2. **`Session._run_fetch_multiple`** (new static helper): the existing
   `asyncio.run(fetch_multiple_async(...))` call, with its TypeError fallback
   for the simplified signature some tests patch in, written once instead of
   three times. `import asyncio` moved inside it. In `get_fastest_laps_tels`,
   the import moved inside `if requests:`.
3. **`_derive_driver_laptime_payloads_from_session`**: each driver's rows are
   one contiguous run in the session table. When they are, each column is now
   a single slice. Interleaved rows and short columns still use the old
   per-row gather, now with `len()` hoisted out of the loop. Output is
   identical (lists, `None` padding).
4. **`Session._fastest_lap_candidates_from_laps_tier(driver_requests)`** (new):
   pandas sessions only, and only when the session is cached and not
   ultra-cold. It reads the laps frame tier (about 2 ms) and selects laps by
   the same rules as the raw scan:
   - deleted laps and laps with no time or lap number are skipped;
   - within a driver, the first lap with the fastest time wins;
   - candidates follow drivers.json order, so `min()` and a stable sort break
     ties the same way.

   It returns None (the caller falls back to the payload scan) when the
   backend is polars, the tier has no frame, or the columns cannot be used.
   Used by `_find_fastest_lap_reference_from_raw` and
   `_get_fastest_lap_refs_from_raw`.

The async variants and the telemetry sources are not touched:
- single laps still come from the P6 driver row;
- `get_fastest_laps_tels` still builds its result from the telemetry payloads.

- `tools/q10_fastest_ab.py`: interleaved fresh-process pairs, alternating

## Parity

**Result frames.** For all 8 entry points, control and candidate results were
pickled and compared with `tools/q10_parity_check.py`. Pandas: type,
subclass, `.driver`, columns, dtypes, index, `equals` and block layout all
match. Polars (7 entries; `pick_fastest` is not available on polars laps in
either tree): schema and `equals` match.

**Fastest-lap selection.** `tools/q10_fastest_ref_gate.py` compares the
laps-tier per-driver candidates, the overall pick and the sorted reference
list against the raw payload scan. It ran on a copy of the user cache:
- 122 sessions from 2018 to 2025 (races, qualifying, practice) and
  2390 drivers: 0 mismatches. 9 tied fastest times were exercised. One
  session was skipped because it has no session_laptimes payload.
- 2026 Monaco: 21 drivers, 0 mismatches.

**Cold path.** On an empty cache dir in offline mode, both trees raise the
same `NetworkError` and fetch nothing. The unit test
`test_cold_session_keeps_the_async_fetch_pipeline` uses a stubbed
`fetch_multiple_async` and checks that the cold path still goes through it
(ultra-cold reference, session laptimes requested once). A partial cache hit
falls back to the async fetch for the whole request list.

## Rejected inside Q10 (probe numbers)

- **Building `get_fastest_laps_tels` from the frame tier (per-driver rows +
  concat) instead of the payload assembly.**
  - Reading 21 driver rows to get one lap each took 58.8 ms, against about
    6 ms for the payload batch read plus about 15 ms of assembly.
  - Parity also breaks: `DriverAhead` comes out as `object` instead of `str`,
    and the frame has 11 blocks instead of 19.
  - For 3 drivers the tier read is 8.8 ms, but the parity problem is the same.
- **Building `Driver.laps` / `get_fastest_lap` from the laps frame tier
  filtered by driver.** The control already returns a different frame on that
  path:
  - categories narrowed to the driver;
  - a different `index` column;
  - `DataFrame` instead of `Laps` when it goes through `get_fastest_laps`.

  So the result would not match the control. The remaining ~54 ms is
  `_process_lap_df` on the 66-row payload: about 45 ms, mostly
  `_replace_null_like_strings` and `_apply_laps_dtypes`. That is a separate
  hypothesis about first-call cost in the laps pipeline.

## Risks / integration notes

- **Laps-tier reference.** The fastest-lap reference on a warm pandas session
  now comes from the laps frame tier. If that tier were stale relative to the
  payload tier, the pick would follow the tier. That is what `session.laps`
  already shows the user. The 122-session gate shows identical picks.
- **Fewer side effects.** The warm `get_fastest_lap_tel` no longer fills the
  per-driver laptime payload memo. A later `get_driver(x)` reads the cached
  payload synchronously instead (sub-ms).
- **Possible conflicts.** `_fetch_laptime_payloads` and
  `_prefetch_driver_lookup_and_laps` had their `asyncio.run` blocks replaced.
  Any other wave-2 change to the same blocks (e.g. an asyncio-free
  `get_driver`) will conflict textually; the logic merges cleanly.
- **Checks.** `ruff check` / `ruff format --check` on `src/ tests/ tools/`:
  clean. `ty check src/tif1`: clean. Unit suite (`-n 8`): 1572 passed,
  coverage 85.71 %. Property suite: 81 passed.
