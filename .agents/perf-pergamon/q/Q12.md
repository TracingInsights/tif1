# Q12 — stronger compression level for frame-tier writes

**Verdict: REJECTED (noise on the read side, 3.4-10x on the write side).**

## Hypothesis

The per-driver pandas rows (`telemetry_frames_drv`, 22 rows, 23.13 MB for
the 2026 Monaco Race) are written with lz4 frame level 0
(`_compress_frame_blob`, python-lz4). lz4 HC (levels 3-12) should shrink
them 10-25 % with identical or faster decompression, so the warm batch read
(SQLite transfer of the blobs + GIL-released pyarrow lz4 decode) gets
cheaper while the extra compression CPU lands in the background writer.

## Mechanism measured (offline, 22 driver blobs, 72.5 MB raw)

| codec | stored | vs L0 | compress (serial) | pyarrow decode serial / 8 threads |
|---|---:|---:|---:|---:|
| lz4 L0 (current) | 23.13 MB | 100 % | 75 ms | 15.0 / 10.6 ms |
| lz4 L1 | 23.13 MB | 100 % | 46 ms | 14.1 / 9.5 ms |
| lz4 L3 (HC) | 20.44 MB | 88.3 % | 568 ms | 14.5 / 10.8 ms |
| lz4 L6 | 20.04 MB | 86.6 % | 866 ms | 12.6 / 9.7 ms |
| lz4 L9 | 19.94 MB | 86.2 % | 1353 ms | 11.1 / 9.0 ms |
| lz4 L12 | 19.84 MB | 85.8 % | 13.3 s | 7.8 / 13.6 ms |
| lz4 L16 | 19.84 MB | 85.8 % | 10.9 s | 7.5 / 6.9 ms |
| zstd-1 (pyarrow) | 19.86 MB | 85.8 % | 59 ms | 27.1 / 7.4 ms |
| zstd-3 | 17.86 MB | 77.2 % | 95 ms | 31.2 / 8.7 ms |

Side findings: python-lz4 and pyarrow's lz4 codec both release the GIL on
*compress* (L9 on 8 threads: python-lz4 226 ms, pyarrow 168 ms), but
pyarrow's compressor writes no content-size field in the frame header, so
its blobs would miss the parallel pyarrow decode path (`_lz4_frame_content_size`
returns -1) and fall back to serial python-lz4. python-lz4 HC keeps the
header, so the L3/L9 candidate caches were built with python-lz4. Block size
(64 KB default vs 1 MB / 4 MB) does not change the stored bytes. zstd-1
matches the HC size at L0-like compress cost, but serial decode is 2x slower
(27 vs 15 ms) — that is the path every single-driver read takes (P6 first
touch, P10 merged frame) — so it is rejected by the probe, as in K3/KR-6/U2.

## Protocol

- Candidate caches: copies of `/tmp/tif1-warm-q-base/cache.sqlite` with the
  22 driver rows re-compressed in place (`UPDATE ... SET frame`) at L3 and L9,
  then `VACUUM`. Row sizes confirmed: 23 133 500 -> 20 435 562 (L3) /
  19 936 388 (L9) bytes; file 69.7 -> 66.9 / 66.4 MB.
- Read wall: fresh process per run, `Cache.get_telemetry_frames_batch` on the
  1452 refs (driver tier), interleaved control vs candidate, box shared with
  other agents (load average 3-12 during the runs). Harness noise calibrated
  with an A/A run (control vs an identical copy).
- Writer wall: `Cache.set_telemetry_frames_batch` of the 1452 decoded frames
  into a scratch copy with the driver rows deleted (the exact call the
  background writer makes), `_compress_frame_blob` patched to the level.

## Why rejected

- The real read-side effect is about 2 ms on the ~40-55 ms batch read
  (SQLite transfer −2.2 ms at 14 % fewer bytes, decode within noise). That
  is ~4 % of the batch read and < 1 % of the 0.28 s warm load, and the
  decisive fresh-process first-read metric does not resolve it: medians
  moved −3.5, +21.8, −7.7 and +0.9 ms across four blocks while the A/A
  calibration alone shows a 1.4 ms / 7-of-10 asymmetry.
- The write side is not free: L3 makes the background writer 3.4x slower
  (0.43 s), L9 breaks the "well under 1 s" bound (1.2-3.1 s serial). L9 with
  a thread pool over drivers would land near 0.3 s (python-lz4 releases the
  GIL on compress) but needs a writer rewrite for a sub-noise read gain.
- zstd at any level regresses the serial single-row path 2x.

The polars IPC rows (25.2 MB, pyarrow IPC lz4) were not re-materialized:
the mechanism (fewer bytes through SQLite) is the same and its ceiling is
the same ~2 ms, so the pandas result settles both.

## Risks / notes for the integrator

- Legacy level-0 rows and HC rows are byte-compatible on the read side
  (same lz4 frame format, same content-size header when written by
  python-lz4); nothing to migrate either way.
- If a later series wants the 14 % disk saving regardless of read wall, the
  safe shape is python-lz4 L3-L9 compressed in a thread pool inside
  `_set_driver_frames` (never pyarrow's compressor, which drops the
  content-size header the parallel decoder relies on).
