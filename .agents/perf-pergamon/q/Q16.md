# Q16 — warm path inside a running event loop (Jupyter)

## Hypothesis

Inside Jupyter (a running asyncio loop on the main thread) the warm path still
pays for event-loop machinery: `_ensure_nested_loop_support` /
`nest_asyncio2.apply()` / `asyncio.run` on cached data, or `get_session`
(schedule loading, TH7 stale-while-revalidate refresh) touching asyncio.

## Verdict

- **Main hypothesis: REJECTED (falsified by probe).** Since Pergamon P5, no warm
  call reaches `asyncio.run`, `nest_asyncio2.apply()` or creates an event loop
  inside a running loop, pandas or polars.
- **KEPT, correctness fix (found by the harness):** `Session.fetch_all_laps_telemetry()`
  (and so `session.load()`) raised `RuntimeError: asyncio.run() cannot be called
  from a running event loop` in Jupyter whenever laps came from the frame tier but
  some telemetry was not in the frame tier. A P5 regression: before P5 the laps
  property always went through `asyncio.run` after `_ensure_nested_loop_support`,
  so nest_asyncio2 was already applied by the time telemetry ran.
- **KEPT, warm-path win (found by the harness, also applies to plain scripts):**
  the sync single-payload pipeline (`PayloadLoader.get`) ignored the
  negative-result tier that the async batch path honours. A warm
  `laps.pick_drivers("LEC").telemetry` on Monaco 2026 went to the network to
  re-confirm that `LEC/66_tel.json` is missing: ~1 s on every warm process, and
  tens of seconds when a CDN is slow (one control run took 16.7 s).

## Harness

- `tools/q16_jupyter_probe.py`: one fresh process runs the "cell" inside
  `asyncio.run(main())`, with `main` calling the sync tif1 APIs directly. That is
  what a Jupyter cell does. IPython/ipykernel are not in the venv. For each call
  it records wall time and the deltas of `asyncio.run` calls, `BaseEventLoop`
  constructions, `nest_asyncio2.apply()` calls and `Thread.start` calls. After the
  cell it runs `gc.collect()` and then times the kernel loop itself:
  20k `await asyncio.sleep(0)`, plus 200 futures and 5k gathered tasks.
- `--no-loop` runs the same calls as a plain script. The scenarios are:
  - `notebook`: get_session, load, laps, fetch_all_laps_telemetry,
    pick_drivers(LEC).telemetry, pick_fastest().get_telemetry(), weather,
    race_control_messages, results.
  - `lapfirst`: no bulk fetch.
  - `coldtel`: laps warm, telemetry not in the frame tier.
  - `loopcost`: `--force-nest` applies nest_asyncio2 after the cell.
- `tools/q16_ab.py` runs interleaved fresh-process A/B pairs. Every run gets a
  fresh copy of the same snapshot copy (`/tmp/tif1-q-Q16/ctl_cache_master.sqlite`,
  copied from `/tmp/tif1-warm-q-base`). The cache format is unchanged, so both
  arms get identical bytes.
- `tools/q16_parity.py` pickles every frame from the control tree and from the
  candidate tree (optionally with the candidate inside a running loop) and
  compares class, columns, dtypes, `equals` and block count.

## Probe results (current tree = control, inside a running loop)

| call | asyncio.run | loops created | nest apply | notes |
|---|---:|---:|---:|---|
| get_session | 0 | 0 | 0 | no threads; `asyncio` not imported in a plain script either |
| load() | 0 | 0 | 0 | 3 threads = the pyarrow-decompress ThreadPoolExecutor |
| laps / weather / rcm / results | 0 | 0 | 0 | memo / tier hits |
| fetch_all_laps_telemetry | 0 | 0 | 0 | 3.9 ms |
| lap.get_telemetry | 0 | 0 | 0 | 3.5 ms (12 ms without a prior bulk fetch) |
| pick_drivers("LEC").telemetry | 0 | 0 | 0 | **~1 s, 6 threads: sync network fetch of a known-missing lap** |
| polars: load + fetch_all | 0 | 0 | 0 | |

- A stale schedule (TTL forced to ~0) makes `get_session` start the
  `tif1-schedule-refresh-2026` daemon thread. The refresh is a sync
  `get_url` and creates no event loop. The thread does import `asyncio` (through
  the HTTP stack), but it is off the critical path, and the kernel already has
  `asyncio` loaded.
- `nest_asyncio2.apply()` costs 0.06 ms (plus 0.26 ms to import `nest_asyncio2`
  when `asyncio` is already loaded). Once the loop is patched, the kernel's loop
  stays slower (8 pairs, after `gc.collect()`): 5k gathered tasks 33.3 → 58.4 ms
  (+75 %, 0/8 faster); `sleep(0)` ×20k is unchanged (55.5 vs 53.5 ms). The warm
  path never triggers it, so nothing to fix there. On the cold path (payload tier
  → assembly, 1452 frames, offline) the nested `asyncio.run` costs nothing
  measurable: 2.31 s in a loop vs 2.35 s as a script (4 pairs). So moving the cold
  path to a worker-thread runner is not worth it.

## A/B numbers (8 interleaved fresh-process pairs, same cache bytes)

Notebook scenario inside a running loop (two separate 8-pair runs):

| call | control median | candidate median | candidate faster |
|---|---:|---:|---:|
| pick_drivers("LEC").telemetry | 968.6 / 1124.9 ms | 68.0 / 70.2 ms | 8/8, 8/8 |
| whole cell | 1601.6 / 1831.8 ms | 684.7 / 738.4 ms | 8/8, 8/8 |
| every other call | equal within noise | | |

- `lapfirst` scenario inside a loop: pick_drivers telemetry 1084.9 → 76.6 ms
  (8/8); cell 1722 → 665 ms (8/8).
- Plain script (`--no-loop`, 4 pairs): pick_drivers telemetry 1044.6 → 77.0 ms
  (4/4); cell 1579 → 608 ms (4/4).
- Kernel-loop throughput after the cell: equal (tasks 32.5 vs 32.4 ms, 4/8).
  Without `gc.collect()` the first run showed a GC-state artefact (35 vs 44 ms);
  with `gc.collect()` before timing it disappears.
- Cold-in-loop (`coldtel`, offline, cache without frame tiers):
  - Control raises `RuntimeError` and returns no telemetry.
  - Candidate applies nest_asyncio2 once and returns all 1452 frames, the same
    as the plain-script path.

## Parity

`tools/q16_parity.py` compared 1460 keys: 1452 telemetry frames + laps, weather,
rcm, results, LEC/VER/SAI driver-merged telemetry and fastest-lap telemetry.
0 mismatches on columns, dtypes, `equals`, class and block count in each of
these runs:

- pandas warm, candidate as a script;
- pandas warm, candidate in a running loop;
- polars warm in a loop (1455 keys);
- pandas, payload tier only, offline, candidate in a running loop vs control
  as a script (the path that crashed before).

The missing lap behaves as before: still `DataNotFoundError` and the same
"Failed telemetry load for LEC lap 66" warning, just without the CDN walk.

## Files changed

- `src/tif1/core.py`: `Session.fetch_all_laps_telemetry` calls
  `_ensure_nested_loop_support("fetch_all_laps_telemetry")` before `asyncio.run`.
  This only runs on the non-warm branch.
- `src/tif1/payload_loader.py`: new `PayloadLoader._known_missing`.
  `PayloadLoader.get` raises `DataNotFoundError` for a payload with a live
  everywhere-missing verdict when `use_cache` is on, matching
  `async_fetch.fetch_json_async`.
- `tests/unit/test_pergamon_contracts.py`: Q16 section, two tests. Both fail
  without the fix.
- `tools/q16_jupyter_probe.py`, `tools/q16_ab.py`, `tools/q16_parity.py`: harness.

## Risks

- The sync loader now honours verdicts for their TTL (`missing_payloads_ttl_days`,
  default 7), just as the batch path already did. A payload that is published
  later is re-probed after the TTL, or after `use_cache=False` or a cache
  invalidate. Verdicts are still only *recorded* by the async path; the sync path
  only reads them.
- The integrator should check whether another wave-2 agent also changed
  `PayloadLoader.get` or `Laps.telemetry` missing-lap handling. The change is
  5 lines plus one helper.
