# Q11 — SQLite read path of the per-driver frame tier

**Verdict: KEPT** (levers c + e; a, b, d rejected with numbers).

Warm pandas telemetry phase (`tools/pergamon_warm_ab.py`, 6 interleaved
fresh-process pairs, final code): **51.7 → 42.0 ms median (−19 %)**, min
46.2 → 41.1 ms, candidate faster 5/6; total 0.286 → 0.276 s (4/6; the other
phases are the unchanged import chain). Micro-harness around
`Cache.get_telemetry_frames_batch` on the 1452-ref batch (10 pairs):
**51.3 → 41.8 ms median (−18 %)**, min 44.9 → 35.9 ms, 9/10 pairs.

## Hypothesis

The warm telemetry load reads 22 driver rows (23.1 MB of lz4 blobs) from
`telemetry_frames_drv`, decompresses them in a `ThreadPoolExecutor` created
per call, then decodes 1452 frames. The SQL part and the executor spin-up
were thought to be ~15 % of the phase; measure `mmap_size`, incremental
blob I/O, a persistent pool, the `laps` pre-check and anything else in the
read path.

## Where the phase went (fresh process, candidate cache copy, before)

| step | ms | note |
|---|---:|---|
| `laps` pre-check query + `json_loads` x22 | 0.10-0.25 | lever (d): nothing to win |
| `SELECT driver, frame ... IN (...)` + `fetchall()` | 11.6-14.2 | 23.1 MB; 4 KB pages → ~5650 overflow pages assembled, then copied into `bytes` |
| lz4 decompression (`_decompress_frame_rows`, min_parallel=2) | 9.4-12.3 | 22 rows chunked `max(8, ceil(22/16))` = 8 → **3 tasks on 8 threads** |
| `decode_driver_frames` x22 → 1452 frames | ~25 | P1/P3 territory, untouched |
| executor spin-up + join | ~0.6 | lever (c) |

## Levers

**(a) `PRAGMA mmap_size=256MB` — REJECTED (noise + risk).** SQLite-only
probe, first fetch of the 22 rows: 12.1-14.2 → 10.7-11.5 ms (−1.3 ms);
second fetch in the same process 10 → 8 ms. Isolated A/B on the finished
code (candidate vs candidate+mmap, 8 pairs, fresh process): 48.3 → 45.2 ms
median, 6/8 pairs; an earlier run under load was 3/8. A 1-3 ms (≤6 %) delta
with a 6/8 win rate is inside the pair-to-pair spread (3-5 ms), and mmap'd
I/O turns disk/network errors into SIGBUS instead of `sqlite3.Error`, which
the cache dir (user home, possibly NFS) cannot rule out. Also re-checked
`page_size=65536` (VACUUM'd copy): 11.6-12.9 vs 12.1-14.2 ms, −0.5 ms —
the cost is the two 23 MB copies and the page walk, not syscalls. Not
shipped.

**(b) `blobopen()` incremental I/O — REJECTED (not possible as proposed).**
`sqlite3.Blob` has no `readinto` on CPython 3.13 (only `read()`, which
allocates a fresh `bytes`), so there is no copy to save; `blobopen().read()`
per row measured 13.5-18.5 ms vs 12.8-15.7 ms for `fetchall()` (3 rounds) —
the extra `rowid` query and per-row handle open cost more than they save.

**(c) Persistent decompression pool — KEPT.** Module-level
`ThreadPoolExecutor` (lazy, `tif1-frame-decompress` thread prefix,
`os.register_at_fork` resets it in a forked child; idle workers exit at
interpreter shutdown through `concurrent.futures`' own atexit hook).
Fresh-process decompression of the 22 rows: per-call pool 6.8-7.3 ms vs
persistent 6.2-6.6 ms (first use, 4 rounds) — ~0.6 ms, kept because it is
free and the streamed read (e) needs the pool to exist before the cursor is
iterated.

**(d) Skipping the `laps` pre-check — REJECTED (negligible).** Measured
0.10-0.25 ms for the whole-session batch (22 short rows, no blob). A
whole-session load already can't know it wants every stored lap without
reading that column; folding `laps` into the blob query would make partial
batches drag unneeded ~1 MB rows through SQLite. Not worth a code path.

**(e) Read-path structure — KEPT (the win).** Two findings:

1. *Chunking starved the pool.* `_decompress_frame_rows` chunked rows with
   `max(8, ceil(n / (workers*2)))`, tuned for the 1452 small per-lap rows;
   for the 22 driver rows that meant 3 tasks on 8 threads. Rows averaging
   ≥ 256 KB now get one task each (small rows keep the chunking):
   11.5 → 6.9 ms (4 rounds; 4 threads 8.4, 16 threads 7.4 — 8 is right).
2. *The cursor is streamed into the pool.* `_get_driver_frames` submits
   each row the moment SQLite returns it (`_submit_frame_rows` inside the
   `_sqlite_lock`, `_completed_frame_rows` after), so SQLite's overflow-page
   assembly of row k+1 overlaps the lz4 of rows ≤ k. Full read
   (SQL + lz4 + decode, 5 rounds): current 44-50 ms → per-row tasks 41 ms →
   streamed 36-39 ms. Running the SQL loop in a worker thread so decode
   could overlap it too was tried and dropped: 35-46 ms, bimodal — the
   `bytes` copy per row needs the GIL and the 5 ms switch interval
   serializes it against the decode loop.

Work submitted from a pool worker runs inline (a worker waiting on the
pool would deadlock once every worker did the same).

## Protocol

- Control tree `/tmp/tif1-pergamon-control/src`, cache copies of
  `/tmp/tif1-warm-q-base/cache.sqlite` per arm (`/tmp/tif1-q-Q11/{control,cand}`).
- Fresh-process probes per lever (`/tmp/tif1-q-Q11/scripts/{sql_probe,dec_probe,pipe_probe}.py`),
  interleaved variants, 3-5 rounds each.
- Micro A/B (`/tmp/tif1-q-Q11/scripts/micro_ab.py`): fresh process per arm,
  first call of `get_telemetry_frames_batch` on the 1452 refs, ABBA order,
  10 pairs. Whole load: `tools/pergamon_warm_ab.py --pairs 6` (and an 8-pair
  run under load 11: telemetry 66.5 → 56.2 ms median, 8/8).
- The 5 ms `get_session` offset the AB tool shows against the control arm
  is the harness (`--src-dir` path insert): both arms running the candidate
  code show it too (0.258 vs 0.237 s, 6 pairs).

## Parity

Control-tree frames vs candidate frames on the full 1452-ref batch:
0 mismatches (`equals`, columns, dtype strings, block count and block
classes, index type, `Telemetry` class); a partial batch with a missing
driver and a missing lap returns the same 8 keys; `whole_driver` returns the
same 78 keys; a fresh read is isolated from a mutated frame. Polars read path
untouched (the pool would save ~0.6 ms of a 53 ms phase there — below noise,
left alone to keep the conflict surface small).

## Risks

- A process-wide thread pool now outlives the batch (8 idle threads after
  the first warm load). Fork safety handled with `register_at_fork`; threads
  are never daemon but `concurrent.futures` drains them at exit.
- `_decompress_frame_rows` still accepts lists; the legacy per-lap path and
  `get_driver_merged_frame` behave as before (small-row chunking unchanged).
