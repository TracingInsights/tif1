# Q6: polars warm telemetry read (`lib="polars"`)

**Verdict: KEPT.** Combined levers (a) no rechunk, (e) streamed cursor, plus
two the probes surfaced: per-worker `IpcReadOptions(use_threads=False)` and
`string_view` string storage. Whole-load polars telemetry phase went
69.5 → 45.4 ms median, faster in 8/8 pairs (post-reboot run, `Q6_warm_ab_polars.json`).
Parity: 0/1452 mismatches.

## Hypothesis
After P4, the warm polars read (`Cache._get_polars_ipc_frames`) does an SQL
fetchall, then per-blob IPC reads in a thread pool, then one
`pl.from_arrow(concat, rechunk=True)`, then 1452 `slice` calls. Some of
these phases are redundant or run serially when they could overlap.

## Mechanism (what changed)
`src/tif1/cache.py`:
- `_get_polars_ipc_frames`
  - **Streamed cursor (e):** when ≥4 drivers are wanted, each SQL row goes
    to the pool (`pool.submit`) as soon as the cursor yields it, so the IPC
    reads overlap the rest of the 22-25 MB blob fetch. With fewer than 4
    drivers the read is serial, as before.
  - **`IpcReadOptions(use_threads=False)` inside the workers:** 8 Python
    workers each started pyarrow's per-column decompression pool. That
    pool is cold on the first warm read and oversubscribes the cores. The
    serial path keeps `use_threads=True`.
  - **`rechunk=False` (a):** the concat of 22 single-batch driver tables
    gives 22 chunks. Each lap slice falls inside one driver's chunk, so
    every lap frame is still single-chunk (checked: 1452/1452
    `n_chunks()==1`). The rechunk only copied about 100 MB, and since that
    memory is newly allocated it page-faulted on the first call (14-24 ms
    first-call vs 2-4 ms without).
- `_write_polars_ipc`: writes `frame.to_arrow(compat_level=pl.CompatLevel.newest())`,
  which stores strings as Arrow `string_view` (polars' own layout).
  `from_arrow` then skips the large_string→view rebuild, and the rows are
  11 % smaller (25.2 → 22.5 MB per session). The storage stays Arrow IPC
  with lz4 inside the stream. Legacy `large_string` rows need no format
  sniffing: the reader does not depend on the schema, and a session mixing
  old and new rows becomes two schema groups, which were already handled.

`tests/unit/test_pergamon_contracts.py`: Q6 section with 2 tests:
- Rows are stored as `string_view`.
- Mixed legacy `large_string` and new rows read back `equals` the source
  frames, with the same schema and single-chunk, on both the pooled path
  and the serial path.
- A corrupt row on the streamed path is a miss.

## Protocol
- Snapshot copies per arm. The candidate copy was re-materialized: the
  polars IPC rows were deleted, then one polars load plus
  `fetch_all_laps_telemetry()` ran on candidate code, and 22 rows were
  confirmed to be `string_view`.
- Parity: `fetch_all_laps_telemetry()` in fresh processes, control tree vs
  candidate, comparing `equals`, schema, type and `n_chunks`. It ran on
  both the re-materialized copy and an untouched legacy copy. Result: 0/1452
  mismatches on both, all frames single-chunk.
- Fresh-process micro around `Cache.get_telemetry_frames_batch(..., lib="polars")`,
  interleaved, first-call timing (the call a warm load pays). Each variant
  was monkeypatched in, and alternative storage tables were built in a
  scratch copy.

## Numbers
Micro: `get_telemetry_frames_batch`, all 1452 refs, read ms, median of 8
interleaved fresh processes.

| variant | median | faster than base |
|---|---|---|
| base (control code) | 58.9 | — |
| (a) rechunk=False | 48.1 | 6/8 |
| (a) + worker use_threads=False | 45.2 | 8/8 |
| (a)+(e) streamed | 44.5 | 6/8 |
| (a)+(e)+use_threads=False | 36.3 | 8/8 |

Storage variants, measured on top of (a)+(e)+nt, 12 rounds:

| variant | median | faster than (a)+(e)+nt |
|---|---|---|
| (a)+(e)+nt baseline | 40.9 | — |
| string_view IPC-lz4 | 34.6 | 11/12 |
| string_view, uncompressed IPC + whole-file lz4 frame | 35.7 | 8/12 |
| (c) large_string, uncompressed IPC + lz4 frame | 46.9 | 7/12 (no better) |

- (b) per-driver `from_arrow` in the workers (no concat) was 42.3 vs 38.7,
  3/8. Rejected.
- (d) lazy slicing: slices cost about 4.5 µs each whatever the chunking,
  and `_from_pydf(pydf.slice())` was no faster. Making slices lazy would
  break the real-DataFrame dict contract, and core touches every frame
  anyway. Rejected.
- Downstream op `frame["Speed"].max()` over all 1452 laps: 3.3-4.3 ms in
  every variant (no rechunk cost downstream).

Whole-load A/B, `tools/pergamon_warm_ab.py --lib polars`, telemetry phase,
medians. The box was loaded by other agents.

| run | control | candidate | faster | total |
|---|---|---|---|---|
| post-reboot, 8 pairs (`Q6_warm_ab_polars.json`) | 69.5 ms | 45.4 ms | 8/8 | 0.4925 → 0.4714 s, 8/8 |
| pre-reboot, 8 pairs | 71.6 ms | 36.4 ms | 7/8 | 7/8 |
| pre-reboot, candidate code on legacy `large_string` rows (existing user caches) | 81.7 ms | 55.1 ms | 8/8 | — |

Storage lever alone (candidate code on both arms, legacy rows vs
string_view rows): 55.3 → 50.8 ms, 9/12. An earlier 8-pair run was 4/8
during a load spike. This lever is small but consistent with the micro
(11/12).

## Risks / integrator notes
- Existing caches keep `large_string` rows (no version bump; bumping
  `_FRAME_TIER_SCHEMA_VERSION` would drop the pandas frame tables too).
  They get the read-path gains right away. They get the storage gain
  (about 5 ms) only when a driver row is rewritten.
- `string_view` IPC needs pyarrow ≥ 16 (declared floor is 25.0.1). An older
  tif1 reading a new row goes through the same pyarrow→`from_arrow` path
  and gets the same polars frame.
- Memory: lap frames now reference per-driver Arrow buffers instead of one
  rechunked buffer. The total is the same, and the transient 100 MB copy is
  gone.
- `_get_polars_ipc_frames` now imports polars/pyarrow before the SQL query.
  It is only reached for `lib="polars"`, so this costs nothing.
- Conflicts: only touches `_write_polars_ipc` and `_get_polars_ipc_frames`
  in `cache.py`, plus an appended test section.
