# Q2 — background preload of the heavy third-party imports in interactive sessions

**Verdict: KEPT.** The win exists only in the interactive (notebook/REPL) case,
which is the main use of the library; every other path is measured at parity.

## Hypothesis

`import tif1` is lazy (~7 ms). The first `tif1.get_session(...)` imports
`tif1.core` and pays ~220 ms for pandas (~193 ms cumulative), numpy (~40 ms)
and pyarrow (~22 ms, inside pandas). In a notebook the user types
`import tif1` in one cell and `get_session` in a later one, so that import
could run while they type. Earlier series rejected *deferring* pandas
(H10/G9/KR-7/V6/L10); this is the opposite lever — overlap with think time.

## Mechanism (`src/tif1/__init__.py`)

At `import tif1`, when the interpreter is interactive (`"IPython" in
sys.modules`, `hasattr(sys, "ps1")` or `sys.flags.interactive`) and pandas is
not yet in `sys.modules`, a daemon thread `tif1-preload` imports **only**
`numpy`, `pandas`, `pyarrow` (never a `tif1.*` submodule: tif1 config reads
env vars at submodule import and users set them between `import tif1` and
`get_session`; a tif1 import in the thread could also form a lock cycle with a
main-thread `import tif1.core`). The later main-thread `import tif1.core`
finds the modules in `sys.modules`, or blocks on the per-module import lock
until the thread finishes — no duplicated work. Import errors in the thread
are swallowed; the main thread's own import reports the real error.

`TIF1_PRELOAD_IMPORTS=1|0` overrides the detection (read with `os.environ`
directly, no `tif1.config` import). `threading` is imported only when the
thread is wanted; non-interactive processes pay two attribute reads and one
`os.environ.get`.

## Protocol

Fresh process per run, interleaved A/B pairs, control = frozen
`/tmp/tif1-pergamon-control/src`, candidate = this tree (copied to tmpfs next
to the control for the parity cases, because the control lives on tmpfs and
the worktree on a 97 %-full NVMe — that location alone was worth +20 ms on
`get_session`, found when the untriggered candidate also read slower).
Warm cache: two copies of `/tmp/tif1-warm-q-base/cache.sqlite`
(`/tmp/tif1-q-Q2/{ctl,cand}`). Harness `/tmp/tif1-q-Q2/h/probe.py` runs
`import tif1; time.sleep(S); get_session(2026, Monaco, Race); session.laps`;
`drive.py` interleaves the arms and records in-process phases plus the
subprocess wall. Box load 1.5-7 (other agents benchmarking).

### Safety checks (`/tmp/tif1-q-Q2/h/checks.py`, fresh processes)

- Non-interactive process, no env: no thread, pandas not imported, only
  `tif1.exceptions` in `sys.modules`; `TIF1_PRELOAD_IMPORTS=0` under an
  IPython stub: same.
- `python -i`, IPython stub, env `1`: thread runs, pandas imported, still only
  `tif1.exceptions` among `tif1.*` (the thread never imports tif1 code).
- pandas already imported: no thread.
- Exit cleanliness: `python -W error -c "import tif1"` with the thread forced,
  exiting while it is still importing: 20/20 clean (rc 0, no output);
  `sys.exit(3)` mid-preload 10/10 clean.
- Deadlock stress, thread forced and the main thread importing immediately
  in six orders (`tif1.core`, pyarrow-first, pandas-first, numpy-first,
  `tif1.get_session`, polars-first): 60/60 runs finish (no hang, no
  `_DeadlockError`), walls 0.23-0.55 s.

## Verdict

KEPT. Notebook/REPL first `get_session`: 0.22-0.30 s → 0.02-0.03 s (8/8 and
6/6 pairs), total wall of the two cells −0.2 s. Scripts: thread never starts,
measured at parity (medians within noise both ways, mins within 1 ms);
thread forced with no think time: parity. The win exists **only** in the
interactive case — stated explicitly as the brief asks — and that case is the
main use of this library.

## Risks / notes for the integrator

- Memory: interactive sessions now hold pandas/numpy/pyarrow even if the user
  only calls `get_events` (which imports pandas anyway through `tif1.core`).
- A broken pandas/numpy install fails silently in the thread; the main
  thread's import raises the same error a moment later, so nothing is hidden.
- `"IPython" in sys.modules` also fires in nbconvert/papermill runs (still
  notebooks) and in any script that happens to import IPython — harmless, the
  thread only pre-imports modules the first `get_session` needs anyway.
- `TIF1_PRELOAD_IMPORTS` is read via `os.environ` in `__init__`, not through
  `tif1.config` (importing config there would defeat the lazy `import tif1`);
  it is not listed in `config.py`'s env table. Docs could mention it.
- No conflicts expected: only `__init__.py` (new block above `setup_logging`)
  and an appended test section.
