# Q13 — cheaper and parallel materialization write (background frame-tier writer)

**Verdict: KEPT.** The 1452-frame Monaco writer wall drops by 47-59 % in two
interleaved 7-pair runs (candidate faster 7/7 both times). The bodies are
byte-identical to the control's and every frame decodes `equals` with the
same block count.

## Hypothesis

After a cold load (or a legacy-cache upgrade) the background writer
`Cache.set_telemetry_frames_batch` → `_set_driver_frames` encodes every
driver with `frame_codec.encode_driver_frames`, then compresses each blob
serially with python-lz4. Measured control split (steady state, 1452 frames,
72.5 MB raw): encode ~83 ms, of which `_frame_parts` is 27 ms; lz4 compress
~36 ms serial. The proposed levers: compress on a small pool (python-lz4
releases the GIL on compress), and cut the encode copies and per-frame
Python work.

## Mechanism (what changed)

Profile findings in the control encode:

- `[str(c) for c in frame.columns]` iterates a pandas 3 `str`-dtype column
  Index one pyarrow scalar at a time: 29 040 `ArrowExtensionArray.__iter__`
  calls, ~20 ms of 157 ms under cProfile.
- `values[0]` on the 2-D `TimedeltaArray` block goes through the
  datetimelike `__getitem__`: ~14 ms cumulative under cProfile.
- `tuple(int(p) for p in block.mgr_locs)` costs a generator per block.
- The constant checks (object `Driver`, Int64 `LapNumber`/`DRS`) run one
  NumPy comparison per frame, ~3000 small ufunc calls.
- Each block is copied three times (`np.concatenate`, `tobytes`,
  `b"".join`). Every copy lands in fresh pages: page faults on a fresh 3 MB
  buffer cost about as much as the memcpy (zero-filled `bytearray` ×22:
  6-35 ms; `np.empty`: 0.1 ms).

Changes, all on the write path:

1. `frame_codec._frame_columns` (new): `Index.tolist()` instead of iterating
   the Index, memoized per column-Index object for one encode call. Frames
   from one layout group share their Index, so a driver usually resolves it
   once. Duplicate labels are still rejected.
2. `frame_codec._frame_parts`: placements via `mgr_locs.as_array.tolist()`.
   Timedelta/datetime blocks use the backing `_ndarray` directly; it keeps
   the first row only, exactly as the control did.
3. `frame_codec.encode_driver_frames`: a spec pass records pending writes
   and computes offsets, then the header is pickled. One `np.empty` buffer
   (magic, length, header, body) is allocated and every block is written
   straight to its final offset (`np.concatenate(..., out=)` / `copyto`):
   one copy per block, pages touched once. It now returns a writable
   `memoryview` over that buffer instead of `bytes`.
4. `_object_column_spec` / `_int64_group_constants` (new helper): one
   concatenation and one vectorized comparison per group. Object columns
   use `joined == head`; Int64 compares data with
   `np.repeat(data[starts], lengths)`. The constant rules are unchanged:
   every frame non-empty, and for Int64 no nulls and constant within each
   frame.
5. `cache._set_driver_frames`: each driver blob is submitted to a
   `ThreadPoolExecutor` (`_frame_compress_pool`, up to 8 workers) as soon
   as it is encoded. The GIL-free lz4 compress overlaps the next driver's
   GIL-bound encode, and futures are resolved before `executemany`. A
   single-driver write (the partial path) or the zstd fallback compresses
   inline. Blobs are still python-lz4 frames with the content-size header,
   so the pyarrow parallel decode path is kept (pyarrow is not used to
   compress; see the Q12 note).
6. `cache._compress_frame_blob` accepts `bytes | bytearray | memoryview`.
   The zstd fallback converts a view to `bytes`, because its binding is
   typed for `bytes`.

Not changed: the merge-with-existing path already decodes only when the row
exists (lever c). `executemany` for 22 rows is not a factor (lever d). The
`str` (pyarrow) dictionary path is not a hotspot (~5 ms).

## Protocol

- Harness `tools/pergamon_q13_write_bench.py` (fresh process, `--src-dir`
  for the control tree). It copies the primed snapshot to a scratch dir,
  reads the session's 1452 pandas frames from the driver rows, then runs 5
  in-process iterations. Each iteration deletes the session's driver and
  per-frame rows and times `set_telemetry_frames_batch` for all 1452 frames
  (full write), then for the first 10 frames into the populated rows
  (partial write: merge-decode of one driver row + re-encode). It also
  prints a parity digest (sha256 of the decompressed blobs, plus a re-read
  `equals`/dtype/block-count check) and can dump the blobs.
- A/B: 7 interleaved pairs (control `/tmp/tif1-pergamon-control/src` vs
  this worktree, order alternated, fresh process per run). Per-process
  median of the 5 iterations, then the median across processes.

| A/B 2 | partial write | 12.35 ms | 11.34 ms | −8 % | 6/7 |

Per-process medians, A/B 2: control 206.0 / 157.6 / 154.8 / 154.1 /
156.6 / 153.6 / 157.1 ms; candidate 93.8 / 88.8 / 88.3 / 69.4 / 75.1 /
83.0 / 68.4 ms.

Split, same process (steady state): encode ~83 → ~55 ms (`_frame_parts`
27 → 17 ms); compress 36-42 ms serial, now overlapped with the encode on
the pool. Compress-only probe: 4 threads 16-18 ms, 8 threads 10-29 ms
(noisy box).

The partial-write gain is within noise. The partial write is one driver:
merge-decode + 76-frame re-encode + one compress, with no pool.

## Parity

- Full Monaco set, control vs candidate driver blobs (decompressed, 22
  drivers): unpickled headers equal 22/22, bodies byte-identical 22/22.
  Whole-blob bytes are identical for 1/22 only, because the pickled header
  is ~200 bytes smaller: column lists of different layout groups can now be
  the same list object (memoized per Index), which pickle writes once.
  Decoding is unaffected.
- Re-read through `get_telemetry_frames_batch`: 0/1452 mismatches
  (`equals`, columns, dtypes, `len(_mgr.blocks)`), control and candidate.
- Stored bytes 23 133 500 → 23 132 920 (header memo).

## Tests

- New section "Q13" in `tests/unit/test_pergamon_contracts.py` (4 tests):
  - round trip over every encoder branch: two layout groups, an empty
    frame, a strided (non-contiguous) view frame, varying Int64 with a null.
    It also checks that the blob is a writable `memoryview` and that the
    lz4 content size is present when the view is compressed directly.
  - body layout equals the per-group concatenation (float block,
    non-constant Int64 data + mask), `Int64c` constants, and a constant
    object column.
  - the column memo never mixes Indexes and still rejects duplicate labels.
  - a multi-driver write uses the pool, a single-driver write does not, and
    every frame reads back `_same`.

## Risks / integration notes

- `encode_driver_frames` now returns a `memoryview` (writable, over a NumPy
  buffer) instead of `bytes`. All in-tree callers and tests only use it as a
  buffer (`bytearray(blob)`, slicing, lz4 compress, `decode_driver_frames`).
  An external caller that needs `bytes` must call `bytes(blob)`.
  `decode_driver_frames(blob)` on the view decodes in place (writable
  buffer).
- The writer now starts up to 8 short-lived threads per multi-driver write.
  They only run lz4, with the GIL released.
- Pre-existing behaviour, not introduced here: a consolidated multi-column
  timedelta/datetime block is encoded from its first row only, as in the
  control. The telemetry assembly never builds such a block.
- Possible conflict: Q11 edits the read side of `cache.py`
  (`_decompress_frame_rows`, `_get_driver_frames`, `_decompress_pool`). Q13
  only touches `_compress_frame_blob`, `_set_driver_frames` and the new
  `_frame_compress_pool` next to `_compress_frame_blob`. If Q11's
  `_decompress_pool` is a shared module-level pool, the integrator may fold
  `_frame_compress_pool` into it.
