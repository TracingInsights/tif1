# Q18: per-lap frame construction from a driver row

**Verdict: KEPT** for levers (a) `str` slicing, (b) `Int64c` constants and the
per-group plan (direct block classes, positional args, timedelta wrapper).
**REJECTED** for lever (c), the object-column decode (−7 % at best, below
noise), and for lever (d), the Rust helper (the per-lap work is Python object
construction, and a Rust string gather beats Arrow `take` by only 1 ms per
legacy session).

## Hypothesis

After P3, `decode_driver_frames` decodes a driver's group arrays once and then
builds ~8 blocks, a `BlockManager` and a `Telemetry` frame per lap. A profile
of the 2018-2025 sessions put `ArrowStringArray.__getitem__` (the per-lap
`DriverAhead` `str` slice) at ~18 % of decode time. The hypothesis was that
this per-lap string work and bookkeeping could move out of Python, with a
Rust extension as a last step.

## Mechanism (what changed)

`src/tif1/core_utils/frame_codec.py`:

- `decode_driver_frames`: when `_FAST_LAP_FRAMES` is set (it equals the
  existing `_DIRECT_BLOCKS_OK and _DIRECT_BLOCK_CLASSES_OK` import probe),
  each group goes to `_lap_frames_into`. Otherwise the old loop runs
  unchanged.
- `_lap_plan(parts, lengths, total)`: resolves per group what the generic
  helpers re-derived per lap. Each block becomes `(code, values, extra,
  placement)`:
  - numpy blocks are tagged plain or datetime-like once.
  - **(b)** `Int64c` constants become one `np.repeat(values, lengths)` int64
    array plus one `np.zeros(total, bool)` mask per group. Each lap gets a
    disjoint slice, so frames stay mutation-isolated. The old code ran
    `np.full` + `np.zeros` + `_int64_array` per lap, about 2 us each.
  - **(a)** `str`: the group's `ChunkedArray` plus its dtype. Each lap is
    built with `object.__new__(ArrowStringArray)` and
    `_pa_array = chunked.slice(start, n)`, `_dtype`, `_readonly = False`,
    which are the same attributes and order that `__getitem__` sets. This
    costs 0.75 us against 5.8 us for `ea[start:end]`.
  - timedelta `Time`: `NDArrayBacked._simple_new(values, dtype)` +
    `_freq = None`. This is `TimedeltaArray._simple_new` without its five
    per-call asserts (0.51 vs 0.97 us). The dtype is checked once per group
    (kind `m`, not unit-less).
- `_lap_frames_into`: the per-lap loop. It slices the arrays, calls the block
  classes directly with positional `(values, placement, 2)` (0.50 vs 0.62 us
  with keywords), and uses the column `Index` shared once per group, Python
  int offsets (`itertools.accumulate`), and the frame class `_from_mgr` and
  `_metadata` resolved once.
- `_fast_arrays()`, `_probe_str_slice()`, `_probe_timedelta()`: run once per
  process (0.26 ms). They check the hand-built `str` slice and the timedelta
  array against the public route: same type, the same `vars()` keys in the
  same order, the same dtype object, `_readonly`, and an Arrow-level `equals`
  that also matches the chunk count. If anything drifts, the plan falls back
  to `ea[start:end]` or `TimedeltaArray._simple_new`.

Unchanged: the cache format, `_group_parts`, `decode_driver_merged`,
`decode_frame`, `helpers.py`, and the polars tier.

## Protocol

- Corpus:
  - 2026 Monaco GP Race: snapshot copy, 22 driver rows, 1452 frames.
  - 2018 Monaco Race (1516 frames) and 2024 Monaco Race (1237 frames):
    copied out of `~/.cache/tif1/cache.sqlite` (read-only) into
    `/tmp/tif1-q-Q18/legacy/cache.sqlite`, then upgraded to driver rows by
    one run of `tools/pergamon_legacy_gate.py` with the integrated tree
    (0 mismatches).
- Control: `/tmp/tif1-pergamon-control/src`. Both arms read the **same**
  cache copy, because the cache format is unchanged.
- In-process decode: `tools/q18_decode_bench.py`. It times
  `decode_driver_frames(..., Telemetry)` over all of a session's driver rows,
  with the decompressed buffers prepared outside the timer. Each process
  takes the best of 40 repetitions, and control and candidate processes run
  interleaved, 3 rounds.
- Full-session read: `tools/q18_batch_ab.py`. It is a fresh-process
  interleaved A/B (alternating order) of `Cache.get_telemetry_frames_batch`
  through `tools/pergamon_legacy_read_bench.py`, 10 pairs per session.
- Whole warm load: `tools/pergamon_warm_ab.py`, 10 pairs, pandas.
- Parity: `tools/q18_parity.py`. For every frame of the 3 sessions it
  compares the candidate fast route against the candidate generic loop, the
  live and pickled frames against the control tree's decode (dumped by the
  control tree), and checks columns, dtypes, `equals`, index, and the block
  signature (block class, placement, values class, dtype, `vars()` keys). It
  also checks that every block is writable and runs a mutation-isolation
  probe across consecutive laps.
- The box was shared with other agents (load 6-14), so absolute times run
  above the RESULTS.md baseline. All comparisons are interleaved.

## Rejected levers

- **(c) object columns** (`DriverAhead` object layout + `Driver` constant).
  The group decode is refcount-bound: `np.empty(object)` alone is 93 us per
  27k-row group, and the fancy index + copy is 426 us. `np.take(..., out=row)`
  is slower (715 us). A single 2-D gather from one table (dict + const in
  one pass) is 396 us, −7 % on 7 ms per session, so it was not kept.
- **(d) Rust.** The per-lap work that remains is the construction of Python
  objects: ndarray views, extension arrays, blocks, the manager and the
  frame. An extension would have to call the same CPython and pandas
  constructors, so there is nothing to move. I probed the one non-object
  step that is left, the group-level `str` dictionary decode (Arrow `take`,
  7.9 ms for 1.08M rows in 2024 Monaco, 1.9 ms of which is building the
  index array). A pyo3 gather (offsets + data, GIL released) plus
  `LargeStringArray.from_buffers` took 6.9 ms against 7.9 ms with `take`, so
  it saves 1 ms per legacy session and only when the optional `tif1_native`
  is installed. Rejected. The probe crate is in `/tmp/tif1-q-Q18/rustprobe`
  and was not shipped.
- Other options measured and found not to pay: a numpy offsets/data string
  build (18 ms vs 7.9 ms with `take`), dictionary-cast instead of `take`
  (8.7 ms), int8 indices (8.0 ms), and inlining `IntegerArray._simple_new`
  (−50 ns).

## Parity

- 1452/1452 (2026), 1237/1237 (2024), 1516/1516 (2018): 0 mismatches in
  each of the three comparisons — fast route vs generic loop, fast route vs
  control (live frames), and fast route vs control (pickled round trip).
  Checked: columns, dtypes, values, index, block classes and order,
  placements, value classes, and `vars()` keys.
- Every block is writable. Mutating `LapNumber`, `DRS`, `nGear`,
  `DriverAhead`, `Time` or `Speed` in one lap leaves the other laps of the
  same group unchanged.

## Risks

- The route depends on three pandas internals that have to keep their
  current shape:
  - `ArrowStringArray` carries exactly `_pa_array`, `_dtype` and `_readonly`.
  - `TimedeltaArray._simple_new` is `NDArrayBacked._simple_new` + `_freq`.
  - Block classes accept positional `(values, placement, ndim)`.

  The first two are probed against the public route once per process and
  fall back on drift. The third is covered by the existing direct-block probe
  in `helpers.py` and by the contract tests. If a pandas upgrade adds an
  attribute to `ArrowStringArray`, the probe fails and the fast `str` path
  turns off, costing speed but not correctness.
- Each frame's `LapNumber`/`DRS` (`Int64c`) now views a per-group array
  instead of owning a private one. The slices are disjoint and writable, so
  isolation holds. The group array stays alive as long as any of its frames
  does, which is already true of the body buffer the numpy blocks view.
- Merge note: only `decode_driver_frames` and the new code appended at the
  end of `frame_codec.py` are touched, with two lines added to the imports.
