# Q20 — CLI fixed costs on a warm cache

**Verdict: KEPT.** `cache-info` 491 → 129 ms (−74 %), `cache-clear --yes` 558 → 195 ms
(−65 %), `events 2026` 504 → 146 ms (−71 %), `sessions 2026 Monaco` 499 → 140 ms
(−72 %), all 8/8 pairs. `fastest` is 30 ms faster (−5 %, 8/8). stdout, stderr and exit
code are byte-identical for every command.

## Hypothesis

Every `tif1` CLI call is a new process, so on a warm cache the run time is mostly
imports and per-command setup. U10 (Ithome) already moved pandas/rich into the command
bodies. The question was what each command still loads that it does not need.

## Probe (`-X importtime`, fresh process, warm 2026 Monaco snapshot)

| command | avoidable cost found |
|---|---|
| `cache-info`, `cache-clear` | `tif1.cache` → `from .core_utils.constants import` runs `core_utils/__init__.py`, which eagerly re-exported `helpers` → **pandas + numpy (~350 ms)**. `cache.py` also had a module-level `from pyarrow import ArrowException` → **pyarrow + numpy (~160 ms)**. Neither command builds a frame. |
| `events`, `sessions` | `tif1.events` did `import pandas` at module level because `Event(pd.Series)`/`EventSchedule(pd.DataFrame)` are defined there (**~340 ms**). `events` built the whole pandas `EventSchedule` (25 `Event` Series) just to print `EventName`. `sessions` with an alias ("Monaco") built an `Event` only to read back its name. |
| `fastest` (table and `-d`) | With laps not yet loaded, `get_fastest_laps`/`Driver.get_fastest_lap` take the "cold" raw-payload path: derive per-driver payloads (22 ms), import `asyncio` (14 ms), `_process_lap_df` on the rows (47-74 ms). The laps frame tier holds the processed table and reads in ~2 ms. |
| `--help` | `typer.rich_utils` 69 ms. This is typer's rich help renderer and it produces the output, so it was left alone. |
| `version` | typer 31 ms + rich.console 19 ms + `importlib.metadata` 13 ms (`tif1.__version__`). Changing this means a new version-source/build setup, so it is not done here. |
| `drivers`, `debug`, `fastest` | pandas (~250-340 ms) is required (`drivers_df`, laps). `rich.progress` (31 ms) draws the progress line that is part of the output. The command bodies run in 47-55 ms, so there is nothing more to cut here. |

## Changes

1. `src/tif1/core_utils/__init__.py`: the package re-exports now resolve lazily (PEP 562
   `__getattr__`, with `TYPE_CHECKING` imports for type checkers). `__all__` and the
   names are unchanged, and nothing imports them at package level today.
2. `src/tif1/cache.py`: the module-level `from pyarrow import ArrowException as
   ArrowError` is replaced by `_arrow_error()`, which looks the class up once and caches
   it. The six `except (..., ArrowError)` clauses now call `_arrow_error()`; Python only
   evaluates that when an exception is actually being matched. The warm load still
   imports pyarrow, because the lz4 codec needs it.
3. `src/tif1/event_frames.py` (new): `Event` and `EventSchedule` moved here unchanged.
   Their references back into the schedule go through `tif1.events.<name>`, so patching
   `tif1.events.get_sessions` and similar still works. Both classes set `__module__ =
   "tif1.events"`, so `repr(type(x))` and pickles are unchanged. A pickle written by the
   control tree loads in the candidate.
4. `src/tif1/events.py`: no pandas import at module level.
   - `Event`/`EventSchedule` resolve through a module `__getattr__`, so `from
     tif1.events import Event` still works. `_create_event` and `get_event_schedule`
     import them where they are used.
   - `_find_event_by_name` is split. The new `_match_event_name` returns the matched
     name (exact → alias → fuzzy, same order, logs and thresholds) without building an
     `Event`; `_find_event_by_name` wraps it.
   - `get_event_by_name` is split the same way. The new `_resolve_event_name` returns
     the name and raises the same errors.
   - `_build_sessions_for_event` now calls `_resolve_event_name` instead of building an
     `Event` and reading `.EventName`.
5. `src/tif1/cli.py`:
   - `events` prints `tif1.events._build_events_for_year(year)`. This is the same list
     that becomes the schedule's `EventName` column, and an empty list still means "No
     events found".
   - `fastest` calls the new `_adopt_warm_laps(sess)`, which binds
     `sess._laps_from_frame_tier()` when it hits. On a miss (cold cache) it does nothing
     and starts no fetch.
6. Tests:
   - `tests/unit/test_cli.py`: the two `events` tests now patch
     `tif1.events._build_events_for_year`. The file keeps its CRLF line endings.
   - New `tests/unit/test_q20_cli_contracts.py` (12 tests):
     - in a fresh interpreter, `import tif1.cache` loads none of pandas, numpy or
       pyarrow, and the schedule name/alias lookups need no pandas;
     - the lazy re-exports resolve to the right objects, and `_arrow_error()` is the
       pyarrow exception class;
     - `Event`/`EventSchedule` keep their public module and survive a pickle round trip;
     - resolved names match `Event.EventName`, and error types are unchanged;
     - the `events` command and `_adopt_warm_laps` behave as intended (hit, miss,
       already loaded).

## Protocol

- `tools/q20_cli_ab.py` runs each command as `python -m tif1.cli <args>` (the
  entry-point module), one fresh process per run.
  - Control is `PYTHONPATH=/tmp/tif1-pergamon-control/src`; candidate is the worktree
    `src`. Both use the same interpreter.
  - Env: `COLUMNS=120 LINES=40 NO_COLOR=1 TERM=dumb`. Both arms read the same cache copy
    (`/tmp/tif1-q-Q20/cache`, from the snapshot); no change touches the cache format.
  - 8 interleaved pairs per command, order alternating.
  - `cache-clear` gets a fresh copy of the cache for every run; the copy is not timed.
  - Each arm's stdout, stderr (timestamps removed) and exit code are collected into a
    set; "identical" means each arm produced exactly one variant and the two were equal.
- Parity runs, byte-compared, control vs candidate:
  - `tools/q20_cli_schedule_parity.py`: `events` for 2017-2027 and `sessions` for every
    event name, its lower-case form, all 90 aliases, typos and non-events, for each
    season 2018-2026. **1267 commands, 0 differences.**
  - `tools/q20_cli_parity.py`: `fastest` table plus `-d` for the first and last driver
    and an unknown code, on all 123 sessions that have a laps frame in a read-only copy
    of the user cache (2018-2025). The candidate used the frame tier in 123/123 sessions.
    **492 commands, 0 differences.** For non-zero exits only the exception line is
    compared, because typer's traceback quotes tree paths.
  - In-process schedule parity on 2017-2027: `get_event_schedule` (with and without
    testing), `get_event_by_name` (fuzzy and exact), `get_sessions` and `get_event(year,
    3)` for every name, lower-case form, alias and typo. The pickled results from each
    tree were compared with `equals`, column order, dtypes and `.year`: **4475 entries,
    0 differences.**

## Risks / notes for the integrator

- **Conflict surface:** `events.py` lost the bodies of `Event`/`EventSchedule`, which
  moved verbatim to `event_frames.py`. If another agent edits those classes, the edit
  has to be carried over to `event_frames.py` by hand.
- In `cache.py` only the `ArrowError` import and the six `except` tuples changed.
- `core_utils/__init__.py` is rewritten (CRLF kept).
- `_build_sessions_for_event` no longer goes through `get_event_by_name`. A test that
  patches `tif1.events.get_event_by_name` to steer `get_sessions` would now need to
  patch `_resolve_event_name`. None in the suite does.
- `cli.fastest` uses two private session members, `_laps` and `_laps_from_frame_tier`.
  If those change, the contract test `test_fastest_adopts_warm_laps_frame` and the
  `fastest` CLI tests catch it.
  - The output is the same because `get_fastest_laps`/`Driver.get_fastest_lap` already
    select from the in-memory laps when they are loaded.
  - Only the CLI changes. The library's lazy `get_fastest_laps` is untouched, because its
    returned frame differs from the loaded-laps frame in category sets and the `index`
    column.
- A typo'd event name (`sessions 2026 Monacco`) still pays `tif1.fuzzy`'s numpy +
  rapidfuzz import (~136 ms). Not changed here.
- Possible follow-up for `version` (−13 ms): a static version source instead of
  `importlib.metadata`. It needs a hatch `dynamic = ["version"]` change, so it is out of
  scope.
- AGENTS.md describes `events.py` without `event_frames.py`; the integrator may want to
  add one line.
