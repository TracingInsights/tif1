# D9. Frame-tier row read: 57 ms for 70 MB (pandas)

Branch `perf/delphi-D9`, worktree `/tmp/tif1-delphi/D9`, measured against the
frozen control (commit 255759b) on 2025-11-03. This report replaces the
integrator's earlier REJECT draft (which measured parallel cursors, not
worker-side `blobopen` reads) and finishes the implementation the handoff
described.

## 1. Hypothesis

The 20 pandas driver rows of a race (70.6 MB of lz4) were read through one
cursor on the caller's thread, under `_sqlite_lock`, and only then handed to
the lz4 pool: ~57 ms of serial copying that bounded a warm
`fetch_all_laps_telemetry()` (110 ms) and `load()` (95 ms). Reading the rows
from the decompression workers themselves, on read-only connections of their
own and through `Connection.blobopen` (one copy into the `bytes`, GIL
released, no SQLite record buffer, each worker's malloc arena reusing its
previous row's buffer instead of the main arena mapping and trimming a fresh
3.5 MB for every row), should cut the read to ~20 ms and take 25-35 ms off
`all_tel` and `load()`.

## 2. What changed

`src/tif1/cache.py` only (plus tests and probes):

- `_get_driver_frames` and `get_telemetry_frame_sources` run one index
  query on the main connection under the cache lock,
  `SELECT driver[, laps], rowid, length(frame) ... WHERE year/gp/session AND
  driver IN (...)` (`length(frame)` reads the record header, not the blob:
  0.02 ms for 20 rows), and submit one task per row to the shared
  decompression pool (`_submit_frame_row_reads`). The serial path (no
  pyarrow lz4 codec, one worker, or a call from a pool thread) keeps the
  Pergamon Q11 streamed cursor with the control's SQL.
- `_read_frame_row` (worker): takes one of the cache's reader slots
  (`BoundedSemaphore`), borrows a reader connection (`Cache._open_reader`:
  `sqlite3.connect(..., check_same_thread=False, isolation_level=None)`,
  `PRAGMA query_only=1`, the same `mmap_size` as the main connection; idle
  readers are kept in `Cache._idle_readers`, at most `_reader_cap` of them),
  reads the blob through `_reader_frame_blob`, returns the connection, and
  decompresses the row with `_decompress_row` as before (narrow-row widening
  included).
- `_reader_frame_blob`: `BEGIN` ... `COMMIT` around a key lookup
  `SELECT rowid, length(frame) ... WHERE year/gp/session/driver` and the
  `blobopen(table, "frame", rowid, readonly=True).read()`. One read
  transaction covers both, so the blob opened is the row the reader's
  snapshot maps to the key; when that snapshot disagrees with the main
  connection's index (another rowid or another length: a write to that row
  is pending on the main connection, or a commit from the frame-writer
  thread landed in between) it returns None and the worker falls back to
  `Cache._read_frame_blob_locked`, a key-based `SELECT frame` on the main
  connection under `_sqlite_lock` (the single-cursor read's own view). Any
  `sqlite3.Error` on the reader (no `blobopen`, a closed reader, a locked
  file) takes the same fallback. The check costs ~6 us per row.
- `_FRAME_READER_CONNECTIONS = 4`, capped at `_decompress_workers()`
  (`Cache._reader_cap`); readers open on first use and are closed by
  `_release_resources` (`_close_readers`: idle ones immediately, a lent one
  when its worker returns it). `get_driver_merged_frame` (one row for
  `Laps.telemetry`) stays on the main connection: one row through the pool
  measured no faster than the cursor. The legacy per-lap table and the
  polars IPC tier are untouched.
- Tests: `tests/unit/test_delphi_d9_row_reads.py` (11 tests, offline):
  rows come through the readers (no main-connection blob read, readers
  return to the idle pool with no open transaction, `query_only` set), the
  batch path (wanted laps and `whole_driver`), the reader cap never exceeds
  the worker count, uncommitted rows fall back to the main connection and
  stop doing so after the commit, a replacement moved onto the old rowid
  before its commit is served from the main connection (SQLite's
  `INSERT OR REPLACE` never reuses a rowid, so the case is built with an
  `UPDATE ... SET rowid`), a row rewritten and committed by another thread
  between the index query and the read is served in its current version, a
  reader whose blob read raises falls back for every row and is still
  returned to the pool, `_reader_frame_blob` closes its transaction on
  success, mismatch and error, readers close with the cache and a late
  return closes too, the idle pool never grows past the cap, the serial
  path reads the same rows through the cursor, and a corrupt row or a
  missing driver is a miss.
- Probes (`tools/perf/`): `delphi_d9_rowread.py` (raw read, the previous
  agent's), `delphi_d9_cache_read.py` (library-level read, fresh process),
  `delphi_d9_phases.py` (index / raw read / read+lz4 / sources / decode
  phases), `delphi_d9_pool_probe.py` (system vs jemalloc pool),
  `delphi_d9_close_probe.py` (exit cost of the readers).

## 4. Verdict: SHIP

The named phases drop by a quarter to a third in every run (`all_tel` 111-120
-> 94-95 ms, 12/12 and 6/8; `load` 83-88 -> 58-61 ms, 12/12 and 8/8) with the
walls not worse (notebook wall -19 ms, 10/12 and 6/8; all_tel wall equal
within the box's noise, 7/12). `driver_tel` and the polars workloads are
unchanged. Parity is exact. The target (read 57 -> ~20 ms) is met for the
read itself (17-20 ms); the wall target of -25..-35 ms on `all_tel` is not
visible under this load because the output page faults and the serial decode
now dominate the phase (see the notes).

## 5. CHANGELOG paragraph

- Warm pandas sessions read the frame tier's driver rows in the lz4
  workers. The 20 rows of a race (70 MB of lz4) were copied out of SQLite by
  one cursor on the calling thread before any decompression started; each
  row is now read by the worker that decompresses it, on one of up to four
  read-only connections through `Connection.blobopen` (one copy, GIL
  released) inside a read transaction that re-checks the row against the
  main connection's index, with the main connection as the fallback for a
  row written in this process and not yet committed. Fresh process, 2025
  Bahrain race: `fetch_all_laps_telemetry()` 111-120 -> 94 ms, `load()` 83-88
  -> 58-61 ms, `get_car_data()` over a driver's laps 24 -> 21 ms; single-row
  reads, `Laps.telemetry` and polars sessions unchanged. The readers open on
  first use and close with the cache.

## 6. Notes for the integrator

- Why this works where D4 (decode in the workers) did not: D4's section 6
  found the cursor loop GIL-chatty (one re-acquisition per row) and any
  Python-heavy side thread convoys it. Here the main thread runs no cursor
  at all during the read; it only waits on `as_completed` and decodes rows as
  they land, and the workers' Python work per row is a handful of calls
  around a GIL-released `blobopen().read()` and `codec.decompress`.
- Consistency: the reader's snapshot is the last commit. The in-transaction
  key check plus the `length(frame)` comparison means a reader never serves
  another driver's row and never serves an older version of a row the main
  connection has replaced (a replacement with the same compressed length at
  a reused rowid is the one undetectable case; `INSERT OR REPLACE` never
  reuses a rowid, the `invalidate`/`clear` DELETEs commit under the lock, so
  it needs a hand-built transaction, and even then it degrades to the old
  laps of the same driver, which the caller then fetches). Tests cover the
  uncommitted, replaced-in-between and moved-rowid cases.
- Lifecycle: readers are opened lazily, kept idle in the cache, closed by
  `_release_resources` (so by `close()`, `__del__` and the atexit hook);
  `_close_readers` takes only `_reader_lock`, briefly, so it is safe from
  `__del__`. A worker holding a lent reader when the cache closes closes it
  on return. Pool threads are joined by `threading._shutdown` before atexit
  runs, so no reader is in flight when the cache closes at exit.
- Fork: a forked child inherits the idle readers as it inherits the main
  connection today (the decompression pool is already reset at fork); no new
  exposure class, but if fork handling is ever added for the main
  connection, drop `_idle_readers` there too.
- Pyodide / no threads: `_decompress_workers()` is 1, the serial cursor path
  runs, no reader is opened. Windows: `str(self.db_path)` is the connection
  string the main connection already uses; `blobopen` exists on every
  supported CPython (3.11+).
- Memory: at most `_reader_cap` compressed rows (4 x ~3.5 MB) are in flight
  instead of every row the cursor could outrun the pool with; the
  decompressed buffers are the same as before.
- What is left in `all_tel` (94 ms): ~40 000 minor faults for the 123 MB of
  decompressed output (110-130 ms of system time spread over the workers,
  the per-fault cost inflated by contention) and the 29-36 ms serial decode.
  jemalloc does not change the fault count; transparent huge pages are
  `madvise` on this box so only an explicit `madvise(MADV_HUGEPAGE)` on the
  output buffers would help, which pyarrow's pools do not expose. A
  decompressor that writes straight into a huge-page or pre-faulted buffer
  (tif1-native) is the next lever, outside this round.
- The handoff's 10-pair rerun by the integrator (`all_tel` 110 -> 89, 7/10;
  `load` 84 -> 61, 9/10) agrees with the numbers above.
- Artefacts in `.agents/perf-delphi/`: `D9_ab_pandas.json` (8 pairs, four
  workloads), `D9_ab_pandas_12.json` (12 pairs), `D9_ab_polars.json`,
  `D9_ab_readers_2_vs_4.json`; parity digests in `/tmp/D9_parity_pandas.json`
  and `/tmp/D9_parity_polars.json`.
