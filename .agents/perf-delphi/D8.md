# D8: driver merged telemetry from the memoized decoded row (pandas)

## 1. Hypothesis

After `load()` (or any earlier lap access of the driver) the session memo
already holds the driver's decoded frame-tier row as a `DriverFrameSource`,
yet `laps.pick_driver(d).telemetry` re-read the row from SQLite, decompressed
and widened it again and decoded it a second time (`get_driver_merged_frame`
-> `decode_driver_merged`), then concatenated the pieces of multi-group rows
with `pd.concat`: ~19 ms per driver in the notebook workload
(`driver_merged_x4` 76 ms). Building the merged frame as a gather over the
memoized source's group arrays should cut that to a few ms per driver, with
the no-`load()` path (`driver_tel` workload, the row is not in the memo) no
worse than before.

## 2. What changed

- `cache.py` `SessionMemo`: `add_telemetry_source` also keeps the source per
  driver (`_driver_sources`); `driver_source(driver)` reads it; `clear()`
  drops it. The per-driver entry survives the materialisation of every lap
  frame of the driver (the pending per-lap entries are popped as frames are
  built), so a merged frame is still a gather after a `fetch_all_laps_telemetry()`
  or an `iterlaps()` loop.
- `core_utils/frame_codec.py`: the body of `decode_driver_merged` moved into
  `DriverFrameSource.merged(laps, drop_repeats=, move=)`. Runs of laps stored
  consecutively in one layout group are one gather over the group's arrays;
  consecutive runs of the same group share one piece. Pieces of different
  groups (a race driver whose laps split between a `str` `DriverAhead` layout
  and an object one) are joined column by column into fresh arrays
  (`_joined_pieces`) with pandas' promotion rule for the layouts the codec
  writes (equal dtypes stay; `str` joined with object becomes object with
  `nan` for a `str` null, as `astype(object)` gives); any other mix falls back
  to `pd.concat`. The `str` group parts carry their dictionary and codes for
  that promotion. `str` columns are sliced on the pyarrow `ChunkedArray`
  directly instead of through `ArrowExtensionArray.__getitem__` per span.
  `_gather_spans` copies by default (the memo keeps the arrays intact: every
  lap frame of the driver is a view of them) and moves in place with
  `move=True`, which `decode_driver_merged` uses for its throwaway decode
  (the previous `_take_spans` behaviour); the move falls back to a copy when
  the spans are not ascending and disjoint (laps asked for out of their
  stored order) or the array is read-only.
- `models.py` `Laps._merged_from_driver_source`: with a memoized source, the
  merged frame is `source.merged(laps, drop_repeats=True)`; without one the
  path is the previous `get_driver_merged_frame` (read, decompress, decode,
  move in place). The source is *not* registered on that path: holding it
  would force the merged frame to copy its rows, and in a fresh process the
  copy of a race driver's ~7 MB of blocks costs ~1700 minor page faults
  (3-4 ms), which is exactly the `driver_tel` regression the handoff
  measured (22.5 -> 24.3 ms, 0/6 and 1/10 pairs).
- `cache.py` `get_telemetry_frame_sources`: a single-row read decompresses
  inline (`_submit_frame_rows(parallel=False)`) instead of through the pool
  (one row gains nothing from a worker and waits for its wake-up).
- Tests (`tests/unit/test_pergamon_contracts.py`, Delphi D8 section): the
  memo keeps the driver source after every lap is built; `merged()` of mixed
  layouts equals `pd.concat` of the lap frames (dtypes, `None`/`nan`
  semantics, requested order, duplicates) without calling `pd.concat`;
  layouts the join does not cover fall back to `pd.concat`; `drop_repeats`
  matches the row take `_join_lap_telemetry` would do; `move=True` gives the
  copy's frame (block signature included) over the source's own memory and
  copies when the spans are out of order; after `load()` the merged frame is
  gathered without any tier read and owns its rows (a write leaves the lap
  frames alone); without a memoized row the tier is read once through
  `get_driver_merged_frame`, nothing is held, and a later lap access holds
  the row from then on.

## 4. Verdict

**SHIP.** The named workload wins: notebook wall 981.5 -> 935.3 ms (-4.7 %,
7/8) on the back of `driver_merged_x4` 75.7 -> 40.3 ms (8/8), with `load`
unchanged; in-process the merged telemetry of four drivers after `load()`
is 60.6 -> 25.6 ms (the target was 19 -> ~8 ms per driver; measured 13-17
-> 5-8 ms). `driver_tel` without `load()` is neutral (23.1 -> 22.7 ms,
6/12; wall 4/12 at +0.4 ms), `car_data_loop` gains 3.5 ms from the inline
single-row read (7/8), `all_tel` and the polars path are unchanged. Parity
is identical on both backends.

## 5. CHANGELOG paragraph

- **Driver merged telemetry from the memoized row (D8).**
  `laps.pick_driver(d).telemetry` after `load()` (or after any lap of the
  driver was touched) gathers the frame from the decoded driver row the
  session memo already holds instead of reading the row from SQLite,
  decompressing and decoding it a second time; a driver whose laps span
  two storage layouts is joined column by column instead of through
  `pd.concat`. Four drivers' merged telemetry in the notebook benchmark
  76 -> 40 ms (8/8), the whole notebook 982 -> 935 ms (7/8); in-process
  after `load()` 61 -> 26 ms for four drivers (2.4x). Without `load()` the
  path is the previous one (23 ms, unchanged): the merged frame then views
  its own decode, where a held row would cost it a copy. A single driver
  row read by a per-lap access decompresses inline instead of through the
  pool (a `get_car_data()` loop over one driver's laps 25 -> 21 ms).

## 6. Notes for the integrator

- **Memo lifetime.** `SessionMemo._driver_sources` keeps every decoded
  `DriverFrameSource` for the session's lifetime; before, a source was
  dropped once all its laps were materialised. The blob buffers were kept
  alive by the lap frames' views anyway, so resident memory is unchanged in
  practice; what stays extra is the source object itself (group tuples,
  cached `_LapBuilder` plans, clocks, column maps: small). `clear()` drops
  them with everything else.
- **Aliasing.** `merged()` without `move` always copies the numpy and
  `Int64` stretches: pandas' copy-on-write tracks references between
  pandas objects, not between frames built independently over one numpy
  buffer, so a view would let a user write to the merged frame change the
  lap frames (the unit test checks the write stays local). `str` columns
  are pyarrow slices (immutable storage), shared safely. `move=True` is
  only for the throwaway decode of `decode_driver_merged`; `_ascending`
  keeps it from overwriting rows when laps are asked for out of their
  stored order (control moved per run, so never saw that case; the branch
  merges consecutive runs of one group into one piece).
- **Why the no-`load()` path does not register the row.** Registering
  forces the copy (3-4 ms of page faults for a race driver in a fresh
  process) on every such merged access, to save a later per-lap re-read
  (~14 ms, and only ~5 ms when that access is a lone lap served by the
  payload tier) in a pattern the harness does not measure. If that pattern
  matters, the cheap follow-up is to keep the compressed SQLite row bytes
  in the memo and have `get_telemetry_frame_sources` skip the SQLite read
  (~2 ms of the ~14): not done here.
- **`_joined_pieces` scope.** The column-wise join covers the layouts the
  codec writes (equal dtypes; `str` + object `DriverAhead`); anything else
  returns None and `pd.concat` of the piece frames runs as before, so a new
  layout cannot silently change dtypes. The `str` group parts are now
  5-tuples (`kind, placement, ea, cats, codes`); consumers index by
  position (`_lap_plan`, `frame`, `frames`), none unpacks by length.
- **Frame tier format unchanged**; no `_FRAME_TIER_SCHEMA_VERSION` bump.
- **Noise.** The box ran at load average 10-14 throughout; phase medians of
  10-20 ms moved by several ms between identical runs (e.g. control
  `all_tel` 132 vs 114, `get_session` 400 vs 433). Read the pairs-won and
  minima next to the medians; the two neutral workloads were re-run at 12
  pairs for that reason.
- **Commit state.** The agent sandbox denied every `git commit`; all
  changes are staged on `perf/delphi-D8` and `D8_COMMITS.md` next to this
  report holds the two intended commit messages (implementation + tests,
  then report + probes).
- **Tools kept** under `.agents/perf-delphi/d8_tools/` (stage timers, the
  page-fault and GC probes, the micro benchmark, the parity and A/B table
  runners), all parameterised on `control|candidate` and run with
  `python -I`.
