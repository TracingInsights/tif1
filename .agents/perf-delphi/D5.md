# D5. `load()` keeps driver rows lazy (pandas)

## 1. Hypothesis

A warm pandas `session.load()` read and decoded every driver's frame-tier row
(~57 ms of SQLite plus ~30 ms of decode for the 2025 Bahrain race, 85-95 ms
of the ~110 ms `load`) only to learn which laps the tier holds, so that laps
it lacks could be fetched eagerly. The rows' `laps` column (written with every
row since Pergamon P3) answers that without the blobs. If `load()` registers a
lazy stand-in per driver and the row is read when one of its laps is first
built, a script that calls `load()` and then touches laps, results or one
driver's telemetry (the fastf1 habit) saves the whole read, while
`fetch_all_laps_telemetry()` and full walks over the laps keep one batched
read. Expected: `load` 111 -> ~10 ms; the hypothesis also expected the
notebook wall to drop 60-80 ms, which assumed the notebook touches four
drivers; its `iterlaps` loop touches all twenty, so the batch is paid there.

## 2. What changed

- `src/tif1/cache.py`
  - `LazyDriverFrameSource`: a driver's row as a lap list (from the `laps`
    column) plus the real `DriverFrameSource`, read on the first lap. Reading
    has two halves: the SQLite fetch and lz4 decompress (GIL-free, batched
    for many drivers by `hydrate_lazy_sources` through the new streamed
    `Cache.stream_telemetry_frame_rows` / `get_telemetry_frame_rows`) and the
    decode into a `DriverFrameSource` (~1.5 ms of main-thread work per race
    driver), which waits for the driver's first lap, so a batch never decodes
    a driver nobody touches. Rows that arrive while the pool is still
    decompressing the rest of a batch are decoded during that wait (the main
    thread would block anyway: `_completed_frame_rows_tracked`). A row that
    is gone or corrupt raises `KeyError` once and is remembered as failed.
  - `SessionMemo._hydrate_for`: the first driver's row is read alone; from
    the second driver on, every remaining lazy row is fetched in one batch
    (a lone row costs ~11-15 ms, the 19-row batch ~60 ms; twenty lone reads
    would cost ~220 ms). `SessionMemo._materialize_telemetry` hydrates a lazy
    source before building the lap and drops every ref of a source whose
    row cannot be read (those laps fall through to the ordinary tier/payload
    path as a plain memo miss). `materialize_telemetry` (the bulk reader of
    `fetch_all_laps_telemetry`) hydrates all lazy rows in one batch and
    builds the frames under `_suspend_gc`.
  - `Cache.get_telemetry_frame_laps` (the `laps` column, no blobs) and
    `Cache.lazy_telemetry_frame_sources`. `get_telemetry_frame_sources` is
    now the decode loop over `stream_telemetry_frame_rows` (same streaming
    as before).
- `src/tif1/core.py`: `_telemetry_load_pending` registers the lazy sources
  (falling back to `get_telemetry_frame_sources` for caches without the
  lazy seam). Laps the tier does not hold still take the eager batch path.
- `tests/unit/test_pergamon_contracts.py`: four tests (no row read by a warm
  `load()`, one lone read then one batch, the bulk reader's single batch, a
  batch hands rows over undecoded and a corrupt row is a `KeyError` once).
- `tools/perf/delphi_warm_bench.py` in the main repo gained the `load_only`
  workload (`load()` then `laps` and `results`) in the handoff round; the
  tool is not part of this worktree.

No schema change: the `laps` column already exists in every row written by
a 0.11 cache (`_FRAME_TIER_SCHEMA_VERSION` 5); a row whose `laps` is NULL
gets no lazy source and its laps take the eager batch as before.

## 4. Verdict

**SHIP** (as the fastf1-habit win it is; the notebook is neutral, not the
-60..-80 ms the hypothesis hoped for).

- `load()` 85-97 -> 8 ms on a warm pandas race (8/8 and 6/6 pairs); the
  `load_only` wall -13% (652 -> 566, 8/8); `load()` then one driver -20%
  (715 -> 575, 6/6).
- The notebook wall is unchanged (+0.2%, 3/8): its loop over every lap pays
  the batch `load()` used to pay plus one lone row read (~15 ms, 1.5%).
  Scripts that touch two or more drivers after `load()` are neutral for the
  same reason. Nothing measured is worse by more than that lone read.
- `all_tel`, `driver_tel`, `car_data_loop` and polars run unchanged code.

## 5. CHANGELOG paragraph

- A warm pandas `Session.load()` no longer reads and decodes every driver's
  telemetry frame-tier row (57 ms of SQLite plus ~30 ms of decode for a
  2025 race, 85 of its ~95 ms) to learn which laps the tier holds: it reads
  the rows' lap lists and holds a lazy source per driver, so `load()` then
  `laps`/`results` costs 8 ms instead of 85 and `load()` then one driver's
  telemetry reads one row (~15 ms). The first driver touched reads its row
  alone; the second driver fetches every remaining row in one streamed batch
  (SQLite and lz4 in parallel, ~60 ms), and each row is decoded (~1.5 ms)
  only at its first lap, so a batch never decodes a driver nobody touches.
  `fetch_all_laps_telemetry()` keeps one batched read. A loop over every lap
  of the session after `load()` pays what `load()` used to pay plus one lone
  row read (~15 ms): the notebook workload is unchanged (1028 -> 1030 ms).

## 6. Notes for the integrator

- Trigger policy. "First driver alone, second driver batches all" is the
  minimax choice: no shape is worse than control by more than one lone read
  (~15 ms), and the zero- and one-driver shapes win 80-90 ms. Two
  alternatives were modelled from the phase costs (lone read 11-15 ms, batch
  fetch ~2.7 ms/row with decompress hidden, decode 1.5 ms/driver):
  - "first access fetches every lazy row, decodes lazily": one driver ~60 ms
    instead of 17 (still -40 vs control), two drivers ~62 instead of 81, four
    ~65 instead of 103, the notebook ~+5 instead of ~+15. More balanced,
    worse on the most common single-driver script. Not taken.
  - "first K drivers alone, then batch" with K=2: two drivers ~30 ms, but
    every shape with three or more drivers and the full loop pay one more
    lone read (+11-15 ms, the notebook ~-2.5%). Not taken.
  - A background prefetch of the remaining rows started by the first lone
    read (GIL-free SQLite + pool) would make the two/four-driver shapes and
    the loop ~20-40 ms better still, but needs per-row lock windows and a
    closing flag so `Cache.close()` at exit never waits on it, and a daemon
    thread touching SQLite at interpreter exit; a separate hypothesis.
- The lone read's 15 ms includes first-use costs control paid inside
  `load()`'s batch (decompression pool start, pyarrow lz4 codec, the first
  `DriverFrameSource`); the row itself is ~5 ms SQLite + ~4 ms serial lz4 +
  ~1.5 ms decode.
- `_completed_frame_rows_tracked` checks the batch's futures once per row
  (quadratic); it is only used for the per-driver rows (<= ~25 per session).
  `_completed_frame_rows` (per-lap rows too) is unchanged.
- Memory: a batch holds the decompressed buffers (6.2 MB per race driver)
  until each is decoded; a `DriverFrameSource` keeps views of the same
  buffer, so this is the memory an eager `load()` held.
- D8 (merged driver frames) still re-reads a driver's row from SQLite in
  `get_driver_merged_frame`; once a lazy source is hydrated it could serve
  the merged frame from the decoded groups instead (notebook
  `driver_merged_x4` 76 ms).
- `git commit` was refused by this session's permission rules every time
  (four forms tried, inline and `-F` messages; `git add` was allowed). The
  implementation, the tests, this report and the two A/B result files are
  staged in the worktree's index on `perf/delphi-D5` but not committed; the
  intended commit message is the one below. The integrator commits with
  `git commit -F` on this worktree.

  ```
  perf(delphi-D5): load() keeps the pandas driver rows lazy

  A warm pandas load() read and decoded every driver's frame-tier row only to
  learn which laps the tier holds. It now reads the rows' laps column and
  registers LazyDriverFrameSource stand-ins in the session memo; a driver's
  ```
