# D4. Decode driver rows in the decompression workers (pandas frame tier)

Verdict: **REJECT**. Decoding the driver rows off the caller's thread does
not shorten a warm `fetch_all_laps_telemetry()` or `load()`; every
placement that runs the decode beside the SQLite cursor loop makes the
read slower than the decode it hides, because the decode is GIL-bound and
the cursor loop re-acquires the GIL once per row. The one GIL-free part of
the decode (the pyarrow dictionary take of the `str` columns) can be moved
to the workers with identical output, but it is worth ~2 ms on the named
workloads and does not meet the bar. The branch holds that variant, tested
and parity-clean, for reference only; nothing on it should be merged.

## 1. Hypothesis

A warm pandas `fetch_all_laps_telemetry()` (1128 laps, 2025 Bahrain race)
spends ~110 ms, of which the SQLite read of the 20 driver rows (70.6 MB) is
~57 ms on the main thread, the lz4 decompression overlaps it on the 8-worker
pool, and the `DriverFrameSource` decodes (header, `np.frombuffer` views,
object-column gathers, the pyarrow take of `DriverAhead`, then the per-lap
frames) run serially on the main thread after the whole cursor is drained.
Constructing the sources (and, for `_get_driver_frames`, the lap frames)
inside the worker right after each row's decompression should overlap the
20 decodes with each other and with the read: target `all_tel` 114 -> ~70
ms, `notebook` load 111 -> ~60 ms.

## 2. What changed (and what was tried)

Measured on this box (fresh process, warm cache, offline; load average
15-29 on 32 cores throughout, so absolute numbers drift):

- Evidence check. SQLite read of the 20 rows: 53-59 ms in a fresh process
  (33 ms once the process is warm). Serial `DriverFrameSource` x20 after the
  drain: 41-54 ms in a fresh process (20-25 ms steady state; the brief's 107
  ms did not reproduce), `frames()` for all 1128 laps 21 ms. The "one-time
  14 ms pyarrow/StringDtype initialisation" did not reproduce either (the
  first `take` of a process costs 0.8 ms; a worker's first call is ~1 ms
  slower than steady state), so no early warm-up was needed. Thread scaling
  of the decode alone, steady state, 20 rows: 1 worker 24 ms, 2 workers
  26-30 ms, 4 workers 30-37 ms, 8 workers 33-43 ms (the sum of per-task
  times grows from 20 ms to 100-200 ms): the decode is GIL-bound and does
  not parallelise, so any win had to come from overlapping it with the
  read.
- Variant A, decode on the worker that decompressed the row
  (`_submit_frame_rows(rows, decode)` with the decode inside the pool task;
  `_suspend_gc` widened to cover the streamed read). Timeline of one fresh
  `all_tel` process: control drains the cursor at 53.5 ms and finishes the
  serial decodes at 94.9 ms (phase 103 ms); with the decode in the 8 workers
  the cursor drains at 148.5 ms (row arrivals 5-13 ms apart instead of 1-5)
  and the phase takes 189 ms. The sum of per-task decompress wall time went
  from 196 ms to 351 ms: the workers' numpy widening and the main thread's
  cursor loop both wait a switch interval behind the Python-heavy decodes.
- Variant B, one dedicated decoder thread fed in completion order
  (`_DecodePipeline`: decompression stays on the pool, decodes serialise on
  one thread, so only two GIL-heavy threads run beside the cursor). Drain
  at 91 ms, decoder done at 182 ms, phase 195 ms. With the interpreter
  switch interval lowered to 0.1 ms for the duration of the read (an
  experiment, not a proposal): drain at 68 ms (same as control), but the
  decoder thread took ~118 ms for decodes that take 54 ms serially on the
  main thread (each of its numpy/pyarrow calls re-acquires the GIL behind
  the main thread and the 8 decompressors); phase 146 ms.
- The mechanism, isolated. Raw cursor read of the 20 rows in a fresh
  process, three reps: alone 59/34/33 ms; beside one Python-busy thread
  175/154/133 ms; beside eight 1396/1593/802 ms; beside one numpy-busy
  thread (releases the GIL often) 126/91/75 ms. With the switch interval
  at 0.1 ms: beside one Python thread 52/39/37 ms, beside eight
  160/151/169 ms. `sqlite3_step` releases the GIL, but the loop takes it
  back once per row and each take waits up to the 5 ms switch interval
  while a Python thread runs; the decode (pickle header, object gathers,
  `ArrowStringArray` and `BlockManager` construction) is such a thread.
- Variant C (kept on the branch): only the GIL-free part moves. The
  decompression worker runs `frame_codec.prepare_driver_strings` right
  after the row's decompression (one pyarrow `take` per `str` column,
  keyed by body offset); `DriverFrameSource(..., strings=)` /
  `decode_driver_frames(..., strings=)` wrap those arrays instead of taking
  them on the caller's thread (a prepared array of the wrong length is
  ignored and taken again). `_submit_frame_rows(rows, decode)` returns a
  `_DecodedRows` view that applies `decode` on the consumer's thread as
  rows complete; `_get_driver_frames` and `get_telemetry_frame_sources`
  use it. Files: `src/tif1/cache.py` (`_prepare_frame_row`,
  `_DecodedRows`, `_submit_frame_rows`, the two readers),
  `src/tif1/core_utils/frame_codec.py` (`_take_str`/`_wrap_str`,
  `prepare_driver_strings`, `strings=` on `_group_parts`,
  `DriverFrameSource`, `decode_driver_frames`),
  `tests/unit/test_delphi_d4_prepared_strings.py` (7 tests: prepared
  arrays equal the plain take, identical frames with and without them,
  wrong-length arrays ignored, corrupt rows still a per-driver miss on both
  readers, inline path from a pool worker, all-null and constant `str`
  columns).

## 4. Verdict

REJECT. The hypothesis' premise (that the 20 decodes could overlap each
other and the SQLite read) fails on the GIL build: the decode does not
parallelise (its per-task time triples at 8 workers) and any Python-heavy
thread running beside the cursor loop slows the read by 2-3x, so the
overlap costs more than it saves at every worker count, with or without a
dedicated decoder thread, and even with the interpreter switch interval
lowered. The GIL-free remainder (the `str` take, ~0.5 ms per row) is the
only part that can move, and moving it is worth ~2 ms on `all_tel` and
`load` with the wall unchanged: below the 3% bar and below the noise of
this box. Do not merge.

## 5. CHANGELOG paragraph (only if the string-take variant were merged; not recommended)

Performance: the pandas frame tier takes the `str` columns of each driver
row (the pyarrow dictionary take of `DriverAhead`) on the decompression
worker right after the row's decompression instead of on the caller's
thread after the whole read, the one part of a driver-row decode that
releases the GIL. A warm `fetch_all_laps_telemetry()` of a 2025 race is
~2 ms faster (112 -> 110 ms in-process); frames are byte-identical.

## 6. Notes for the integrator

- The convoy is the finding worth keeping. The frame-tier cursor loop is
  GIL-chatty (one re-acquisition per row); the 8 lz4 workers get away with
  it because lz4 and the numpy widening release the GIL, and even they
  inflate each other (per-task decompress wall 6-13 ms beside the cursor vs
  1-4 ms alone). Anything that adds Python-heavy work beside that loop,
  including D9's parallel SQLite connections if their row handling is done
  in Python threads, should be measured with the fresh-process timeline
  (`cursor drained at` vs `collect done`) rather than in-process repeats:
  the steady-state numbers in one process (decode 20-25 ms, read 33 ms)
  are 2x better than the fresh-process ones the workloads actually see.
- A 0.1 ms `sys.setswitchinterval` during the read does remove the convoy
  for the cursor (raw read beside a Python thread 133-175 -> 37-52 ms) but
  the side-thread decode still ran 2x slower than serial, so it was not
  enough; it is also a process-global setting a library should not touch.
- Not measured, possibly worth a look: 3-4 decompression workers instead
  of 8 for driver-sized rows (the pool is sized for the 1400-row legacy
  tier), given how much the 8 inflate each other beside the cursor.
- Free-threaded CPython would change this picture entirely; the abi3
  wheels do not cover it.
- Experiment artefacts: `D4_ab_pandas.json` (the official A/B of the
  committed tree), `D4_ab_pandas_prepared_10.json` (the earlier 10-pair run
  of the same variant under heavier load). Probe scripts lived in
  `/tmp/d4probe` and are not part of the tree.
