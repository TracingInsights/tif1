# D2. Pandas-session startup trim

## 1. Hypothesis

A warm pandas `get_session` (pandas already imported) spends tens of
milliseconds in tif1's own startup on work a cached session never uses
before its first telemetry frame, or at all: the pandas block-assembly probe
(`_probe_direct_blocks`), the async fetch layer and HTTP session module, the
CDN manager, `tif1.types`, the Ergast value parsers, `importlib.resources`
for the vendored schedule, and a handful of module-level regex compiles.
Deferring each to its first use should cut the in-process startup roughly
in half and take the same amount off the whole-process wall of the
`import_get_session`, `laps` and `results` workloads.

## 2. What changed

Measured first, pandas and numpy pre-imported, then `import tif1` +
`get_session(2025, "Bahrain Grand Prix", "Race")`, warm cache, offline, no
profiler. The hypothesis's 60 ms was a cProfile number; the real cost on
this box is 33-37 ms (control, 12 paired runs: median 33-37, min 32):

| phase (control) | ms |
|---|---:|
| `import tif1.core` (34 modules) | 18.4 |
| first `_resolve_gp_name`: lazy `tif1.events` import 3.2 (of which `importlib.resources` 1.6), first `files()` call 1.25, vendored load + convert + validate 0.6 | 5.3 |
| `import tif1.models` | 2.5 |
| `import tif1.core_utils.pandas_blocks` incl. the probe (the probe body alone, second call: 1.6; the rest is pyarrow's pandas shim import, `pyarrow.pandas_compat` + `pyarrow.vendored.version` 2.5, and the first `ArrowStringArray` of the process) | 6.3-7.8 |
| `Session()` | 0.1 |

asyncio was already lazy in control (Pergamon P5): the "8 ms async_fetch
import" of the hypothesis was cProfile inflation of `async_fetch` ->
`cache` + `http_session` (0.9 ms real).

Mechanisms (files):

- `core_utils/pandas_blocks.py`: `_DIRECT_BLOCKS_OK` starts as `None`;
  `_direct_blocks_ok()` runs `_probe_direct_blocks` on the first frame
  build and pins the verdict (tests still pin `False`).
  `_frame_from_columns` and every `frame_codec` entry point (`encode_frame`,
  `decode_frame`, `_frame_parts`, `_writable_body`) call it;
  `frame_codec._FAST_LAP_FRAMES` is resolved the same way by
  `_fast_lap_frames()`. `core._load_pandas_models` no longer imports or
  probes the block module; `helpers._load_pandas_blocks` stays as the
  eager seam. Pergamon Q3 tried this part and the lazy CDN singleton and
  rejected them at +2.7 ms on the import (`DO_NOT_RETRY`: "generic import
  trims of tif1's own modules (2.7 ms)"); with pandas 3.0.6 the probe
  module costs ~6 ms because its str column pays the first
  `ArrowStringArray` of the process, and D2 bundles it with the items
  below, so it was re-measured as instructed.
- `core.py`: no module-level import of `async_fetch` (and through it
  `http_session`), `cdn` or `types`. `fetch_multiple_async` and
  `get_cdn_manager` are thin delegates that keep their module-global names
  (tests patch `tif1.core.fetch_multiple_async`; the fetch paths look the
  name up at call time, and the `TypeError` fallback for simplified test
  doubles is unchanged); `_validate_json_payload` imports its
  implementation on call; `ScheduleBackend` is a `TYPE_CHECKING` import.
  `payload_loader.cdn_manager` and `ergast/payloads.py`'s `cdn_manager`
  import `get_cdn_manager` on first use (`CDNManager` under
  `TYPE_CHECKING`).
- `core_utils/ergast_results.py`: `tif1.ergast.structure` (four regex
  compiles) is bound through `lazy_module`; it loads when a classification
  is merged (the first `results`).
- `events.py`: the vendored schedules are read through `pathlib` next to
  the module (`_vendored_schedule_bytes`, `_vendored_schedule_names`);
  `importlib.resources` is used only when the package directory is not on
  disk (an archive install), checked once. `circuit_info.py` still uses
  `files()` (not on the startup path).
- `core_utils/lazy_import.py`: `lazy_pattern(...)`, a `LazyPattern` proxy
  that compiles on the first attribute read and rebinds the module global
  (as `lazy_module` does). Used for the seven patterns of the startup
  path: `core._ISO_SECONDS`, `events._ALIAS_NOISE_RE`,
  `events._F1SCHEDULE_YEAR_PATTERN`, `session_state._ISO_TIMESTAMP`,
  `ergast_results._ISO_DATE`, `models._LEGACY_OFFSET_RE`,
  `models._CLASSIFIED_STATUS_RE` (~0.1 ms each at import, ~0.7 ms total).
- Tests: `tests/unit/test_delphi_d2_startup.py` runs `get_session` in a
  fresh interpreter (offline, empty cache) and asserts that the import of
  `tif1` plus the call added none of `asyncio`, `importlib.resources`,
  `niquests`, `polars`, `pyarrow.pandas_compat`, `pydantic`, `rapidfuzz`,
  `rich`, `typer`, `tif1.async_fetch`, `tif1.cdn`, `tif1.http_session`,
  `tif1.core_utils.pandas_blocks`, `tif1.core_utils.frame_codec`,
  `tif1.ergast.structure`, `tif1.fuzzy`, `tif1.plotting`, `tif1.types`,
  `tif1.validation` to `sys.modules` (pandas and `tif1.models` must be
  imported); plus contract tests for the lazy probe (runs once, pinned
  verdict honoured, a failed probe routes every entry point to the
  fallback, `_load_pandas_blocks` probes eagerly), the core delegates, both
  lazy CDN-manager properties, the vendored-schedule reader (bytes equal to
  the `importlib.resources` answer, archive fallback, missing year) and
  `lazy_pattern`. `test_pergamon_contracts.py` reads the lap-frame flag
  through `_fast_lap_frames()`; `tools/perf/q18_parity.py` likewise.

After the change (same measurement): `import tif1.core` 15.6 ms (28
modules), first `_resolve_gp_name` 3.0 ms, `tif1.models` 2.7 ms, no block
module. The warm startup now imports, besides tif1's own modules: sqlite3,
orjson, lz4, zstandard and tif1_native (all needed by the first cache read).

## 3. Measurements

All runs on the shared box (load average 10-30 on 32 cores: other agents'
suites were running), fresh process per rep, offline, each arm on its own
primed cache, interleaved (ABBA).

### 3a. In-process startup, pandas pre-imported (what D2 targets)

### 3c. Parity

- pandas: `0 differing surfaces out of 133`
  (`/tmp/delphi_parity_pandas.json` vs the candidate digest).
- polars: the candidate digest differs from the control digest in 56
  surfaces, all of them `Race|Qualifying/analysis{i}/{tel,dist,resample,
  resample1s,fill,car,pos,car_pad}`; every other polars surface (laps,
  results, drivers, state tables, fastest-lap and driver telemetry,
  pick_*, split, `all_tel` frames) is identical. The analysis laps are
  chosen from `laps["Driver"].unique().to_list()`, and polars' `unique()`
  does not keep order, so the four "fastest" laps differ from run to run:
  the **control tree against its own stored digest** differs in 64
  surfaces, again all `analysis*` and nothing else. The polars digest is
  therefore not reproducible on those surfaces for any tree
  (`delphi_parity.py` should pass `maintain_order=True` there); D2 touched
  no polars frame code.

## 4. Verdict

**SHIP** (on the in-process clause of the brief; the wall target of the
hypothesis was not reachable).

- tif1's own warm startup (pandas pre-imported): 33-37 -> 19-21 ms, -13 to
  -14 ms, 12/12 pairs in every mode; a pure gain for anything that never
  builds a telemetry frame, and -7 to -8 ms net for a script whose first
  action after `get_session` is a telemetry frame or `results`.
- Whole-process wall of the named workloads: -9 ms (1.7%), -13 ms (2.4%),
  -4 ms (0.7%) at 10/20, 16/20, 17/20 pairs. Below the 3% wall bar, but
  the in-process `get_session` phase win is clear and the wall is not
  worse. The hypothesis's "wall -30 ms" assumed the cProfile-inflated 60
  ms; the real startup was 34 ms, of which the change removes 40%.
- What remains of the 20 ms: `tif1.core`'s own import (~4 ms of pyc load
  and class bodies), `cache` 1.5, `models_shared` 1.4 (the `CircuitInfo`
  dataclass), `models` 2.5, `payload_loader` 0.9, `helpers` 0.8,
  `exceptions` 0.6, sqlite3/orjson/lz4/zstd 2.4 (needed by the first cache
  read), `events` 1.5 + the schedule load 0.6. None is deferrable without
  restructuring the modules (Pergamon Q3 reached the same conclusion).

## 5. CHANGELOG paragraph

**Performance**: a warm pandas `get_session` no longer pays for work it does
not use. The block-assembly probe (`_probe_direct_blocks`, ~6 ms with pandas
3.0.6 because its string column initialises pyarrow's pandas shim and the
first `ArrowStringArray` of the process) runs at the first telemetry frame
build instead of at session creation; `tif1.core` no longer imports the
async fetch layer, the HTTP session module, the CDN manager or `tif1.types`
at module load (the fetch paths and the Ergast tier resolve them on first
use); the Ergast value parsers load with the first classification merge;
the vendored event schedules are read through `pathlib` instead of
`importlib.resources` (its import and first `files()` call were ~3 ms of
the first event-name resolution); and the seven regexes of the startup path
compile on first use. tif1's own startup with pandas already imported drops
from ~34 ms to ~20 ms (-13 to -14 ms, 12/12 interleaved pairs), the
fresh-process wall of a cached `get_session` + `laps` script by ~10 ms;
the first telemetry frame of a process gets ~6 ms of the deferred one-time
pyarrow/pandas string initialisation, the first `results` ~1.5 ms. A fresh
interpreter test (`tests/unit/test_delphi_d2_startup.py`) pins the modules
a warm pandas session may import.

## 6. Notes for the integrator

- Overlap with Pergamon Q3: Q3's lazy probe and lazy CDN singleton are
  part of this change (re-done from scratch, not from `Q3.patch`: the probe
  now lives in `pandas_blocks.py`, and the CDN manager is still built when
  `tif1.cdn` is imported; it is the import that moved). Q3 rejected them at
  +2.7 ms; the probe's cost has since grown with pandas 3 (the str column
  of the probe frame), and D2 adds the events, async_fetch, types,
  structure and regex items on top.
- The `DO_NOT_RETRY` entry "schedule path (5 ms)" may refer to an earlier
  look at the first event resolution; the mechanism here (pathlib instead
  of `importlib.resources`) removes the 3 ms of the 5.3 ms that was
  `importlib.resources`' import and first `files()` call. `files()` is
  kept for archive installs (`_package_on_disk()` checks once); on a
  filesystem install the two paths read the same bytes (tested).
- Moved, not removed: the first telemetry frame (or the first `results`
  when it comes first) pays ~6 ms of one-time pandas/pyarrow string
  initialisation that the startup probe used to absorb, plus the probe's
  own 1.5 ms. The `tel` mode above is still a net -7 ms. A notebook that
  does `get_session` + `load()` sees the same net gain.
- `core.fetch_multiple_async` and `core.get_cdn_manager` are now delegates.
  Patching `tif1.core.fetch_multiple_async` works as before (40+ tests do);
  patching `tif1.async_fetch.fetch_multiple_async` now also reaches core's
  callers (it did not before, since core held its own reference).
  `async_fetch`'s `atexit` cleanup hook registers on its first import, i.e.
  only in processes that fetch; a warm process has nothing to clean.
- `pandas_blocks._DIRECT_BLOCKS_OK` is `None` until the first frame build;
  code must read it through `_direct_blocks_ok()` (as `frame_codec` and
  `helpers._frame_from_columns` do). `frame_codec._FAST_LAP_FRAMES` is the
  same: `_fast_lap_frames()`. Pinning either to `False` still forces the
  fallback route.
- The polars parity digest's `analysis*` surfaces are non-deterministic
  for every tree (polars `unique()` order); worth fixing in
  `tools/perf/delphi_parity.py` (`unique(maintain_order=True)`) before the
  next round so polars changes can be checked at a glance.
- Not done, candidates for a later round: `zstandard`/`lz4` imports in
  `cache.py` (1.6 ms, but needed by the first json-tier read, so only the
  `import_get_session` shape gains); `tif1.cdn` builds the manager
  singleton at import (0.4 ms, only paid by cold loads now); the
  `CircuitInfo` dataclass (1 ms, public fastf1-compatible class, kept).
