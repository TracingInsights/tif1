# D3. Polars sessions: no pandas, no pyarrow on warm paths

## 1. Hypothesis

A warm polars session still imported pandas or pyarrow on three paths, and
the import was most of the phase: `t0_date`/`session_start_time` returned
`pd.Timestamp`/`pd.Timedelta`/`pd.NaT` (pandas: ~230 ms on the `state`
workload); the `DriverAhead` column of a native-decoded telemetry payload was
built with a pyarrow `take`, and `pa.array(ndarray)` pulls pandas in through
pyarrow's pandas shim (`get_driver("VER").get_fastest_lap_tel()`: ~250 ms
instead of ~20); the polars frame tier read its per-driver Arrow IPC rows
with pyarrow's reader (~27 ms of import on `driver_tel`, `all_tel` and the
notebook flow). Building the string column with a polars gather, returning
stdlib `datetime`/`timedelta` scalars on polars, and reading the IPC rows
with polars' own reader when pyarrow is not resident should remove those
imports without changing any frame.

## 2. What changed

- `src/tif1/core_utils/helpers.py`: `_polars_typed_channel` builds the
  `DriverAhead` column of a `DictionaryChannel` with
  `_polars_strings_from_codes`: `pl.Series([*categories, None],
  dtype=pl.String).gather(codes)`. polars counts a negative index from the
  end, so every `-1` (missing sample) lands on the appended null. ~60 us for
  a race lap against ~120 us through pyarrow (measured on 770 rows; 180 vs
  730 us on 20 000), and no pyarrow or pandas import. The all-null case is
  unchanged (`pl.Series([None] * n, dtype=pl.String)`); dtype `String`,
  nulls where the codes were `-1`, one chunk. `_arrow_strings_from_codes`
  stays for the pandas column (`_driver_ahead_from_codes`).
- `src/tif1/core.py`: on a polars session `t0_date` is a naive UTC
  `datetime.datetime` (`None` when unknown) and `session_start_time` a
  `datetime.timedelta` (`None`), built from the same int64 nanoseconds the
  pandas scalars are built from (`t0_ns // 1000` microseconds; both values
  are millisecond-exact). pandas sessions are unchanged. The derived
  `session_info` (no `session_info.json`: Ergast-only seasons, or a 2018+
  session whose file is missing) used `self.event` (pandas) on both
  backends; a polars session now builds it from the pandas-free schedule
  row (`_derived_session_info_native`: `_event_row()`, `StartDate` from the
  session's local schedule date or, on Ergast schedules, its UTC date,
  `GmtOffset` through `events._parse_gmt_offset`), with the same dict the
  pandas path gives once its `Timestamp`/`Timedelta` are converted. With the
  file present nothing changed (that path was already stdlib).
  `core_utils/session_state._event_value` reads a plain mapping row too.
- `src/tif1/cache.py`: `_get_polars_ipc_frames` picks its reader with
  `_ipc_reader_prefers_arrow()` (`sys.modules.get("pyarrow") is not None`).
  When pyarrow is resident (a pandas session in the process, the frame-tier
  writer after a cold load, user code) the existing pyarrow path runs
  unchanged (it reads a 4 MB driver row in ~6 ms, zero-copy over the blob,
  and concatenates the tables once). Otherwise each row is read with
  `pl.read_ipc(bytes)` in the same worker pool (polars releases the GIL:
  258 ms serial vs 42 ms pooled for the 20 race rows), the frames of one
  schema are stacked with `pl.concat(how="vertical", rechunk=False)` (the
  schema key is `tuple(schema.items())`, `pl.Schema` is unhashable) and
  the laps are the same global-offset slices. The row count check uses the
  frame height. Legacy `large_string` rows, corrupt rows and the serial
  (<4 drivers) path behave as before on both readers. `_write_polars_ipc`
  and `_read_polars_ipc` (the writer's merge read) keep pyarrow: polars'
  `write_ipc` measured 28.7 ms against pyarrow's 6.1 ms for the 4 MB VER
  row, and the writer runs after a cold load in the background thread that
  the exit joins.
- Measured and rejected for the reader: polars 2 has no eager in-memory
  IPC file reader (`PyDataFrame.read_ipc` is in the `.pyi` stub but not in
  the extension; `read_ipc` is `scan_ipc(...).collect()`, one plan per row,
  the first of the process ~7 ms), `read_ipc` takes no `rechunk` or
  `memory_map` any more, `read_ipc_stream` is not faster and would need a
  stream-format writer. polars' reader copies the buffers: 12-20 ms for the
  VER row (8.4 ms even uncompressed) against pyarrow's 6-7 ms, hence the
  residency switch instead of a plain replacement.
- Tests: `tests/unit/test_polars_without_pandas.py` reads six more surfaces
  in the fresh interpreter (`get_driver("VER").get_fastest_lap_tel()` on a
  native-shaped payload with `DictionaryChannel` codes including a `-1`,
  `laps.pick_driver("VER").telemetry`, `t0_date`, `session_start_time`,
  `session_info`, `total_laps`), asserts the stdlib scalar types and the
  `DriverAhead` values, and asserts that neither pandas nor pyarrow was
  imported (the child disarms `register_frame_writer`: the tier writer is
  pyarrow's and not a read path). `tests/unit/test_native_decoder.py`:
  `TestPolarsDriverAheadFromCodes` (codes with `-1`, a `"None"` token, all
  missing, equality with the list-built series, and the build with
  `sys.modules["pyarrow"] = None`). `tests/unit/test_session_state.py`:
  polars scalars equal the pandas session's to the microsecond, `None`
  when unknown, and the derived `session_info` of a polars session equals
  the pandas one for 2025 Bahrain (f1schedule row) and 1995 Brazil (Ergast
  row). `tests/unit/test_pergamon_contracts.py`: the P4/Q6 tier tests run
  under both readers (`arrow_reader` parametrization), plus a read with
  pyarrow unimportable and the residency check itself.
- Docs: `docs/api-reference/core.mdx` (`t0_date`, `session_start_time`
  types per backend), `docs/migration-from-fastf1.mdx` (session-state
  table). `AGENTS.md`: the polars scalar types, the derived `session_info`
  path and the reader choice.

## 4. Verdict

SHIP. Every polars workload the hypothesis names is faster by more than 3%
on the whole-process wall with 6/6 pairs: `state` -43% (the pandas import
behind `t0_date` is gone), `driver_fastest_tel` -45% (pyarrow and pandas
behind the `DriverAhead` build), `driver_tel` -9% and `all_tel` -13%
(pyarrow behind the IPC read). The untouched workloads are unchanged, the
pandas backend is unchanged, and the only parity differences are the two
scalar types the hypothesis allows.

## 5. CHANGELOG paragraph

- A warm polars session no longer imports pandas or pyarrow. `t0_date` and
  `session_start_time` return `datetime.datetime` (naive UTC) and
  `datetime.timedelta`, `None` when unknown, on a polars session (pandas
  sessions keep `pd.Timestamp`/`pd.Timedelta`/`NaT`); the derived
  `session_info` of a polars session is built from the schedule row
  without pandas. The `DriverAhead` column of a native-decoded telemetry
  payload is a polars gather instead of a pyarrow `take`, and the per-driver
  Arrow IPC rows of the polars frame tier are read with polars' own reader
  when pyarrow is not already imported (pyarrow's reader, faster
  in-process, is used when it is). 2025 Bahrain race, warm cache, fresh
  process: `session.t0_date` 229 ms -> 0, `get_driver("VER").
  get_fastest_lap_tel()` 254 -> 24 ms, `laps.pick_driver("VER").telemetry`
  52 -> 39 ms, `fetch_all_laps_telemetry()` 168 -> 114 ms; whole-process
  wall 685 -> 392, 693 -> 380, 454 -> 413 and 580 -> 505 ms.

## 6. Notes for the integrator

- Surface change (allowed by the hypothesis): `t0_date`/`session_start_time`
  types on polars sessions. Code that did `session.t0_date + pd.Timedelta(...)`
  on a polars session keeps working (`datetime + Timedelta` is a `Timestamp`),
  `pd.isna(session.t0_date)` keeps working for `None`; `session.t0_date is
  pd.NaT` checks must become `is None`. Documented in `core.mdx` and the
  migration page.
- The reader choice is a process-state switch (`sys.modules`), so the same
  session can read its rows with either reader depending on what ran
  before; both give equal frames (tests pin both paths, and the pyarrow
  path is byte-for-byte the previous code). `pl.read_ipc` in polars 2 is a
  `scan_ipc().collect()` (one lazy plan per driver row, ~0.5 ms, the first
  of a process ~7 ms); it is still 20 ms cheaper than importing pyarrow for
  one row, and 7 ms cheaper for the 20 rows of a race, measured on this
  box. If a later polars version grows an eager in-memory reader, switch to
  it.
- Not changed: the frame-tier writer (`_write_polars_ipc`, pyarrow, 4.7x
  faster than polars' `write_ipc` on a 4 MB row) still imports pyarrow in
  its background thread after a cold polars load; the exit joins that
  thread. `Session.date` on polars still reads `self.event` (pandas); not
  in the hypothesis and not on the measured workloads.
- The writer's merge read (`_set_polars_ipc_frames` -> `_read_polars_ipc`)
  will raise `AttributeError` if a `None` frame reaches it (seen while
  writing the tests with a bad payload); pre-existing, callers filter
  `None` frames today.
- The delphi harness's `notebook` workload needs a polars-aware `iloc`
  step (`laps[i]` or `laps.row(i)`) before it can measure polars sessions.
- `tests/unit/test_polars_without_pandas.py` sets
  `core.register_frame_writer` to a no-op in the child; without it the
  pyarrow assertion would fail on the writer thread, not on a read path.
