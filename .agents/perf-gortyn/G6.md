# G6. liblz4 in tif1-native: keep E4's fault saving without lz4_flex's decode cost

Branch `perf/gortyn-G6`, worktree `/tmp/tif1-gortyn/G6`, measured on
2026-11-03 against the G1 tree (`/tmp/tif1-gortyn/G1`, E4 on 0.11.3 with
the lz4_flex wheel) and the frozen 0.11.3 control (`/tmp/tif1-gortyn-control`,
f692ee7).

## 1. Hypothesis

Elis E4 / Gortyn G1 decompress the pandas frame tier's driver rows into
`MADV_HUGEPAGE` buffers through `tif1_native.lz4_frame_decompress_into`.
That removes ~30k page faults and 45-54 ms of system time per race
`fetch_all`, but its pure-Rust `lz4_flex` block decoder is ~1.6x slower than
the liblz4 that pyarrow's codec runs, and G1 read that lost user CPU as the
reason the phases barely moved. G6 replaces the block decode with liblz4
itself (`lz4-sys`, C source compiled by `cc` into the wheel), so the fault
saving should no longer be paid back as CPU. Bar: the decoder within 10% of
pyarrow's, and the warm phases better than G1's.

## 2. What changed

- **Inherited base:** G1 as staged (E4 on 0.11.3), unchanged. Intended
  commit 1 in `G6_COMMITS.md`. `git commit` is denied in this sandbox, so
  everything is staged.
- **`native/src/lz4.rs`:**
  - What stays: the frame parsing (magic, FLG/BD, content size, block
    words, stored blocks, end mark) and every error and message the E4
    tests pin (`not an lz4 frame`, `unsupported lz4 frame: checksums` /
    `dictionary id` / `frame version`, `destination too small`,
    `corrupt lz4 frame: ...`).
  - What changed: compressed blocks go to liblz4's `LZ4_decompress_safe`.
    A linked block after the first goes to `LZ4_decompress_safe_usingDict`,
    with the previous <= 64 KB of output in `dst` as the dictionary. That
    dictionary ends where the block's output starts, so liblz4 takes its
    in-place prefix path (no copy, no external dictionary).
  - `lz4-sys` binds only `LZ4_decompress_safe`, so the module declares the
    `_usingDict` prototype itself. That function is `LZ4LIB_API` (stable)
    in lz4.h 1.10, and `use lz4_sys as _;` keeps the static archive linked.
  - The GIL release and the buffer checks in `lib.rs` are unchanged.
  - The one new piece of logic: liblz4's safe decoder may wild-copy up to
    ~32 bytes past a block's output, inside the room it is given. With the
    content size in the header, the last block's room is exactly its
    output, as before. Without it, the last block (the end mark follows it)
    is decoded into a scratch buffer and copied, so the bytes past the
    content stay untouched. tif1's rows always carry the size, so this path
    is never hot.
- **`native/Cargo.toml` / `Cargo.lock`:** `lz4-sys = "1.11"` (1.11.1, liblz4
  1.10.0; it pulls in `cc`, `find-msvc-tools`, `shlex` at build time and
  `libc`) replaces `lz4_flex`. The crate stays 0.2.1. **No lz4_flex fallback
  is kept:** every leg of the wheel matrix has a C compiler (section 6), and
  any platform outside the matrix builds from the sdist, which needs Rust
  anyway; a C compiler is now required too. Pyodide is not built.
- **Size:** the wheel grows by 6.6 KB (270 710 -> 277 328 bytes). The linker
  keeps only `lz4.c`'s decoder objects; no `LZ4*` symbol is exported.
- **`native/tests/smoke.py`** (run on every built wheel by `native.yml`): two
  hand-built two-block linked frames, with and without the content size.
  The second block's match reaches into the first, so the prefix-dictionary
  path runs. The test checks the output, an untouched destination tail and
  the too-small `ValueError`. Python-lz4 decodes both frames too (header
  checksums are valid). Checked on the G6 and G1 builds.
- **`tests/unit/test_gortyn_g6_native_lz4.py`** (10 tests, skipped without
  the extension):
  - unsized frames with 4 MB of slack, at 64 KB and 4 MB block sizes and
    three lengths: the slack stays untouched;
  - sized and unsized frames decode identically;
  - independent blocks decode;
  - a match before the first byte of output is a `corrupt lz4 frame`, not an
    out-of-bounds read.
- **`native/README.md`:** liblz4, and the C compiler needed for local and
  sdist builds.
- **`.github/workflows/native.yml`:** a comment block on the C toolchain of
  each leg (no step changes, see section 6).
- **`.github/workflows/ci.yml`:** in the `native` job, the "native decoder is
  active" check also asserts `NATIVE_LZ4_DECOMPRESS_INTO is not None`, so the
  E4/G6 tests cannot skip silently there. The comment there now names gcc.
- **Probes (`tools/perf/`):**
  - `gortyn_g6_warm_ab.py`: G1's harness plus `--control-site` /
    `--candidate-site`, an unpacked wheel ahead of one arm only. The G1 and
    G6 trees have byte-identical `src/` (68 files, sha256), so the wheel is
    the only difference between the arms.
  - `gortyn_g6_fault_probe.py`: G1's probe plus a per-arm `SITE=` overlay.
  - `gortyn_g6_decode_speed.py`: E4's decode-speed probe interleaved over
    wheel overlays.
- **Build:** `cargo build --release --offline` succeeds on x86_64 Linux. The
  wheel is `uvx maturin build --release --offline -m native/Cargo.toml -o
  wheels` (`tif1_native-0.2.1-cp311-abi3-manylinux_2_34_x86_64.whl`,
  untracked), unpacked into `native/target/site` (gitignored), and run as an
  overlay first on `PYTHONPATH` with the main venv's interpreter, as G1 did.
  The G1 arm uses G1's overlay `/tmp/tif1-gortyn/G1/native/target/site`.

## 3. Measurements

Box: 32 cores, shared with the other Gortyn agents. Following G1's finding
that separate per-arm caches bias the row-read phases, every A/B here puts
both arms on one cache (`/tmp/tif1-gortyn-warm-G6`). A warm offline read
writes nothing, and both trees read the same frame-tier format.

### Decoder speed, serial, both 2025 Bahrain sessions' 40 driver rows (186 MB out)

`gortyn_g6_decode_speed.py` (E4's probe; pre-faulted destinations, best of 7
per process, three interleaved rounds, ms):

| arm | pyarrow, reused | pyarrow, kept | native, reused | native, kept |
|---|---|---|---|---|
| G1 (lz4_flex) | 41.0-41.3 | 41.9-42.1 | 67.1-67.3 | 68.1-68.2 |
| G6 (liblz4) | 40.9-41.1 | 41.9-42.1 | **39.9-40.0** | **41.2-41.4** |

The new decoder is 2.5% faster than pyarrow's codec on the same rows and
1.68x faster than lz4_flex, so the bar (within 10% of pyarrow) is met. The
remaining edge over pyarrow is the absent per-call allocation and frame
context.

## 4. Verdict: SHIP, as the decoder of the tif1-native 0.2.1 release (it supersedes G1's lz4_flex)

Both halves of the bar are met where the decoder sits on the critical path.

1. **Decoder speed: met.** 40.0 ms vs pyarrow's 41.0 ms over the 40 rows
   (lz4_flex 67.1). Per race `fetch_all`, the user CPU is 17.6-19.5 ms below
   G1's, with E4's fault and system-time saving intact (56.7k -> 26.5k
   faults, -54..-62 ms sys).
2. **Warm phases vs G1: met on the phases that wait on a row decode.**

   | phase | change vs G1 | pairs, run 1 | pairs, run 2 |
   |---|---|---|---|
   | `car_data_loop` | -0.5..-1.9 ms | 9/12 | 8/12 |
   | `driver_tel` | -0.4..-0.5 ms | 8/12 | 7/12 |
   | `iterlaps_tel_loop` | -4.1..-6.9 ms | 6/12 | 8/12 |

   Against the 0.11.3 control, the whole mechanism now gives:

   | phase | control -> G6 | pairs |
   |---|---|---|
   | `car_data_loop` | 27.2 -> 23.1 ms (-15%) | 10/12 |
   | `driver_tel` | 26.1 -> 24.1 ms | 11/12 |
   | `iterlaps_tel_loop` | 148.3 -> 142.1 ms | 8/12 |

3. **`all_tel` does not move, and is not expected to.** That phase reads
   the 20 rows on the 4 decompression workers with the GIL released, while
   the main thread assembles frames, so the decode is off its critical
   path. G1's guess that the lz4_flex CPU was what held this phase back
   was wrong for this phase. It was right for the synchronous one-driver
   reads, where the faster decode now shows.
4. **No wall moves 3%** against G1. Against the control, the wall
   differences follow `get_session` noise.

Ship it with the 0.2.1 wheel release in place of the lz4_flex decoder.

- **The cost:** a C compiler in every wheel build and in sdist installs,
  and 6.6 KB of wheel.
- **What it buys:** the decoder pyarrow already uses, at 1.68x lz4_flex's
  speed, and a slack guarantee lz4_flex did not keep (section 6).
- **No lz4_flex fallback:** no target in the matrix lacks a C toolchain.

## 5. CHANGELOG paragraph

- Warm pandas sessions decompress the frame tier's driver rows into
  huge-page buffers when `tif1-native` 0.2.1 is installed on Linux.
  - **How it works:** `tif1_native.lz4_frame_decompress_into` decodes a
    row's lz4 frame with the GIL released, through liblz4's block decoder
    (the one pyarrow's codec runs, vendored by `lz4-sys` and built into
    the wheel). It writes into an anonymous private mapping advised
    `MADV_HUGEPAGE` (2 MB pages), instead of 123 MB of fresh memory
    zero-filled one 4 KB fault at a time.
  - **Decode speed:** 40 ms for the 40 driver rows of the 2025 Bahrain race
    and qualifying, against pyarrow's 41 ms.
  - **`fetch_all_laps_telemetry()`** (fresh process, Bahrain race): 26 500
    minor faults instead of 56 700, 93 ms of system time instead of
    147-155 ms, with no extra user CPU.
  - **Per-driver reads:** per-lap `get_car_data()` over a driver 27.2 ->
    23.1 ms. `laps.pick_driver("VER").telemetry` 26.1 -> 24.1 ms.
  - **Lap loop:** the `iterlaps()` telemetry loop 148 -> 142 ms.
  - **Unchanged:** the `fetch_all_laps_telemetry()` call itself (its rows
    already decompress on worker threads).
  - **Keep the pyarrow codec:** rows under 2 MB, Windows, macOS, Pyodide,
    THP `never`, older wheels and `TIF1_DISABLE_NATIVE=1`.
  - **Building:** from source, tif1-native now needs a C compiler next to
    the Rust toolchain.

## 6. Notes for the integrator

- **Merge G6 instead of G1's `native/` changes.** G6's tree is G1 plus:
  the decoder, the crate dependency, the smoke/unit tests, the docs, the
  `ci.yml` assert and the probes. `src/` is identical to G1's. The release
  steps are G1's (G1.md section 6):
  1. Merge to `main`.
  2. `gh workflow run native.yml --ref main -f environment=testpypi`.
  3. `gh workflow run native.yml --ref main -f environment=pypi`.

  `pyproject.toml` keeps `tif1-native>=0.2,<0.3`. `uv lock
  --upgrade-package tif1-native` changes only the `tif1-native` block of
  `uv.lock`. tif1 does not depend on `lz4-sys`; it is a build dependency
  of the wheel only.
- **Wheel matrix, what was verified and what was not.**
  - *Verified here:* only x86_64 Linux glibc (`cargo build --release`,
    `cargo clippy`, the maturin wheel, the tests).
  - *Reasoned, not run:*
    - manylinux2014 x86_64/aarch64: the images carry gcc.
    - musllinux_1_2: maturin-action's cross images provide a musl gcc, and
      `cc` finds `<target>-gcc` / `CC_<target>`.
    - macOS universal2: cc passes `-arch` per target, and maturin builds
      and lipo-merges the two halves.
    - Windows x64 and arm64: MSVC through find-msvc-tools. `lz4-sys`'s
      build script handles Windows explicitly: MinGW i686 flags and
      `CRT_STATIC`. The Rust MSVC default is the dynamic CRT, and cc
      follows the `crt-static` target feature, so they match.
  - *Fallback:* `native.yml` carries no new step. If a leg fails on the
    C build, the fix is that leg's `CC_<target>` or toolchain setup, not
    an lz4_flex fallback.
  - *Safety net:* the smoke test now decodes an lz4 frame on every built
    wheel, so a leg that links but miscompiles fails there.
  - The first PR touching `native/` runs the full matrix (the
    `pull_request` path filter): watch the musl and windows-11-arm legs.
- **A latent lz4_flex bug the new tests found.** G1's build writes 2 bytes
  past the content of an unsized frame when the destination has slack
  (`test_unsized_frame_leaves_the_slack_untouched`, the 1 MB cases, on
  G1's wheel). tif1 never reaches it: its rows always carry the content
  size, so the room is exact. It still contradicted E4's "nothing past the
  content" comment. With liblz4 the same hazard (wild copies inside the
  room) is real by design and is handled by the scratch buffer for an
  unsized frame's last block.
- **E4's inherited error mapping:** an unsized frame decoded into a buffer
  smaller than one block reports `destination too small` for any decode
  failure, corrupt input included. That is unchanged (an E4 test pins
  it). The new corrupt-input test uses a full block of room.
- **Where the remaining time is.** With the decoder at pyarrow's speed,
  `fetch_all` (~95-100 ms warm) is the main thread's frame assembly plus
  the 4-reader blob read (~50 ms, not fault-bound: G1 step 4), not
  decompression. The faults left (~15k blob bytes, ~9k main-thread) do not
  convert to time. Further wins there are on the assembly side, not the
  codec.
- **Methodology:**
  - Same cache for both arms (G1's finding).
  - `gortyn_g6_warm_ab.py --control-site/--candidate-site` is what makes a
    wheel-only A/B possible; G1's `--site` puts one overlay on both arms.
  - `all_tel` needs about 20 pairs on this box before a pair count means
    anything.
- **Commits:** `git commit` is denied here. Everything is staged, with the
  intended messages in `.agents/perf-gortyn/G6_COMMITS.md`.
- **Artefacts:**
  - Committed: `.agents/perf-gortyn/G6_ab_pandas_*.json`.
  - Untracked: the wheel in `wheels/`; the overlay, the parity digests and
    a scratch frame-checksum script in `native/target/` (gitignored).
