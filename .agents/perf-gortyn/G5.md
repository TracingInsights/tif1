# G5: lock bump to the newest stables, and the pandas 3.1.0 probe drift

## 1. Hypothesis

`pyproject.toml` allows pandas 3.1.0, polars 2.1.0 and the other newest seam
packages, so a fresh install runs on them today, while `uv.lock` (and CI) stay
on pandas 3.0.6 / polars 2.0.0. G2 read pandas 3.1.0 statically and predicted
that both Pergamon Q18 array probes (`_probe_str_slice`, `_probe_timedelta`)
fail there, which silently puts the lap-frame route back on pandas' own slicing
for every lap. G5 runs the seam tests and the unit suite on the newest stables,
fixes every drift so the fast paths run on both the locked and the newest
versions, bumps the lock, and measures the versions (locked vs newest) and the
code (control vs this tree, both on the newest).

## 2. What changed

Setup: `uv` was denied by this session's sandbox (every `uv` call "requires
approval", including `uv --version`), and so was any interpreter other than the
main venv's. Instead of the throwaway venv, the newest wheels were installed
with the main venv's pip into a directory inside the worktree
(`pip install --no-deps --target .newpkgs pandas polars polars-runtime-32 numpy
pyarrow niquests urllib3-future qh3`, not staged). Every "new versions" run
below uses `PYTHONPATH=.newpkgs:src`, so these packages shadow site-packages:
pandas 3.1.0, polars/polars-runtime-32 2.1.0, numpy 2.5.4, pyarrow 26.0.1,
niquests 3.21.2, urllib3-future 2.25.905, qh3 2.1.0. qh3 2.1.0 is accepted:
urllib3-future 2.25.905 pins `qh3<3.0.0,>=1.5.4`.

Brought in from G2 (copied from `/tmp/tif1-gortyn/G2`, unchanged):
`tests/unit/test_private_seams.py`, `tests/unit/test_upstream_canary_report.py`,
`tools/upstream_prereleases.py`, `tools/upstream_canary_report.py`,
`.github/workflows/upstream-canary.yml`. If G2 merges first, these are the same
files and drop out of the diff.

**What the newest versions broke (unit suite on the new versions before the
fixes: 28 failed, 3489 passed).** Four distinct drifts:

1. **Q18 array layouts (`pandas-lap-frames` seam), as G2 predicted.** pandas
   3.1.0 gives every Arrow slice an empty `_cache` dict (`_from_pyarrow_array`).
   Its `TimedeltaArray` has no `_freq` (and no `freq`) at all. Both probes
   returned False.
2. **`TimedeltaArray.total_seconds()` rounds differently.** 3.1.0 computes
   `floor_s + residual / pps` (a divmod split, plus a nudge above 2**53 ticks)
   instead of `asi8 / pps`. Two tif1 fast paths copied the old arithmetic by
   hand: `Telemetry._differential_distance_fast` (`Distance`,
   `DifferentialDistance`, `integrate_distance`) and `_fastest_lap_frame`
   (`LapTimeSeconds`). On pandas 3.1 they no longer match tif1's own fallback
   (`dt.total_seconds()`) or fastf1, which reads `dt.total_seconds()`. This
   caused 24 Q8 contract failures.
3. **`Laps.to_sql(index=True)` raised `DatabaseError` on pandas 3.1.**
   `SQLTable.insert_data` now runs `temp = temp.reset_index()` instead of
   `reset_index(inplace=True)`. It names the index `level_0` when an `index`
   column exists. `Laps.reset_index` then dropped that column, so the INSERT
   had one binding too few. This is a real user-visible bug on the pandas that
   `pyproject.toml` already allows.
4. **Two test premises:** `pd.to_timedelta(float seconds, unit="s")` now infers
   `us` instead of `s`; `to_timedelta(inf)` now raises `OutOfBoundsTimedelta`
   (a `ValueError`) instead of `OverflowError`.

polars 2.1.0, numpy 2.5.4, pyarrow 26.0.1, niquests 3.21.2 and qh3 2.1.0 broke
nothing. All the polars, OCSP and hazmat seam tests pass.

**Fixes (library):**

- `core_utils/frame_codec.py`: `_array_layout()` reads once per process which
  optional attributes pandas' own arrays carry: whether an Arrow slice has
  `_cache`, and whether `TimedeltaArray` has `_freq`. `_str_slice(...,
  cache=)` and `_timedelta_array(..., freq=)` mirror that layout. `_lap_plan`
  picks `_P_STRC` (slice + empty `_cache`) and `_P_TDN` (no `_freq`) on
  pandas >= 3.1, and `_P_STR`/`_P_TD` (unchanged code, unchanged branch
  order) on 3.0.x. `_str_spans` passes the layout too. The probes stay the
  guard, unchanged except that they build with the detected layout and read
  `freq` through `getattr`. On any other drift the route falls back exactly as
  before.
- `models.py`: `_differential_distance_fast` takes its seconds from
  `time.total_seconds()` (NaT -> 0, then the same diff/clip/multiply), and
  `_fastest_lap_frame` takes `LapTimeSeconds` from
  `lap_time.array.total_seconds()`. Both now equal pandas' own arithmetic on
  any version. The unit guard is unchanged (s/ms/us/ns only); the unused
  `pps` lookup is gone.
- `models.py` `Laps.reset_index`: drops `level_0` only when pandas named it
  (no index level and no column was already called `level_0`), so
  `to_sql(index=True)` works on both pandas lines and a pre-existing `level_0`
  column is no longer deleted. (On 3.0.6 the only behaviour change is that
  last case. Before, `Laps({"level_0": ...}).reset_index()` silently dropped
  the user's column. fastf1's `Laps` does not override `reset_index`, so this
  follows fastf1.)

**Tests:** new `test_fast_lap_arrays_follow_the_installed_array_layout` (both
layouts forced on either pandas: block attrs exactly as named, frames equal to
the generic route, `_str_spans` attrs). New
`test_seconds_are_the_installed_total_seconds` (`LapTimeSeconds` bit-equal to
`total_seconds()` over 50 random ns/ms draws). New
`test_an_index_named_level_0_keeps_its_column`. Adjusted:
`test_fast_lap_arrays_match_the_public_slicing_route` (`freq` through
`getattr`, plus a `vars()` comparison with pandas' own slice); the `inf` test
expects whatever `pd.to_timedelta` itself raises; the seconds-resolution
track-status test builds `m8[s]` explicitly.

**Not done: the `uv.lock` bump.** `uv lock --upgrade-package ...` could not
run here (sandbox). I did not hand-write the lock. uv records the
environment-filtered wheel list (qh3 keeps 64 of 115 wheels), resolution
markers per fork (numpy has a 2.4.6 fork for Python 3.11) and the extras
metadata, and the new releases change `requires-dist`: urllib3-future adds the
`ws-fast` extra and moves to `qh3<3`, niquests adds `ws-fast`, polars changes
its extras, and pandas raises its numpy floor. A hand-written lock that is
subtly wrong breaks `uv sync --locked` in CI. Because of that, the `SEAMS`
`verified` versions stay at the lock's pins; `test_seam_table_follows_the_lock`
would fail otherwise. The integrator's steps are in section 6.

Harness: `tools/perf/gortyn_g5_warm_ab.py` is a copy of `delphi_warm_ab.py`
with `--control-site`/`--candidate-site` (a directory put on `PYTHONPATH`
before the arm's `src`) and `--bench`. The measurement scripts are in
`.agents/perf-gortyn/G5_scripts/`: `q18_micro.py`, `ulp_check.py`,
`import_time.py`, `perf_gate_new.py` (the perf gate with `.newpkgs` prepended
to its children's `PYTHONPATH`) and `tables.py`.

The process-level A/B cannot resolve the Q18 effect. The 10-pair notebook
candidate median of 910 ms is a burst on the box: its minimum is 717 ms against
the control's 747 ms. So I measured the mechanism directly
(`G5_scripts/q18_micro.py`). It encodes VER's 57 race laps as one driver blob
and times `decode_driver_frames` 200 times with the probes' verdict and with
`_FAST_ARRAYS` forced off, in one process:

| pandas | probes | fast route best / median | fallback best / median | gain |
|---|---|---:|---:|---:|
| 3.1.0 (control tree) | fail | (fallback only) | 2.09 / 2.14 ms | - |
| 3.1.0 (G5) | pass | 1.92 / 1.98 ms | 2.09 / 2.14 ms | 8% |
| 3.0.6 (G5 = control) | pass | 1.95 / 1.99 ms | 2.42 / 2.48 ms | 24% |

The fix restores the route, but pandas 3.1 made its own slice path faster
("fast path for slices" in `ArrowExtensionArray.__getitem__`). The route is
worth ~3 µs per lap on 3.1.0 (0.17 ms per driver blob, ~3.4 ms for a 20-driver
`fetch_all_laps_telemetry()`), against 8 µs per lap on 3.0.6. That is below
what the process A/B can see on this box.

- Newest versions (`G5_scripts/perf_gate_new.py`): timing: 0 of 60 pandas
  phases and 0 polars phases over the limit (machine factor 1.05). Two phases

### 3e. Parity (`delphi_parity.py`, 133 pandas / 131 polars surfaces)

| tree, versions | vs control digests (locked) |
|---|---|
| G5, locked | **pandas 0, polars 0 differing** |
| G5, newest | polars 0; pandas 32 differing (all `Distance`/`DifferentialDistance`) |
| control, newest | pandas 0, polars 0 differing |

The 32 pandas surfaces are 2 sessions x 4 analysis laps x
`dist`/`fill`/`resample`/`resample1s`, and only those two float columns. They
are a value change at the last ulp, not a repr or dtype drift. On pandas 3.1,
G5 follows `total_seconds()`, which changed its rounding. The control keeps
`asi8 / pps` and so stays bit-equal to its pandas 3.0 output, but on 3.1 it
disagrees with its own fallback path (`dt.total_seconds()`, taken when a speed
is NaN), with fastf1, and with tif1's Q8 contract tests (24 failures). Size
over 228 laps of four drivers (`G5_scripts/ulp_check.py`): at most 14 samples
per lap get a different `seconds` value. The largest `Distance` deviation is
1.8e-12 m (3.4e-16 relative, ~1.5 ulp). On the locked versions nothing
changes (0 differing).

## 4. Verdict: PARTIAL

**Ship the library fixes** (`frame_codec.py`, `models.py`, the tests), plus
G2's seam files if G2 is not merged on its own:

- They make the whole suite green on the pandas that `pyproject.toml` already
  installs for new users (28 failures before).
- They fix a real pandas 3.1 bug (`Laps.to_sql(index=True)` raised).
- They keep `Distance`, `DifferentialDistance` and `LapTimeSeconds` equal to
  pandas' and fastf1's arithmetic on every pandas version.
- They restore the Q18 lap-frame route on 3.1. It is worth less than expected
  there: 8% of the decode, ~3 µs per lap, because pandas 3.1's own slicing got
  faster.
- They cost nothing on the locked versions: 0 differing surfaces, phases
  within noise.

No workload meets the 3% wall criterion; this is a correctness and hardening
change, not a speed-up.

**The lock bump itself is not delivered** (uv denied here; see section 6 for
the one command). The measurements support doing it: pandas 3.1.0 is neutral on
wall time, and CI should test what fresh installs run. polars 2.1.0 costs
~8 ms of import per polars process, which users already pay; pinning polars
back would only hide it from CI.

## 5. CHANGELOG

- pandas 3.1 support. On pandas 3.1.0 (allowed by the version range, so what
  a fresh install gets) the lap-frame builder of the telemetry frame tier
  silently fell back to pandas' own slicing for every lap, because pandas
  3.1 changed the attributes of a sliced Arrow string array and dropped
  `TimedeltaArray._freq`. The builder now reads which attributes the
  installed pandas sets and mirrors them; the probes still guard it (decode
  of a 57-lap driver blob 2.09 -> 1.92 ms on 3.1.0, unchanged on 3.0.6).
  `Telemetry.add_distance`/`integrate_distance`/`calculate_differential_distance`
  and the fastest lap's `LapTimeSeconds` now take their seconds from
  `total_seconds()` itself, so they match pandas and fastf1 bit for bit on
  either pandas (3.1 rounds through a divmod split; the difference is at most
  ~1.5 ulp, 1.8e-12 m over a lap). `Laps.to_sql(index=True)` no longer raises on
  pandas 3.1, and `Laps.reset_index()` no longer drops a column the frame
  already called `level_0`.
