# G3: per-driver typed columnar telemetry files, with the reader

## 1. Hypothesis

A race's cold telemetry is 1128 lap files of ~61 KB gzipped JSON, and a cold
`load()` is bound by those bytes. A driver's wave is 57 requests. A typed
columnar encoding should carry the same values in about half the bytes
(Delphi's estimate) and in far fewer requests. This round produces the format,
the encoder the data pipeline will run, and a reader that tries the files
first and falls back to the JSON, without changing any value tif1 returns.

## 2. What changed

- `src/tif1/core_utils/columnar_telemetry.py` (new): the `tel.v1` codec.
  - One file is `{driver}/tel.v1.{first}.bin`, the driver's laps `first`..`first+9` (`first` = 1, 11, 21...).
  - Layout: magic + raw size + one zstd-19 frame holding a JSON header and 8-aligned, byte-shuffled typed buffers.
  - Column encodings:
    - `int`: narrowed int64 channels and DriverAhead codes.
    - `dec`: `time` as int ms deltas, decoded `n / 10.0**k`.
    - `split`: whole samples as narrowed ints plus a bit mask; interpolated samples as raw float64.
    - `f64`: raw float64.
  - `decode_driver_file` returns per lap exactly what the native decoder returns for the lap JSON: key order, int64/float64 bits, DictionaryChannel codes and categories, `dataKey`.
  - The encoder decodes every column back and compares the bits.
  - Full spec: `design/TELEMETRY_COLUMNAR_FORMAT.md` (new).
- `src/tif1/async_fetch.py`: the reader.
  - `fetch_multiple_async(..., driver_files=None)`: when a batch has two or more laps of a driver, those laps may come from the driver's files. The lazy stream passes `driver_files=True` (`core.py`).
  - `_gather_fetches` starts every wave file up front (`_start_wave_driver_files`). Otherwise `fetch_all`'s 22 slots would start only one or two files at a time.
  - Each file is downloaded once per process in the fetch thread pool (`_driver_file_future`, a `concurrent.futures.Future`) and shared by the wave's lap requests on any event loop.
  - Each decoded lap is handed out once, then goes through the existing payload-tier write (`_persist_telemetry_payload`, factored out of `_fetch_from_source`, same behaviour).
  - Fallback to the lap JSON:
    - The file is missing.
    - The file is unreadable (`ColumnarFormatError`).
    - Every mirror fails.
    - The file lacks the lap.
  - A 404 on the primary CDN is final. The mirrors copy the same repository and the JSON fallback is correct either way.
    - It is recorded in `missing_payloads` per file and per session (`tel.v1.session` marker).
    - It ends probing for that session in-process.
  - Off with `telemetry_columnar=False` (`TIF1_TELEMETRY_COLUMNAR`, new config key, default True), with validated telemetry, offline, and in Pyodide.
- `src/tif1/payload_loader.py`: `HttpTransport.get_bytes` on `NiquestsTransport` and `InMemoryTransport`.
  - It rides the first-wave stdlib bridge like the JSON waves do: `bridge_open()`, which starts the niquests warm-up in the background.
  - A bridge 404 is final.
- `src/tif1/first_wave.py`: `fetch_status` and `_StdlibClient.get_with_status`. `get` is unchanged in behaviour. Without them, a 404 cost a niquests import on the critical path.
- `src/tif1/core_utils/constants.py`: numpy-free path helpers (`columnar_chunk_first_lap`, `columnar_file_path`), so a polars lone-lap request never imports numpy through the reader.
- `tools/data/encode_driver_telemetry.py` (new): the pipeline encoder.
  - Sources: `--json-dir` (a session folder of the data repository, `.json` or `.json.gz`) or `--cache` (a tif1 cache).
  - `--verify` checks bits per lap and builds the pandas and polars frames from both sources (`assert_frame_equal(check_exact=True)` / `DataFrame.equals`).
  - Needs `tif1-native`.
- Harnesses:
  - `tools/perf/gortyn_g3_format_compare.py`: layouts (a)/(b)/(c), size and decode time.
  - `tools/perf/gortyn_g3_cold_local.py`: a local HTTP/1.1 CDN in the parent process that serves the session from a primed cache.
    - Throttling: token buckets per connection (6 MB/s) and for the link (8 MB/s), 30 ms first-byte delay.
    - Interleaved fresh-process control/candidate runs, request/byte counts, `--verify` frame digests, `--no-files`.
- Docs: `AGENTS.md` architecture bullet; `docs/api-reference/config.mdx` (`telemetry_columnar`).
- Tests:
  - `tests/unit/test_columnar_telemetry.py` (23): exact round trips, encodings, frames equal from file vs JSON on both backends, chunk paths, corrupt files, concurrent decode in 8 threads.
  - Reader through `InMemoryTransport`: wave from files, a large batch starting all files, a lone lap keeping its JSON, the stream flag, 404 fallback once per session, persisted file and session verdicts, unusable files, a lap absent from its file, off/validated modes, payload-tier writes.
  - `tests/unit/test_first_wave.py`: binary bridge requests and the final bridge 404 without niquests.

## 3. Measurements

### Format choice (all 1405 laps of the 2025 Bahrain race and qualifying)

`tools/perf/gortyn_g3_format_compare.py`; JSON is the lap payloads, gzip -6
(the CDN's 71.3 MB matches the brief's ~69 MB):

| layout | race (1128 laps) | quali (277 laps) | decode / driver (race) | exact |
|---|---|---|---|---|
| JSON gzip | 71.32 MB | 24.27 MB | 30.0 ms (native, 57 payloads) | - |
| (a) Arrow IPC zstd-19, per driver | 57.49 MB | 19.95 MB | 3.1 ms | no, as written: int16/int32 ms columns differ in dtype |
| (b) `tel.v1`, one file per lap | 54.64 MB | 18.19 MB | - | yes |
| (c) `tel.v1`, one file per driver | 51.39 MB | 17.68 MB | 11.6 ms | yes, 0 mismatches |
| chosen: `tel.v1`, 10 laps per file | 52.50 MB (119 files) | 17.79 MB (34 files) | ~2 ms per file | yes, `--verify` 0 differences |

Bytes: **−26% race, −27% qualifying**. That is not Delphi's −50%, which
assumed float32 channels.
- `rpm`, `speed`, `throttle`, `x`, `y`, `z` hold about one whole sample per interpolated float64 sample (fastf1's car/position merge).
- `distance`, `rel_distance`, `DistanceToDriverAhead`, `acc_x/y/z` are float64 throughout. These six channels are ~65% of a file at ~6-7 bytes per sample after compression.
- Lossless predictors gain ~1%: XOR with the previous sample or with a linear prediction (`scratch/predict.py`). `distance` is not reproducible from `speed`×dt.

The pandas/polars frame build from decoded files costs the same as from
decoded JSON: ~20 ms per race driver either way.

Why 10 laps per file:
- With one file per driver, `driver_tel` was **slower**: 1726 vs 1518 ms in a single local run. The 2.6 MB file rode one connection at ~4.7 MB/s (574 ms), while the 57 JSON requests spread over 22 connections.
- Ten-lap files (~450 KB) make a race driver's wave 6 parallel requests, for +2% bytes over one file per driver.

## 4. Verdict: PARTIAL (ship the format, the encoder and the reader; turn the reader on with the files)

Keep everything. With files on the CDN, the cold telemetry paths are 8-24%
faster on the whole process (pandas `all_tel` −20%, `notebook4` −9%,
`driver_tel` −8%, all 5/5; polars `all_tel` −24%, `notebook4` −8%), with
identical frames.

Today no file exists. Probing costs one jsDelivr 404 round trip per session
per week (+~100 ms on the first cold driver wave). So:

- **Recommendation:** merge with `telemetry_columnar` defaulting to **False**, unless the data pipeline publishes `tel.v1` files in the same release.
- Flip it to True once the 2025/2026 repositories carry the files.
- The tree keeps the brief's default (True). The flip is one line in `config.py` plus the docs sentence.

## 5. CHANGELOG

- Cold telemetry can now come from per-driver columnar files: `{driver}/tel.v1.{first}.bin`, ten laps each, typed columns in one zstd frame. A race driver's laps are 6 requests and 2.7 MB instead of 57 requests and 3.7 MB, and a race is 52.5 MB instead of 71.3 MB of gzipped JSON.
  - The decoded values are bit-identical to the JSON, so every frame is unchanged.
  - On a throttled local CDN (8 MB/s link, 6 MB/s per connection), `fetch_all_laps_telemetry()` takes 8.5 s instead of 11.0 s and `laps.pick_driver("VER").telemetry` 543 ms instead of 649 ms.
  - Missing, unreadable or incomplete files fall back to the lap JSON. A missing file is remembered for the session for `missing_payloads_ttl_days`.
  - A single lap always reads its JSON.
  - `telemetry_columnar` (`TIF1_TELEMETRY_COLUMNAR`) turns it off.
  - `tools/data/encode_driver_telemetry.py --verify` writes the files for the data repositories and checks every lap.

## 6. Notes for the integrator

- **Data side.** Run `tools/data/encode_driver_telemetry.py --json-dir "<repo>/<GP>/<Session>" --out-dir "<repo>/<GP>/<Session>" --verify` per session, with `tif1-native` installed.
  - About 25 s per race at level 19 on this box.
  - It adds ~52 MB per race and ~18 MB per qualifying to the `{year}` repository.
  - Files are ≤ ~0.6 MB, far under jsDelivr's 20 MB per-file limit.
  - Publish a session's files together: the reader takes one 404 as "this session has none" for 7 days. A half-uploaded session falls back to JSON (correct, slower) until the verdict expires.
- **Default.** See the verdict. If files ship later, flip `telemetry_columnar` to True in that release and re-run `gortyn_g3_cold_local.py` against the live repository.
- **Bytes floor.** −26% is the lossless floor for these values. Getting to Delphi's −50% needs float32 for the interpolated/derived channels upstream, which would change user-visible values. Not done.
- **Thread-safety bug caught here.** `cache._zstd_decompress` (one shared `zstandard.ZstdDecompressor`) corrupted data when decoding in several fetch threads on Python < 3.14. The decoder uses `cache._zstd_decompress_mt`, and a regression test decodes in 8 threads.
- **Probes.** All files of a wave start up front, so a session without files sends up to 6 parallel 404s on its first wave (one round trip). The JSON fallback then starts immediately.
- **Unexplained.** polars cold `driver_tel` shows no win (1215 vs 1237 ms, 1/5) while polars `notebook4`/`all_tel` win. Worth a look: the per-lap polars frame build may overlap the JSON wave better than a 10-lap file's burst.
- **Harness observation (both trees).** With `cdn_first_wave=False`, a cold session sometimes fetches `session_laptimes.json` twice (5 vs 6 session requests between runs of the same tree). It is not G3's doing.
- **Commits.** `git commit` is denied in this sandbox: everything is staged. The intended messages are in `.agents/perf-gortyn/G3_COMMITS.md`.
- **Result files.** `.agents/perf-gortyn/G3_formats.json`, `G3_cold_local_{pandas,polars}.json`, `G3_cold_local_nofiles_pandas.json`, `G3_cold_live_pandas.json`, `G3_ab_pandas.json`.
