# G1. E4 on 0.11.3: huge-page lz4 buffers through tif1-native 0.2.1

Branch `perf/gortyn-G1`, worktree `/tmp/tif1-gortyn/G1`, measured against the
frozen 0.11.3 control (`/tmp/tif1-gortyn-control`, f692ee7) on 2026-11-03.

## 1. Hypothesis

Elis E4 decompresses the pandas frame tier's driver rows into
`MADV_HUGEPAGE` anonymous mappings through a new
`tif1_native.lz4_frame_decompress_into` (pure-Rust `lz4_flex`, GIL
released). On the Delphi tree that cut the decompression page faults from
31k to 1.4k (`fetch_all` 57k -> 26.5k, system time 141 -> 92 ms) for a 1-3%
wall effect. G1 re-applies E4 on 0.11.3 (where Elis E5 reads rows ahead on
two lanes and E9 changed the readers), re-measures it with a 0.2.1 wheel
built from this tree, and tries the next fault source E4 named: the
`blobopen().read()` bytes (~15.5k faults). The verdict bar is the in-process
phases. The walls are not expected to move 3%.

## 2. What changed

- **Inherited base (staged, unchanged from E4):** `native/src/lz4.rs`,
  `native/src/lib.rs` (`lz4_frame_decompress_into`), `native/Cargo.toml`
  0.2.1 + `lz4_flex 0.11`, `native/Cargo.lock`, `native/README.md`,
  `src/tif1/core_utils/json_utils.py` (`NATIVE_LZ4_DECOMPRESS_INTO`),
  `src/tif1/cache.py` (`_huge_page_rows_enabled`, `_huge_page_buffer`,
  `_huge_page_decompress`, called from `_expand_narrow_row` and
  `_decompress_row`), `tests/unit/test_elis_e4_huge_page_rows.py`, E4's
  probes and the E4 report and artefacts under `.agents/perf-elis/`. The
  staged diff against f692ee7 is E4 only: 530 insertions and 4 deletions in
  `native/`, `src/` and `tests/`. No Elis E5/E9 code is touched.
- **Coverage on 0.11.3 (checked by reading the code and by the probe's
  counter):** every driver-row read ends in `_decompress_row`, and so in
  `_expand_narrow_row` -> `_huge_page_decompress`. That holds for the batch
  reader (`_submit_frame_row_reads`), the per-row worker read
  (`_read_frame_row`), the E5 read-ahead (`_PrefetchedRow.take` and
  `_prefetch_lane`), the serial fallback (`_decompress_frame_rows`) and the
  codec-less path (`_decompress_frame_blob` -> `_expand_narrow_row(blob,
  None)`). The probe counts 20/20 race rows on the huge-page path, both for
  `load(laps=True)` + `fetch_all` and for the harness's `session.laps` +
  `fetch_all` route.
- **Step 4 (chunked blob reads into a huge-page buffer): measured, rejected,
  reverted.** It is not in the tree; the patch is kept as
  `.agents/perf-gortyn/G1_step4_chunked_blob_read.patch`.
  `_reader_frame_blob` read a row of at least 2 MB with
  `Blob.read(chunk)` into a fresh huge-page buffer (`ctypes.memmove`, GIL
  released) instead of one `Blob.read()`.
- **New harness and probes (`tools/perf/`):**
  - `gortyn_g1_warm_ab.py`: a copy of `elis_e4_warm_ab.py` plus `--site DIR`,
    which puts an unpacked wheel ahead of each arm's `src` on `PYTHONPATH`.
  - `gortyn_g1_fault_probe.py`: interleaved faults/sys/user of a warm
    `fetch_all`, with source trees as arms. It counts huge-page rows and
    huge-page blob reads. `--route harness` loads the laps the way the warm
    bench's `all_tel` does.
  - `gortyn_g1_blob_read.py`: the raw cost of reading the 20 race rows,
    whole vs chunked, serially and on 4 threads.

### Environment deviation: no private venv (the /tmp quota)

The per-user quota on `/tmp` (tmpfs, shared by every agent and by the stale
caches and venvs of the Delphi/Elis rounds, ~13 GB) left ~7 MB free when the
round started, and it ran out completely several more times during the run.
The release build of the crate failed with `EDQUOT`, and a full venv like
E4's (754 MB) could not fit. Writes outside the worktree were denied, so
neither a target directory nor a venv on `/home` was possible.

- **The wheel:** built with `uvx maturin build --release -m
  native/Cargo.toml -o wheels` after zeroing, with their mtimes kept, the
  build-time-only artefacts of the proc-macro chain (syn,
  pyo3-macros-backend, quote, ...) in `native/target`. Their macro `.so`
  was already built and cargo checks only mtimes. Result:
  `wheels/tif1_native-0.2.1-cp311-abi3-manylinux_2_34_x86_64.whl`
  (untracked). `native/target/release` was deleted afterwards.
- **In place of the venv:** the wheel is unpacked into
  `native/target/site` (gitignored), and both A/B arms run the main venv's
  interpreter with that directory first on `PYTHONPATH`. `tif1_native` then
  resolves to 0.2.1 from the overlay and every other package is the main
  venv's. This is what E4's private venv amounted to (the main venv's
  exact versions plus the 0.2.1 wheel). Both arms always share the overlay;
  the control tree never calls the new function.

Then the real harness, 512 KB + memmove (the best probe variant) against the
E4 base, same cache, 12 pairs (`G1_ab_pandas_step4_vs_base_12.json`):

| workload | phase | E4 base | step 4 | pairs won |
|---|---|---|---|---|
| all_tel | `all_tel` | 104.0 | 119.2 | 5/12 |
| notebook | `iterlaps_tel_loop` | 149.7 | 156.6 | 5/12 |
| car_data_loop | `car_data_loop` | 27.3 | 25.0 | 7/12 |
| driver_tel | `driver_tel` | 25.6 | 25.8 | 4/12 |

The faults do halve, but the cut does not turn into time:

- **The 4 readers are not fault-bound.** With 4 threads (the reader cap),
  the raw read of 70 MB takes ~50 ms however the faults go, from 19.6k down
  to 3.3k.
- **Every chunk needs the GIL.** Each chunk re-takes the GIL from the main
  thread, which is decoding the frames. Small chunks lose badly; at 64 KB
  the 4-thread read is slower than one `read()`. This is the Delphi D4 /
  E5 effect again.
- **The phases get worse.** In the harness, `all_tel` and the lap loop
  lose at 5/12.

Reverted. `sqlite3.Blob` has no `readinto` on 3.13, and only a native blob
reader that fills the buffer without the GIL could remove these faults
without adding GIL round trips. That is not worth it for a ~3 ms ceiling on
a 4-thread read.

## 4. Verdict: PARTIAL, merge only with the next tif1-native release that ships for another reason

On 0.11.3 the mechanism does exactly what E4 measured: faults 56.7k ->
26.5k and system time -45..-54 ms per race `fetch_all`, all 20 rows on the
huge-page path, the native-off path the control's. The phase wins are real
but small:

| phase | win | pairs won |
|---|---|---|
| `car_data_loop` | -1.2..-2.9 ms | 10/12 in all three runs |
| `driver_tel` | -1.4..-1.5 ms | 11/12 in both runs |

These clear the bar (better median, at least 4 of 6 pairs) with the wall not
worse. The two phases E4 was mainly about do not clear it on this box:

- **`all_tel`:** 5/12, 1/12, 1/10, 6/12 across four runs. A same-code A/A
  moved it by 23 ms, so this is noise, not a measured regression.
- **The notebook lap loop:** 7/12, 1/12, 5/10. Its best-of-run minimums
  improve every time (-4..-6 ms), but the medians do not.

No wall moves.

Keep the code: it is exact, self-contained and falls back cleanly. Do not
cut a 0.2.1 wheel release for it alone. The cost is a new crate dependency
(`lz4_flex`) and a full wheel-matrix release for ~1-3 ms phases and ~50 ms
of system CPU per race. Ship it when tif1-native is released for another
reason, or with the liblz4 decoder (section 6), which would add back the
~10-30 ms of user CPU lz4_flex costs.

Step 4 (chunked blob reads): REJECT, numbers above.

## 5. CHANGELOG paragraph

- Warm pandas sessions decompress the frame tier's driver rows into
  huge-page buffers when `tif1-native` 0.2.1 is installed on Linux.
  `tif1_native.lz4_frame_decompress_into` decodes a row's lz4 frame with the
  GIL released into an anonymous private mapping advised `MADV_HUGEPAGE`
  (2 MB pages), instead of 123 MB of fresh memory zero-filled one 4 KB fault
  at a time. Fresh process, 2025 Bahrain race: `fetch_all_laps_telemetry()`
  takes 26 500 minor faults instead of 56 700, with 95 ms of system time
  instead of 139-152 ms. Per-lap `get_car_data()` over a driver: 28.5 ->
  25.9 ms. `laps.pick_driver("VER").telemetry`: 27.5 -> 26.0 ms. The whole
  call and the `iterlaps()` telemetry loop are unchanged within noise. Rows
  under 2 MB, Windows, macOS, Pyodide, THP `never`, older wheels and
  `TIF1_DISABLE_NATIVE=1` keep the pyarrow codec.

## 6. Notes for the integrator

- **Release steps for 0.2.1** (nothing changes until it is on PyPI):
  1. Merge the `native/` changes to `main`. The `push` trigger then runs
     `native.yml` as build-and-test only, and the `native` CI job runs the 25
     E4 tests against the commit's extension.
  2. Dispatch the workflow, first to TestPyPI, then to PyPI:
     `gh workflow run native.yml --ref main -f environment=testpypi`, then
     `gh workflow run native.yml --ref main -f environment=pypi`. In the
     Actions UI: "tif1-native wheels" -> Run workflow -> branch `main`,
     environment `testpypi` / `pypi`. The upload job uses the
     `testpypi-native` / `pypi-native` trusted-publisher environments.
  3. `native/Cargo.toml` is already 0.2.1; `pyproject.toml` keeps
     `tif1-native>=0.2,<0.3` (0.2.1 is inside it, so
     `tests/unit/test_pyproject_markers.py` is unchanged).
- **What `uv lock --upgrade-package tif1-native` changes:** only the
  `[[package]] name = "tif1-native"` block of `uv.lock`: `version = "0.2.0"`
  -> `"0.2.1"`, the sdist URL, hash, size and upload time, and the
  URL/hash/size/upload-time of every wheel (macOS universal2,
  manylinux2014 x86_64/aarch64, musllinux_1_2 x86_64/aarch64, Windows
  x64/arm64). The dependency list stays numpy, with the same
  `python_full_version` markers, since `native/pyproject.toml` still says
  `numpy>=1.26`. tif1's own `requires-dist` entry (`specifier = ">=0.2,<0.3"`)
  and the marker string do not change, and no other package moves.
- **Benchmark methodology (affects every Gortyn agent):** the brief's
  separate per-arm caches bias the row-read phases. In a same-code A/A,
  `all_tel` came out 116 vs 139 ms (0/6) depending only on which cache copy
  an arm read. For frame-tier work, A/B on one shared cache.
- **The `all_tel` phase on this box is bimodal** (~90 vs 105-140 ms in both
  arms). A pair count on it needs many more pairs, or a quiet box.
- **The bigger remaining lever is the decoder, not the faults.** The faults
  that remain after E4 (blob bytes ~15k, main-thread decode ~9k) do not
  convert to time: the 4-reader read is bandwidth- or lock-bound at ~50 ms,
  and chunking adds GIL round trips. The lz4_flex decoder hands back
  0-33 ms of user CPU per race against pyarrow's liblz4. Vendoring liblz4
  through `lz4-sys`, which needs a C toolchain in the wheel builds, would
  likely turn the saved system time into a measurable phase win. Not tried
  (a dependency decision).
- **Quota:** `/tmp`'s per-user quota is consumed by old rounds' caches and
  venvs (`/tmp/tif1-delphi-warm-D*`, `/tmp/tif1-elis-warm-E*`,
  `/tmp/tif1-elis-venv-E4`, `/tmp/tif1-venv312`, `/tmp/tif1-verify-*`, ~9 GB).
  Clean them before the next round. G1 freed only its own build directory.
- **Commits:** `git commit` is denied in this sandbox. Everything is staged,
  and the intended messages are in `.agents/perf-gortyn/G1_COMMITS.md`.
- **Artefacts:** `.agents/perf-gortyn/G1_ab_pandas_*.json` (all A/B runs
  above) and `G1_step4_chunked_blob_read.patch` (the rejected step). The
  wheel is in `wheels/` and the overlay in `native/target/site` (both
  untracked).
