# G2: upstream pre-release canary (hardening job)

## 1. Hypothesis

Two rounds put fast paths on private upstream API (pandas internals, polars
`_plr`, niquests' OCSP cache, the `qh3._hazmat` load, `threading._register_atexit`).
Each path has a fallback, so a drift cannot change results. It can, however,
quietly put a hot path back on the slow route, and today a user finds that after
an upgrade. A scheduled canary that runs the tests against the newest upstream
releases and pre-releases should find it first. It needs a seam list whose
tests fail when a fast path is *not taken*, so that a failure names the seam
instead of showing up as a vague perf delta. This is not a performance change:
library code is untouched.

## 2. What changed

- `tests/unit/test_private_seams.py` (new, 16 tests, ~1 s). `SEAMS` lists 10
  seams. Each entry has: the package, the version it was verified against, where
  tif1 uses it, the private names, what the fallback costs, and the test that
  proves the fast path is active:

  | seam | package (verified) | what the test asserts is active |
  |---|---|---|
  | pandas-direct-blocks | pandas 3.0.6 | `_from_arrays`, `_DIRECT_BLOCKS_AVAILABLE`, `_DIRECT_BLOCK_CLASSES_OK`, `_probe_direct_blocks()`; direct frame == public route; `encode_frame` returns bytes (no frame tier otherwise) and round-trips |
  | pandas-lap-frames | pandas 3.0.6 | `_probe_str_slice()`, `_probe_timedelta()`, `_fast_lap_frames()`; driver blob round trip |
  | pandas-arrow-strings | pandas 3.0.6 | `ArrowStringArray._pa_array`, `_from_pyarrow_array`, `_concat_same_type`; `_str_dictionary` takes the Arrow path |
  | pandas-lap-rows | pandas 3.0.6 | `_FAST_LAP_ROWS`; `_interleaved_row` does not return `None`; `Laps.iloc[i]` dispatches to `Laps._ixs` (spy); `_lap_from_row` == `Lap(...)` |
  | pandas-constructor-hooks | pandas 3.0.6 | pandas calls `_constructor_from_mgr`/`_constructor_sliced_from_mgr` of `Laps`, `Telemetry`, `SessionResults` (spies) |
  | polars-ipc-stream-reader | polars 2.0.0 | `_ipc_stream_reader()` callable; `_read_polars_ipc_row` returns the frame with `pl.read_ipc` patched to raise (the existing E6 test passes on the fallback too) |
  | polars-pydf-wrap | polars 2.0.0 | `_from_pydf(df._df.clone())` is equal and isolated; `ErgastPolarsResponse._from_pydf` hook yields plain frames |
  | niquests-ocsp-pickling | niquests 3.21.1 | `_ocsp_module()` not None, pickling-state keys, `Session._ocsp_cache` and the adapters' `_ocsp_cache` exist |
  | qh3-hazmat-preload | qh3 1.9.4 | `qh3/_hazmat*.so` is where the preload looks; niquests' `OCSPResponse` comes from `qh3._hazmat` |
  | threading-register-atexit | CPython 3.11-3.15 | `_register_atexit` callable; a hook registered after a pool exists runs before the pool's join (subprocess) |

  Meta tests: every entry has its test; `verified` equals `uv.lock`'s pin (a
  lock bump fails `test_seam_table_follows_the_lock` until someone re-verifies
  the entry); the workflow installs every seam package. Assertion messages carry
  "<pkg> <installed> installed, seam verified against <verified>".
- `.github/workflows/upstream-canary.yml` (new). It runs weekly (Mon 04:23 UTC)
  and on `workflow_dispatch` (input `channel`: `pre` default, or `nightly`, which
  adds the scientific-python nightly index for pandas/numpy/pyarrow). It is
  Linux, Python 3.13, 30 min timeout, never a PR check, and only files issues on
  `TracingInsights/tif1`. The steps:
  1. `uv sync --all-extras`.
  2. `uv pip install --prerelease allow --upgrade $CANARY_PACKAGES` (pandas,
     polars, polars-runtime-32, numpy, pyarrow, niquests, urllib3-future, qh3),
     then print the installed versions.
  3. The seam tests, the unit suite (`-n auto`, no `-x`) and the perf gate, each
     `continue-on-error` with a JUnit report.
  4. The issue body (`tools/upstream_canary_report.py`), also written to the job
     summary, and the artifacts.
  5. One open `upstream-drift` issue per channel: created on the first failure;
     on later failures its body is rewritten and a comment links the run; a green
     run closes it. The label is created with `--force`, so the step is
     idempotent.
  6. A final step that fails the job when any test step failed.
- `tools/upstream_prereleases.py` (new): the newest stable release and newer
  pre-releases per package from PyPI's JSON API, or `--installed`.
- `tools/upstream_canary_report.py` (new) plus `tests/unit/test_upstream_canary_report.py`
  (3 offline tests: failing test ids and messages, capped list, the workflow's
  package list == the tool's).
- `AGENTS.md` build/test section and `CONTRIBUTING.md` document the seam list and the job.
- `.agents/perf-gortyn/G2_wheel_drift.py`: the in-memory drift check used below.

## 3. Measurements

**No A/B and no parity run:** no library code changed (`git diff --stat src/` is
empty), so the warm/cold A/B and the parity digests do not apply.

**Seam tests on the pinned versions:** 16/16 pass in ~1.0 s.
**Mutation check:** I simulated drift in each seam (12 cases: `_from_arrays`
removed, block classes off, `_from_mgr` off, string-slice probe false,
`_from_pyarrow_array` removed, `_FAST_LAP_ROWS` off, the iloc indexer bypassing
`_ixs`, `take` not calling the frame hook, the IPC reader gone, the IPC reader
signature raising `TypeError`, the OCSP module unavailable, `_register_atexit`
removed). Each one fails the matching seam test, and the message names the
seam. For the IPC signature case, the existing E6 reader test compares only
the resulting frame, so it passes on the fallback. I did not check the
other cases against the rest of the suite.

**Unit suite:** 3517 passed, 8 skipped, 97 s (6 workers). **ruff** check and
format: clean. **ty:** clean.

**Pre-releases available today (2026-11-03, `tools/upstream_prereleases.py`):** none newer
than the stable releases for any of the 8 packages. `--prerelease allow
--upgrade` therefore installs the newest stables, which all lead the lock:

| package | lock | newest |
|---|---|---|
| pandas | 3.0.6 | 3.1.0 |
| polars / polars-runtime-32 | 2.0.0 | 2.1.0 |
| numpy | 2.5.3 | 2.5.4 |
| pyarrow | 26.0.0 | 26.0.1 |
| niquests | 3.21.1 | 3.21.2 |
| urllib3-future | 2.24.900 | 2.25.905 |
| qh3 | 1.9.4 | 2.1.0 |

**Running the job's steps locally: not possible on this box.** `/tmp` is a
tmpfs with a per-user quota (`usrquota`), and all agents share uid 1000. During
this run the quota was at its limit: a 64 MB probe failed after 9 MB, and file
edits and even tool output writes intermittently failed with EDQUOT. `uv`
needed approval that this session could not get, and writes outside the
worktree were denied. A throwaway venv or `pip --target` with the new wheels
(~450 MB) would have failed, and it would also have starved the other agents'
benchmarks.

**What I did instead:** a static drift check, entirely in memory
(`G2_wheel_drift.py`). It downloads the locked and the newest wheel of each
seam package into RAM and compares the source of every private symbol tif1
uses: functions and classes by AST, compiled modules by symbol name. Result:
14 changed symbols, all in pandas.

- **polars 2.1.0 / polars-runtime-32 2.1.0:** `_from_pydf`, `_df`, `_plr`
  unchanged; `read_ipc_stream` still present in the binary.
- **niquests 3.21.2:** `InMemoryRevocationStatus`, the `qh3._hazmat` import,
  and `_ocsp_cache` in sessions and adapters are unchanged.
- **qh3 2.1.0:** `_hazmat` is still an extension at the same path.
  `OCSPResponse(raw, *, raise_on_missing_nextupdate=True)` gains a keyword, and
  `next_update` now falls back to `thisUpdate`. `ocsp_cache` uses
  `deserialize`/`next_update`, so its behaviour is unchanged, and
  `MIN_REMAINING_SECONDS` still rejects such answers.
- **pandas 3.1.0, likely drift.** This is a static reading; I could not run it:
  - `ArrowExtensionArray.__getitem__` now answers slices with
    `_from_pyarrow_array(...)`, which also sets `obj._cache = {}`. tif1's
    `_probe_str_slice` requires `list(vars(got)) == list(vars(ref))` and its
    `_str_slice` sets only `_pa_array/_dtype/_readonly`, so **the probe should
    return False**.
  - `TimedeltaArray._simple_new` dropped `freq` and no longer sets `_freq`,
    while `_timedelta_array` sets `_freq = None` and `_probe_timedelta`
    compares `vars()`. So **this probe should return False too**.
  - Together: on pandas 3.1.0 the Pergamon Q18 lap-frame route would silently
    take `ea[start:stop]` and `TimedeltaArray._simple_new` for every lap.
    `test_pandas_lap_frames` would fail on the canary's first run, naming the
    seam.
  - Other pandas changes do not break a probe: `DataFrame._ixs` refactored but
    still calls `_constructor_sliced_from_mgr`; `iLoc._getitem_axis` is
    unchanged, so `Laps._ixs` still runs; `fast_xs` now caches the interleaved
    dtype itself (GH#62263); `_constructor_sliced_from_mgr` uses
    `object.__setattr__`; `BlockPlacement` gained `__new__`; `sanitize_array`'s
    list branch changed (not the object-ndarray branch `_lap_from_row`
    mirrors); `maybe_convert_objects` and `ints_to_pytimedelta` stubs are
    unchanged.

**The job's runtime (estimate; target < 10 min):** these are not measured on a
runner:
- `uv sync` ~0.5-1 min;
- the upgrade ~0.3 min;
- seam tests 2 s;
- the unit suite 97 s here on 6 workers, and the ci.yml comment says ~3 min on
  a hosted runner;
- the perf gate ~1 min here per AGENTS.md (not run locally: it seeds caches for
  both backends in `/tmp`); a 2-core runner could take 2-3 min.

Expected total 6-9 min. The 30-min timeout leaves room for a slow
perf-gate rerun.

## 4. Verdict: SHIP

It hardens the build at zero runtime cost: no library code changed, and the
unit suite gains ~1 s. The seam tests are proven to catch every simulated drift
under the seam's name. The static check says the canary will most likely flag
pandas 3.1.0 (the Q18 array probes) on its first run, which is the case this
job exists for. One weakness: the runtime target is estimated, not measured
(see §3).

## 5. CHANGELOG

- Private upstream API is now tracked. `tests/unit/test_private_seams.py` lists
  the 10 places where a fast path uses private pandas, polars, niquests, qh3 or
  CPython API, with the version each was verified against. It asserts that each
  fast path is the one taken, not its fallback, so a drift fails a named test
  instead of making `iterlaps` or the frame tier slower without an error. A
  weekly `Upstream canary` workflow (not a pull-request check) runs those tests,
  the unit suite and the perf gate against the newest releases and pre-releases
  of those packages, and opens or updates one `upstream-drift` issue when
  something fails.

## 6. Notes for the integrator

- **Expect the first canary run to fail on pandas 3.1.0**
  (`test_pandas_lap_frames`; see §3). The library-side fix is small but outside
  this hypothesis: `_str_slice` should set `_cache = {}` when the reference
  slice has it, or copy the reference's attribute set. `_timedelta_array`
  should skip `_freq` when `TimedeltaArray._simple_new` no longer sets it. The
  probes already guard both. Re-measure Q18 after the fix: pandas' own slice
  path also got faster in 3.1.0, so part of the gap may be gone. pandas 3.1.0
  also caches the interleaved dtype in `fast_xs`, which shrinks the value of
  tif1's `_row_interleaved_dtype` memo; worth a re-measure on the lock bump.
- **On the bump:** the perf-gate parity digests hash reprs, so a pandas or
  polars bump may fail the canary's perf gate on parity even without a seam
  drift. That is still user-visible drift and is reported, but when reading the
  issue, tell it apart from a phase regression.
- **Lock bumps:** `test_seam_table_follows_the_lock` deliberately fails on a
  lock bump of pandas, polars, niquests or qh3. Re-run the seam file on the new
  lock and update `verified`. If that is too much friction for automated bumps,
  relax it to a warning, but then the "verified against" column rots.
- **Untested workflow wiring:** I could not run actionlint or a YAML parser
  here (no PyYAML in the venv, `uv` blocked). I reviewed the workflow by hand.
  Run one `workflow_dispatch` before relying on the schedule. Check
  `uv pip install --prerelease allow` with uv 0.10.2, the `gh issue list
  --search "in:title pre"` lookup, and `actions/upload-artifact@v4` (not
  SHA-pinned, unlike checkout).
- **Resolver conflicts:** qh3 2.x vs urllib3-future's requirement was not
  resolved here. If the resolver refuses the combination, the upgrade step
  fails the job before any test runs, and no issue is filed, because the report
  step needs the versions file. Consider `continue-on-error` there if that
  turns out noisy.
- **Environment:** the shared `/tmp` quota on this box is exhausted (all agents
  are uid 1000; ~11 GB of it is outside this round's directories). Later rounds
  need space freed, or worktrees and caches put on the home disk.
