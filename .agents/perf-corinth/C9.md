# C9: Schedule APIs without the pandas import

## 1. Hypothesis

`get_event_schedule(2025)` costs 394-469 ms, nearly all of it `import pandas`,
on polars scripts too: a polars season loop that reads the schedule pays the
pandas import only for the schedule. fastf1 returns a pandas `EventSchedule`,
so the default has to stay. The hypothesis was in three parts: (1) see what
scripts do with a schedule (round numbers, event names, dates, session names,
row loops, filters); (2) make that reachable without pandas, for example a
`lib="polars"` option that returns a polars frame with the same columns and
mapped dtypes; (3) cut what remains of the pandas `EventSchedule` build after
the import.

## 2. What changed

- `src/tif1/events.py`
  - `get_event_schedule(..., lib="pandas" | "polars")` and
    `get_events_remaining(..., lib=...)`. The default `"pandas"` is unchanged.
    `"polars"` returns a plain `polars.DataFrame` built by
    `_polars_schedule_frame` from the pandas-free schedule rows
    (`_schedule_native_rows`, the same rows `_event_row` already built for
    polars sessions). It keeps the columns in the order pandas gives
    (`_frame_columns`: first appearance over the row dicts, as
    `DataFrame(list_of_dicts)` orders them). It builds typed Series from
    Python lists. Datetime columns are built from integer microseconds plus an
    eager `cast`, because a polars `Datetime` Series built from Python
    `datetime`s runs a query plan per column (~5 ms for the first, 11 in all).
    No pandas, numpy, pyarrow or query plan. The dtype mapping is in the
    docstring and the docs: `RoundNumber` Int64; `F1ApiSupport` Boolean; circuit
    coordinates Float64; `EventDate` and `Session{i}DateUtc` naive
    `Datetime("us")` (as pandas); `Session{i}Date` naive `Datetime("us")` with
    the local wall time (pandas holds tz-aware datetimes with mixed offsets, which
    one polars column cannot hold; the offset is in `GmtOffset`); everything else
    String; missing values are null. If polars is not installed, the call logs a
    warning and returns the pandas schedule, as `get_session` does. An unknown
    `lib` raises `ValueError`. Typed with `@overload`s.
  - The pandas `get_event_schedule` builds its rows with
    `event_frames._event_data` (the dict that each `Event` Series was built from)
    instead of building one `Event` Series per event and calling `to_dict()`.
    `Series.to_dict()` on an object Series only boxes numpy scalars, and the
    dict holds Python scalars, so the input to `EventSchedule(rows)` is
    identical.
  - `get_events_remaining` (pandas) reads `EventFormat`/`Session3DateUtc`/
    `Session5DateUtc` once with `tolist()` instead of `iterrows()` (one Series per
    event). Same `pd.Timestamp` comparisons and the same `drop(index=...)`.
  - `get_event` and `get_event_by_round` resolve on the schedule payload
    (`_match_event_name`, `_resolve_event_round`, the resolvers `get_session`
    already uses) and build only the matched `Event`, not the season frame plus a
    second `Event`. `get_event_by_round(None)` keeps
    `EventSchedule.get_event_by_round`'s message.
- `src/tif1/event_frames.py`: `Event.__init__`'s body moved into
  `_event_data(year, name, metadata, backend)` (shared by `Event` and the
  schedule rows; no behaviour change).
- Tests:
  - `tests/unit/test_schedule_polars.py` (38 tests): the pandas schedule
    equals the per-event-Series build (`assert_frame_equal`, dtypes, value
    types); column order; polars vs pandas value for value on 7
    year/backend/testing combinations; polars dtypes and sample values;
    `include_testing=False`; `get_events_remaining` polars vs pandas at 4
    dates × 2; index labels kept; unknown `lib`; fallback without polars;
    `get_event` equals the schedule lookups for names, aliases, typos, rounds,
    floats and bools; the round error messages; unmatched names give `None`.
  - `tests/unit/test_polars_without_pandas.py`: a third fresh-interpreter
    child reads the `lib="polars"` schedules and `get_events_remaining`
    and asserts that pandas, numpy and pyarrow stay unloaded.
- Docs: `docs/api-reference/events.mdx` (new "Polars schedules" section with
  the dtype table and an example; I ran the example offline on the season
  cache), stale performance notes corrected; one `README.md` compatibility row.
  CHANGELOG.md is not edited (paragraph below for the integrator).
- Harness (my copies, in the tree):
  - `tools/perf/corinth_c9_schedule_ab.py`: the `delphi_warm_ab.py` protocol
    (ABAB, flipped every pair, fresh processes, wall plus phases, medians, p90,
    pairs won) over schedule workloads the Delphi bench lacks, with `--cold`
    (empty cache per run, online). In the control arm, a `lib="polars"`
    workload falls back to the pandas schedule (the control has no `lib=`):
    that is what a polars script had to do.
  - `tools/perf/corinth_c9_schedule_parity.py`: the schedule digest and the
    polars value-for-value check.

## 4. Verdict: SHIP

- `lib="polars"` meets the bar on every polars workload: wall −53 to −55% on
  the schedule calls, −49% on the season loop, −48% on the warm current
  season, 10/10 pairs each; cold 4/5 and 5/5. A polars script that starts
  from the schedule never imports pandas.
- The pandas-side changes are a PARTIAL by the rule's letter. The phases are
  clearly faster (schedule −33%, remaining −28%, get_event by name −38% and by
  round −96%, 15-20 of 20 pairs). The wall is not resolvable on this box,
  because a ~10 ms saving sits under a ±50 ms pandas-import noise. The parity
  digest is identical, and the changes remove code (Series per event, iterrows,
  a second schedule frame in `get_event`). I recommend keeping them.

## 5. CHANGELOG paragraph

- **Schedules without pandas.** `get_event_schedule()` and
  `get_events_remaining()` take `lib="polars"` and return a polars frame with
  the `EventSchedule`'s rows and columns. tif1 builds it from Python lists, with
  no pandas, numpy, pyarrow or query plan. Before this change, a polars script
  that read the schedule imported pandas for it alone. Warm, fresh process: a
  2025 schedule 605 → 270 ms, `get_events_remaining` 611 → 285 ms, a 24-race
  polars season loop (schedule plus laps and results) 726 → 368 ms, all 10/10
  pairs. Cold current season 2.6-2.9 s → 1.1-1.2 s. Local session times are
  naive wall-clock `Datetime`s (the offset is in `GmtOffset`) and missing values
  are null; the default stays fastf1's pandas `EventSchedule`. The pandas
  schedule is built from its row dicts instead of one `Event` Series per event
  (27.7 → 18.5 ms after the pandas import, 7.4 → 2.2 ms per later call).
  `get_events_remaining` reads whole columns instead of `iterrows` (33.7 → 24.1
  ms). `get_event`/`get_event_by_round` resolve on the schedule payload and
  build only the matched `Event` (30.1 → 18.7 ms by name, 12.6 → 0.5 ms by
  round). The frames are unchanged (568 schedule surfaces identical, 1950-2026,
  every backend). (Corinth C9)

## 6. Notes for the integrator

- **Default stays pandas, also for `config.lib == "polars"`.** The Ergast
  standings (`_as_lib`) follow `config.lib` when `lib=None`. I did not do that
  for schedules: fastf1 code that calls `schedule.get_event_by_round(...)` would
  break for users who set `lib=polars` for sessions. If the maintainer prefers
  the standings' convention, change the default to `None` → config. It is a
  one-line change, but a user-visible one.
- **`Session{i}Date` in polars is local wall time, naive.** This is a mapping
  decision, not a lossless copy: the pandas column holds tz-aware datetimes with
  per-event offsets. The alternatives were an ISO string column (lossless,
  unusable for arithmetic) or UTC (duplicates `Session{i}DateUtc`). The mapping
  is documented in the docstring and `docs/api-reference/events.mdx`.
- The polars frame is a plain `pl.DataFrame`: no `year`/`backend`
  attributes, no `get_event_by_*` methods (polars discourages subclassing).
  `get_event()` still returns the pandas `Event`. I added no pandas-free
  `Event`-like object: the frame's `row(i, named=True)`/`iter_rows(named=True)`
  covers per-event access.
- Datetime Series from Python `datetime`s go through a polars query plan
  (`select_seq` → `collect`, ~5 ms the first time per process). Integer
  microseconds plus `Series.cast` avoid it. The same trap may exist elsewhere in
  `models_polars.py`/`core.py`. A grep for `dtype=pl.Datetime` on list input
  would find it.
- `get_events()` (the old alias) has no `lib=`. It is easy to add if wanted.
- The warm pandas walls here are noisy because the box was shared (pandas import
  430-870 ms against the brief's 341). The phase numbers and pairs won are the
  reliable reading for the pandas side.
- Commits were denied by the sandbox: everything is staged, and the intended
  message is in `.agents/perf-corinth/C9_COMMITS.md`.
