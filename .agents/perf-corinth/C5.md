# C5. Python 3.14 warm paths

Branch `perf/corinth-C5`, tree `/tmp/corinth/C5`, measured on 2026-11-06
against the frozen control `/tmp/corinth/control` (552c357). Both arms read one
cache copy, `/tmp/corinth/warm-C5`. Interpreters: CPython 3.14.8
(`/tmp/corinth/venv314`) and 3.13.15 (the main venv). `git commit` is denied
in this sandbox, so everything is staged. The intended commits are in
`C5_COMMITS.md`.

## 1. Hypothesis

On Python 3.14 the warm workloads ran 7-10% slower than on 3.13 (pandas laps
444 -> 476 ms, `get_session` 345 -> 374 ms in process, all_tel 629 -> 680).
C5 asked what 3.14 costs that 3.13 does not, and to fix the part tif1
controls without hurting 3.13.

The main finding is that the premise behind the current gate is out of date.

- Naxos N10's GC promotion (`gc.freeze(); gc.unfreeze()` after the import
  and frame bursts) is gated off for every 3.14
  (`sys.version_info < (3, 14)`), because 3.14.0 shipped the incremental
  collector.
- **CPython 3.14.5 reverted that collector to the generational GC of 3.13,
  and 3.15 reverted it before its first beta.** Sources:
  - the core team's announcement, "Reverting the incremental GC in Python
    3.14 and 3.15", 2026-04-16 (https://discuss.python.org/t/107014),
    citing memory-pressure reports collected in gh-142516;
  - the 3.14.5 release (2026-05-10;
    https://pydevtools.com/blog/python-3145-rolls-back-the-incremental-garbage-collector/).
- The 3.14.8 interpreter here confirms it. Its
  `internal/pycore_interp_structs.h` has `generations[NUM_GENERATIONS]`
  again, plus `dummy1 /* was work_to_do */`. Its `gc.get_threshold()` is
  `(2000, 10, 10)`.
- N10's micro-benchmark gives the same result on 3.14.8 as on 3.13
  (`naxos_n10_gc_promote_micro.py`). The freeze/unfreeze pair takes
  0.00-0.01 ms with a 1 M-object heap. The next 20 k allocations take 2.0-3.9
  ms instead of 10.6-14.0 ms.

So on 3.14.5+ every warm script still paid the gen-1 collections N10
removed on 3.13. That is 18-35 ms of GC inside pandas `get_session()` (one
~25-33 ms gen-1 pass over the pandas import), 7 ms on polars, 5 ms after the
pandas `fetch_all` burst, and more in the notebook loop. That accounts for
most of the 3.14 `get_session` gap (+29 ms).

## 2. What changed

**Commit 1: the gate (`src/tif1/core_utils/gc_control.py`).**

- New `generational_gc(version)`, which returns True for:
  - 3.11-3.13;
  - 3.14.5 and later;
  - 3.15 from `(3, 15, 0, "beta")` on. The revert landed in a9 or b1, so
    gating at the beta skips at most one alpha.
- It returns False for:
  - 3.14.0-3.14.4 (the incremental collector);
  - the 3.15 alphas;
  - 3.16+, until someone measures it. The revert thread says the incremental
    GC may return in 3.16 through a PEP.
- `gc_promote_ok()` calls it instead of `sys.version_info < (3, 14)`.
- The other guards are unchanged: CPython only, GIL builds only, the
  freeze-count check, and the young-count threshold.

**Commit 2: the per-lap frame build (`src/tif1/cache.py`,
`SessionMemo._materialize_telemetry`).**

- A lazy `lap.telemetry` loop (the notebook's `iterlaps()` loop) builds one
  memoized frame per lap from the decoded driver row. N10 covered the batch
  twin (`materialize_telemetry`) but not this per-lap path.
- Over a race that loop triggers ~30 young collections, two of them gen-1
  passes: 8-9 ms on a quiet box, 25 ms at load 40. A `gc.callbacks` count
  shows they collect **0 objects**.
- The build plus the frame adopter now run under
  `suspend_gc(promote=True)`. The promotion fires only when the young
  generation crossed its threshold during the build, so the collections that
  would have fired inside a build are replaced by O(1) promotions.
- A `KeyError` still drops the source exactly as before (Delphi D5). A
  source returning `None` keeps its old behaviour.
- This applies on 3.13 too, wherever promotion is on.

**Tests (`tests/unit/test_naxos_n10_gc_promote.py`)**

- The gate table: 3.13, 3.11, free-threaded, 3.14.0, 3.14.4, 3.14.5, 3.14.8
  (also free-threaded), 3.15a8, 3.15b1, 3.15.2, 3.16.
- The per-lap build runs with GC off, the adopter included. It calls the
  promotion, memoizes, and turns GC back on.
- A missing lap still drops the source, with GC back on.
- On 3.14.8 the N10 promotion tests now **run** (they were skipped before)
  and pass.

**Docs:** the `gc_control.py` entry in `AGENTS.md`.

## 4. Verdict

**SHIP, both commits.**

Commit 1 (the gate) clears the bar on Python 3.14:

| workload | wall | pairs won |
|---|---|---|
| pandas all_tel | -5.2% | 7/8 |
| pandas all_tel (CPU harness) | -6.7% | 12/12 |
| pandas notebook | -6.6% | 7/8 |
| pandas notebook (CPU harness) | -5.8% | 10/12 |
| polars laps | -11% | 7/8 |

- Every `get_session` loses its 7-35 ms of GC in every run.
- The pandas laps and load_only walls are within noise. Their `get_session`
  CPU is still -17 to -21 ms (10-12/12).
- It changes nothing on 3.13: the same answer from the gate, and the
  identical-code workloads swing both ways.
- It also covers 3.15 (beta and later), which CI tests.
- It restores the 3.13 behaviour on the interpreters whose collector is the
  3.13 one again. Same semantics, same guards, same tests.

Commit 2 (the per-lap build) is a phase win:

- the iterlaps loop is -12% on 3.13 (9/12) and -19% on 3.14 together with
  the gate (143 -> 116 ms);
- the loop's GC goes from 8 ms to 1 ms in every run;
- the whole-process notebook wall is not worse (-1.5% on 3.13, 7/12).

Its trade-off is N10's, extended to one more site.

- A promotion that fires inside a lap build also moves young cyclic garbage
  the user created since the last collection into the oldest generation. It
  is then freed at the next full collection instead of the next young one.
- In the measured loop there is none: all 30 collections freed 0 objects.
- If the integrator wants promotion only in one-off bursts, commit 2 is
  independent and can be dropped. Commit 1 is the main result.

The remaining 3.14 cost is upstream and was not pursued:

- numpy's import (+16 ms);
- `_colorize`'s dataclasses (+6.5 ms);
- 3.14's `site` (+5-8 ms per interpreter start);
- partly offset by pyarrow (-10 ms).

## 5. CHANGELOG paragraph

- Warm sessions on Python 3.14.5+ and 3.15 get the GC promotion that 3.11-3.13
  already had (Naxos N10).
  - **Why it was off.** It was turned off for every 3.14 because 3.14.0
    shipped an incremental collector.
  - **What changed in CPython.** CPython 3.14.5 (and 3.15 before its first
    beta) reverted that collector to the generational one of 3.13, where
    `gc.freeze(); gc.unfreeze()` is again an O(1) move.
  - **Where it applies now.** GIL builds of 3.14.5+ and 3.15. It stays off
    on 3.14.0-3.14.4, the 3.15 alphas and 3.16+.
  - **What 3.14 was paying.** A pandas `get_session()` on 3.14 spent 18-35
    ms in a gen-1 collection that freed nothing (7 ms with polars).
  - **Numbers** (fresh process, warm cache, 2025 Bahrain race, a loaded box):
    - pandas `fetch_all_laps_telemetry()` script: 597 -> 557 ms (12/12
      pairs);
    - the benchmark notebook: 675 -> 636 ms (10/12);
    - polars `laps`: 245 -> 218 ms (7/8).
  - **Result.** A warm pandas `laps` script now takes the same time on 3.14
    as on 3.13 (455 vs 454 ms).
- A loop over the laps' telemetry builds each lap's frame with GC paused,
  promoting the survivors when the young generation fills.
  - Previously, the ~30 young collections such a loop triggered over a race
    traversed the memoized frames and freed nothing.
  - Benchmark notebook `iterlaps()` loop: 141 -> 124 ms on 3.13 (GC 8 -> 1
    ms) and 143 -> 116 ms on 3.14.

## 6. Notes for the integrator

- **CHANGELOG.** The Naxos entry in `CHANGELOG.md` says the promotion is
  "skipped ... on 3.14+ (incremental collector)". I left that text alone for
  the series write-up. With commit 1 it should read "on 3.14.0-3.14.4, the
  3.15 alphas and 3.16+".
- **Interpreters not run here.** uv commands needed approval in this
  sandbox, so I could not install 3.15 or 3.14.0-3.14.4.
  - The 3.15 side of the gate rests on the announcement and on 3.15.0 final
    having shipped after the revert.
  - Follow-up: on 3.15, check that `pycore_interp_structs.h` has
    `generations[NUM_GENERATIONS]` and run
    `tools/perf/naxos_n10_gc_promote_micro.py`. CI's 3.15 leg now runs the
    N10 promotion tests (they skip where `gc_promote_ok()` is False), which
    exercises it.
  - If 3.16 keeps the generational GC, widen `generational_gc` after the
    same check.
- **No runtime detection.** I found no public API that tells the two
  collectors apart. Both expose three `get_stats()` entries, and
  `get_threshold()` is not a reliable tell across the 3.14 patch releases.
  Hence the version table, pinned by the test.
- **Commit 2's semantics** are the same as N10's promotion. Young cyclic
  garbage present when a promotion fires waits for the next full collection.
  Full collections are not suppressed: young collections still run in user
  code between builds, and a `gc.collect()` still frees everything (pinned
  by the N10 test).
- **Perf gate baseline.** Commit 2 moves the pandas notebook's
  `iterlaps_tel_loop` down on 3.13. Rewrite the baseline on a quiet box
  after merging. The gate passes as is.
- **What else was running.** Up to nine other Corinth agents ran throughout
  (load 13-41). No cold or network measurement was needed: C5 is a warm-path
  hypothesis and touches no fetch code.
