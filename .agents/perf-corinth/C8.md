# C8: tel.v2 decode CPU (one native call per file)

## 1. Hypothesis

Naxos N7 shipped the `tel.v2` columnar telemetry files (reader off until the
data repositories publish them). A race's files decoded in ~472 ms of CPU
(4.1 ms per ten-lap file) against 273 ms for `tel.v1`, and on a fast link
that decode decides the cold load. N7 put the predictions in Rust
(`tel_integ`, `tel_accx`, `tel_lateral`, `tel_spline`, `tel_interp`,
`tel_apply`) but left "mostly numpy orchestration around the kernels":
byte-unshuffle copies, boolean masks, one kernel call per column, per-lap
slicing, all under the GIL. C8: decode the whole file body in one native call
(header, unshuffle, value encodings, anchors, dates, predictions, residuals,
per-lap output) with the GIL released, keep the numpy decoder as the
fallback, and let the fetch pool decode files in parallel.

## 2. What changed

No format change: the files, the encoder's output and the decoded values are
the same; the work moved into Rust and out of the GIL.

- `native/src/telfile.rs` (new): `decode(body)` decodes a whole `tel.v2`
  file body (the content of its zstd frame) and `File::laps()` hands out the
  laps' channels. It is the Python `decode_driver_file` step for step:
  - a strict JSON parser for the orjson header (RFC 8259 numbers, escapes and
    surrogate pairs, control characters and lone surrogates rejected,
    int64-only integers, finite floats, depth limit; a repeated key resolves
    to its last value, as orjson);
  - buffers: the numpy dtype strings the encoder writes (`|i1 |u1 <i2 <u2 <i4
    <u4 <i8 <u8 <f8`), bounds-checked, byte planes gathered back;
  - value encodings `int`, `f64`, `dec` (wrapping int64 cumsum, exact powers
    of ten), `split`; `np.unpackbits` semantics (big bit order, zero padding);
    numpy's casts (`astype(int64)` for nested `int` parts, direct uint64 ->
    float64 for `split` integers);
  - the layout (`_Rows`), the anchors (`_Anchors`: per-lap previous/next car
    row) and the row dates (`_row_dates`: `rint`, the 2**40 ms limit, wrapping
    int64 nanoseconds);
  - every predicted encoding (`interp`, `lerp`, `spline`, `integ`, `integs`,
    `ratio`, `accx`, `lat`) through the existing `telcols` kernels and the
    same residual application;
  - the per-lap output with the Python cursor semantics (`keys` order, slices
    clipped like Python slices, `DriverAhead` codes cast to int32 with
    wrapping, `json`/`cats` values converted to Python objects).
  Anything it does not recognise is an `Err`: an encoding or dtype the encoder
  does not write, a non-boolean `delta`, a float lap number, a column listed
  twice, a channel listed twice in a lap's `arrays`, an array size larger
  than the body could hold (8 x body bytes: every sample takes at least one
  byte, so a larger size is a corrupt header, not an allocation to attempt),
  any length mismatch. Nothing indexes out of bounds on a malformed body.
- `native/src/lib.rs`: `tif1_native.tel_decode_file(body, dict_factory=None)
  -> {lap: tel}`. The decode runs in `py.detach` (GIL released); only the
  result objects (one dict per lap, one numpy array per channel copied with
  `PyArray1::from_slice`, `dict_factory(codes, categories)` for
  `DriverAhead`, the JSON values) need the interpreter. Any `Err` becomes a
  `ValueError`.
- `native/src/telcols.rs` (same bits, faster):
  - the spline is split into `Basis::new(xd, xe)` (knots, collocation matrix,
    elimination, each target's interval and B-spline values: everything that
    depends on the dates only) and `Basis::evaluate(yd)` (the right-hand side
    elimination, back substitution and evaluation), with the original
    operations in the original order; `spline_lap` (the `tel_spline` kernel
    the Python decoder calls) is `Basis::new(..).evaluate(..)`. The
    whole-file decoder keeps the last basis per lap and reuses it when the
    next spline column's point rows in that lap are the same rows over the
    same dates: `x`/`y` share 98.7% of the race's laps, `x`/`z` 94% (the
    qualifying 75% / 58%).
  - `apply` is branch-free (a zero distance maps the key back to the same
    bits: `ordered` is an involution).
  - `lateral`'s `numpy.unwrap` calls libm `fmod` only when `|dd + pi| >=
    2 pi`: `fmod(a, b)` is `a` itself when `|a| < |b|` (exact), which is
    nearly every sample.
  - row lists (anchor rows, `interp` rows with their car rows, `integ` rows
    with their previous car row, the remaining rows) are built once per file
    in `Anchors::new`; the columns scatter by index instead of walking masks
    (the masks are ~50/50, so the branchy loops mispredicted on every other
    row).
- `src/tif1/core_utils/json_utils.py`: `NATIVE_TEL_DECODE_FILE` handle
  (None without the function).
- `src/tif1/core_utils/columnar_telemetry.py`: `decode_driver_file` calls
  `NATIVE_TEL_DECODE_FILE(body, DictionaryChannel)` after the zstd step and
  falls back to the column-by-column decoder on `ValueError` (that decoder
  then decodes the file or raises `ColumnarFormatError`, exactly as before).
  zstd stays in Python: `zstandard` releases the GIL (8 threads: 65 -> 8.6 ms
  for the race's 119 frames) and a Rust zstd would be a new crate (the crate
  builds offline with its locked crates only, N7). The reader
  (`async_fetch._load_driver_file`) already decodes each file in a fetch-pool
  thread, so files now decode in parallel.
- `tools/data/encode_driver_telemetry.py --verify`: decodes every file with
  the three decoders (whole-file, column-by-column around the kernels, numpy
  twins) and compares each with the JSON, frames included.
- Tests: `tests/unit/test_columnar_telemetry.py` (+17, skipped when the
  installed tif1-native has no `tel_decode_file`): whole-file == column
  decoder == input on plain laps, fastf1-shaped laps, laps whose `y`/`z`
  point rows differ from `x`'s (no shared basis there), one- and six-sample
  laps with a repeated date, `lerp`, `integ`, arrays writable; six header
  edits the native decoder must decline (big-endian dtype, integer `delta`,
  a column twice, a float lap number, an unknown encoding, a missing
  reference) where the codec then decides (same values or the same
  `ColumnarFormatError`); five malformed bodies. Rust tests: JSON corner
  cases, unshuffle, unpackbits, the two corrupt-header declines.
- Harnesses: `tools/perf/corinth_c8_decode_bench.py` (decode time one-thread
  and in an N-thread pool, `--verify` bit comparison of the three decoders on
  real files); `tools/perf/corinth_c8_cold_local.py` (copy of N7's local
  throttled CDN with `--control-python` and `--same-files`). The Rust test
  `telfile::tests::bench_bodies` (ignored, `TIF1_C8_BODIES=dir cargo test
  --release -- --ignored --nocapture`) prints the time per decoding phase
  (`timed!`, compiled into test builds only).

## 4. Verdict

**SHIP** (whole-file decoder, the kernel speed-ups, tests, harnesses), in
the same tif1-native release that carries N7's kernels.

The decode is 37% less CPU per race on one thread and, the larger effect,
no longer holds the GIL: the fetch pool decodes files in parallel (race
276 -> 74 ms wall in 8 threads). Where decode CPU matters (a fast link) the
cold telemetry loads win on both backends: all_tel −10.9% / −13.5% wall
(8/8 pairs each), `fetch_all_laps_telemetry()` −19% / −20%; notebook4
−3.1% (6/8) / −10.0% (7/8); polars driver_tel −5.5% (6/8), pandas
driver_tel a tie on the wall (phase −7.7%). On an 8 MB/s link the transfer
dominates and the walls tie (polars notebook4 −6.3%, 8/8, is the one win),
with no regression. Decoded laps are bit-identical (1405 laps, three
decoders, frame digests on both backends), parity 0/133 and 0/131, warm
paths untouched.

Against the brief's bar: all_tel passes on both backends at 100 MB/s (≥3%,
8/8), polars notebook4 and driver_tel pass, pandas notebook4 is at the bar
(−3.1%, 6/8), pandas driver_tel does not move the wall (one driver's six
files are ~15 ms of decode). Since the files are not published yet, the
gain lands when the reader is turned on; it removes most of the CPU cost N7
measured against v1 (N7: v1 273 ms per race, v2 472 ms; v2 is now ~298 ms on
one thread here, and parallel).

## 5. CHANGELOG

- A `tel.v2` columnar telemetry file now decodes in one tif1-native call,
  `tel_decode_file`: the header, the byte planes, the value encodings, the
  predictions and the residuals are decoded in Rust with the GIL released,
  instead of a column-by-column numpy decoder around the prediction kernels.
  The decoded laps are the same bits. One thread decodes the 2025 Bahrain race's
  119 files in ~315 ms instead of ~490 ms (qualifying: 165 instead of 238),
  and because the GIL is free the fetch threads decode files in parallel:
  8 threads take ~80 ms for the race instead of ~330 ms. The prediction
  kernels got faster too, with identical results: the quadratic spline's
  date-only work is shared between `x`, `y` and `z` when their points match
  (98.7% of the race's laps for `x`/`y`), the residuals are applied without
  branches, and `numpy.unwrap`'s remainder skips `fmod` when it cannot
  change the value. On a 100 MB/s local CDN a cold
  `fetch_all_laps_telemetry()` takes 2.48 s instead of 3.07 s with pandas
  (process 4.02 s instead of 4.51 s) and 2.35 s instead of 2.92 s with
  polars; on an 8 MB/s link the transfer still dominates (no change). Without `tel_decode_file` the
  column decoder is used as before.

## 6. Notes for the integrator

- **Release order is unchanged from N7**, with one more function in the
  same unreleased tif1-native 0.3.0: `tel_decode_file` ships with the six
  kernels (no new crate, no new Python dependency). The reader's gate stays
  `native_columnar_decoder_available()` (the six kernels); a build with the
  kernels but without `tel_decode_file` (none was released) decodes column
  by column as before. The CI `native` job runs the 17 new tests with the
  extension built from the commit; the main venv (tif1-native 0.2.1) skips
  them.
- **Where it pays.** Cold telemetry waves on fast links: the decode used to
  be GIL-bound CPU in the fetch-pool threads, competing with the main
  thread's frame building and with each other; now 8 threads decode the race
  in ~80-90 ms of wall instead of ~330-500. On an 8 MB/s link the transfer
  hides the decode either way (ties). Warm sessions never read the files.
- **Not done: zstd in Rust** (the hypothesis listed it). `zstandard`
  already releases the GIL and runs libzstd; a Rust zstd would add a crate
  (`zstd-sys`) for the ~10 us `bytes()` copy and one Python call per file.
- **Exactness is by construction plus verification.** The Rust decoder
  mirrors the Python one operation for operation; the predictions are the
  same `telcols` code the column decoder calls; the cached spline basis runs
  the same operations on the same inputs. Verified: 0 differing laps of 1405
  (race + qualifying) against the column decoder and the numpy twins
  (`corinth_c8_decode_bench.py --verify --numpy`), the encoder's `--verify`
  with all three decoders and the pandas/polars frames, and the cold
  harness's frame digests on both backends. Any layout the Rust side does
  not take falls back to the Python decoder (tests pin six such edits).
- **Remaining decode CPU** (race, Rust phase timer, one thread, ~2.6 ms per
  file): spline ~35% (basis build ~45%, evaluation ~35% of it; the back
  substitution is a division chain that cannot be reordered without changing
  bits), `lat` ~20%, the header JSON ~5%, anchors ~5%, the rest small.
  Further CPU cuts would need either a format change (e.g. storing the spline
  basis inputs differently) or SIMD that keeps the operation order; neither
  is needed for the wall: the decode is now parallel.
- **Qualifying gains less per file** (one-thread 6.6 -> 4.8 ms): its laps
  are longer (up to 12.5k rows: out/in laps) and share fewer spline bases
  (x/y 75%, x/z 58% of laps). Partial sharing (bases differing in a few
  points) was not attempted.
- **Panic safety**: a Rust panic would surface as `PanicException`
  (BaseException), which the reader's `except Exception` would not catch;
  the decoder indexes only within checked bounds and declines oversized
  headers before allocating. A fuzz pass over random header edits would be a
  cheap follow-up.
- **Commits**: `git commit` was denied in this sandbox; everything is
  staged and `C8_COMMITS.md` lists the three intended commits.
- **Harness**: both cold arms ran on private venvs over the main venv's
  packages (same interpreter): the control (552c357) on
  `/tmp/corinth/venv-C8-base` with tif1-native built from the control's
  `native/` (N7 kernels), the candidate on `/tmp/corinth/venv-C8` with
  tif1-native built from this tree. Same files for both arms (`--same-files`:
  the format did not change; 153 files, 15.30 MB).
