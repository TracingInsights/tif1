# Corinth C4: current-season freshness (schedule and Ergast TTL refreshes)

## 1. Hypothesis

A current-season script (`get_session(2026, event, "R")`, `.laps`, `.results`)
is nearly 3x slower once the cached calendar and Ergast files are older than
their TTLs (`schedule_ttl_hours`, `ergast_ttl_hours`, both 6 h) than when
they are fresh. A cold run is slow too. The idea was to trace the refresh
requests and keep them off the critical path. The options were: refresh only
what the call needs; send no request where the data provably cannot change;
send conditional requests; overlap or defer the refresh. Every answer must
stay equal to the control's.

## 2. What the trace showed (`tools/perf/corinth_c4_trace.py`)

Pandas, 2026 Mexico City GP (round 19, the latest race), control tree:

| state | get_session | laps | results | total |
| :--- | ---: | ---: | ---: | ---: |
| warm | 346 | 3 | 14 | 370 |
| TTLs expired | 835 | 2 | 152 | 996 |
| cold | 1022 | 40 | 145 | 1215 |

- **Expired `get_session` (+490 ms).** The calendar is served stale, and its
  refresh already runs in a background thread (Thebes TH7). That thread does
  three things through niquests, all under the GIL while the main thread
  imports pandas:
  - it imports niquests (~120-145 ms of CPU);
  - it builds the session and restores OCSP verdicts;
  - its revocation check downloads and parses a **246 KB Let's Encrypt
    CRL** (`yr1.c.lencr.org/57.crl`) for raw.githubusercontent.com, about
    200 ms.

  The main thread loses ~0.5 s. The refresh itself usually never finished
  before the script exited (still at the CRL when the process ended), so
  the next script paid it all again.
- **Expired `results` (+140 ms).** The Ergast prefetch thread fetched
  `stats/2026/events.json` (the season index, needed only to map round to
  folder slug) and then `results.json`, one after the other, through
  niquests (a new TLS connection plus an OCSP POST).
- **Cold `get_session`.** The same niquests import and CRL run on the main
  thread before the pandas import starts (`get_session` blocks on the
  calendar fetch).

Conditional requests: both hosts honour `If-None-Match` and answer 304
(raw.githubusercontent.com with a strong ETag and a 5-minute cache;
jsDelivr `@main` with a weak ETag and `s-maxage=43200`). The bodies are
small, though: the calendar is 10 KB (~3 KB gzipped) and parsing plus
converting it costs 0.64 ms; a Stats `results.json` is 3 KB. So a 304 would
save ~1 ms in a background thread. The cost is the connection, not the body.
I did not implement conditional requests: the transport protocol would
need a new method for no measurable gain.

Finality, from the data. I read the GitHub commit history of the Stats
repository for every 2026 round's `results.json` (19 rounds) and for six
`quali_results.json`/`sprint_results.json` files. Each file has **exactly
one commit**, written 0-22 days after the race (Miami 22 d, China 14 d,
most within one day), and none was ever rewritten. 2025 Mexico shows the
same: one commit, the day after the race.

## 3. What changed

1. **`first_wave.ensure_client()`** (`src/tif1/first_wave.py`): the stdlib
   `http.client` + `ssl` client of the Elis E2 first wave (same `wassima`
   roots, User-Agent, gzip) is built on demand, once per process, on the
   calling thread. `NiquestsTransport.get_json` (`payload_loader.py`) sends
   single requests over it whenever no niquests session exists. Before, it
   did this only when a first wave had run.
   - **What this covers:** the calendar fetch of a cold `get_session`, the
     background calendar refresh, and the Ergast Stats refreshes. None of
     them imports niquests or downloads the CRL any more.
   - **Fallback:** any answer other than a `200` with a JSON object still
     goes to niquests, and `cdn_first_wave=False`, a proxy or a missing
     `wassima` keep niquests for everything.
   - **Reuse:** the first wave reuses the client (`_build_client`), so a cold
     load builds the TLS context once instead of twice.
   - **Tests:** the unit suite turns it off (`first_wave._on_demand`, conftest),
     because its sockets are blocked.
   - **Security:** these requests skip niquests' revocation check, like every
     first-wave request already does (documented in `config.mdx` and
     `environment-variables.mdx`).
2. **Settled classifications** (`ergast/payloads.py`,
   `is_settled_classification`). A current-season Stats file is permanent,
   like a past season's, when all of these hold:
   - it is `results.json`, `quali_results.json` or `sprint_results.json`;
   - it is one round's file and holds rows;
   - it was fetched at least 14 days after that round's race started. 14 days
     is the FIA right-of-review window, and the commit history above shows
     the files are never rewritten.

   The latest round (Mexico: 5 days) keeps `ergast_ttl_hours`, as do
   missing or empty files (the repository adds some files up to 3 weeks
   late), laps, pit stops, standings and every Jolpica answer.
3. **Stored season index for finished rounds** (`ergast/stats.py`,
   `StatsSource.settled_round`). Suppose `events.json` was fetched after a
   round's race had started. That round's number, name and folder can no
   longer change, so one-round lookups (`rounds(season, r)`, `round_info`,
   `file`) answer from the stored index even past its TTL. A round that was
   still ahead when the index was fetched refreshes the index, and so does
   a round missing from it or any season-wide lookup.
   `Session._resolve_cached_ergast_payload` checks `season_index_stored`
   instead of `season_index_cached`, so a warm session with a stale index
   resolves a settled round inline, without a thread.

Docs: `docs/api-reference/ergast.mdx` (freshness table),
`docs/api-reference/config.mdx` and
`docs/reference/environment-variables.mdx` (`cdn_first_wave`), all
STE-checked with 0 violations. `AGENTS.md` is updated. Tests:
`tests/unit/test_ergast_current_season_freshness.py` (10) and 5 new
`test_first_wave.py` tests.

## 4. Measurements

Harness: `tools/perf/corinth_c4_ab.py`, my extension for this flow. It
interleaves control (`/tmp/corinth/control/src`) and candidate in ABAB
order, one fresh interpreter per run, running `current.py`'s script. Both
arms share one cache copy (`/tmp/corinth/home-C4/cur`, a copy of
`/tmp/corinth/cur` with the 2026 British GP added).

The states:
- **warm:** every TTL'd row (the f1schedule calendar, `stats/2026/*`) is
  marked fetched 60 s ago before each run.
- **expired:** the same rows are marked fetched 7 h ago, which is what a
  script pays 6 h after the last refresh. I used this instead of `TTL=0`
  because with `TTL=0` a refresh that lands is stale again at once, so the
  calendar refreshes twice per run.
- **expired_offline:** the expired state with `TIF1_OFFLINE_MODE=true`.
- **cold:** an empty cache per run, live CDN.

## 5. Verdict: SHIP

The expired state wins 14-44% of the whole-process wall: pandas 7/8 and
8/8 pairs, polars 5/8 (in-process 8/8) and 7/8. The cold state wins 29-48%,
6/6 on every arm. The latest round still refreshes every `ergast_ttl_hours`
and the calendar every `schedule_ttl_hours`. A round's classification is
kept only once the commit history shows it cannot change, so every answer
matches the control's. The schedule refresh now actually lands within a
short script (~0.1 s instead of never).

## 6. CHANGELOG

- Current-season scripts no longer pay for refreshes of the cache. The
  calendar fetch on a cold `get_session()`, its background refresh after
  `schedule_ttl_hours`, and the Ergast Stats refreshes after
  `ergast_ttl_hours` now use the standard-library HTTPS client of the cold
  first wave whenever niquests is not loaded. Through niquests they paid its
  import and a 246 KB certificate revocation list for raw.githubusercontent.com
  (~0.5 s under the GIL beside the pandas import); the refresh also used to
  die with short scripts. A round's Stats classification (results,
  qualifying, sprint) fetched 14 days or more after the race is now kept
  permanently, like a past season's: every 2026 round's file was written
  once and never changed. A one-round lookup of a finished round no longer
  re-fetches the season's `events.json`. 2026 race script
  (`get_session`, `laps`, `results`), whole process: 6 h after the last
  refresh, pandas 1145 → 854 ms on the latest round and 897 → 582 ms on an
  earlier one (polars 764 → 659, 918 → 514); cold, pandas 1717 → 922 ms and
  polars 1140 → 593 ms. Warm and offline runs are unchanged, and the
  answers are identical.

## 7. Notes for the integrator

- **Security trade-off, widened.** Before, only a cold load's first wave
  and its follow-ups skipped niquests' revocation check. Now every single
  sync request of a process without a niquests session does: the calendar
  and the Ergast/Jolpica refreshes of warm sessions. The chain and host
  name are still verified against the same roots. `cdn_first_wave=False`
  restores niquests for all of them, and the docs say so. Review this
  against the maintainers' stance on N1-style "process-wide" decisions.
- **`cdn_preconnect=False`** no longer means "no stdlib requests": the
  on-demand client ignores it (the docs now say the cold-load part depends
  on it). Gate the client on `cdn_preconnect` too if that matters.
- **Jolpica 429s.** A non-200 on the stdlib path is retried through
  niquests (the existing bridge behaviour), so a Jolpica 429 now costs one
  extra request in processes without niquests. Before, this happened only
  after a cold first wave.
- **The settled rule.** It relies on the Stats generator writing a round
  once. If the generator ever starts rewriting old rounds (a correction
  regenerated weeks later), a session fetched in between keeps the old
  rows until `tif1 cache-clear --ergast`. That is the same exposure past
  seasons already have. `SETTLED_AFTER_SECONDS` is the single knob.
- **Not done.** Cold `results` (now ~70 ms) still runs `events.json` and
  `results.json` in series on a cold cache, because the slug comes from the
  index. Fetching both in parallel would need the slug before the index:
  `race_slug(event name)` agrees with the index for 19/19 2026 rounds, but
  the repository's renamed races ("bahrain-grand-prix-in-malaysia") make it
  a guess. Conditional requests were measured as worthless here (§2).
- Cold `laps` gives back 10-40 ms of the cold `get_session` gain (§4).
  Starting the first wave before the calendar fetch is impossible: its URL
  needs the resolved event name.
