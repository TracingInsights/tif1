# C3. The Ergast interface (`tif1.ergast`), cold: report

## 1. Hypothesis

A cold `Ergast().get_*` query (fresh process, empty cache, live CDN) pays a
chain of serial costs that do not depend on each other: `import pandas` (~390
ms, done by `tif1.ergast.interface` at import, before the query is known),
then the niquests import and its OCSP-checked handshake for the season's
`{year}/events.json` (381 ms traced on `get_race_results(season=2024)`), then
only once the slugs are known the per-round Stats files (~230 ms for 24
files), then ~50 ms of frame building. The network work can overlap the
pandas import, skip niquests (the stdlib first-wave client already does that
for session loads), and fetch `events.json` and the round files in one wave
(the slugs are predictable from the packaged copy of `events.json`). Parity:
the answers stay identical.

Trace of the control (`tools/perf/corinth_c3_trace.py race_results_2024`,
pandas imported before the query by the module import):

```
query 670 ms
    8.9 ->  390.4 (381.5) MainThread  .../Stats@main/2024/events.json
  392.2 ->  530.5 (138.3) pool        .../2024/bahrain-grand-prix/results.json
  ... 20 workers, 24 files, the last two start after the first batch ...
  482.7 ->  620.9 (138.2) pool        .../2024/abu-dhabi-grand-prix/results.json
  (frame build to 670)
```

Candidate, same query, pandas pre-imported so the network is visible:
`events.json` and all 24 round files start together 61 ms into the query
(34 ms of that is the stdlib TLS context: `wassima` import 16, CA bundle 9,
`ssl` context 9) and end by ~145 ms; query 260 ms instead of 583.

## 2. What changed

- `src/tif1/ergast/frames.py` (new): `ErgastResultFrame`, `ErgastResultSeries`,
  `ErgastSimpleResponse` (the pandas subclasses) moved out of `interface.py`
  unchanged. `interface.__getattr__` resolves them (and caches them in the
  module globals), their `__module__` stays `tif1.ergast.interface`, so the
  public paths, reprs, `isinstance` checks and pickles are the same. `from
  tif1.ergast import Ergast` no longer imports pandas.
- `interface._execute_overlapped`: when the frame modules are not imported yet
  (pandas; plus polars and pyarrow for `result_type="polars"`) and the plan is
  routed to Stats (`router.routes_to_stats`, a static check), `execute(plan)`
  runs in a daemon thread (`contextvars` copied) while the calling thread
  imports through `lazy_import.import_promoted` (Naxos N10: GC suspended,
  survivors promoted). The answer or the exception comes back unchanged. A
  Jolpica-routed plan, or a runtime without threads, imports first and then
  fetches (the order of the module-level import it replaces). With the
  modules already imported, everything runs inline as before.
- `first_wave.standalone_client()`: the wave's stdlib client when a wave ran,
  else one of its own built once per process (same `_tls_context`, trust
  store, User-Agent, gzip). It is kept apart from the wave's `_client`, so an
  Ergast query never opens the session telemetry bridge (`bridge_open`),
  whose niquests hand-over needs the wave's URLs. `reset()` clears it.
- `ergast/payloads._stdlib_get_json`: for the production `NiquestsTransport`
  while niquests has no warm session, with `cdn_first_wave` on, outside
  Pyodide, a Stats file goes over the standalone client: `200` with a JSON
  object is the answer, `404` raises `DataNotFoundError`, `403` raises
  `NetworkError(status_code=403)` (what `try_sources_repo` walks past, as
  niquests reports them), anything else (a redirect, another status, a
  transport error, a non-object body) is asked again through the transport
  (niquests). The mirror walk, the retry/backoff, the 403 pause and the cache
  rules of `_fetch_stats` are unchanged. Jolpica requests stay on niquests
  (429 `Retry-After` handling).
- `ergast/router._prefetch_cold_season` + `_predicted_files` +
  `StatsSource.packaged_index`: when `{season}/events.json` is not fresh in
  the memo/SQLite tiers, the round files the handler will read are predicted
  from the packaged Ergast schedule (`tif1.events._load_vendored_ergast_year`:
  round, `raceName` -> slug, dates for the `completed()` filter, `Sprint`
  key, circuit id) and fetched together with `events.json` in one
  `stats_payloads` call (the existing thread pool, memo and SQLite write-back).
  The handlers then run unchanged and find the files in the memo. The
  prediction mirrors each handler: the selected rounds' files for
  results/qualifying/sprint (and `constructors`, and `races`/`circuits` when
  they filter on results), the round's file for laps, pit stops and a round's
  standings, the last started round's file for season standings (the first
  probe of `last_completed_round`). Skipped offline, inside `cache_only()`,
  without threads, when there is no packaged copy. The answer always comes
  from the fetched `events.json`: a renamed race costs one wasted request
  (its "missing" verdict is cached under its own key) and the handler fetches
  the right slug as before. If `events.json` itself failed (no cached copy),
  that error is raised directly instead of walking the mirrors a second time.
- Tests: `tests/unit/test_ergast_cold_path.py` (21 tests): no pandas on
  `import`/`Ergast()` in a fresh interpreter, class paths and pickling, the
  overlap (thread names, exception identity), inline Jolpica/raw plans and
  their import-then-fetch order, `routes_to_stats`, `_predicted_files` per
  endpoint, the packaged slugs (São Paulo), one wave on a cold season and none
  on a warm one, a mispredicted slug, a failing `events.json` walked once, no
  wave offline, the stdlib statuses, the mirror walk over the stdlib, the
  standalone client (built once, never opens the bridge, reuses the wave's
  client, a missing trust store tried once).
- Docs: `AGENTS.md` (Ergast tier and HTTP bullets), the `first_wave` module
  docstring.
- Harness: `tools/perf/corinth_c3_ergast_ab.py` (new; interleaved
  fresh-process A/B of ten Ergast queries, cold = new empty cache per run and
  live CDN, warm = one primed cache per arm offline, `--pre-import pandas` for
  the notebook shape; digest per answer: class, module, columns, dtypes,
  index, values, `source`, `total_results`, `is_complete`, for multi
  responses the description and every content frame; exits 1 on a digest
  difference) and `tools/perf/corinth_c3_trace.py` (per-request timeline of
  one cold query, niquests and stdlib requests).

### What was measured and dropped along the way

- Overlap alone, with the query on niquests: cold walls only -3..-5% (3
  queries, 3 pairs). The niquests import and handshakes in the query thread
  compete with the pandas import for the GIL. The stdlib client is what makes
  the overlap pay.
- Overlapping a Jolpica-routed query (niquests in the thread) with the
  pandas import: `driver_info_2024` 842 -> 1361 ms wall; its request took 803
  ms instead of 310 (GIL convoy plus import-lock contention). Jolpica plans
  now run inline.
- Running the Jolpica plan inline but fetching before the import (the
  lazy order): polars `driver_info` 2150 -> 2309 (1/5). Importing first
  through `import_promoted` gives 899 -> 890 polars and 851 -> 836 pandas.
- Earlier full runs, before the last two fixes: `C3_cold_pandas_v1.json`,
  `C3_warm_pandas_v1.json` (high load, kept for the record).

## 4. Verdict: SHIP

Every Stats-routed query is 34-46% faster cold on pandas (wall, 5/5 pairs
each; e.g. `get_race_results(season=2024)` 1084 -> 638 ms) and 28-39% faster
on polars (5/5 each). The notebook shape (pandas already imported) cuts the
query itself by 55-69% (583 -> 261 ms). The Jolpica-routed query is even
(-1..-2%), warm is neutral to slightly better, and parity is exact on every
digest, the session surfaces and the fastf1 compliance test.

## 5. CHANGELOG

- Cold `tif1.ergast` queries are 34-46% faster (pandas, fresh process, empty
  cache; `get_race_results(season=2024)` 1084 -> 638 ms,
  `get_qualifying_results(2023, 5)` 799 -> 487 ms; polars results 28-39%).
  `from tif1.ergast import Ergast` no longer imports pandas. A query answered
  from the Stats repository fetches while pandas (and polars/pyarrow for
  `result_type="polars"`) imports. Its files go over the standard-library
  client the session first wave uses instead of importing niquests, with the
  same trust store and the same OCSP trade-off; `cdn_first_wave=False` turns
  this off. When a season's `events.json` is not cached, it is fetched in one
  parallel wave with the round files the query reads, predicted from the
  packaged schedule. With pandas already imported, the query itself is
  55-69% faster (583 -> 261 ms for a season of race results). Answers are
  unchanged.

## 6. Notes for the integrator

- **Security trade-off, widened slightly.** Stats files of a cold Ergast
  query now skip niquests' OCSP check, as the session first wave already
  does (chain and host name are still verified against the same `wassima`
  roots). `cdn_first_wave=False` sends them through niquests again. Jolpica
  is untouched.
- **A 404/403 over the stdlib is final for Stats files.** For the session
  transport (`NiquestsTransport.get_json`), `test_first_wave.py` pins that a
  non-200 single request goes to niquests. The Ergast loader does not reuse
  that seam: it has its own `get_json` that treats 404/403 as the refusals
  the mirror walk expects, so a missing Stats file does not import niquests.
  Anything else still goes to niquests.
- **The overlap thread** is a daemon thread named `tif1-ergast-query`. Its
  exception is re-raised in the caller as the same object; the traceback
  shows the worker frames. `cache_only()` and other context variables are
  copied in. Only Stats-routed plans with pandas not yet imported take it.
  A Stats miss that falls back to Jolpica inside the thread still overlaps
  (rare; it measured slower in the Jolpica case above).
- **Speculative files.** If the Stats repository renames a race after the
  packaged schedule was vendored, a cold query pays one extra request (two
  mirrors, both 404) for the stale slug and caches a "missing" verdict under
  that key. Re-vendoring (`tools/vendor_ergast_schedules.py`) removes it.
  The current season's packaged copy can lag. Only rounds whose packaged
  race date has passed are predicted, so a moved race is at worst one wasted
  request or one round fetched after `events.json`, as before.
- **Fan-out width** stays `max_concurrent_requests` (20). A 24-round season
  plus `events.json` runs as 20 + 5. On the stdlib client each concurrent
  request is its own TLS connection; the second batch reuses kept-alive
  ones (~30 ms). Not tuned (DO_NOT_RETRY: concurrency above 22 for telemetry).
- **Follow-up, not done: a polars-native build of the Ergast frames.**
  `result_type="polars"` still builds the pandas frame and converts it
  through pyarrow, so a polars user pays the pandas and pyarrow imports
  (~450 ms of a ~650-860 ms cold query). Building directly from
  `structure.flatten_rows` would have to reproduce pandas' inference plus
  `pl.from_pandas` exactly (None -> NaN -> null in int columns, datetime and
  duration units, mixed columns). That is a parity project of its own.
- **Follow-up: the post-network build** of `race_results_2024` is ~50 ms warm
  (`flatten_rows` 50%, 25 small `DataFrame` constructions 50%). It now sits
  on the critical path after the pandas import.
- `fastf1` and its deps in `/tmp/corinth/venv-C3` (284 MB) only serve the
  compliance test. Delete it if disk is short.
