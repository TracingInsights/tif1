# E4. `fetch_all` output page faults: decompress into huge-page buffers (tif1-native)

Branch `perf/elis-E4`, worktree `/tmp/tif1-elis/E4`, measured against the
frozen control (b5b91ed) on 2026-11-03. Private venv `/tmp/tif1-elis-venv-E4`
(the main venv's exact package versions, `.agents/perf-elis/E4_venv_requirements.txt`,
plus the tif1-native 0.2.1 wheel built from this branch).

## 1. Hypothesis

A warm `fetch_all_laps_telemetry()` decompresses the race's 20 pandas driver
rows (70 MB of lz4) into 123 MB of fresh memory. The kernel zero-fills that
memory one 4 KB page fault at a time: ~31 000 minor faults and ~80 ms of
system time across the 8 decompression workers. THP is `madvise`-only on this
box, and neither pyarrow's codec nor python-lz4 can decompress into a buffer
the caller owns. A tif1-native entry point that decodes an lz4 frame into a
caller buffer, fed with `MADV_HUGEPAGE` anonymous mappings, should cut the
faults ~20x and shorten `all_tel`, the notebook's lap loop and `car_data_loop`.

## 2. What changed

- `native/src/lz4.rs` (new) and `native/src/lib.rs`: `lz4_frame_decompress_into(src, dst) -> int`.
  It parses the lz4 frame header (rejecting the legacy format, checksums
  and dictionary ids as "unsupported"), walks the blocks, and decodes each
  block straight into `dst`. A linked block uses the previous 64 KB of output
  as the dictionary (`lz4_flex::block::decompress_into_with_dict`). Stored
  blocks are copied as they are. The GIL is released through `py.detach`, and
  the buffers come in through the buffer protocol (`PyBuffer<u8>`, which abi3
  supports from 3.11). The function checks the content size, writes nothing
  past the content (a larger `dst` keeps its tail), and raises `ValueError`
  for a destination that is too small, read-only or non-contiguous, and for
  corrupt frames.
  `native/Cargo.toml`: crate 0.2.1 (a compatible addition, still inside the
  `tif1-native>=0.2,<0.3` marker), new dependency
  `lz4_flex = 0.11` (default features off, `std` + `checked-decode`; pure Rust, no C, no platform code).
- `src/tif1/core_utils/json_utils.py`: keeps the imported `tif1_native` module
  and exports `NATIVE_LZ4_DECOMPRESS_INTO` (None without the extension, with
  0.2.0, or with `TIF1_DISABLE_NATIVE=1`).
- `src/tif1/cache.py`:
  - `_huge_page_rows_enabled()`: probed once per process. It needs the native
    function, a non-emscripten runtime, `mmap.MADV_HUGEPAGE`, and a THP
    setting that is not `[never]`.
  - `_huge_page_buffer(size)`: maps `MAP_PRIVATE | MAP_ANONYMOUS` with a size
    of `ceil(size / 2 MB) * 2 MB + 2 MB`, then returns a `size`-byte
    `memoryview` that starts on a 2 MB boundary, after `madvise(MADV_HUGEPAGE)`
    on the rounded span. Whatever alignment the kernel picks, every page of
    the row can be a huge page; the unaligned head is never touched. The
    mapping is unmapped when its last view goes away.
  - `_huge_page_decompress(src, size)` returns the buffer or None, and None
    sends the caller back to the codec path. It is called from
    `_expand_narrow_row` (narrowed rows: every pandas driver row today) and
    from `_decompress_row` (plain lz4 rows), only for rows of at least 2 MB.
    Smaller rows, payload rows and the polars IPC tier keep their paths.
  - The narrow-row widening (`frame_narrow.expand`) and the frame decoder's
    `np.frombuffer` views (`DriverFrameSource`) run unchanged on the
    `memoryview`.
- Tests: `tests/unit/test_elis_e4_huge_page_rows.py` (25 tests, offline). They
  cover: decompress-into equals python-lz4 and pyarrow-codec bytes for linked,
  independent, 256 KB/1 MB/4 MB block and size-less frames; incompressible
  (stored) blocks; a larger destination keeps its tail; too-small (with and
  without a stored size), read-only, checksummed, truncated and scrambled
  frames raise `ValueError` (never crash); a huge-page buffer is aligned,
  writable and of the right size; big plain and narrowed rows land in an
  `mmap`; small rows stay on pyarrow; disabled huge pages, a native rejection,
  a missing extension, THP `[never]` or an unreadable sysfs file, and
  emscripten all fall back.
  The native tests skip on the main venv (tif1-native 0.2.0) and run on the
  private venv.
- `native/README.md`: one paragraph on the new function.
- Probes and harness (`tools/perf/`): `elis_e4_ceiling.py` (the fault
  ceiling: pyarrow vs liblz4-through-ctypes into plain, huge and pre-faulted
  mmaps, plus the native decoder), `elis_e4_alltel_probe.py` (faults, sys/user
  time of a warm `fetch_all`, native vs disabled), `elis_e4_decode_speed.py`
  (serial decode speed of pyarrow vs the native decoder), and
  `elis_e4_warm_ab.py` (a copy of `delphi_warm_ab.py` with
  `--control-python/--candidate-python` and `--control-env/--candidate-env`;
  it uses the Delphi `delphi_warm_bench.py` workloads).

## 3. Measurements

Box: 32 cores, shared with the other Elis agents. `get_session` alone moved
370-470 ms between runs, so read pairs won and in-process phases. Every A/B
ran both arms on the private venv (same interpreter, same packages; the
control tree never calls the new function), so the venv's location (/tmp vs
/home) cannot bias the result.

### Ceiling (`elis_e4_ceiling.py`, 20 race rows decompressed + widened on 8 threads, fresh process, median of 8)

| mode | wall ms | minor faults | sys ms | user ms |
|---|---|---|---|---|
| pyarrow codec (control) | 21.4 | 31 454 | 83.5 | 56.5 |
| liblz4 (ctypes) into private mmap, no madvise | 23.1 | 31 462 | 80.3 | 55.1 |
| liblz4 into mmap + MADV_HUGEPAGE | 16.8 | 1 386 | 29.9 | 53.0 |
| same + MADV_POPULATE_WRITE prefault | 36.3 | 1 485 | 29.9 | 59.7 |
| tif1-native into private mmap | 23.2 | 31 414 | 79.2 | 71.7 |
| tif1-native into mmap + MADV_HUGEPAGE (shipped) | 17.8 | 1 380 | 30.5 | 66.6 |

Python's default `mmap.mmap(-1, n)` is `MAP_SHARED`, which is shmem, and its
huge pages follow `shmem_enabled` (`never`): the first probe run got no
huge pages at all until the map was made `MAP_PRIVATE`. Prefaulting is
slower, because it serializes the zeroing in one call.

### Whole `fetch_all_laps_telemetry()` (`elis_e4_alltel_probe.py`, fresh process, median of 6)

| arm | phase ms | minor faults | sys ms | user ms |
|---|---|---|---|---|
| native (huge-page rows) | 112.4 | 26 504 | 91.5 | 167.8 |
| `TIF1_DISABLE_NATIVE=1` | 149.5 | 57 056 | 141.4 | 157.3 |

All 20 rows take the huge-page path. Per-thread attribution of the remaining
26.6k faults (`RUSAGE_THREAD` around each stage): blob reads 15.5k (the
`blobopen().read()` `bytes`; `sqlite3.Blob` has no read-into),
main-thread decode 9.2k, decompression 1.8k (was ~31k). Peak RSS after
`fetch_all` was 386.6 MB with native and 386.2 MB without, so the 2 MB rounding
costs nothing measurable.

### Decoder speed (`elis_e4_decode_speed.py`, serial, both sessions' 40 rows, 186 MB, best of 7)

pyarrow (C liblz4) 40.8 ms against 66-68 ms for tif1-native, in every
variant: lz4_flex 0.11 and 0.14 with and without `checked-decode`, and a
hand-written prefix-mode decoder with liblz4-style 16-byte wild copies
(safe: 70.9 ms, unsafe fast path: 66.2 ms). The cache state of the
destination does not explain the gap; both arms keep their outputs.
liblz4 is ~1.6x faster on these rows (142k sequences per 3.8 MB, mostly 4-7
byte matches). The hand-written decoder was dropped: it was no faster than
the fuzzed crate. So the shipped path gives back ~10 ms of user CPU per race
(spread over the workers) out of the ~50 ms of system time it saves.

## 4. Verdict: PARTIAL

The mechanism works as predicted. The decompression's page faults drop from
~31k to ~1.4k, the process's faults in `fetch_all` halve (57k -> 26.5k), and
system time falls by a third (141 -> 92 ms). Parity is exact, and the
disabled/missing-extension path is the control's.

It does not clear the bar on wall time. No workload's whole-process wall
improves by 3% in a reliable way: `car_data_loop` -3.2% in one run and -1%
in the next, `all_tel` -1.4% / -2.5% at 9/12 and 6/12. The phase wins are
real but small and noisy under this box's load: `all_tel` -4 ms (9/12) in
the quieter run and -1 ms (7/12) in the louder one, `car_data_loop` -1..-3
ms (8/12 twice). The most consistent is the notebook lap loop, -3..-24 ms at
9-10/12 with the wall not worse. Two things cap the win:

- The fault saving is spread over 8 workers, so ~50 ms of system time
  becomes ~4-5 ms of wall.
- The pure-Rust decoder is ~1.6x slower than pyarrow's liblz4 and hands
  back ~10 ms of that CPU.

What to keep, if the integrator wants it: the whole change. It is exact,
self-contained, falls back cleanly, and gives consistent pairs-won on the
three touched phases. It is also the base for the next lever (see notes).
Do not count it as a headline wall win; ship it only with a tif1-native 0.2.1
wheel release (the Python side is inert with 0.2.0). If adding `lz4_flex`
to the native crate, plus a release of the wheel matrix for single-digit
milliseconds, is not worth it, rejecting is defensible too. The measured
numbers above stand either way.

## 5. CHANGELOG paragraph

- Warm pandas sessions decompress the frame tier's driver rows into
  huge-page buffers when `tif1-native` 0.2.1 is installed on Linux.
  `tif1_native.lz4_frame_decompress_into` decodes a row's lz4 frame with the
  GIL released into an anonymous private mapping advised `MADV_HUGEPAGE` (2 MB
  pages). The 123 MB a race's 20 rows decompress to used to be zero-filled one
  4 KB fault at a time. Fresh process, 2025 Bahrain race:
  `fetch_all_laps_telemetry()` takes ~1 400 decompression page faults instead
  of ~31 000 (57 000 -> 26 500 for the whole call), with 92 ms of system time
  instead of 141 ms across the workers. Phases: `fetch_all_laps_telemetry()`
  90 -> 86 ms, the notebook's `iterlaps()` telemetry loop 142 -> 139 ms,
  per-lap `get_car_data()` over a driver 29 -> 26 ms. Rows under 2 MB,
  Windows, macOS, Pyodide, THP `never`, older wheels and
  `TIF1_DISABLE_NATIVE=1` keep the pyarrow codec.

## 6. Notes for the integrator

- Release: the Python side is a no-op until a tif1-native 0.2.1 wheel is
  published (`native.yml`, manual dispatch). 0.2.1 stays inside the
  `>=0.2,<0.3` marker, so `pyproject.toml` and the marker test are unchanged;
  bump the floor to `>=0.2.1` only if you want to require it. No new
  platform code in Rust: `madvise` lives on the Python side, behind
  `hasattr(mmap, "MADV_HUGEPAGE")`, `IS_EMSCRIPTEN` and the sysfs read.
  `lz4_flex` is pure Rust and builds on every target of the wheel matrix.
  CI's `native` job will run the 25 new tests (they skip elsewhere).
- Safety: the Rust side has no `unsafe` beyond turning the two buffer-protocol
  exports into slices inside `detach`. The exports are held for the call.
  Python callers in tif1 always pass a freshly mapped buffer nobody else
  sees. A caller that mutated `dst` from another thread during the call would
  race, as with any `readinto`.
- Memory: rows are rounded up to whole 2 MB pages (avg ~1 MB touched slack per
  row). Peak RSS of a `fetch_all` was unchanged in the measurement (386.6 vs
  386.2 MB), probably because the control path's glibc arenas keep similar
  slack. Each row is one mapping (20 per race, 40 for race + quali, far below
  `vm.max_map_count`).
- THP `defrag=madvise` (this box) means a madvised fault may compact memory
  directly. On a fragmented, memory-starved host that can stall a fault.
  The kernel falls back to 4 KB pages when it cannot get a huge page, so
  correctness is unaffected. If that ever shows up, the gate is
  `_huge_page_rows_enabled()`.
- The two remaining fault sources are larger than what this round removed.
  1. Blob reads: 15.5k faults, ~60 MB of fresh `bytes` from
     `blobopen().read()`. glibc gives each worker's first one or two rows
     new pages. `sqlite3.Blob` has no read-into on 3.13, so this needs
     either a native SQLite blob reader (out of scope) or reading in
     fixed-size chunks into a reusable per-worker huge-page buffer and
     decoding from it.
  2. Main-thread decode: 9.2k faults.
- Decoder speed: liblz4 (pyarrow) decodes these rows 1.6x faster than
  lz4_flex or a hand-written prefix-mode Rust decoder (both measured).
  Vendoring liblz4's C source into the crate (the `lz4-sys` crate, which
  needs a C toolchain in the wheel builds) would add ~10 ms of user CPU back
  per race to the win. That is a dependency decision, not tried here.
- `fetch_all_laps_telemetry()` under `load(laps=True, telemetry=False)` in
  the probe (149.5 ms control-equivalent) is slower than the harness's
  `all_tel` workload (90-103 ms). The probe pays the lazy-row registration
  inside the timed call; the harness workload does not. Both show the same
  direction.
- Artefacts: `.agents/perf-elis/E4_ab_pandas.json` (8 pairs, first build),
  `E4_ab_pandas_12.json` (12 pairs), `E4_ab_pandas_final.json` (12 pairs, final
  build), `E4_ab_pandas_disabled.json` (both arms native off),
  `E4_venv_requirements.txt`. Parity digests are in `/tmp/E4_parity_pandas.json`
  and `/tmp/E4_parity_polars.json`. The wheel is in
  `/tmp/tif1-elis/E4/wheels/` (untracked).
