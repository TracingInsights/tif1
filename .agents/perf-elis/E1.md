# E1: Lazy telemetry in `load()`: result

Branch `perf/elis-E1`, control is b5b91ed (Delphi). Verdict: **SHIP as opt-in**
(`telemetry="lazy"` and the `load_telemetry_lazy` key, default False). I recommend
**not** flipping the default this round (see section 6).

## 1. Hypothesis

A cold `session.load()` with telemetry fetches all 1128 lap files of a race (~9 s,
bandwidth-bound) before the script touches a lap. Most notebooks then use a few
drivers. The proposal: `load(telemetry="lazy")` only notes which laps are pending.
The first access of any lap of a driver fetches that driver's laps in one parallel
wave. `fetch_all_laps_telemetry()` fetches the drivers not touched yet in one batch,
exactly as the eager load does. The frames must be the ones the eager load builds,
and warm sessions must be unaffected.

## 2. What changed

- `src/tif1/core.py`
  - `load()` / `load_async()`: a truthy `telemetry` goes through
    `_lazy_telemetry_requested()`. `"lazy"` (case-insensitive) is lazy. `True` is
    lazy when `load_telemetry_lazy` is set. Any other string raises `ValueError`.
    Lazy calls `_register_lazy_telemetry()` instead of `_load_all_laps_telemetry()`.
  - `_register_lazy_telemetry()` runs `_telemetry_load_pending()` first, the same
    warm readers as the eager load (pandas frame-tier rows become D5 sources). So a
    warm pandas lazy load holds exactly what an eager one holds and registers
    nothing. The remaining laps are grouped by driver in laps-row order in
    `Session._lazy_telemetry_refs`.
  - `_ensure_lazy_telemetry(refs)` takes each driver in `refs` off the pending
    table, under an RLock, and fetches all of them in one
    `_fetch_lazy_telemetry_wave`.
    - On a cached session (`_lazy_telemetry_from_cache()`), the second wave also
      takes every driver still pending, as D5's lazy rows do. Without this, a warm
      polars loop over every lap read 19 IPC rows one by one (~20 ms each, polars'
      own reader, no pool): notebook 701 → 1074 ms. With the rule it is 662 vs 660.
    - The CDN path never does this, so cold waves stay per driver.
  - `_fetch_lazy_telemetry_wave(refs)` builds frames the same way the eager batch
    does:
    1. Frame tier first, on a cached session.
    2. Then `_prefetch_telemetry_payloads`: memo, then SQLite payload tier, then one
       `fetch_multiple_async` wave with the eager batch's options (`use_cache`,
       `write_cache`, `validate_payload`, `defer_telemetry_writes=True`).
    3. Then `_frames_from_payloads`, which uses the same `_create_telemetry_df` +
       `_bind_telemetry` as the eager loop.
    4. Then `_schedule_frame_materialization`, the same frame-tier writer.
  - Hooks:
    - `_get_telemetry_df_for_ref` on a memo miss. This serves `Lap.telemetry`,
      `get_car_data`, `PolarsLap`, `Driver.get_fastest_lap_tel` and
      `Session.get_fastest_lap_tel`.
    - `_telemetry_frames_for_refs`, the polars `Laps.telemetry` / `car_data` batch.
  - `fetch_all_laps_telemetry` (sync and async) clears the pending table and
    fetches every memo miss in one batch, as before.
    - The async batch now returns its map in laps-row order whenever frames were
      memoized before it.
    - Before this change, laps touched earlier (lazily, or by any per-lap access in
      control) came first in the dict. The eager map is always in laps-row order,
      so this keeps the lazy map identical to it.
- `src/tif1/models.py`: the pandas merged `Laps.telemetry` path calls
  `session._ensure_lazy_telemetry(refs)` (via `getattr`, so in-memory fakes still
  work) before it reads the memo. After a lazy wave the merged frame is the concat
  of memoized frames, the same path the eager load takes.
- `src/tif1/config.py`: `load_telemetry_lazy` (default False), env
  `TIF1_LOAD_TELEMETRY_LAZY`.
- Tests: `tests/unit/test_lazy_telemetry_load.py`, 24 tests, offline, both
  backends. They cover:
  - no telemetry request at load;
  - one wave per driver, and a second access makes no request;
  - merged telemetry and a two-driver batch are each one wave;
  - `fetch_all` after a touch fetches only the rest, with keys and frames equal to
    eager;
  - per-lap and merged frames equal to eager;
  - the config key, an eager load unchanged, a bad string raises, `load_async`
    lazy;
  - the env var;
  - the cached-session batching rule against the per-driver CDN path.
- Tools, all in `tools/perf/`:
  - `elis_cold_bench.py`: a copy of `delphi_cold_bench.py` that adds
    `notebook_4drivers`, `notebook_lazy`, `iterlaps_all` / `iterlaps_all_lazy`, and
    `--control-workload` so one interleaved A/B can run eager control against lazy
    candidate.
  - `elis_e1_lazy_parity.py`: frame-by-frame eager vs lazy comparison, cold plus
    warm read-back of the caches each run wrote, and `--warm-cache`.
  - `elis_warm_lazy_ab.py`: same tree on both arms, `TIF1_LOAD_TELEMETRY_LAZY` set
    per arm.
  - `elis_e1_import_ab.py`, `elis_e1_warm_wave_probe.py`: probes.

## 4. Verdict

**SHIP (opt-in).** `load(telemetry="lazy")` cuts the cold four-driver notebook from
9.8 s to 3.0 s on both backends (-70%, 5/5 pairs each). Every frame is identical to
the eager load's, and the default (eager) path is unchanged: parity 0/133 and
0/131, warm and cold A/Bs within noise.

The lazy mode's cost is a whole-session lap loop on a cold cache: +6.5%, 0/3.
Because of that, the default stays eager.

## 5. CHANGELOG

- `Session.load(telemetry="lazy")` leaves the telemetry where it is until a lap
  needs it. The first access of any lap of a driver (`lap.telemetry`,
  `get_car_data()`, `Laps.telemetry`, `get_fastest_lap_tel()`) fetches all of that
  driver's laps in one parallel wave. `fetch_all_laps_telemetry()` fetches the
  drivers not touched yet in one batch. The frames, the cache writes and the frame
  tier are the ones `telemetry=True` produces.
  - A cold 2025 Bahrain race notebook that uses four drivers (merged telemetry,
    fastest laps' car data, a four-lap analysis, results) drops from 9.8 s to
    3.0 s on pandas and from 9.9 s to 3.0 s on polars. `load()` itself takes
    0.13 s instead of 8.4 s.
  - A warm polars `load()` drops from 179 ms to 8 ms; the frame tier is read when
    a lap is first touched, and the second touched driver reads all the remaining
    rows in one pooled batch.
  - Touching every lap of a cold session is ~6% slower than the eager load (20
    driver waves instead of one batch), so `telemetry=True` stays eager.
    `load_telemetry_lazy` (env `TIF1_LOAD_TELEMETRY_LAZY`) makes `True` mean
    `"lazy"`.

## 6. Notes for the integrator

- **Default flip: not now.** Four reasons:
  1. The lazy cold worst case (every lap) is +6.5%.
  2. `load()` no longer surfaces telemetry network failures. A lazy wave failure
     appears at the first lap access, where `Lap.telemetry` records it and returns
     an empty `Telemetry` as it does today for per-lap failures.
  3. A user who loads online and then goes offline (a train notebook) expects
     `load()` to have cached everything.
  4. fastf1's `load(telemetry=True)` is eager.

  Flipping becomes attractive if:
  - a cold lazy session keeps fetching the remaining drivers in the background
    after the first wave (a speculative-prefetch idea; measure it against
    DO_NOT_RETRY's "speculative ... prefetch" entries first, those were about warm
    tiers); or
  - the waves of consecutive drivers are pipelined (start driver k+1's wave when
    driver k's lap loop begins). That would remove the worst case.
- `Session.get_fastest_lap_tel()` after a lazy load fetches the fastest driver's
  whole lap set (~0.5 s), not one file (~0.1 s). This is what the hypothesis
  specifies ("first access of any of its laps"). If it matters, exempt that one
  call site with `allow_prefetch`-style plumbing.
- `get_fastest_laps_tels()` (raw payload path) is not hooked. After a lazy load it
  fetches only the fastest laps' files (fewer bytes than a driver wave). Its
  results are built from payloads either way, so values match.
- `fetch_all_laps_telemetry_async` now returns its map in laps-row order whenever
  frames were memoized before the batch.
  - This also normalizes control's behaviour after per-lap accesses; the values
    and keys are unchanged.
  - The map's frame *class* still depends on access history (a touched lap's memo
    entry is the session-wrapped `Telemetry`, an untouched one the bound frame).
    That is pre-existing behaviour in control; the unit test runs the same flow on
    both arms.
- Thread safety: the pending table and the waves run under `_lazy_telemetry_lock`
  (an RLock). Two threads touching the same driver wait for one wave; the second
  finds the frames in the memo.

  updated in this branch. The new value and config key need an entry; use the
