# E3. Persist the OCSP verdict across processes

## 1. Hypothesis

niquests' certificate revocation check (OCSP, on by default since Olympia
H11) costs 120-240 ms in every cold process: before the first request it
imports qh3 and posts to the certificate authority's responder. The answer is
valid for hours to days (`nextUpdate`), and niquests already memoises it per
process in `InMemoryRevocationStatus`, keyed by the SHA-256 fingerprint of
the leaf certificate. If that memo can be pre-seeded, a GOOD verdict
persisted in the SQLite cache lets the next process skip the responder round
trip for the same certificate, with the check still on.

## 2. What changed

The seam exists. `niquests/extensions/revocation/_ocsp/__init__.py`'s
`InMemoryRevocationStatus` supports pickling (`support_pickle()`,
`__getstate__`/`__setstate__`: `{_store: {fp: OCSPResponse.serialize()},
_issuers_map: {fp: Certificate.serialize()}, ...}`). The sync `Session`
creates one lazily in `on_post_connection` only when `session._ocsp_cache is
None` and hands it to every adapter. A cache that is already set is used
as-is. tif1's async fan-out runs on the same shared sync session
(`async_fetch._get_async_session` -> `http_session.get_session`), so there is
one cache to seed.

The probe also found a second, larger-than-expected cost inside the check.
`from qh3._hazmat import ...` (the OCSP code's only qh3 import, a 1-2 ms
extension module) first runs the `qh3` package `__init__`, which imports the
whole QUIC stack: **32 ms of CPU** (`-X importtime`: `qh3` 32.3 ms
cumulative, `qh3._hazmat` 1.0 ms). With `http_disable_http3=True` (the
default since Argos A7), nothing else in a tif1 process imports qh3. With the
check off, a cold load never imports it (verified).

Files:

- `src/tif1/ocsp_cache.py` (new, imported only on the cold path that
  builds an HTTP session):
  - `preload_hazmat()` loads `qh3/_hazmat*.so` under the name `qh3._hazmat`
    with `ExtensionFileLoader`, without the package `__init__` (1.8 ms instead
    of 33 ms). A later `import qh3` (HTTP/3) runs normally and reuses the
    module from `sys.modules` (tested). It is skipped if `qh3` is already
    imported, and any failure falls back to the normal import.
  - `seed(session, cache)` reads the json-tier row `tif1/ocsp_verdicts`. It
    keeps entries whose stored `next_update` is at least 5 minutes ahead and
    whose `saved_at` is under 7 days old, and the row version must match
    (`1:<niquests.__version__>`, so an upgrade drops the row once). Each
    response is decoded and re-validated (SUCCESSFUL, GOOD, `nextUpdate`
    ahead). The survivors are restored with `InMemoryRevocationStatus.__setstate__`
    into `session._ocsp_cache` and the adapters. With no row it imports
    nothing.
  - `persist(session, cache)` takes the session's `__getstate__()`. For
    fingerprints it has not judged yet, it keeps only SUCCESSFUL + GOOD +
    `nextUpdate` at least 5 minutes ahead, and **re-authenticates the signature
    against the issuer** (`authenticate_for`). niquests skips that check for
    private-address peers and behind proxies; such an answer then never
    outlives its process. It merges into the row, keeps the 8 newest entries,
    and writes once per new verdict (a no-op pass otherwise).
- `src/tif1/http_session.py`: `_create_session` calls
  `_prepare_revocation_check` when the check is on (preload, then seed when
  `http_revocation_cache`, the cache and online mode allow). The warm-up
  threads call `persist_ocsp_verdicts` after `done.set()`, so the main thread
  never waits on it. `close_session` calls it too (it uses the already-open
  cache only, so it never re-opens one at exit).
- `src/tif1/config.py`: `http_revocation_cache` (default True,
  `TIF1_HTTP_REVOCATION_CACHE`).
- Docs: `docs/reference/environment-variables.mdx`
  (`TIF1_HTTP_REVOCATION_CHECK` reworded, new `TIF1_HTTP_REVOCATION_CACHE`
  with the security note), `docs/api-reference/config.mdx`,
  `docs/api-reference/http-session.mdx` (STE checker: 0 violations on all
  three), `AGENTS.md`.
- `tests/unit/test_ocsp_cache.py` (24 tests, offline, fake OCSP answers):
  round trip through a fake and the real SQLite json tier; REVOKED / UNKNOWN /
  unsuccessful / expiring / no-`nextUpdate` / bad-signature never persisted;
  persist idempotent and incremental; 8-entry cap keeps the newest; seed skips
  other versions, too-old, metadata-expired, undecodable, re-validates-revoked
  and answer-expired rows; seed never replaces an existing cache; no row means
  no import; a contract test on the real niquests/qh3 surface (catches
  upstream drift, asserts the cap stays under niquests' 10-entry `hold`
  threshold); a fresh-interpreter test that the preload skips the QUIC stack
  and a later `import qh3` still works; the config switches; persist uses the
  open cache only; the warm-up threads persist after signalling.
- `tools/perf/elis_e3_cold_bench.py`: a copy of `delphi_cold_bench.py` with
  three arms per rep, in rotating order: `control` (control tree, empty
  cache), `first` (candidate, empty cache: a first-ever process, which writes
  the row) and `second` (candidate on a cache holding *only* the OCSP row the
  previous `first` run wrote: the previous SQLite file with every row of every
  table deleted except that one). `second` is a returning user meeting an
  event it has not cached: every payload is still fetched cold.
  `tools/perf/elis_e3_ocsp_probe.py`: the single-GET probe below.

Why one SQLite row instead of the frame/payload tiers: the row is ~6 KB of
base64 per entry, read once per cold process (the cache is already open for
`_preconnect_cdn`'s probe) and written at most once per new certificate.

Where the time goes (phase medians). On pandas the gain is in `get_session`
(laps run 1: 657 -> 572; fastest_lap_tel 716 -> 624). `get_session` imports
pandas while the warm-up threads connect, and today the warm-ups' OCSP CPU
(the qh3 import) and responder wait spill past the pandas import. On polars
(lighter import) the warm-ups are still running when the first wave waits on
them, so the gain shows up in the first data phase (`laps` 265 -> 203,
`fastest_lap_tel` 454 -> 337). The `first` arm's gain is the qh3 preload
alone (~30 ms of GIL-held import that ran in a warm-up thread beside the
pandas/polars import). Persisting the row costs it ~2 ms in a warm-up thread
(1.2 ms signature check plus one SQLite write).

## 4. Verdict: SHIP

A returning user's cold process (any session it has not cached, with a
verdict younger than its `nextUpdate`) is 8-17% faster on pandas `laps`
(12/12 pairs over two runs), 10.5% on pandas `fastest_lap_tel` (4/6), and
14-16% on polars (6/6 each). The revocation check stays on. A first-ever
process also gains from the qh3 preload (polars 6/6 and 5/6; pandas 9/12 over
two runs, within noise on the first run). Warm paths and every user-visible
value are unchanged.

## 5. CHANGELOG

- Cold loads keep the certificate revocation (OCSP) check but no longer pay
  for it again in every process. niquests' GOOD answers are kept in the SQLite
  cache (one row, at most 8 certificates, each until its `nextUpdate` and never
  longer than 7 days) and restored into the next process's revocation cache,
  so a certificate checked before skips the round trip to the CA's responder.
  Only SUCCESSFUL, GOOD answers whose signature verifies against the issuer are
  kept; REVOKED and UNKNOWN answers never are. The check also no longer imports
  qh3's QUIC stack: tif1 loads only the `qh3._hazmat` extension it needs (2 ms
  instead of 32 ms). Cold pandas `laps` on a machine that has used tif1 before:
  863 -> 793 ms (6/6 interleaved pairs; a rerun 991 -> 819, 6/6),
  fastest-lap telemetry 1005 -> 900 ms; polars `laps` 685 -> 575 ms,
  fastest-lap telemetry 867 -> 742 ms (6/6 each). `http_revocation_cache=False`
  (`TIF1_HTTP_REVOCATION_CACHE=false`) checks again in every process.

## 6. Notes for the integrator

- **Security trade-off (documented in the env-var and config pages).** A
  process that uses a kept answer finds a revocation only after that answer's
  `nextUpdate` (hours to days; GlobalSign's jsDelivr answer was valid ~11 h
  when measured) or 7 days, whichever is first. That is the validity window
  the CA itself publishes; browsers cache OCSP the same way. Anyone who can
  write the cache directory can forge a kept answer. They could equally
  rewrite every cached payload, so the cache directory's permissions are the
  boundary (the docs say so). Answers niquests accepted without a signature
  check (proxy, private-address peer) are re-authenticated before they are
  written, so they never outlive their process. The issuer certificate used
  for that check is the one niquests used (from the verified TLS chain on
  CPython 3.10+, else AIA), so it is no weaker than niquests' own in-process
  memo.
- **Private niquests surface.** tif1 sets `session._ocsp_cache` and
  `adapter._ocsp_cache` (private attributes) and relies on the documented
  pickling contract of `InMemoryRevocationStatus`. The contract test in
  `test_ocsp_cache.py` fails loudly if niquests changes them, and the row
  version includes `niquests.__version__`. The smallest upstream change that
  would make this a public seam is a `Session(revocation_cache=...)` argument
  (or `Session.revocation_cache` property) accepting a pre-built
  `InMemoryRevocationStatus`.
- **The qh3 shortcut** depends on qh3 shipping `_hazmat` as a top-level
  extension module inside the package directory and on nothing reading
  `qh3._hazmat` as an attribute of the package (searched qh3, niquests,
  urllib3-future, jh2, wassima: none does). A later `import qh3` binds the
  package normally but leaves the `_hazmat` attribute unset on it. If HTTP/3
  is turned back on (`http_disable_http3=False`), qh3 is imported in full at
  that point anyway. Upstream, qh3 could make its `__init__` lazy (or niquests
  could import `qh3._hazmat` without the package), which would remove the need
  for the shortcut.
- niquests' `hold` heuristic (stop checking once the cache holds at least 10
  entries collected less than a second apart on average) would switch the
  check off entirely if a restored cache reached 10 entries, because restored
  entries carry no timings. That is why the row keeps at most 8 (asserted in
  the contract test). tif1 talks to 1-3 certificates (jsDelivr, sometimes the
  Hugging Face and StaticDelivr fallbacks, Jolpica).
- The verdicts are written by the warm-up threads (cold `get_session`) and at
  `close_session`/exit. A process that never warms connections and exits
  without the atexit hooks (e.g. `os._exit`) simply does not persist; the next
  process checks again.
- Possible follow-up: CRL (`should_check_crl`, used only for certificates
  without an OCSP endpoint) has the same pickling seam
  (`InMemoryRevocationList`); the CDNs tif1 uses all publish OCSP, so it was
  not touched.
- Raw results: `.agents/perf-elis/E3_cold_pandas.json`,
  `E3_cold_pandas_laps_rerun.json`, `E3_cold_polars.json`,
  `E3_ab_warm_pandas.json`.
