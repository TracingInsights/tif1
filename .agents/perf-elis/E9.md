# E9. E2 follow-up: hide the bulk wave's niquests start-up, and finish E2

Control: the frozen E2+E3 tree (`/tmp/tif1-elis-control-e9/src`). Candidate:
this worktree (`perf/elis-E9`). The base commit `perf(elis-E9): base: E2 + E3`
holds the inherited work; E9's own changes come after it.

## 1. Hypothesis

With E2, a cold script imports niquests only when a telemetry wave starts. The
import (~90-135 ms of CPU), the session build and the first TLS handshakes
then sit on the critical path of that wave. Control used to hide them behind
the pandas import. Starting the niquests import and connection warm-up
earlier, in a daemon thread, should hide them again: (A) when the first-wave
bodies are handed over (the laps build starts then), or (B) at the first
telemetry access. The laps-only scripts must not lose E2's gain. Part 2
finishes E2: a `cdn_first_wave` knob, the OCSP decision, the docs, and the
`AGENTS.md` notes.

## 2. What changed

### Trigger points measured, and why neither ships

Timelines (`tools/perf/elis_e9_timeline.py`, a returning user's cache that
holds only the OCSP row) and a multi-arm cold bench
(`tools/perf/elis_e9_cold_variants.py`; the arms were selected by a
measurement-only `TIF1_E9_TRIGGER` switch, which is not in the committed
tree) showed this:

- **(B) first telemetry access** gives the import no lead. In the code base,
  the first telemetry access (`_resolve_telemetry_ultra_cold_mode`) is
  0.4-4 ms before the fan-out imports niquests itself. B measured the same
  as control everywhere (laps 642 vs 623, 3/5; fastest_lap_tel 633 vs 678,
  2/5; driver_tel 1507 vs 1509, 2/5).
- **(A) first-wave handover** gives a lead of the laps build and the
  `pick_driver` prelude (~40-80 ms). The import is CPU under the GIL, and the
  main thread does not wait on anything in that time. So the import
  convoys with the laps build: the `laps` phase went from 42-53 ms to 67-76 ms
  in every run. The first version also cost laps-only scripts +83 ms of
  process wall (0/5): at exit, `http_session.close_session` (atexit) waited
  on `_session_lock`, which the warm-up thread held for the whole niquests
  import. That wait is fixed (see below). The rerun had A at laps 655 vs 662
  (3/5), fastest_lap_tel 655 vs 640 (0/5), and driver_tel 1380 vs 1358 (2/5).
  A brings no driver_tel gain, and it costs the laps build: REJECT.

The import's CPU can be hidden only where the main thread waits, and a cold
telemetry script waits mostly *inside the telemetry wave*. That gives the
shipped form:

### The bridge (shipped)

The first telemetry wave starts on the stdlib connections that the first wave
already opened. niquests imports and connects in a daemon thread meanwhile:

- `src/tif1/first_wave.py`
  - `bridge_open()`: True while the wave's client exists and niquests is
    not ready: no shared session yet, or its warm-up is still connecting
    (`http_session.warm_connections_pending()`). It never waits.
  - The first call starts `warm_niquests()`: one daemon thread runs
    `http_session.warm_connections(<first-wave URLs>)`, which imports
    niquests, builds the session (seeding E3's OCSP verdicts) and HEADs two
    connections. The thread does nothing when a session already exists.
    `start()` keeps the wave URLs and timeout for the warm-up, and
    `reset()` clears them. The module docstring gives the new contract and
    the security note.
- `src/tif1/async_fetch.py`
  - `_stdlib_served(...)`:
    - A first-wave URL is handed over from its slot, as in E2. It is never
      re-fetched over the stdlib when the slot failed.
    - Any other URL rides the stdlib connections while `bridge_open()` is
      True (`_stdlib_payload`).
  - Parsing is the same as on the niquests path: telemetry goes through the
    typed `decode_telemetry_payload` under the same `validate_telemetry`
    condition, anything else through `json_loads`.
  - Bridge requests are bounded by `min(timeout, cdn_hedge_max_delay)`
    (4 s). They are not hedged, so a stalled request goes to niquests after
    that, and niquests hedges.
  - Anything but a `200` with a JSON object returns None, and the same
    attempt goes to niquests. So the CDN fallback, 404 / 403 (A11, K9),
    retries, the circuit breaker and hedging are unchanged. Validation, the
    cache write-back and the missing-verdict bookkeeping run as for a
    niquests response.
  - When the bridge closes (niquests warm), the remaining requests of the
    wave and every later wave run on niquests: HTTP/2, hedging, and the OCSP
    check.
- `src/tif1/payload_loader.py`
  - The sync transport now uses the stdlib connections while a niquests
    session is missing *or still connecting*, so a single request never
    waits for a background warm-up.
- `src/tif1/http_session.py`
  - New `warm_connections_pending()`.
  - `close_session()` returns at once when no session exists. It never
    waits for a session that a daemon warm-up is building, which would
    stall an exiting script for the rest of the niquests import.

### E2 loose ends

- **Knob.** `cdn_first_wave` (default True, env `TIF1_CDN_FIRST_WAVE`,
  `config.py`). With `False`, `_preconnect_cdn` runs the Olympia pre-connect
  instead: niquests is imported on the calling thread, there is one warm-up
  HEAD per first-wave path, and every request goes through niquests (and its
  OCSP check). There is no stdlib wave and no bridge. It is independent of
  `cdn_preconnect`. With `cdn_preconnect=False` nothing runs, as before.
- **OCSP decision: document, do not auto-skip.** The stdlib requests are
  verified (chain and host name against `wassima`'s roots, as niquests does)
  but skip the OCSP check. Skipping the wave "when the user set
  `http_revocation_check=True` explicitly" cannot be detected reliably:
  `Config.save()` writes every default into `~/.tif1rc`, so a saved config
  carries `http_revocation_check: true` whether the user meant it or not.
  So the trade-off is documented, and the explicit `cdn_first_wave=False`
  switch restores the check on every request. niquests' check is also
  soft-fail (an attacker who blocks the responder defeats it), and the
  files are public CDN JSON. With E9 the unchecked set grows from "two
  small files and single requests" to "also the first telemetry requests,
  until niquests is warm". In the measured `driver_tel` that was the whole
  57-file wave: the warm-up HEADs (TLS + seeded OCSP) finished after the
  wave did. The docs say this.
- **Docs** (STE checker clean, 0 violations vs the baseline):
  - `docs/reference/environment-variables.mdx`: new `TIF1_CDN_FIRST_WAVE`
    with a warning on the check; `TIF1_CDN_PRECONNECT` reworded (it no
    longer imports the HTTP client).
  - `docs/api-reference/config.mdx`: `cdn_first_wave` field and env list.
  - `COMPATIBILITY.md`: an "HTTP" key-difference bullet.
  - `AGENTS.md`: the `first_wave.py` architecture notes, including the
    bridge, the knob, and why the handover trigger was not kept.
- **Tests** (offline, fake `http.client` connections, no niquests):
  - `tests/unit/test_first_wave.py` (+5):
    - The telemetry wave on the stdlib (gzip and identity bodies, typed
      decode, one kept-alive connection, niquests never imported, one warm-up
      started on the wave URLs).
    - The bridge stays open while the warm-up connects and closes after.
    - The wave on niquests once it is warm.
    - A refused (404) bridged request goes to niquests.
    - No bridge without a wave.
  - `tests/unit/test_preconnect.py` (+3):
    - `cdn_first_wave=False` warms niquests instead of starting the wave.
    - The `TIF1_CDN_FIRST_WAVE` env switch.
    - `close_session` does not wait for a session that another thread is
      building.
- Tools: `tools/perf/elis_e9_timeline.py`, `elis_e9_cold_variants.py`
  (multi-arm, returning-user caches), and `elis_e9_cold_bench.py`. That last
  one is the E3 three-arm bench with two changes: the OCSP row is primed by
  a `driver_tel` run, because a laps-only E2+ process never imports niquests
  and writes no row, and a `first` run that writes no row keeps the previous
  row.

## 4. Verdict

**SHIP the bridge** (with the `close_session` exit fix and the
`cdn_first_wave` knob). **REJECT both trigger points as stated.**

- The section's approach (1), starting niquests early at the handover (A)
  or at the first telemetry access (B), does not pay. A convoys with the
  laps build (+20-30 ms on `laps`, 0/5 on `fastest_lap_tel`, no
  `driver_tel` gain). B has no lead.
- The same goal is reached differently: the first telemetry wave starts on
  the already-open stdlib connections, and niquests imports in its shadow.
  Cold `driver_tel` for a returning user: pandas 1515 -> 1233 ms (4/5;
  variant run 1358 -> 1228, 5/5), polars 1412 -> 1301 ms (5/5). The
  first-ever process: 1410 (3/5) and 1292 (4/5).
- E2's `laps`/`fastest_lap_tel` wins are kept (unchanged code paths, within
  noise). `notebook` is flat.
- Warm runs are unchanged (identical module set; 4/8 same-cache).
- Parity is identical, warm (0/133, 0/131) and cold (0 differing frames on
  both backends, including the bridged telemetry).
- The trade-off is a wider set of requests that skip niquests' OCSP check.
  It is documented, and `cdn_first_wave=False` turns it off; see the notes.

## 5. CHANGELOG paragraph

- A cold script's first telemetry wave no longer waits for the HTTP library.
  Since the stdlib first wave (Elis E2), niquests was imported only when a
  telemetry wave started, which put its import (~90-135 ms of CPU), the
  session build and the first TLS handshakes in front of the wave's first
  request. The wave now starts on the standard-library connections the first
  wave already opened, while niquests imports and connects in a background
  thread; the import's CPU runs while the main thread waits on the network,
  and once niquests has connected the rest of the wave and every later one
  run on it as before (HTTP/2, hedging, the revocation check). Requests on
  the stdlib connections verify the certificate chain and host name but skip
  the OCSP check, and are not hedged (bounded by `cdn_hedge_max_delay`);
  anything but a `200` with JSON goes to niquests. A cold
  `laps.pick_driver("VER").telemetry` script on a machine that has used
  tif1 before takes 1233 ms instead of 1515 ms with pandas and 1301 ms
  instead of 1412 ms with polars; cold `laps` and fastest-lap scripts are
  unchanged. `cdn_first_wave=False` (`TIF1_CDN_FIRST_WAVE=false`) sends every
  request through niquests and its revocation check. An exiting script no
  longer waits for a niquests session that a background warm-up is still
  building.

## 6. Notes for the integrator

- **Security scope grows** (documented in the env-var page, the config page
  and `COMPATIBILITY.md`). E2 skipped niquests' OCSP check for two small
  files and the single requests made before niquests existed. E9 adds the
  first telemetry wave until niquests' warm-up connects (~0.3-0.5 s after
  the wave starts). That was the whole wave in the measured `driver_tel`
  scripts; a `load()` of all telemetry moves to niquests early on. Chain
  and host-name verification stay on. `cdn_first_wave=False` restores the
  check for every request. If the integrator prefers a narrower scope, the
  bridge can be capped (e.g. the first N requests) at some cost to the
  win.
- **Not hedged.** A bridged request is not hedged (TH3). It is bounded by
  `cdn_hedge_max_delay` (4 s) and then goes to niquests, which hedges. A
  stall on jsDelivr during the bridge window therefore costs up to 4 s
  instead of the hedge delay (1-4 s, EWMA-based).
- **Connections.** Each executor worker opens its own HTTP/1.1 stdlib
  connection to jsDelivr (one TLS handshake each, at most the
  executor's worker count). After the bridge closes, niquests opens its own
  pool. The idle stdlib connections are kept until the process exits (or
  until the server closes them). They are not counted in
  `http_session.get_connection_stats()`.
- **stdlib-only** (never import niquests on a cold load unless a request
  fails) measured another ~50 ms on `driver_tel` (1175 vs 1228). It would
  make niquests a fallback-only dependency for cold loads, with no HTTP/2,
  no hedging and no OCSP. That is a policy decision, so it is left out.
- **Handover trigger (A)** is rejected with numbers, and **B** is equivalent
  to E2 by construction (no lead). Do not retry either: under the GIL the
  import only hides where the main thread waits.
- The `close_session` exit fix is independent and worth keeping on its own.
  Any daemon warm-up that is still building the session at exit would
  otherwise block the exit for the rest of the niquests import (+83 ms
  measured).
