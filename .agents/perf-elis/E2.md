# E2: cold first wave on the stdlib while niquests stays unimported

## 1. Hypothesis

`import niquests` (~120-145 ms of CPU) and the first niquests connection
(DNS, TLS and the OCSP revocation check, ~350 ms from `get_session` to a warm
connection) sit on every cold process. The first wave of a cold load is two
small files (`drivers.json`, `session_laptimes.json`). Fetching them over
`http.client` + `ssl` (same trust store, User-Agent and gzip) in daemon
threads while pandas/polars imports would let the TLS handshake and TTFB
overlap the import; (a) with `import niquests` moved to a background thread,
(b) the smaller step: niquests' import only moved off the main thread.

## 2. What changed

The timeline probe (`tools/perf/elis_e2_timeline.py`) showed the starting point:

- pandas cold `laps`: the Olympia pre-connect HEADs (TLS + OCSP) finish about
  60 ms before the pandas import does, so the network is already hidden. The
  serial costs are the niquests import (118 ms on the main thread) and the
  first-wave GET wait (~50 ms).
- polars: the import is shorter, so the first GETs wait up to ~115 ms for
  the warm-up and then 45-60 ms for the body.
- stdlib probe (`elis_e2_stdlib_probe.py`): ~43 ms of CPU for setup
  (`ssl`/`http.client` import 17, `wassima` import + bundle 17, context 9),
  then both bodies arrive in ~125-155 ms of wall time.

Four variants were measured interleaved with a measurement-only switch (see §3):

- `control`: Delphi as is.
- `b`: niquests import + warm-up moved to a daemon thread, no stdlib wave.
- `a`: the stdlib wave, plus the niquests import + warm-up in a daemon thread.
- `lazy`: the stdlib wave, and niquests imports only when a request needs it.

`a` and `b` lose because of the GIL. The background import convoys with the
pandas import: the pandas import went from 430 to 657 ms in one timeline, and
`b` lost 0/7 on every workload. `lazy` is the shipped form, with one
addition: the stdlib connections stay open, and single sync requests use
them until a niquests session exists.

Files:

- `src/tif1/first_wave.py` (new, ~300 lines).
  - `start(urls, timeout)`: one daemon thread builds the TLS context, with
    `ssl.create_default_context(cadata=wassima.generate_ca_bundle())`, which
    is the store niquests verifies against (`trust_env` is off) and ALPN
    `http/1.1`. Then it GETs the first-wave URLs from the primary CDN, one
    thread per URL, with the tif1 User-Agent, `Accept: */*` and
    `Accept-Encoding: gzip, deflate`.
  - `take(url)`: hands a body over once, with a bounded wait (`WAIT_LIMIT` is
    3 s from the wave start).
  - Only a 200 with a gzip/deflate/identity body is handed over. Anything else
    returns `None` and the request goes through niquests exactly as before:
    another status (404, 403, 3xx, 5xx), a timeout, a TLS or DNS failure, a
    proxy, no `wassima`, or a body that does not parse to a JSON object. So
    the CDN fallback, the 403/404 semantics (A11, K9), retries and hedging
    (TH3) all stay in `cdn.py`/`async_fetch.py`.
  - `fetch(url)`: a single GET over the kept-alive wave connections. A stale
    idle connection is replaced once.
  - When the context cannot be built (a proxy, no `wassima`), the wave thread
    runs the old `http_session.warm_connections` instead, in the thread.
- `core._preconnect_cdn`: calls `first_wave.start(...)` instead of importing
  niquests and calling `warm_connections` on the main thread. Gating is
  unchanged: cold only, `cdn_preconnect`, offline/CI mode, `THREADS_AVAILABLE`
  (Pyodide untouched). The docstring is updated.
- `async_fetch.fetch_json_async`:
  - The niquests client and its exception tuple are resolved lazily, on the
    first request that needs them (`_niquests_session()`).
  - Before a niquests GET, a URL with a pending first-wave slot is served
    from the slot (`_first_wave_payload`, parsed in the executor). It then
    runs the same validation, raw cache write-back, circuit-breaker and
    missing-verdict bookkeeping.
- `payload_loader.NiquestsTransport.get_json`:
  - A first-wave slot is taken first.
  - While no niquests session exists (`http_session._shared_session is
    None`) and the wave's client is up, a single request uses
    `first_wave.fetch`: the fastest lap's telemetry file, or the Ergast Stats
    file.
  - Anything but a 200 JSON object falls through to niquests.
- Tests:
  - `tests/unit/test_first_wave.py` (new, 15 tests, fake `http.client`
    connections, no sockets). It covers the handover with headers and gzip,
    one handover per URL, every non-200 / undecodable / error case deferring,
    the bounded wait, the proxy path and the warm-up fallback, keep-alive
    reuse and stale-connection replacement, the async fan-out without niquests
    and the 403 re-fetch on niquests, and the sync transport before and after
    a niquests session exists.
  - `tests/unit/test_preconnect.py`: the fixture records `first_wave.start`,
    and the cold-session test also checks that `get_session` no longer
    imports niquests.
- Measurement tools (in `tools/perf/`): `elis_e2_timeline.py`,
  `elis_e2_stdlib_probe.py`, `elis_e2_cold_variants.py` (multi-arm
  interleaved cold driver), `elis_e2_cold_parity.py` (cold-session frame
  parity between two trees), `elis_e2_warm_modules.py`.

Where the time goes in the candidate's cold `laps`:

- No niquests import.
- No niquests OCSP/TLS on the critical path.
- The `laps` phase no longer waits for its GETs (115 → 35-45 ms in
  `E2_cold_variants2_pandas.json`).

For cold `fastest_lap_tel`, the telemetry file rides the stdlib keep-alive
connection: one GET of ~130 ms, against ~490 ms when niquests is imported and
connected on demand. niquests is never imported. For `driver_tel`, the bulk
telemetry wave imports niquests on demand (the same 120 ms of CPU control

TLS handshakes were hidden behind the pandas import in control; now they
are on the critical path. That costs 25 ms (calm link) to 175 ms (busy

The earlier 7-rep runs put polars `driver_tel` at +3% (1/7, no keep-alive

The link was shared with the other agents and very noisy. Control walls for

## 4. Verdict: PARTIAL

Keep it for the scripts it is made for: −33% on cold `laps` on both
backends (5/5), and −21% to −30% on cold `fastest_lap_tel` (4/5 and 5/5).
Values are identical cold and warm. But it is not a clean SHIP: cold
`driver_tel`, which starts a bulk telemetry wave, is 2-12% slower on pandas
(0/5 in the official run). niquests' OCSP check and its first TLS handshakes
used to be hidden behind the pandas import and are now on the critical path.

Hypothesis (a) as stated, and (b), are rejected with numbers. Under the GIL,
the background `import niquests` convoys with the pandas or polars import
and costs more than the serial import: `b` lost 0/7 everywhere, and `a`
was 2/7 on pandas `laps`. That is the "(b) probably impossible" the section
predicted, now measured.

The integrator can ship it as is if cold laps-only and fastest-lap scripts
matter more than a ~25-175 ms loss on scripts that start a telemetry wave.
The better course is to pair it with E3 (a persisted OCSP verdict): this
round's `driver_tel` runs with OCSP off had `lazy` at 1258 against control's
1274. Without the OCSP round trip the residual loss goes away, and the
laps/fastest-lap wins remain.

## 5. CHANGELOG paragraph

- Cold sessions fetch their first files without loading the HTTP library.
  `get_session` now fetches `drivers.json` and the session laptimes over
  Python's own `http.client` (the same certificate store, User-Agent and
  gzip as niquests) while pandas or polars imports. niquests, which took
  ~120-145 ms to import plus a TLS handshake and an OCSP check before its
  first request, is imported only when a request needs it: a telemetry
  wave. Until then, single requests (the fastest lap's telemetry, the Ergast
  classification) reuse the kept-alive stdlib connections. Anything but a
  `200` goes through niquests as before, so the CDN fallback and the
  404/403 handling are unchanged. A cold `session.laps` script takes 586 ms
  instead of 876 ms with pandas and 430 ms instead of 645 ms with polars;
  a cold `get_fastest_lap_tel()` takes 609 ms instead of 871 ms. A cold
  script that fetches a driver's whole telemetry is 25-175 ms slower,
  because niquests' OCSP check no longer overlaps the pandas import.

## 6. Notes for the integrator

- **Security trade-off.** The stdlib requests verify the certificate chain
  and the host name against the same roots as niquests
  (`wassima.generate_ca_bundle()`). They do not run niquests' OCSP
  revocation check, which is on by default (`http_revocation_check`). That
  check is soft-fail in niquests: an attacker who can block the responder
  defeats it anyway. The files are public CDN JSON. Still, a user who set
  `http_revocation_check` expecting every request to be checked may want the
  wave off. Today, `cdn_preconnect=False` turns off the whole hook (wave and
  warm-up). A follow-up could skip the stdlib path when the user explicitly
  sets `http_revocation_check=True`, or add its own knob, and document it
  in `docs/reference/environment-variables.mdx` / `COMPATIBILITY.md`. I
  did not change any docs.
- **Interaction with E3.** If E3 persists the OCSP verdict across processes,
  most of the `driver_tel` loss goes away. With OCSP off, `lazy` matched
  control on `driver_tel`: 1258 vs 1274. Measure E2+E3 together before
  deciding.
- **Untried follow-up for the bulk-wave loss.** Start the niquests import
  and warm-up in a thread once the first-wave bodies are handed over (that
  is, when the laps build starts) rather than at `get_session`. That moves
  the GIL contention from the pandas import to the laps build, which should
  hide the OCSP round trip for telemetry scripts. It costs laps-only
  scripts some of their gain, likely staying well below control.
- **Proxies.** With an `https`/`all` proxy in `urllib.request.getproxies()`,
  the wave is skipped and the thread warms niquests connections as before
  (in the thread, not on the main thread). DNS uses the system resolver,
  which is niquests' first resolver. If DNS fails, niquests fetches the
  files and keeps its DoH fallbacks.
- **HTTP/1.1** for the stdlib requests (ALPN `http/1.1`). jsDelivr serves it
  with keep-alive. Only the first-wave files and single sync requests made
  before a niquests session exists use it. The async fan-out always runs on
  niquests.
- **Hedging.** The handover returns in about 1 ms, so the first latency
  samples of jsDelivr are small. The hedge delay is clamped to
  `_HEDGE_MIN_DELAY` (1 s) either way, so no behaviour changes, but the EWMA
  starts lower than before.
- `http_session.get_connection_stats()` does not count the stdlib requests.
- `wassima` is a niquests dependency, not a direct tif1 dependency. If it is
  missing, the wave falls back to the niquests warm-up.
- The measurement-only variant switch (`.e2_variant`) is not in the
  committed tree. `tools/perf/elis_e2_cold_variants.py` documents it if
  someone wants to re-run the four-arm comparison.
