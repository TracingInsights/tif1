# E5. The second lazy driver row reads the session's other rows ahead (pandas)

Branch `perf/elis-E5`, worktree `/tmp/tif1-elis/E5`, measured against the
frozen control `/tmp/tif1-elis-control` (b5b91ed) on 2026-11-03. The box
was shared with the other Elis agents throughout (load average 8-14), so
whole-process walls carry +-30 ms of noise from `get_session` alone (which
runs before any changed code); the in-process phases and pairs won are the
signal. `git commit` was denied in this session: everything is staged and
the intended message is in `E5_COMMITS.md`.

## 1. Hypothesis

After a warm `load()` the pandas driver rows are lazy (Delphi D5): the first
driver a script touches reads its row alone (~10-15 ms), and the second
driver's first lap reads every remaining row in one batch (~45-60 ms for a
race's 19 rows, all of it waited for). If the remaining rows were read in
the background (through D9's worker-side `blobopen` readers) while the
script works on the drivers it touched, the next drivers would find their
row already read: 20-40 ms better on the two- and four-driver shapes and on
the notebook's loop over every lap (`iterlaps_tel_loop`), with a closing
flag so `Cache.close()` and the interpreter exit never wait for the reads,
memory bounded as in D9, and a one-driver script not worse.

The two- and four-driver part holds (-39 and -26..-34 ms in-process). The
loop part is falsified: reading ahead beside the lap builds made the loop
slower than the batch it replaces, at every degree of parallelism tried
(section 3.3), so a loop keeps the batch.

## 2. What changed

`src/tif1/cache.py` only (plus tests and probes):

- `SessionMemo._hydrate_for`: the first lazy driver still reads its row
  alone (and is remembered as `_lazy_first_driver`). At the second lazy
  driver, once per session (`_lazy_prefetch_started`):
  - if it is the driver right after the first in the laps' order
    (`_walks_lazy_order`: a loop over the laps or over `session.drivers`
    touches them in that order and will touch all of them), the D5 batch
    runs as before;
  - otherwise `_prefetch_others` reads the second driver's own row alone
    (`LazyDriverFrameSource.fetch`, the same lone read as the first) and
    then starts reading every other unread lazy row of the session ahead,
    in the laps' driver order (`Cache.prefetch_telemetry_frame_rows`).
  - Without the parallel path (no pyarrow lz4, one worker, Pyodide, a call
    from a pool thread), with a cache that lacks the seam or is closed, the
    D5 batch runs. Any later unread row (a second `load()`) batches as in D5.
- `Cache.prefetch_telemetry_frame_rows(year, gp, session, drivers)`: one
  index query (`driver, rowid, length(frame)`, as D9), then a
  `concurrent.futures.Future` per row in a `_PrefetchedRow` handle, and
  `_PREFETCH_LANES = 2` pool tasks (`_prefetch_lane`) that pop the handles
  from one shared deque and read them one after the other through D9's
  `_read_frame_row` (a reader slot, `blobopen`, lz4, the narrow-row
  widening in the worker). At most two rows are in flight, which also
  bounds what an exit waits for.
- `_PrefetchedRow.take()` (called from `LazyDriverFrameSource._load` at the
  row's first lap): a read no lane has started is cancelled and read on the
  caller's thread instead of waiting behind the queue; a running one is
  waited for; a cancelled one (by close/exit) is read inline. The decode
  into a `DriverFrameSource` stays at the first lap, as in D5.
- `LazyDriverFrameSource`: `_prefetched` slot, `prefetch()`,
  `cancel_prefetch()` and `fetch()`; `hydrated` and `decodable` count a
  row read ahead (so a bulk reader does not re-read it and D8's merged
  frame takes it instead of a throwaway decode).
- Lifecycle:
  - `Cache._prefetches` (under `_reader_lock`) holds the futures;
    `_cancel_prefetches()` runs first in `_close_readers()`, so `close()`,
    `__del__` and the atexit close cancel every queued read (the one in
    flight returns its reader, which D9 then closes).
  - Interpreter exit: `concurrent.futures` joins the pool from a
    `threading` exit hook, and a worker drains its whole queue before it
    exits, so queued reads would hold the exit. `_track_prefetching_cache`
    registers `_cancel_all_frame_prefetches` with
    `threading._register_atexit` (falls back to `atexit`) after the pool
    exists; those hooks run in reverse order, so it cancels the queued
    reads before the join and only the rows in flight finish (probe:
    eight 0.4 s reads on two lanes, exit join 0.35 s with the hook,
    1.55 s without).
  - `SessionMemo.clear()` cancels the reads its sources still hold.
  - Fork: a handle records the pid that created it. In a forked child
    `take()` reads inline without touching the future (a read running at
    the fork would never complete there, and its lock may have been held),
    and `_cancel_prefetches` drops the parent's futures untouched.
- `Cache.lazy_telemetry_frame_sources` returns the stand-ins in the order
  of the requested drivers (the laps' order) instead of the SQL index order
  (alphabetical). The reads ahead and `_walks_lazy_order` use that order;
  nothing else iterates the memo's sources in a user-visible way.

Tests: `tests/unit/test_elis_e5_prefetch.py` (11, offline, five-driver
session):
- the sources follow the laps' order;
- one driver never starts the reads ahead;
- the second driver starts them once, in laps order, and every other row
  comes from them (no further row read);
- an in-order walk (`iterlaps`) batches instead;
- `fetch_all_laps_telemetry()` takes the rows read ahead;
- a row turned bad falls through to the ordinary miss;
- a row no lane started is read by the caller;
- a cache closed mid-prefetch cancels the queued reads and leaks no reader
  (every opened reader is closed);
- the forked-child path;
- the exit hook cancels the queued reads;
- a subprocess test that the interpreter exit never waits for them.

Probes and harness (`tools/perf/`):
- `elis_e5_warm_bench.py`: a copy of `delphi_warm_bench.py` plus
  `load_then_1_driver`, `load_then_2_drivers` and `load_then_4_drivers`
  (`load()`, then the fastest lap's `get_car_data()` of the first N of
  VER, LEC, NOR, PIA).
- `elis_e5_warm_ab.py`: `delphi_warm_ab.py` pointed at that bench.
- `elis_e5_lanes.py`: interleaved control vs lane counts, loop and N-driver
  shapes.
- `elis_e5_timeline.py`: per-row read windows against the loop.
- `elis_e5_row_phases.py`: lz4 vs widening per row.
- `elis_e5_first_access.py`, `elis_e5_probe.py`: first-access breakdown and

### 3.3 Why the loop keeps the batch (probes, fresh process per run, interleaved, medians)

First design: the reads ahead started at the *first* driver, one pool task
per row (8 at once). Timeline of one loop (`elis_e5_timeline.py`):
- each row took 20-47 ms in a worker against ~5 ms alone, and the 19 rows
  took 88 ms;
- the loop seldom waited for a row (2 and 6 ms, then never), yet each
  driver's laps took ~5 ms instead of ~3 beside the reads.

Per row (`elis_e5_row_phases.py`, serial), lz4 into the fresh 6 MB buffer
is 3.2 ms (57.7 ms for the 20 rows) and the narrow-row widening 0.8 ms
(6 numpy ops). The cost is the page faults of the fresh buffers, as D9
found (parallel read+lz4 barely beats serial). Faulting threads of one
process contend with each other and with the main thread's own work, so
reading ahead beside the lap builds costs about what it hides.

`elis_e5_lanes.py`, lap loop after `load()` (ms, 8 reps):

| trigger | control | 1 lane | 2 lanes | 4 lanes | 8 lanes |
|---|---|---|---|---|---|
| first driver | 151.9 | 192.0 | 165.9 | 155.8 | 165.4 |
| second driver | 141.5 | | 161.7 | 156.3 | |
| first driver, `setswitchinterval(0.0005)` (mechanism check, 6 reps) | 153.2 | | 149.5 | 165.4 | |
| second driver + in-order batch (final rule), 10 reps | 178.1 | | 182.0 | | |

GIL hand-off latency is not the mechanism (a 0.5 ms switch interval
changes nothing beyond noise). In the final rule the loop runs the
control's code.

`elis_e5_lanes.py`, N-driver shapes (access ms, 8 reps):

| trigger | shape | control | 2 lanes | 4 lanes |
|---|---|---|---|---|
| first driver | 1 driver | 25.4 (wall 492) | 26.1 (wall 515) | 28.1 (wall 518) |
| first driver | 2 drivers | 73.1 | 40.1 | 40.5 |
| first driver | 4 drivers | 75.2 | 42.6 | 49.3 |
| second driver | 2 drivers | 72.7 | 35.4 | 34.7 |
| second driver | 4 drivers | 75.9 | 47.9 | 50.9 |

Starting at the first driver cost the one-driver script ~20 ms of wall
(the reads in flight at exit, and the rows read for nobody). Starting at
the second costs it nothing and keeps the gain. Two lanes beat four on the
four-driver shape and hold half the rows in flight at exit. Hence the
final trigger (the second driver, unless it walks the laps' order) and
`_PREFETCH_LANES = 2`.

## 4. Verdict: SHIP (PARTIAL against the hypothesis)

What to keep: the whole change. Results:
- A script that touches a second driver out of the laps' order after
  `load()` no longer pays the 19-row batch: two drivers' fastest-lap car
  data 71-78 -> 32-33 ms in-process, wall -6.8% / -12.2% (7/8, 8/8).
- Four drivers: 78-89 -> 52-74 ms, wall -7.5% / -5.9% (8/8, 6/8).
- Every other measured workload runs the control's code and is neutral,
  the one-driver script included.
- Parity is exact.

The hypothesis's notebook claim is rejected with numbers: reading ahead
beside a loop over every lap is 4-50 ms slower than the batch at every
lane count (3.3), because the cost is page faults that contend with the
lap builds, not waiting. So an in-order walk keeps the D5 batch and the
notebook is unchanged.

## 5. CHANGELOG paragraph

- After a warm pandas `Session.load()`, the second driver a script touches
  no longer reads every other driver's frame-tier row before its first lap
  (19 rows, ~45-60 ms for a 2025 race, all of it waited for). It reads its
  own row alone, like the first driver, and the remaining rows are read
  ahead in the decompression pool, in the laps' driver order, on two
  serial lanes, while the script works on the drivers it touched. A row
  no lane has started yet is read by the caller instead of waiting behind
  the queue. `load()` then two drivers' fastest-lap car data: 71-78 -> 32
  ms (process 572-598 -> 525-533 ms); four drivers: 78-89 -> 52-74 ms.
- A loop over the laps or the drivers (the second driver is the one after
  the first in the laps' order) keeps the single batch, which is faster
  there than reading ahead beside the lap builds. Scripts that touch one
  driver read one row, as before.
- The reads still queued are cancelled when the cache closes and before
  the interpreter joins the pool at exit, so the exit waits for at most
  the two rows in flight.

## 6. Notes for the integrator

- Mechanism behind the loop result: a driver row costs ~5 ms alone, mostly
  page faults of its fresh 6 MB output buffer (lz4 3.2 ms, widening
  0.8 ms, read ~1 ms). Faulting threads of one process contend with each
  other and with the main thread: eight rows at once took 20-47 ms each,
  and the lap builds beside them slowed from ~3 to ~5 ms per driver. E4
  (decompress into huge-page or pre-faulted buffers) attacks exactly this
  cost. If E4 ships, re-measure the loop with `_walks_lazy_order` disabled:
  reading ahead may then win there too.
- `_walks_lazy_order` is a heuristic: second driver == the driver after
  the first in the laps' order. A script that looks at the top two
  finishers in classification order gets the batch, i.e. the control's
  behaviour: no regression, no gain. A loop starting mid-order is still
  detected; a loop in another order (alphabetical, by team) reads ahead
  and pays the loop cost of 3.3 (~+15 ms on a race).
- `threading._register_atexit` is private API, the hook
  `concurrent.futures.thread` itself uses. A `getattr` fallback to
  `atexit` keeps it importable if it ever goes (then the exit would wait
  for the queued reads again, at most ~50 ms for a race). The subprocess
  test pins the behaviour.
- `_prefetch_lane` resolves its futures by hand
  (`set_running_or_notify_cancel` / `set_result` / `set_exception`), as
  `concurrent.futures`' own work items do, so `cancel()` keeps its
  meaning: a lane skips a row the caller took over.
- Memory: rows read ahead are held decompressed (~6.2 MB per race driver)
  until their first lap decodes them, the same buffers the D5 batch held.
  A script that touches two drivers and stops holds up to 18 of them until
  the session goes away (reading ahead does not know the script stopped).
- `LazyDriverFrameSource.decodable` is now True for a row read ahead, so
  D8's merged `Laps.telemetry` of such a driver takes the row (waiting for
  it, or reading it inline if no lane started it) and gathers from the held
  source, instead of the throwaway decode it used for an unread lazy row.
- The reads ahead use D9's reader slots (at most `_reader_cap`, 4). The
  two lanes take two; a caller's inline read takes a third.
- Pyodide / one worker: `_can_decompress_in_parallel` is False, so the
  D5 batch runs and nothing is read ahead.
- Artefacts in `.agents/perf-elis/`: `E5_ab_load_then_final.json`,
  `E5_ab_load_then.json`, `E5_ab_pandas.json`, `E5_ab_same_cache.json`,
  `E5_ab_notebook_same_cache.json`. Parity digests in
  `/tmp/E5_parity_pandas.json` and `/tmp/E5_parity_polars.json`.
