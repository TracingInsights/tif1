# E10: pipelined lazy waves (E1 follow-up): result

Branch `perf/elis-E10`. The control is the frozen E1 tree (`/tmp/tif1-elis-control-e10/src`),
so every A/B below isolates this follow-up. The eager-vs-lazy rows run the control
tree's eager load against this tree's lazy load. Verdict: **SHIP**. Recommendation
on the default: **flip `telemetry=True` to lazy**. The performance case is now
complete. Two semantic points are left to the integrator (section 6).

`git commit` was denied in this sandbox. Everything is staged, and the intended
commits (E1 base, then E10) are in `.agents/perf-elis/E10_COMMITS.md`.

## 1. Hypothesis

E1's `load(telemetry="lazy")` fetches a driver's laps in one wave on first access.
A cold script that touches every lap pays 20 sequential waves. Each wave has its own
ramp-up and tail, so the script is ~6.5% slower than the eager 1128-file batch, and
that worst case kept the default eager. The idea: run every lazy request through one
prioritised stream. The laps a caller waits for go first. The free slots (a wave's
tail, the time the script spends on frames) fetch the next pending driver
(pipelining) or every pending driver (continuation). A foreground wave joins or
promotes the background requests instead of fetching twice. The lazy mode then
loses its worst case without slowing a script that touches four drivers.

## 2. What changed

- `src/tif1/core_utils/telemetry_stream.py` (new, pandas/polars-free):
  `PriorityFetchStream`.
  - One asyncio loop on a daemon thread, started on demand. It exits when idle, so
    it never pins a `Session`.
  - Keyed requests in two queues. Foreground keys always go first; background keys
    start only while no foreground key is queued, at most
    `background_concurrent` of them. The total cap is `max_concurrent_requests`
    (22).
  - A key is fetched once whatever its priority. `request()` joins a key in flight,
    promotes a queued background key, and serves a done key from its result.
    `prefetch()` replaces the background queue; stale keys are dropped.
  - `close()` drops the queues and returns the futures still in flight.
    `close(cancel=True)` also cancels them.
  - Every future resolves: a failure is logged and resolves to `None`.
  - A `threading._register_atexit` hook (it runs before `concurrent.futures` joins
    its workers) closes live streams with `cancel=True`. Without it, a background
    request in flight at exit hit the shut-down pool and walked the CDN retry loop:
    dozens of warnings, 1 s backoff sleeps, a tripped circuit breaker. Measured;
    see section 6.
- `src/tif1/core.py`:
  - `_fetch_lazy_telemetry_wave` sends cold waves (not `_lazy_telemetry_from_cache()`,
    threads available, `lazy_telemetry_lookahead != 0`) through
    `_stream_telemetry_payloads`. That method does E1's memo/SQLite plan, then
    `stream.request()` for the misses, then queues the lookahead, waits on the
    futures, memoizes the payloads, and flushes the collected payload-tier writes.
    Frames are built by the same `_frames_from_payloads` +
    `_schedule_frame_materialization` as before.
  - The stream's per-request fetch is the module-global `fetch_multiple_async([req],
    ..., telemetry_writes=writes)`, with the eager batch's options. Tests still
    serve it from memory.
  - `_queue_lazy_lookahead`: the **sequential rule**. Each wave records the next
    pending driver in laps-row order (`_lazy_lookahead_next`). Only a wave that
    includes that predicted driver queues the next `lazy_telemetry_lookahead`
    drivers as background work. Any other wave clears the background queue. An
    unconditional lookahead cost a cold four-driver notebook +24% (measured below),
    because background requests share the link with the foreground wave they trail.
  - `_close_lazy_telemetry_stream`, run by both `fetch_all_laps_telemetry` variants
    and by a new lazy `load()`. It drops the queues, waits for the requests in
    flight, memoizes every payload the stream holds, and flushes its writes. So the
    eager batch fetches only what is still missing.
  - `_in_lap_order`: `fetch_all_laps_telemetry` (sync and async) returns its map in
    laps-row order whenever newly built frames join memoized ones. E1 did this only
    after a network batch. With the stream, all remaining payloads can already be
    memoized, and the key order then differed (found by the lookahead −1 parity
    run, fixed, and covered by a unit test).
- `src/tif1/async_fetch.py`: `fetch_multiple_async(..., telemetry_writes=list)`
  collects the payload-tier writes into a caller-owned list without flushing.
  `schedule_telemetry_writes(entries)` is the flush, factored out of the existing
  deferred-write path, unchanged.
- `src/tif1/cdn.py`: the hedged primary/backup race (`_hedged_primary_async`) now
  cancels its child tasks when it is itself cancelled. The waits moved unchanged
  into `_hedge_wait`. Before, `asyncio.wait` left them running ("Task exception was
  never retrieved" at exit).
- `src/tif1/config.py`: `lazy_telemetry_lookahead` (default 1; −1 = every pending
  driver; 0 = E1's per-driver `fetch_multiple_async` waves, no stream) and
  `lazy_telemetry_background_requests` (default 22). Env vars
  `TIF1_LAZY_TELEMETRY_LOOKAHEAD`, `TIF1_LAZY_TELEMETRY_BACKGROUND_REQUESTS`.
- Tests:
  - `tests/unit/test_lazy_telemetry_stream.py` (new, 27 test items, offline). Stream
    mechanics: priority, fetch-once, promotion, queue replacement, background cap,
    zero background slots, failure → `None`, close, cancel. Session side, both
    backends:
    - a sequential wave queues the next driver; first and unpredicted waves queue
      nothing;
    - lazy frames equal eager;
    - `fetch_all` takes the stream's payloads (nothing fetched twice) and keeps
      laps-row order without a network batch;
    - lookahead −1; lookahead 0 keeps one batch per wave;
    - cached sessions skip the stream;
    - writes reach the background writer;
    - `telemetry_writes` collection.
  - `tests/unit/test_lazy_telemetry_load.py`: E1's fixture pins
    `lazy_telemetry_lookahead=0`. Those tests count one `fetch_multiple_async` batch
    per wave; the stream issues one call per request. The assertions are unchanged.

### Design probes (pandas, cold, E1 control vs variants of this tree)

| variant | workload | E1 | variant | pairs | note |
|---|---|---|---|---|---|
| unconditional lookahead 1 (2 reps) | iterlaps_all_lazy | 11727 | 8486 | 2/2 | |
| unconditional lookahead 1 (2 reps) | notebook_lazy | 3214 | **3977 (+24%)** | 0/2 | **foreground wave with a background wave in its tail: VER 578/615 → 923/843 ms, PIA 478/512 → 754/872** |
| stream, 0 background slots (3 reps) | notebook_lazy | 3109 | 3304 | 0/3 | waves +8/+30/+10/+41 ms; rest is `get_session` noise |
| sequential rule, lookahead 1 (3 reps) | notebook / iterlaps | 3163 / 11322 | 3240 / 8998 | 0/3 / 3/3 | VER 571 → 604, others equal |
| sequential rule, lookahead −1 (3 reps) | iterlaps / notebook | 11311 / 3170 | 9350 / 3218 | 3/3 / 1/3 | continuation is not better than lookahead 1 |

The hypothesis asked for the foreground wave's latency with and without a background
wave in flight. The unconditional probe answers it: a background driver filling the
tail slots of a 57-file wave makes that wave 35-60% slower. The link is shared, so
the trailing foreground requests split the bandwidth. That is why the shipped rule
pipelines only sequential access, where the background driver is the next one the
script reads.

Lookahead 1 and −1 tie on the whole-session loop. With lookahead 1 the pipe never
drains, so continuation buys nothing and only adds traffic the script may not use.
The default is 1.

Fake-network wave overhead (`elis_e10_stream_overhead.py`, 57 requests, 50 ms each,
22 in flight, median of 15): ideal 150.0, E1's gather 152.8, stream 153.6 ms.

## 4. Verdict

**SHIP.** A cold lazy session that reads every lap drops from 11.4 s to 8.9 s
(pandas, 4/5) and from 10.3 s to 8.5 s (polars, 5/5). That is now 10-14% *faster*
than the eager load (4/5, 5/5), where E1 was 6.5% slower. The four-driver notebook
is unchanged against E1 and stays at −70% against eager (5/5 on both backends).
Frames, `fetch_all` maps and cache contents are identical to the eager load in every
parity mode. Warm and eager paths do not change.

## 5. CHANGELOG

- A cold `load(telemetry="lazy")` session runs its telemetry fetches through one
  background stream (`PriorityFetchStream`). The laps the code waits for go first,
  and each lap is fetched once. When the code reads the drivers in laps-row order,
  the next driver's laps fill the free request slots while the current driver's
  frames are built (`lazy_telemetry_lookahead`, default 1; −1 for every pending
  driver; 0 for one wave per driver).
  - A cold loop over every lap of the 2025 Bahrain race after a lazy load drops
    from 11.4 s to 8.9 s on pandas and from 10.3 s to 8.5 s on polars. That is now
    10-14% faster than `load(telemetry=True)` followed by the same loop, where it
    was 6.5% slower.
  - A four-driver notebook in another order makes no background requests and keeps
    its 3.0 s (eager: 10.0 s).
  - `fetch_all_laps_telemetry()` takes the payloads the stream already holds.
  - Interpreter exit cancels the stream's requests in flight. A cancelled hedged
    CDN request now also cancels its backup request.

## 6. Notes for the integrator

- **Default flip: recommended on the numbers.** No cold workload I measured is
  slower lazy than eager, on either backend:
  - every lap: −10% / −14%;
  - four drivers: −70%;
  - `fetch_all` after a lazy load: the eager batch;
  - laps only: `load()` 0.13 s instead of 8.5 s;
  - warm pandas: identical;
  - warm polars `load_only`: faster (E1).

  What remains is semantics, and it is the integrator's decision:
  1. A telemetry network failure surfaces at the first access of the lap, not in
     `load()`. The lap gets an empty `Telemetry`, as for any per-lap failure.
  2. `load()` no longer fills the cache before a script goes offline.
  3. fastf1's `load(telemetry=True)` is eager. Results and frames are identical
     either way.

  The flip is one line: `"load_telemetry_lazy": True` in `config.py`. The docs then
  need these changes:
  - `docs/concepts/sessions.mdx` `load()` parameters: "`telemetry` (bool or
    `"lazy"`): If True, make the telemetry of all laps available. A lap's driver is
    fetched on the first access (see Lazy telemetry). Set the config key
    `load_telemetry_lazy` to `False` to fetch all the telemetry in `load()`."
  - The Lazy telemetry note: swap the last two sentences for "Set
    `load_telemetry_lazy` to `False` before work without a network."
  - `docs/api-reference/core.mdx` `telemetry`: the same wording.
  - `docs/migration-from-fastf1.mdx`, section 1 Lazy Loading: add "In tif1,
    `session.load()` does not fetch telemetry. A driver's telemetry is fetched on
    the first access of one of its laps. fastf1 fetches all of it in `load()`. Set
    `load_telemetry_lazy` to `False` for fastf1's behaviour."
  - `config.mdx` / `environment-variables.mdx`: default `True`.
  - Also check `exceptions.mdx:1709` and `:2739` and `jupyter.mdx:381`, which say
    that `telemetry=True` fetches all lap telemetry.

  With the default flipped, the eager `notebook` / `all_tel` workloads would need
  `TIF1_LOAD_TELEMETRY_LAZY=false` to stay comparable.
- **Background failures.** A failed background request resolves to `None`.
  - When the script later reads that driver, its foreground request finds the done
    key, gets `None`, and the lap takes the per-lap path, which records the failure
    (`_record_telemetry_failure`) as an eager load's missing lap does.
  - The stream also logs a warning when its fetch raises. `fetch_multiple_async`
    itself logs non-404 failures, as in the eager batch.
  - Nothing is raised on the background thread.
- **Exit.** Background requests in flight at exit are cancelled by a
  `threading._register_atexit` hook. That is a private CPython API, used through
  `getattr` with an `atexit` fallback. It is the only hook that runs before
  `concurrent.futures` joins its pool. Without the hook, a script that ended mid-
  lookahead printed ~60 CDN failure warnings and tripped the circuit breaker on the
  dying interpreter. The GETs already running in pool threads still finish, so exit
  can wait up to one request (~0.2-0.5 s) when a script ends during a lookahead
  wave.
- **Writes.** Stream payload writes are collected per stream and handed to the
  background writer after each foreground wave and whenever the stream idles.
  Payloads fetched in the background for a driver the script never reads are still
  written to the payload tier (no frame-tier row), unless the process exits first.
  In that case they are dropped, which is harmless.
- **Lazy tail latency** (E1 too, not E10-specific). In a lazy run, one slow CDN
  response blocks the script at that driver's wave. The first pandas lazy-vs-eager
  notebook run caught a network incident: a 13.9 s wave, while the eager arm lost
  4 s in its load. The rerun was 5/5. The eager batch hides a straggler behind the
  other 1100 requests; a 57-file wave cannot.
- **Sequential rule false positives.** A notebook that compares the top four
  finishers reads them in laps-row order (classification order). From its second
  driver on, the next one is prefetched. That helps, and only the driver after the
  last one is wasted background traffic.
- **Thread model.** The stream thread exits when idle, and a new one starts on the
  next request. Each start pays `asyncio.run` setup (<1 ms). The fetches still run
  on the shared `async_fetch` executor and niquests session, as before.
