● Yes, but I'd widen the version range rather than require 2.0. Polars 2.0.0
  came out on PyPI on 2026-10-06, and tif1 runs on it with no code changes.

  Your pin is currently polars>=1.44.1,<2. Since polars is a required
  dependency, that cap is the real problem: anyone who already has polars 2 in
  their environment either can't install tif1 or gets downgraded. I'd change it
  to "polars>=1.44.1,<3", so both 1.x and 2.x users can install it, and lock to
  2.0.0 for development and CI.

  I tested this in a throwaway worktree with polars 2.0.0, and the worktree has
  since been removed:
  - Tests: all 1389 unit and property tests pass, all 13 integration tests pass
    against the live CDN, and there were no polars deprecation warnings.
  - Real session (polars backend): I loaded the 2025 Bahrain GP race laps,
    weather, messages and fastest laps without telemetry. Shapes and dtypes were
    identical on both versions: laps 1128×45, race control Time stays
    Datetime[ns].
  - Type check: no new polars-related errors. The diagnostics that differ come
    from other packages in the test environment.
  - Speed: no measurable difference. Both versions take about 3 ms once cached,
    and my one 8.5 ms vs 3.3 ms reading didn't hold up on repeat runs. Don't
    expect a speed gain from this alone.

  Why it's safe: I checked the official upgrade guide against how tif1 uses
  polars, and the big breaking changes miss us:
  - Streaming as the default engine: the guide says this can change row order in
    group_by and joins. tif1 never uses lazy frames or collect(), and the one
    group_by (core.py:3061) sorts afterwards.
  - Text to date casts: casting text straight to a date now raises an error. The
    race-control parsing (core.py:1110) already converts with
    str.to_datetime(...) first, so it's fine.
  - concat: only the change to how="horizontal" breaks code, and tif1 uses only
    "vertical" and "vertical_relaxed".
  - Removed or renamed APIs: none of the ones tif1 uses are affected (melt,
    join_nulls, how="outer", cut/qcut and so on). The two how="outer" joins in
    models.py are on pandas frames.

  One caveat: 2.0.0 is a week old. With the wider range, users choose their own
  version, so you don't have to wait for a 2.0.1. The only thing that changes is
  which version your own CI runs.

  Weather and race-control hardening (polars backend)

  The root cause was that polars raises its own error types for bad data, which
  slipped past except clauses written for pandas' ValueError/TypeError. So where
  pandas degrades gracefully, polars crashed session.load(). Three layers now
  mirror the pandas branch exactly:

  - Sentinels handled before the frame is built. "None" strings in weather and
    race-control payloads are replaced by nulls at construction, the way the
    laps path already did it (helpers.py now shares one
    _coerce_null_like_payload helper). This matters because a String→Boolean
    cast is unsupported in polars even with strict=False, so a Rainfall column
    polluted by one sentinel could never be recovered after the fact.
  - Non-strict weather casts, matching pandas' to_numeric(errors="coerce");
    WindDirection is rounded rather than truncated, matching pandas
    (core.py:1290).
  - Polars errors degrade like pandas errors: weather and race control now
    return an empty frame with a warning instead of aborting. The error tuple
    only includes polars' base exception when polars is already loaded, so
    pandas sessions never pay the ~260 ms polars import (core.py:112).

  Verified output-neutral: all 24 frames (laps, weather, race control, fastest
  laps on polars; weather and race control on pandas; four sessions) are
  byte-identical before and after. Eight new tests cover this; the five core.py
  tests fail without the fix and pass with it.

  Docs examples that were broken on every polars version (backends.mdx,
  data-export.mdx)

  - laps[mask]: polars treats a boolean mask as a column selector. It raises, or
    when the mask length happens to equal the column count, silently returns
    the wrong columns. Both places now use filter, and the "works with both
    backends" claim is corrected with a wrapper keyed on session.lib.
  - .dt.total_seconds() on LapTime: the polars backend stores it as Float64
    seconds, so the example now builds a Duration from it.
  - map_elements inside agg calls the function per value, not per group.
    Replaced with an expression, plus map_batches(returns_scalar=True) for a
    genuine Python function. Both agree across all 20 drivers on real data.
  - Horizontal concat of laps and telemetry failed on the duplicate Time column.
    Both tabs now concat a same-height rank frame.
  - to_parquet is pandas-only; labelled as such, with a note that it needs
    pyarrow (a dev-only dependency) and a link to the polars write_parquet
    section.

      474 +### Missing values and sentinels                              
      475 +                                                              
      476 +The upstream payloads encode a missing value in two ways: JSON
          + `null`, and the literal string `"None"`. The string form appe
          +ars in 2026 lap data and in the `Lap` column of race control m
          +essages for every non-race session. tif1 normalizes both forms
          + on both backends before it applies the dtype contract:       
      477 +                                                              
      478 +- Laps: the strings `"None"`, `"none"`, `"null"`, `"nan"`, and
          + `""` become a missing value. The replacement runs only when a
          + payload contains one of these tokens.                        
      479 +- Weather and race control messages: the same tokens become a 
          +missing value. On polars the replacement runs before the frame
          + is built, so a column with one sentinel keeps its `Boolean`, 
          +`Float64`, or `Int64` type instead of becoming `String`. On pa
          +ndas the replacement runs before the `astype` and `to_numeric`
          + passes.                                                      
      480 +- Casts are non-strict on both backends. A value that cannot b
          +e parsed becomes a missing value; it does not raise.          
      481 +                                                              
      482 +The representation of a missing value follows the backend: `nu
          +ll` on polars; `NaT` for time columns, `NaN` for floats, `<NA>

          +mns on pandas. One difference is intentional: the race control
          + `Lap` column is a plain `int64` on pandas (FastF1 convention)
          +, so a message without a lap has `Lap == 0` there and `null` o
          +n polars.
